# L4 Hook 接线

## 1. 为什么事件接线需要独立设计

工程流程有自己的责任、产物、状态与完成条件，Claude Code 则提供工具、子代理、会话和事件。Hook 把两者接在自然发生的工作边界上：开始时交付必要上下文，结束时接收实际产物，Main 正常保存时衔接本人的专业消费者。它使流程不依赖作者记住一串额外登记命令。

这条连接也容易产生误解：输出了文字，不等于模型收到；进程返回失败，不等于平台拒绝动作；子代理停止，不等于交付已合格；父会话收到 Agent 返回，本身也不证明原答卷已收。真实完成返回若准确关联原责任，系统可按 §5.3 复用原消费者兜底，普通 Main 阅读不代填或抢收。因此输入、责任路由、输出对象、退出码与失败处理需要统一设计，不能让每个 handler 自行解释。

本篇定义平台总线与工程消费者之间的接线契约。[事件选点](L4-hook-anchor-catalog.md)解释为什么选择某个事件，[子代理工程衔接](L4-agent-dispatch-governance.md)定义任务与责任，[阶段答卷](L4-stage-form.md)定义专业接收，[运行控制面](L4-runtime-control-plane.md)定义事实、证据效力与推进条件，[状态机核心](L4-state-transition-core.md)定义合法事务。Hook 负责把已有能力准确接入，不再维护执行调度、启动审批、存活监测或第二份工程流程。

接线的机制取舍与整改收口由[工作流边界与收敛设计](L4-workflow-convergence.md)约束。减少作者操作须同时核运行和维护成本；先删除不必要依赖、合并重复生产、复用原能力，再修必要断点。以下接收、反馈和恢复合同保留其实际支持范围，不因一个故障扩展成通用协调器，也不以新增普通工具门禁或作者手续补偿接线问题。

## 2. 注册、命令与执行预算

### 2.1 使用同一个真实入口

模板的 [settings.json](../../settings.json)安装到目标项目的 `.claude/settings.json`。当前十类事件均调用同一二进制和 CLI 入口，例如：

```sh
"$CLAUDE_PROJECT_DIR"/.claude/bin/loop-harness hook --event SubagentStop --root "$CLAUDE_PROJECT_DIR"
```

引号必须保留完整路径。事件名同时来自注册参数和平台输入，入口核对两者一致；配置写成一个事件、payload 却说另一个事件时应报错，不静默转成另一条业务路径。stdout 留给平台协议，诊断写 stderr，不在命令前后拼接调试输出。

| 注册类别 | 当前注册范围 | 现有用途与三阶段目标 |
| --- | --- | --- |
| `SessionStart` | 无 matcher 限制 | Main 恢复当前责任与必要入口准备 |
| `PreToolUse` | `*` | 进度与当前材料提示；S7／S8／S9 监听就绪原答卷；不按工具身份或 scope 决定许可 |
| `PostToolUse` | `*` | Main 本人保存、相关材料变化、适用的父返回和诊断观察；包括自定义工具，消费者仍核对成功状态和当前责任 |
| `SubagentStart`、`SubagentStop` | 无角色 matcher 限制 | 新原生子代理的上下文与专业交付衔接 |
| `Stop`、`TeammateIdle` | 无 matcher 限制 | 原收尾与兼容责任判断，按实际分支反馈 |
| `PostToolUseFailure`、`ConfigChange` | `*` | 适用路径的原生失败与配置变化审计 |
| `PreCompact` | 无 matcher 限制 | 既有诊断缓冲维护；静默，不创建阶段恢复事实 |

PostToolUse 使用 `*` matcher 监听全部工具，包括自定义工具。列入监听只表示该工具成功后可以进入监听器，不表示每次都提交答卷。特别是 Read、Glob、Grep 服务有限观察和原接续，不能成为新 Worker 的第三个必经接收点。

### 2.2 注册存在，不代表所有分支都执行

当前注册均为同步 command Hook；PostToolUse 平台超时为 30 秒，其他事件为 10 秒，未配置 `async` 或 `onFailure`。较长上限用于 [S4 接收及 S5 当次准备](L4-agent-guidance.md#s4-s5-guidance)的有限内部预算，普通事件仍受原 6/8 秒工作/进程预算约束，不是每次工具调用的等待目标。`worktree.baseRef: head` 配合原生工作区使用，未注册 WorktreeCreate 来替换默认创建。PermissionRequest、TaskCompleted 等也不属于当前注册集；平台有某项能力，不构成本项目必须启用它的理由。

同一事件可能被原生专用接线提前处理，也可能进入 Main 的投影、专业消费者或旧记录恢复。注册表不能被解释为“每个事件都跑整个 Controller”。相同角色并发、前后台原生执行和恢复事件都要保留这种分支关系。

事件、matcher、命令和超时的逐项选择归[事件选点](L4-hook-anchor-catalog.md)。注册变化须同步安装配置、[模板检查](../../internal/migration/templates.go)、[策略中的事件声明](../../docs/control/hook-policy.json)与相应测试；事件名对账只是第一层，不能代替实际触发和输出验证。

## 3. 输入契约：观察平台事实，不制造平台事实

### 3.1 保留实际消费字段的原义

平台 JSON 从 stdin 进入 [policy.Input](../../internal/policy/engine.go)。字段可能随事件不同而缺失，应按照当前事件解释，不把所有字段都设成各阶段共同必填。

| 字段组 | 本项目消费方式 | 需要守住的区别 |
| --- | --- | --- |
| `hook_event_name`、`session_id`、`cwd` | 确认事件、会话及实际工作环境 | 会话身份与工程责任、控制根不同 |
| `agent_id`、`agent_type` | 观察原生执行者及类型 | 类型不等于任务，平台 actor 不强求等于工程 owner |
| `tool_name`、`tool_use_id`、`tool_input`、`tool_response` | 识别真实保存、相关返回和工具观察 | 工具成功、异步启动与专业接收不同 |
| `transcript_path`、`agent_transcript_path`、`last_assistant_message` | 在适用返回中寻找准确任务与产物引用 | 父会话转录、子会话转录与最后收尾文字不同 |
| `stop_hook_active` | 避免 Stop 纠正反复阻止同一执行结束 | 它不是履职完成或业务豁免 |
| `teammate_name`、`team_name` | 原团队事件及已登记记录的兼容识别 | 不为新原生任务预建 Team 或平台身份 |
| `file_path`、`error`、`source` | 适用的原生观察和审计 | 缺失时不补造错误、测试或来源事实 |

Input 是有类型的消费结构，不是自动保存所有未知 JSON 字段的原始转发器。新增官方字段要检查是否真的被保存、传入需要它的消费者；不能宣称平台任意新增字段已无损进入全部策略。内部的 `facts`、`runtime_context`、`target_id` 等兼容载体，也不能当作平台已经证明完成的字段。

平台集成测试应使用真实事件形状；库级测试可以构造内部事实，但应明确它验证的是领域逻辑。不能把通过测试私有字段注入的事实称为真实平台执行、阅读或接收证据。

### 3.2 任务内容和转录各有用途

Main 在真实原生任务中交付原 brief／view、本人原答卷路径、必要材料与专业目标。Start 提供短提示，不按角色认领答案。已有当前责任关联足以定位时直接复用；确需转录时有界读取真实 user 任务，忽略 tool_result 中的伪引用。`last_assistant_message` 可能仅为收尾文字，不能当作完整报告或新增必交引用。

S7／S8／S9 用已有派发和原责任关联确定本人原卷，不要求作者重新返回路径、声明 actor 或提交来源证明。定位不是专业真实性认证；准确原卷路径仅标识已有责任，不证明产品、证据、实际独立性或 worktree 所有权。未知、多义或关联损坏交 Main／系统，不按角色、唯一候选、目录尾巴、最近文件或模糊文本猜选。

已发行 S9 brief 的完整绝对、控制根相对及 `./` 控制根相对引用继续可表达同一责任，相对引用不是 Worker cwd 的读文件路径。匹配保留完整 token 边界，不做 basename、任意 `../`、变量或 URL 推导；真实任务中的句末标点不应使准确引用失效，路径后缀与邻接文件名不能误命中。同责任等价引用去重；已有派发关系明确属于本次执行的多项责任分别处理，仅文本共现而无法确定当前责任时保留歧义并交 Main／系统。既有绝对最终消息回退仅服务原适用记录，不把重新返回引用变成新作者步骤。

同次事件的责任定位、接收与 Main 反馈共享已有选择，转录读取结果在请求内复用，不由多个适配器重复扫描。Start、Pre、成功 Post 与 Stop 使用相同当前责任语义。S0～S6、S10～S11 的专属任务与来源规则仍按各阶段原合同执行，不从三阶段最小接收推出全局协议变化。

## 4. 根目录与入口优先级

### 4.1 控制根与执行位置分开保留

注册命令用 `CLAUDE_PROJECT_DIR` 定位初始 Harness 和 `--root`。控制根使用已有工程关联解析，`cwd` 保留实际执行位置。其他原入口在无旧 bootstrap 时仍可按其原合同从同一 Git 仓库的工作区寻找唯一已绑定工程权威；多个可能控制根或无法定位时明确诊断，不凭目录名称选权威。

S6 的原生 Plan／Result 与 Git 贡献仍保留原执行根和 Main 权威根，不借 Main 同名答案补 Worker 产物，具体 Git 边界见[工作区治理](L4-worktree-governance.md)。S7／S8／S9 复用已发行路径和已有责任关联读取本人原卷，不另遍历 Git worktree、比对 HEAD／branch／pin 或认证 actor 与来源根来授予答卷资格。实际产品位置、工作树、专业独立和输入适用性由 Main 与执行者负责。

删除旧 session／root、frozen execution、C／D、typed 的并行接收和恢复接线；当前消费者按当前真实责任及派发关联处理。显示 reader 只投影事实，不成为第二个认证消费者；真实关联缺失交系统，不借角色、同名文件或另一个作者的稿件代替。

### 4.2 原事件一次路由，已收只续未完

公开 Hook 按以下目标顺序处理：

1. 解码输入、核注册事件，使用已有关系定位控制根与实际执行环境。
2. 读取必要的已有实际派发关系和最小接收进度，选择适用处理器。无关处理器让事件继续，不因历史 route、brief 或旧阶段存在而声称已处理；准确关联不足时保留相关未知并交 Main／系统，不吞掉其他已明确的责任。Start 缺完整任务且无准确已有关系时只给中性提示或静默。
3. S7／S8／S9 的 Pre、成功 Post、Stop／SubagentStop 进入 §5.2 同一接收链。已收交接只投影或续未完成后继；尚未完成责任的新尝试按 §5.2 观察，不覆盖历史交接。
4. 其他阶段的保存、父返回、配置审计和控制周期按各自现有入口执行；未处理事件进入其原适用分支，不将三阶段的职责推广为所有事件跑全 Controller。
5. 输出本次真实接收、后继与准备状态，给实际接手者准确原入口。

仅遇到已有未完成事务时，系统沿其受支持入口续未完成部分，并保留实际接收状态；不规定每个事件都恢复配对事务、刷新完整 Snapshot 或复验历史。pending 不证明阶段、责任或交付完成；恢复不能吞掉已具备接收条件的事件。恢复失败如实反馈，不要求作者改字段、重存或制造新事件。同一权威 state／journal 的 pending 尚未完成且无法判定时，属于共享控制面故障，Writer 不得随意跳过后继续追加；系统／Main 沿原入口处理，普通专业工作继续。它可能阻塞该权威写入，不是作者门禁。

上述路由是 S7～S9 的目标接线，现有实现中的分支顺序与提前返回须按公开入口验证后调整；不能将旧 `Purpose`、typed 优先、C/D 来源核验或宽静默保留为新链门禁。旧责任沿原关联接续，不重新签发或要求迁移格式。

公共 Snapshot 或责任索引读取失败时，保留具体错误与原路径，不能解释为无责任或已接收。能确定 Main 时，在适用模型上下文说明系统缺口及恢复入口，普通工具继续；未知 Helper 不冒充 Main。SubagentStop 的用户提示不等于父会话已收到，真实 Main 后续事件独立读取原事实。请求显式取消后不启动新选择、接收或后继，不承诺后台最终完成。

## 5. 新原生 Worker 的开始、执行与结束

### 5.1 Start 提供上下文，执行由平台负责

原生 Start 的提示说明：按 Main 实际任务中的准确材料开展专业工作，保存本人产物，自然事件调用原消费者，原生返回时兜底接收。新原生路径不要求先登记平台 actor、建立 Team、通用读回、激活、AgentBegin 或框架 launcher。

平台的 SubagentStart 可以向子代理注入上下文，不能阻止子代理创建；Stop 的纠正反馈则会影响该执行是否继续。输出字段必须按相应事件使用。[官方事件契约](https://code.claude.com/docs/en/hooks#subagentstart)

下面只是上下文输出的形状示意，不是供作者填写的工程记录：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "SubagentStart",
    "additionalContext": "请按 Main 实际任务中的准确简报开展工作，在指定原路径保存本人产物，如实汇报结论或阻塞。"
  }
}
```

### 5.2 S7／S8／S9 自然保存与一次最小接收

三阶段统一以 `PreToolUse` 监听当前本人原卷，成功 `PostToolUse` 和 `Stop`／`SubagentStop` 复用同一消费者兜底。适用成功 Post 包括支持的保存工具和其他成功工具；其他工具只提供观察时机，不证明刚写入答卷，失败工具不作为成功保存。普通工具始终自由，不按 scope、actor、文件状态或阶段进度决定许可。

监听先从已有派发／责任关联定位本人，读取最小接收状态。未接收时只读取该原卷一次，单次完成解析、理解原结论与有限分流所需的必要结构及当前责任关联检查。定位、适配、保存与分流共享本次内容，不反复打开、不递归读取其他责任。未就绪保留原稿，具体结构错误给准确位置，同一暂缺不反复刷屏；系统不推断作者未来是否还想编辑。已有可理解专业结论或本卷既有必要表达即接收；未表达判断的空值通常保留草稿，明确的“无／不适用”按原意交接。S9 原 Impact 空数组的默认模板与合法无变化无法区分，按 [工作流收敛 §3.3.1](L4-workflow-convergence.md) 接收并允许提前观察，不推算 PASS 或 Main 实际工作完成；不要求精确保存事件或额外标记。模板与 brief 交代这一自然观察含义，不新增结束表达或填写顺序。

系统信任作者的专业声明，不核 Git `??`／ignore／HEAD／index／branch，不回读或散列证据，不核原题干 hash、pin、typed／flat 一致性、全 Claim 覆盖、因果或实际独立性。必要结构只服务理解与分流，不能因某条 check 失败自动推翻作者总体判断，也不能从所有 checks 成功推算 PASS。非关键缺项不阻止接收，不逐条比对题面或断言集合增加覆盖门；错误、未知和 blocked 可如实交接。专业判断、真实执行和完整覆盖由作者、Main 与适用独立责任承担。

原消费者可靠保存本次原内容、原结论、责任接收结果和未完成后继所需的最小事实一次。已收交接直接复用原事实，不重接收或重转阶段；私人文件后改不覆盖已收事实，真实专业变化走原修订／返工或未完成责任的新尝试。Writer 的并发一致性和事件幂等是内部持久化，不是作者门禁或新增旁账。

一次 blocked／未完成交接的已收状态与责任仍在继续分别认定。S7～S9 均由 Main 已有继续安排，或明确仍属原责任的本人自然继续，接上当前新尝试；本人在原未完成责任内继续无需 Main 另作强制动作；后续自然事件才观察该原卷的新结论，旧交接原样保留，相同旧内容不重复接收。不得要求作者补恢复证明、调用 resume／submit 或重存旧卷。已收且责任已结束、没有新尝试和未完后继时不读私人原稿并快速返回；责任不明确交 Main，不按文件变化猜选。必要的未完成责任观察计入 §10.6 总成本。

S9 Plan 独立就绪即可接收，Result 缺失不阻止 Plan。作者在既有授权内连续实施，无需等另一作者或第二次批准；Plan 接收不代表 Result 或阶段完成。真实 blocked／contract_conflict 可直接如实交 Main，即使 Plan 尚未形成，也不要求倒填 Plan 或凑出 completed。S8 `inconclusive`、来源受阻与其他真实未完成同样可交接，不强迫制造正结论；`inconclusive` 本身不判定本人未履职，已收回执不依赖私人原稿。S9 Main 的空 Impact 即使先被观察，仍沿同一活跃责任的自然事件接收后续更新，不锁死后续 Builder 贡献或要求重存。

不增加 submit、done、marker、独立完成状态、返回引用、重存、结果证明或独立 Main 最终答卷。真实必要批准仍由原主体作出，Hook 不代批；当前机制中在途原卷由当前消费者沿原关联接收，删除旧格式和旧来源接线。

### 5.3 Stop 兜底接收与正确责任交接

S5 按原 Stop 审查合同接收；S6 按原合同接收本人 Plan／Result 与真实 Git 贡献。S7／S8／S9 Stop 与 Pre、成功 Post 共用 §5.2，不重复执行一套强校验。平台停止、工具成功或合法 JSON 本身都不表示责任完成。

三阶段首次返回可以交真实未完成、阻塞或系统缺项，保留原稿和具体下一责任；不要求再次 Stop 才允许结束。作者能修的结构错误给准确题目，系统准备、责任索引、Writer 和后继问题交 Main／系统，Main 不代填 Worker 结论。`stop_hook_active` 防循环不制造 PASS。其他阶段保留其已有纠正与退出合同，不由本节统一放宽或强化。

Main 收到 Agent／Task 的真实完成返回是具名兜底观察事件：从真实派发／返回与原责任的准确关联取得原接收摘要，原卷未收或原责任有明确新尝试时可读取该作者原卷并复用 §5.2 同一消费者，将实际接收与下一责任反馈 Main；不由角色、prose 或唯一候选猜选。普通 Main 阅读、转述或保存不取得代填或代收 Worker 卷的资格；不要求额外的 D worktreePath／worktreeBranch、C retained actor、typed 来源或 prose 证明。异步启动和 SendMessage 即时成功仅表示启动／发送，不是专业返回或接收。真实完成通知、Main 模型上下文和工程接收事实分别验证。

接收后按 §10.8 同次分流并准备下一原材料；Main 的实际集成、长检查、合并和资源处理仍在普通工作中执行，不塞进短 Stop。已收作者不为同事未完成、Main 未集成或资源未回收再次履职。没有准确责任、已关闭责任的迟到通知或系统故障，不借同名答案重新开卷；保留真实事实交 Main。

## 6. Main 的自然工作与收尾

### 6.1 本人保存调用本人消费者

Main 的 SessionStart 可以恢复当前阶段并进行该入口已有的必要准备。PreToolUse 主要提供进度和准确材料；在未走只投影分支的具名路径中，仍可能运行原控制周期或准备，不能笼统称整个事件永远只读。它不按工具类型、平台身份、scope 或旧 activation 给予许可、拒绝普通工具。

Main 的成功 PostToolUse 先处理有限诊断观察、真实材料变化、本人的准确答案保存及原接续，再按适用工具处理父返回或旧观察。S2～S4 真实材料变化可以触发缺题准备；S2 沿原已签发模板恢复缺失投影，保留已有作者内容，已接收答案丢失时提示恢复原文而不生成空白草稿。已经接受的 S4 后继也可在原成功读取事件接续；这与重新收取 Worker 私有答卷不同。具体阶段例外归[阶段答卷](L4-stage-form.md)，不能用一句“所有 Post 只观察”抹掉已落地的正常入口。

S7／S8／S9 在自然事件上接收当前本人原卷；Main 的普通 Read、转述或保存不授权其代写或抢收 Worker 原卷；准确真实完成返回的观察边界见 §5.3。其他阶段按原保存与父返回合同接续，不由三阶段监听更改其接收时机。真实平台提前返回与反馈渠道需分别验证，不保证每次父返回都有集成摘要。

### 6.2 Main Stop 看 Main 的剩余责任

Main 的收尾与 Worker 本人结束分开。原 Main Stop 前置检查在已知不应结束时先反馈，避免为了发现该事实先推进转换或刷新摘要。规划缺项、已确定而未派发的审查责任、已返回而未消费的结果等，按当前原记录处理。S7～S9 的 Main Stop 同时按 §5.2 兜底本人原卷并接续适用分流；真实 blocked 或系统障碍可以首次如实交接，不用重复 Stop 换取结束。

Main Stop 目前不是对所有阶段重验全部产品与证据的通用门；S10、人类等待和终态有自己的投影与领域消费者。它不替人作决定，也不将“Main 没被 Hook 阻止结束”解释为发布授权。

删除旧 TeammateIdle 和固定 execution 的收尾接线，不为旧分支要求当前原生任务额外 Plan 或完成报告；`stop_hook_active` 防循环不授予完成资格。

## 7. 输出给谁，怎样影响继续

### 7.1 内部判断与平台协议分别表达

内部 Decision 的 `allow/info/warn/audit/deny/block` 是实现载体，不是所有事件通用的官方六枚举。当前 [PreToolUse 渲染器](../../internal/hook/pretooluse.go)输出进度与 `additionalContext`，不设置 `permissionDecision`。旧 [adapter](../../internal/hook/adapter.go)仍有渲染 deny 的能力，不能由此推导当前普通工具路径已执行该策略。

| 实际结果 | 当前输出方式 | 退出及含义 |
| --- | --- | --- |
| 正常且无需补充 | 可静默 | 0，回到平台原流程 |
| 支持上下文的正常事件 | `hookSpecificOutput` 中使用对应 `hookEventName` 和 `additionalContext` | 0，传递原责任材料与下一动作 |
| 面向用户的简短提示 | 适用事件的 `systemMessage` | 不等于模型已经收到专业上下文 |
| 具名原生观察审计 | 追加审计，协议 stdout 静默 | 0，不改变原操作结果 |
| 需要本人继续的 Stop 纠正 | stderr 给准确问题与下一动作，stdout 静默 | 2，按本项目所用平台 Stop 方式反馈 |
| 允许结束的软提醒 | 适用的用户提示或后续 Main 上下文 | 0，不借 Stop 的继续机制通知别人 |
| 输入、通用审计或输出故障 | stderr 诊断；按实际故障路径退出 | 1 不等于本项目发出了工具 deny |

`systemMessage` 在同步 Hook 中是用户侧提示，不能代替模型上下文。Stop／SubagentStop 的继续反馈送到相应执行，不能用作发给父会话的软通知；本项目选择 stderr／exit 2 做纠正，不把普通提醒放进会继续执行的 Stop 上下文。[官方输入输出契约](https://code.claude.com/docs/en/hooks#hook-input-and-output)

### 7.2 只渲染已经成立的事实

质量投影保留原 `status`、候选、观察 revision、缺项、冲突与 `transition_committed`。只有真实提交才显示推进；图投影没有运行该轮 Gate 时，不补造一个通过或 `advanced`。原生接收回执与领域缺项也不应被统一渲染器改成新的结论。

`warn` 不升级成阻断，`audit` 不泄漏成控制输出。整个 stdout 应是一个当前事件能消费的协议结果，不能夹入测试日志、第二个 JSON 或调试横幅。接收已经提交但输出失败时，应按原回执恢复，而不是因为没有看到成功提示就重新创建一份交付。

## 8. 上下文、提示与重复投递

Hook 交付哪些内容、与入口和专业材料怎样分工，由 [Agent 指引的分层与交付](L4-agent-guidance.md) 定义。本篇解释其事件和输出边界；不能在 Hook 文案中另设阶段门或让展示缓存产生业务事实。

### 8.1 有限背景不能挤掉当前工作

上下文先交付当前阶段、本人责任、准确题目和答案位置、具体缺项及下一动作，再补读序、范围和可选候选。Worker 应能根据 Main 的真实任务开始工作；缺少准确路径是准备或路由问题，不能只扔一个 Runtime 路径让其猜责任。

当前有几种不同的长度处理，不能统称为“所有内容最多 800 字”：

- [生命周期上下文](../../internal/hook/lifecycle.go)以约 800 个 Unicode 字符安排简短背景和可选细节；已有完整责任交付优先保留，放不下的可选背景省略。
- 某些过长的旧背景构造会回退到原入口引用；不能据此承诺所有分支永远给出完整题目路径。应优先修正准备与信息排序，避免把正常工作变成恢复阅读。
- [进度显示](../../internal/hook/progress.go)的 480 字符限制只作用于简短用户提示，不代表模型上下文被同样截断。
- 通用较长上下文另有有界截断；准确责任交付应放在背景之前。专用原生输出与图投影也不是全都经过同一个长度函数。

背景压缩不应改变专业条件、裁掉路径尾部或把必需命令截成不可执行的片段。需要很多细节时，交付准确专业材料入口，由相应题目解释本人的工作。

### 8.2 展示与模型上下文分别去重，不减少责任

普通 PreToolUse 的显示去重按会话、执行者和稳定事实判断，忽略单纯 revision 抖动。它只移除重复 `systemMessage`，保留模型上下文、缺项、冲突、审计及拒绝反馈。SessionStart／SubagentStart 等重新进入时要能重新看到必要信息。

S2 的普通只读投影另有模型上下文去重：已知会话、执行者和当前责任下，完整内容与上次成功交付相同，才改为简短的继续提示。新错误、缺项、路径或责任变化重新交付完整内容；会话开始与上下文压缩边界重置。缺少会话或缓存不可读时保守交付全文。这项能力只在已接线的 S2 图投影启用，不推广为其他阶段的通用上下文删减。

S2 的 UI 投影只盘点需求所引用模块的必要文件并指出准确缺失位置，不在每次普通工具前重跑完整场景验证；文件存在不表示语义通过。完整验证仍是专业设计工作，按照场景规则使用原 `scenario` 命令执行。

提示缓存和软提醒的投递标记只在 stdout 写出成功后更新。输出失败不应提前缓存成“已经通知”；缓存丢失、竞争或损坏至多导致多提醒一次，不能成为权限或完成依据。成功写出也只说明本进程交出了输出，不证明平台已经注入，更不证明接收者理解并完成了工作。

Main 的集成软提醒从原 checkpoint 和待处理贡献生成，经适用的父会话事件投递。同一事实未变可以去重；事实变化后重新提示。不在 Worker Stop 中用“继续执行”来催 Main 合并，也不因提醒预算耗尽改变集成事实。实际 [reminderDelivery](../../internal/cli/worktree.go)有适用会话与分支限制，不是全体 Main 回调的通知保证。

## 9. 失败方向按事件与责任决定

### 9.1 没有全局“失败就拦”开关

| 失败位置或情况 | 当前处理与应保留的事实 | 后续责任 |
| --- | --- | --- |
| JSON 无法解码、注册事件不一致 | 报输入诊断，不伪造另一类事件 | 修复调用或输入 |
| 控制根无法解析 | 诊断后允许平台原流程，不猜权威目录 | Main／系统检查原绑定与目录 |
| 普通进度或来源不可判定 | 保留未知或具体准备问题，不发工具 deny | 继续可开展的工作，修原准备或来源 |
| 原生 Stop 没有唯一责任 | 不猜绑、不借同事答案 | Main 核对实际任务与返回 |
| 已知责任有专业缺项 | 原消费者拒收，保留准确缺项与原产物 | 本人按该责任修正或如实返回 blocker |
| 原生 Stop 来源、准备或未知故障 | 保留准确对象与原诊断，exit 0 交 Main，不创建完成事实 | Main 修原来源或接收接缝，不要求作者猜改答案 |
| 已接收但后继或输出失败 | 保留已经成立的接收与未完成后继 | 恢复原后继，不重复制造接收 |
| 原生审计写入失败 | stderr 诊断，适用观察分支仍 exit 0 | 修审计环境，不改原工具成功事实 |
| 通用审计、序列化或 stdout 失败 | 当前部分通用路径 exit 1，不能概括为全部静默成功 | 区分协议故障与业务拒绝，查询原事实 |
| 旧记录的 Stop／Idle 问题 | 沿其具名消费者、回执与防循环逻辑处理 | 不将旧执行手续推广到新原生任务 |

失败方向须同时说明适用范围。原生普通事件提前返回时，可能根本没有执行通用审计或恢复；不能承诺每个工具失败都有一条记录。通用路径的审计失败与原生观察器的审计失败也有不同退出方式，不能混成同一个全局策略。

### 9.2 纠正只延续本人可完成的工作

Stop 反馈需要说明实际缺项、准确位置、本人下一动作；没有这些信息，只让执行者“再试一次”容易形成循环。S7／S8／S9 允许首次如实交接未完成；其他适用纠正路径尊重 `stop_hook_active`，不因同样缺项无限拦截。放行后 Main 根据原记录处理未完成工作，不以放行冒充质量豁免。

真实 blocker、作者已交付、同伴未完成、Main 待集成和系统缺源分别属于不同责任。收尾判断应消费当前事实，不能仅凭历史 blocker、一个 terminal 字串或一段最终聊天让全部工作自动完成。

新原生 Start／Stop 只负责专业衔接，旧分支中仍存在的首写、激活或通用身份链不成为恢复捷径。三阶段真实输入变化由作者与 Main 判断其影响；批准记录、重复事件和 pending 事务由原消费者／Writer 承接，不借 Hook 另造来源证明或修订协议。其他阶段专属来源门仍按其原合同执行。

## 10. 十秒预算与中断恢复

短 Hook 可以做必要的有界读、上下文准备、专业接收与原后继事务。完整产品测试、长合并、工作区创建、检查环境修复和资源清理应在普通工作中完成。把耗时任务搬到 Hook 内，会使平台超时与专业失败难以区分。

### 10.1 机制减负的作者契约

S7／S8／S9 使用[工作流收敛 §3.3.1](L4-workflow-convergence.md)与对应 L3 的现行目标合同：作者取得原责任、完成专业工作并自然保存原卷；Hook 定位本人、一次最小检查和保存，再按原结论接续。不能把减少作者动作换成更多机器证明、兼容状态机或重复消费。

正常接收、适用转换和下一责任准备在本次交接内完成，失败保留已成立部分并给实际接手者原入口。没有实际执行者时如实说明未完成，不要求作者重存、额外工具调用或重启旧 Worker 来调度。S0～S6、S10～S11 的专属专业检查与真实授权继续按原合同承担。

### 10.2 删除证明工作，再合并必要读取

| 层次 | S7～S9 的必要工作 | 应移除的旧工作 |
| --- | --- | --- |
| 分流与定位 | 原事件、已有派发关联、当前责任和最小已收进度 | 无关处理器初始化、扫描全部 packet／私人原稿、按角色猜选 |
| 本人原卷 | 未接收时读取一次，解析必要结构、就绪与原结论；请求内共享输入 | 服务只传路径导致下一层重开，重复题干或 flat／typed 比对 |
| 保存 | 原内容、结论和责任进度可靠保存一次，内部并发保护 | Candidate／Final／Receipt 或证明链的重复接受与重新认证 |
| 分流与准备 | 消费已收原结论、适用责任进度和真实批准，准备当前下一材料 | 全 Claim 覆盖、CleanRound／ObservationBatch、Git／证据／hash、因果闭合或修复真实性机器复核 |
| 反馈 | 本人已收到哪一步、实际未完成工作及准确接手入口 | 长历史复读、无动作的占位命令、重存与再 Stop 要求 |

必要责任索引与接收结果不是新账本。主状态保留路由所需小记录，原专业内容保存一次；已有正文外置、Writer 和回执可复用，不需要新格式先行。已收且责任已结束、无新尝试和未完后继的事件不读私人原卷或全部历史；活跃 Main Impact 依 §5.2 观察当前原卷更新，不重读历史；未完成责任自然继续的观察沿 §5.2，责任变更只刷新所需当前关联。

#### 10.2.1 一次自然事件的执行顺序

定位控制根与当前责任后，先看已收事实。未收则只读本人原卷一次并完成最小解析；未表达可交接内容或 JSON 尚未写完整时通常保留草稿；S9 原 Impact 的空数组按 §5.2 接收并接受可能提前观察。已有可理解结论则保存并更新责任进度，不猜作者是否还想编辑。随后直接用本次接收结果与已有适用责任结论执行 §10.8 分流，准备下一材料并一次反馈。已收交接则直接从当前进度恢复未完后继；尚未完成责任已接上新尝试、或 Main 的原 Impact 责任仍在进行时按 §5.2 观察当前原卷，已收终结责任快速返回。

锁内仅维护可靠保存、并发和幂等，不重证当前产品、历史签发、Git 或证据。真正的专业检查、集成和长操作由 Main／作者完成后记入原专业产物，不能为了短 Hook 的完成指标转移到接收内部。

#### 10.2.2 同次复用与后续修改

本次读取到的原卷内容在定位、结构解释、接收与分流中共用；不能在两层之间重读变成不同输入。未接收作者可继续编辑，下一自然事件观察实际新稿；已接收后改私人文件不改原记录，按真实修订／返工或原未完成责任的新尝试处理。读取已收事实不要求私人文件仍存在或摘要未变。

删除旧 typed／flat、C／D、pin、Candidate／Final 和旧回执的并行接收与恢复接线。当前派发责任由当前原卷与唯一消费者接续，不为清理旧机制要求作者再生产稿件、重新证明来源或重放强核；内部投影不是新的专业交付。

#### 10.2.3 有界转录与审计

仅在当前责任需要定位时读取有界真实任务，近尾命中即停，多个适配器复用同一读取结果。不相关事件不读转录，不能要求作者缩短会话、换 Agent 或重报引用降低成本。

审计只记录实际事件和必要观测，不参与专业接收资格。复用原去重能力，避免每次追加解码、散列全部历史；索引可重建而非第二业务来源。审计、统计或 stdout 失败不抹去已收事实，也不产生普通工具 deny。输出失败不缓存成已送达；平台实际投递仍须验证。

### 10.3 中断按最小持久事实恢复

| 实际窗口 | 内部处理与接手 |
| --- | --- |
| 未接收、原卷未就绪 | 保留原稿，作者继续专业工作；真实 blocked 可先交 Main |
| 已读取尚未提交 | 同次有限续跑复用原输入；后续自然事件读取实际未收稿，不声称未保存字节已被固定 |
| 原 Writer 暂存或 pending | 原 Writer 在有限预算内识别并恢复原事务，保留原输入与已成立事实；同权威 pending 无法判定时按 §4.2 报系统故障，不随意跳过或要求作者重交 |
| 原接收已保存，反馈失败 | 恢复反馈，保留接收；不要求重存或再次接收 |
| 已接收，转换／材料未完成 | 只恢复原未完后继；已转换不重转、已批准不重批 |

显式取消不启动新接收或新后继。工作 deadline 与进程截止点区分，有限尾段只处理本次已捕获输入和原未完事务，不重新发放预算或启动无关业务。安全处理内部暂存属于系统职责，不要求作者删文件、改 ID 或补证明。没有跨进程执行者时不能承诺强杀后无人触发完成；原异常入口由 Main／系统用于恢复，不成为正常交卷第二步。

### 10.5 存储只服务原内容与当前责任

保留已接收专业内容、owner／责任关联、结论和真实批准，并发不得覆盖；内部正文可复用当前已有存储，不新增结果证明表。删除旧格式读取和旧回执兼容接线，不因删除代码改写或删除用户数据。

正常提交后事实可读、并发不覆盖、进程中断后接续和原已收／在途历史继续，是内部可靠性的具体故障边界。单文件损坏、整份权威状态丢失、历史防篡改分别说明所需恢复、允许损失和成本，不由旧完整 checkpoint 或全量双副本自动推成永久义务。实现比较必要最小事实、增量或其他简单表示；不能删掉灾损能力却声称保证完全不变。

Hook 及其原消费者、原 Writer、pending 和恢复均不计算、登记或验证任何散列；不得用其他散列算法或改名指纹保留同一机制。原内容、回执和后继不各存一份完整专业正文；实际结构化事实、读取、锁等待与持久化成本如实测量。

存储、并发和事务恢复的验证关注同答不重复、责任改变不误绑、已收后修改不改历史、所支持故障只续未完部分；不以历史来源、文件摘要或 Git OID 验真作为任何阶段的存储验收前提；各阶段真实专业工作和原消费者保留。

### 10.6 三阶段组合验收与运行成本

使用[接收与恢复验收清单](L4-hook-acceptance-checklist.md)展开现行合同；清单若仍要求旧强核应同步修订，不能反过来给作者增加手续。至少验证：

- 三阶段 Pre 监听、成功 Post 与 Stop 兜底到同一原消费者；未表达可交接内容或 JSON 未写完的分步草稿通常不接收；S9 原 Impact 空数组按 §5.2 接收并接受可能提前观察模板的代价。已有可理解结论即接收，不推断作者是否尚想编辑；同一缺项不刷屏，普通工具可用，自然保存一次足够。
- 每次未收事件只读取本人原卷一次，结构、就绪与结论共享本次内容；无关答卷、Git、证据与摘要损坏不触发本人资格门。已收终结责任且无新尝试的事件不重读原卷、不重接收；活跃 Main Impact 和同责任 blocked 后自然继续按 §5.2 观察，保留旧交接。
- 正常与 blocked／未完成均可如实交接；原 checks 中单项失败不会被机器自动推翻总体结论，机器也不由 checks 成功推算 PASS。
- 原接收、真实批准、转换和材料准备各窗口失败后保留实际事实，重放不重复责任、批准、实际适用的授权预算或转换，也不重复建立完整验证责任。
- 当前派发的题干和路径由当前消费者沿实际责任接续；删除旧 C/D、typed 与历史来源接线。原卷缺失或责任冲突反馈准确系统问题，不猜选。
- S7 Finding→S8、适用责任完成且无 Finding→S10；S8 原 Main 处理选择及实际批准→S9；S9 实际集成、原影响判断与独立 Targeted 结论→新 S7，分别验证真实材料准备。

以同一完整任务测量草稿、首次接收、blocked 后继续、已收重放和中断窗口的总事件数、原卷读取次数与字节、解析、消费者调用、锁等待、持久化、后继和 Hook 墙钟成本，并证明各阶段实际 Hook 调用不计算或登记散列，并观察日常工具延迟。单事件最多一次读取不证明长任务总成本最优；高频观察的累计代价应如实呈现，优先消除无关初始化和重复工作，不靠缓存掩盖接收错误，也不要求额外重存、延迟交付或禁用普通工具换数字。固定当前任务规模，增加无关历史正文、日志、责任和转录，验证普通接收不因它们线性增长。历史 Git 或全日志扫描的耗时须如实归为待撤下实现，不用缓存命中或套件总时长掩盖目标差距。

外层传输、审计、专业未就绪、结构错误、并发冲突和已收后继失败分开报告。指标沿既有 bounded spool／doctor／health，不新建业务日志；外层强杀可能来不及保存内部计时，不补造完成 span。源码、进程接线、平台 matcher 与真实 Claude 会话分别报告，未运行不记通过。

### 10.7 原稿路径、产品变化与资源处理

原答卷路径是派发已有责任的读写入口，不是产品资格证明。S7 Reviewer、S8 Investigator、S9 Builder、Main 专业材料及独立 Targeted 使用各自准确原卷；不要求 `??`、非 ignored、非 HEAD／index、原模板 SHA、typed attempt、sourceDigest 或 proof 单文件投影才能接收。未知 sibling 或私人中间产物也不因未引用而触发答卷拒收。

专业任务仍约束产品写面、真正授权、独立分工和真实检查。Main 与作者对实际产品变化和辅助产物负责，不把删除机器资格解释为任意改产品。实际集成、保存产品、必要检查与资源回收在普通工作中完成；资源回收使用原对象及真实清理授权，不因接收成功自动删除文件或扩大整目录排除。

删除旧 C／D、frozen、typed、Candidate／Final、source pin 的并行接收、来源证明及恢复接线；当前原责任由唯一消费者接续，已收事实不撤销。清理失败与专业后继分开反馈，不要求 Worker 重做交付，不强删未知内容。

### 10.8 原结论到下一责任的最小分流

| 当前已收事实 | 自动接续与专业接手 |
| --- | --- |
| S7 原答卷报告实际 Finding | TR-008 交 S8 原 Finding、现场、阻塞和未完成范围；不等另造 Batch 或全 Claim 证明。Main 安排其余安全检查；已派发责任在 S8 的晚到原卷仍按已有责任接收，新 Finding 交 Main 判断，不重开 S7 或自动改写已批准合同 |
| S7 无 Finding，原计划适用必需责任均已报告完成 | TR-009 准备 S10；读取已有结论和责任进度，不重算覆盖、不认证独立性、不生成 CleanRound 或 Main 最终答卷 |
| S7 必需工作 blocked／未完成且无 Finding | 如实交 Main 恢复，不当作 PASS 或进入 S10 |
| S8 Investigator 保存 supported／refuted／inconclusive | 保存本人原结果；Main 作因果与路由判断。新假设只作建议，不自动签发或构成出口门 |
| S8 Main 原处理选择、合同及适用真实批准成立 | 沿原批准／路由消费者进入 S9 并准备材料；不重新机械认证因果、全部假设或证据。无需修复的原路由按 Main 选择接续 |
| S8 未获必要真实批准或仍有专业未知 | 交 Main 或实际决定主体，不由 Hook 代批，不为推进伪造正结论 |
| S9 Plan 已收，Result 未完成 | 保留 Plan，作者连续工作；blocked／合同冲突交 Main，不倒填或伪造 Result |
| S9 原 Result 已收，Main 集成／必要检查未完成 | Main 执行真实集成和检查，保留本人原影响判断；系统不把 Builder completed 冒充 Main 完成 |
| S9 独立 Targeted 原结论已通过、原计划仍适用的独立责任已有结论 | 接续原 Handoff，准备新的完整 S7；不以 Final／Changeset、额外 Main 完成信号或机器独立性证明为前置，定向通过不冒充完整验证 |
| S9 Targeted 非环境失败／范围变化 | 按实际结果交 Main／S8 判断；只写 `fail` 而未分类时原因保持未知，不默认同一根因或强迫补分类；环境 blocked 先交 Main 恢复原验证前提 |

本次接收具备分流条件时，同次尝试转换和下一材料准备，反馈已完成到哪里及准确路径。适用需求变更、发布阻断和用户实际约束仍由原真实决定处理，不被默认分流掩盖；新工作不统计审查轮数或调查重入次数，不由默认次数产生审批。多个内部事务可以分开持久化，但不是作者多次提交；已收后只续未完，已批准不重批、已转换不重转。

Main 返回、普通进度、显式恢复和 CLI 失败使用同一当前责任与原接收结果组装反馈，至少包含原路径、已收部分、实际缺口、接手人和准确下一步。不把空 action 变成 `Next: .` 或通用 reconcile；Worker 晚返回不取得 Main 的 S10 审计责任。Main 的真实审计材料仍由 S10 原合同准备。

### 10.9 失败交付与具名异常恢复

真实执行、工程接收和失败分别表达。Agent／Task 的 `async_launched` 或一致异步字段只说明启动，SendMessage 成功只说明发送；明确 completed 和真实完成通知可触发当前原责任观察，但不证明工作已被接收。执行字段缺失或冲突时保留未知，不根据 prose、角色或 ready 猜运行状态，不新增轮询手续。

| 已知窗口 | 原恢复边界 |
| --- | --- |
| 未接收原卷仍可用 | Main／系统的具名恢复入口复用同一最小接收核心，只读当前原卷一次；不要求 Worker 重存、再次返回或新建 packet |
| 原稿尚无可理解交接表达或有妨碍理解／分流的结构错误 | 原作者继续同一未收稿；非关键缺项不拒收，真实错误／blocked 按实交 Main，不冻结草稿为永久非法 |
| 已有原 pending | 原 Writer 恢复配对后从已成立事实继续，不以当前私人新稿替换事务固定输入 |
| 已收交接的反馈或后继失败 | 原回执与最小进度决定尚缺什么，只补该交接的转换／准备，不重读该次原稿或重跑专业检查；原未完成责任自然继续的新尝试仍按 §5.2 观察 |
| 原卷丢失且无已收内容／可识别 pending | 明确缺失与已有事实，交 Main 恢复；不输出指向失效输入的假恢复命令，不借同名文件或 hash 补造原内容 |

现有 `runtime stage-answer consume --root <Main-root> --path <准确原卷>` 等显式入口仅在实际支持该责任及其可用输入时交付；新链复用自然接收核心，不经过旧 typed／flat 双卷核验、Git baseline 或 Candidate／Final 再认证。当前实现尚未支持的恢复窗口应明确待落实，不为完整恢复菜单新增状态或派生输入。正常作者不用该命令。

请求内捕获原责任、已到达窗口和具体错误即可组装失败反馈；预算耗尽后不再读 Snapshot、原卷、Git 或历史闭包来证明错误。可复用既有每责任小诊断，有限保留实际尝试和原消费者原因，不保存答案正文、第二套接收状态或无限历史。诊断只是导航，已收事实优先；新责任或新接收后旧错误不能继续催原作者。失败分类用真实类型化错误，未知明确未知，不分析英文关键词决定作者责任。

工作与诊断发布共用原绝对进程截止点，发布只序列化已捕获事实及有限小文件 I/O，不运行接收或来源核验。显式取消终止新发布；进程强杀或发布失败仅保留实际 stderr／传输观测，不伪造可绑定的专业错误。诊断、审计与输出故障不改变业务已收，不保证跨会话必达。

同一次 Main 投影仅调用一个适用责任生产者，复用其结果，不能最后用字符串去重掩盖重复组装与读取。brief、模板、角色、Skill、Hook、命令帮助和安装材料必须共同移除旧重交／再 Stop、typed 优先、来源强核与工具门禁要求。落地验收覆盖原卷未就绪、一次接收、Plan 已收、blocked、pending、反馈失败、转换失败、输入丢失、请求取消与真实完成通知；检查实际调用次数、已收幂等和模型收到的下一责任，不以 helper 存在或 Hook exit 0 代替全链通过。

### PreCompact 与压缩后的恢复

专业结果、阶段事实和恢复依据在原消费者执行时已经由 Writer 保存。PreCompact 没有新的专业输入，不能为了补一份摘要而临时收卷、运行阶段控制周期或遍历全部证明。公开 Hook 在既有诊断维护后静默返回；原生提前返回的职责仍沿原边界，不额外要求每个 Worker 做维护。

压缩后的 SessionStart 从 Runtime、原责任与已接受产物重新取得当前阶段、准确路径和下一动作。Milestone 可以帮助导航，但只是原工程事实的摘要，不保证每次压缩前重写，也不要求恢复时逐字重放旧提示。已经接受的工作不因提示丢失而重做，尚未表达可交接内容或 JSON 未写完的私人草稿也不会因压缩而变成已接收结果。框架不承诺替作者保存全部工作记忆或进程状态，不依靠 PreCompact 输出保证模型记住任务。

## 11. 审计和观测怎样帮助查错

[通用审计信封](../../internal/policy/engine.go)关联事件、会话、Runtime、观察 revision、执行者、规则、决定及耗时；适用的质量投影与原 Hook 输出共同来自相应控制结果。跨进程规则身份统一为现有 `HOOK_*` 形式，内部常量仍可保留原命名。

策略按当前安装位置和实际版本读取，权限与反馈语义按原声明执行。Hook 不计算、登记或校验策略 SHA，也不经策略摘要证明加载；策略内容与专业结论各由原责任处理，真实配置变更不自动批准专业工作。

原生失败和配置观察沿已有平台事件、实际责任与真实输出区分重试和不同观察，不计算或登记 payload 指纹；没有可判别关联时保留未知或允许重复提示，不以生成散列补齐。原生 Start／Stop 观察不等于平台执行或专业结果已成立。

[原生观察器](../../internal/hook/native_observer.go)只保存必要、有限字段；其失败错误和配置元数据先按既有 Capture 模式检查完整值，再限长，命中时用隐藏说明代替整字段。它不复制原工具输入／输出，也不因过滤而否决已发生的动作。已有平台事件身份和原责任用于区分已知事件；无法区分时不以散列补造关联。

[Outbox](../../internal/audit/outbox.go)负责追加、去重和持久化，不统一改写工程事实或识别任意机密。其他错误和采集入口仍承担写入前处理责任，既有模式的范围见[运行控制面](L4-runtime-control-plane.md)。限长和模式检查各有用途，不能混称全局脱敏保证；不通过散列替代必要脱敏或登记新的标识。

同次调用在内存累计已经结束的阶段：Runtime 锁等待与持有、journal 扫描、候选校验、持久化、来源读取和原专业接收。已存在的 Hook 决策记录可带 `call_phases`，以阶段路径、调用次数和毫秒累计值表达；原生接收的既有观察在调用结束时追加，避免只记录接收前的耗时。S7～S9 只计量实际最小接收工作，旧 Git／来源证明耗时用于迁移诊断，不将其恢复为必要阶段。`doctor`／`health` 从同一 outbox 展示这些数据，不在被测路径另取 metrics 锁、不新增阶段日志，也不向普通工具调用输出计时提示。嵌套阶段有重叠，不能把各段总和当作墙钟时间；没有完成的 span 不进入统计。

来源读取次数表示逻辑调用，不能直接当成 Git 进程数。原计时分别呈现实际 Git 调用、固定对象复用、目录读取和分支核对；自动门、selector 来源准备、转换预检、锁内校验和具名 action 则帮助定位预算落在哪段。用同事件、责任和提交结果对账，不以最后报错的 action 名称推断它独占整个预算。上述 Git 计时适用于仍有实际消费者的其他阶段或历史实现；S7～S9 新链不运行这些检查。

计时记录说明实际测到了什么。平台先终止进程时，可能没有末尾审计或计时，不能补写一次 `timed_out=true` 冒充原进程观察。需要结合平台日志、原消费者回执、pending 与指标定位。采样与日志有助于找责任，不替代测试结果、独立判断或人的决定。

## 12. 接线怎样验证，哪些工具不能误读

### 12.1 验证层次分别回答不同问题

| 验证层次 | 应覆盖的内容 | 不能代替的证明 |
| --- | --- | --- |
| 静态注册与安装检查 | 事件、matcher、路径引号、超时、安装位置、策略声明 | 真实事件确实触发并投递 |
| 输入与渲染测试 | 实际字段、嵌套结构、退出码、stdout／stderr 分工、合法 UTF-8 | Claude 接收了对应上下文 |
| 公开消费者测试 | 准确引用、同角色并发、本人产物、重复 Stop、Main／Worker 分离、真实缺源 | 一个真实模型完成了专业工作 |
| 配置命令的进程测试 | 从 settings 命令到二进制、stdin、输出及退出的实际边界 | 角色加载、后台返回与同会话继续 |
| 真实 Claude 隔离测试 | 实际版本、触发事件、前后台与恢复、收到反馈的会话 | 目标产品已通过独立质量验收 |

真实平台测试必须记录执行器版本、实际转录、Hook 输入与输出、退出、专业接收回执及接收会话。特别要确认准确题目是否到达 Worker、Stop 反馈是否到达本人、Main 是否收到应由其处理的交接；stdout 有字不是接收证明。用模拟答案测试接线时，应明确没有执行产品建设与独立产品判断。

### 12.2 当前 smoke 与诊断入口的限制

[platform smoke 脚本](../../tools/claude-hook-smoke.sh)检查静态注册、已知的 match-all／MCP-wide matcher 形式和直接 Harness 进程，并检测 Claude CLI 安装；当前认可 `*` 注册，按 PostToolUse 30 秒、其他已注册事件 10 秒核对预算。它不启动真实专业会话，也不执行完整客户端 matcher 引擎；未知 matcher 形式需要实际平台证据。安装检测或直接进程通过仍不能证明真实事件触发、同 actor 继续和反馈交付。

`doctor` 处理静态结构和约定，`health` 提供累计运行信号，`ready` 只读诊断当前质量条件。它们各自有用途，不互相充当“实际 agent 已收工”的证明；普通继续不需要反复运行全套诊断。

删除旧 `dry-run --fixture` 兼容入口及其专属测试；当前只读诊断按 `ready` 的实际结果说明质量条件，不模拟 Hook，也不作为 Agent 开始或结束条件。

## 13. 修改接线时需要共同维护什么

新增或改变事件，应先说明具体消费者、为什么现有事件不够、实际输入是什么、输出发给谁、能否影响继续、故障时保留什么、正常成本是多少。然后同步注册与安装、输入字段、路由优先级、专业消费者、输出适配、审计与验证；不能只加一个 matcher，就让角色或作者承担未说明的机制。

| 维护面 | 实际入口或约束 |
| --- | --- |
| 注册与安装 | [settings](../../settings.json)、[模板检查](../../internal/migration/templates.go)、[策略事件声明](../../docs/control/hook-policy.json) |
| CLI 和根解析 | [run.go](../../internal/cli/run.go)、[workspace](../../internal/workspace) |
| 原生责任 | [native_s6.go](../../internal/cli/native_s6.go)、[native_s9.go](../../internal/cli/native_s9.go)、[native_review_hooks.go](../../internal/cli/native_review_hooks.go) |
| 进度与恢复 | [controller.go](../../internal/cli/controller.go)、[projection.go](../../internal/cli/projection.go)、[运行控制面](L4-runtime-control-plane.md) |
| 输出与继续反馈 | [pretooluse.go](../../internal/hook/pretooluse.go)、[adapter.go](../../internal/hook/adapter.go)、[lifecycle.go](../../internal/hook/lifecycle.go)、[mainstop.go](../../internal/hook/mainstop.go) |
| 提示与实际集成提醒 | [progress.go](../../internal/hook/progress.go)、[worktree.go](../../internal/cli/worktree.go) |

旧策略、兼容 adapter 和仅供旧协议的恢复命令连同注册、调用、测试与操作材料一并移除；当前接收、转换和真实故障恢复由唯一现行链承担，不让旧身份链、激活或全事件门禁重新出现。

本机制承载 L1 的自然路径、可执行反馈与有限约束。判断接线是否正确，应看当前责任能否在真实平台上获得准确材料、完成专业工作、由原消费者接收，并在失败后回到正确的人或执行继续。不能以一个合法 JSON、一张事件表或全部 handler 都返回 0 代替这个判断。
