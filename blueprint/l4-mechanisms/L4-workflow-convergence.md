# L4 工作流边界与收敛设计

## 1. 目的、适用对象与设计依据

框架的价值是辅助 Agent 充分思考，以真实产物、明确检查和独立判断兜住质量下限，使功能能够连续、快速地迭代。它应发挥航空飞行前检查单的作用：在合适时点提醒容易遗漏的问题，指出检查对象和判断依据，发现问题后交给明确责任人。检查单的价值来自减少实际遗漏；填满字段、增加签收步骤或运行更多检查，不能单独证明质量提高。

本篇承接 [L1](../l1-principles/L1-design-principles.md) 的产物引导、必要约束、成本和收敛原则，约束跨阶段机制的取舍、交接设计及验收结束条件。消费者是框架设计、实现和审查人员；维护决策写入已有任务说明或 PR 描述，不新增产品答卷、维护状态机、例行审批或逐工具许可。

只有原则而没有取舍规则，整改就容易形成循环：发现断点，增加适配，再为新适配补提示、恢复和验证。为此，机制的准入必须同时回答它改善哪项专业工作、避免哪种具体遗漏，以及带来多少执行和维护成本。当前实现中存在一个分支，不自动构成继续补全该分支的理由。

本篇统一定义“不猜测”、机制成本、整改范围与收口规则；[手续收敛](L4-procedure-reduction.md)定义作者交互，[指引分层](L4-agent-guidance.md)定义内容归属，[Hook 接线](L4-hook-platform-wiring.md)定义事件实现，[验收清单](L4-hook-acceptance-checklist.md)提供验证方法。各篇引用这些边界，不再各自扩展一套收敛标准。

Blueprint 是实现方案的约束和取舍依据。“先更新 blueprint”要求先完成设计推导；不能先选定局部补丁，再将其写进 blueprint 作为依据。每项改动都应说明它承载哪项现行设计义务、为何由此处负责，以及与其他载体组合后怎样完成阶段工作。引用了设计文档、修改了所有相关文件或通过了局部测试，都不能单独证明方案忠于架构。

## 2. 支持的工作主线与保证边界

### 2.1 从专业责任到明确交接

对每项专业责任，主线是：取得目标和必要材料，思考或执行，保存真实产物，完成适用检查，获知接收结果及下一责任。S0～S11 组织专业工作的时序和独立分工；内部状态、文件和事件仅在支撑这些工作时保留。

这不规定每阶段只有一个文件、每个任务只有一个动作，或所有工作都能合并为一份答卷。不同作者、判断、产物和真实时序可以独立存在；同一事实不要求作者重复登记。阶段未完成时可以继续合法工作，领域出口是否合格由对应消费者判断。

| 职责 | 框架应提供的支持 | 保证边界 |
| --- | --- | --- |
| 辅助思考 | 当前目标、适用材料、关键问题、判据、边界和风险视角 | 代理承担推导和调查；模板不预填专业结论 |
| 守住质量下限 | 明确专业问题、必要的答卷结构、适用的独立审查和真实授权 | 作者对观察、检查与依据负责；框架接收不证明其专业结论为真 |
| 记录与交接 | 原责任的输入、实际交付、接收结果和明确接手人 | 平台启动、交付接收、Main 集成与阶段完成分别认定 |
| 处理故障 | 保留已成立事实，交付具体原因和受支持的原恢复入口 | 依实际触发者恢复；没有执行者时不承诺自动续跑 |

### 2.2 “不让 Agent 猜”的准确含义

| 问题类型 | 应怎样处理 | 判定例子 |
| --- | --- | --- |
| 系统协议 | 提供准确路径、字段形状、接收入口、当前责任及可执行下一步 | 需要读源码才知道答案外层结构，属于必须修正的缺口 |
| 专业判断 | 给材料、问题和判断依据，允许调查、选择和有据的不适用 | 如何划分模块、哪些场景受影响，由作者判断；系统不伪造答案 |
| 上游决定或环境缺失 | 说明缺项、影响和接手责任，保留实际未知 | 缺必要授权或运行环境，不能靠补一个 PASS 继续 |
| 未支持能力 | 明确适用范围和限制；新能力单独评估 | 无跨进程执行者时只能证明重新进入可恢复，不能承诺无人触发完成 |

“没有 gap”指已承诺工作路径的信息、机制和交接一致，不要求覆盖所有理论平台组合或预先回答所有业务问题。现有承诺内的故障不得事后改称不支持；必要专业未知不得伪装成系统已知事实。

### 2.3 检查单怎样帮助思考

问题应指向真实工程失效，并要求可供下一责任使用的判断与依据。适用视角包括：

| 思考视角 | 应帮助作者回答的问题 | 所需依据 |
| --- | --- | --- |
| 目标与边界 | 改变什么行为，哪些约束和已有行为必须保持？ | 原需求、真实场景及明确范围 |
| 方案与关系 | 为什么采用这个方案，涉及哪些提供者、消费者和共享约束？ | 设计取舍、实际契约与实现关系 |
| 失败与恢复 | 正常、失败、中断和边界条件下，用户或下游会观察到什么？ | 适用场景、不变量与具体失败后果 |
| 验证与反证 | 怎样发现方案不成立，预期观察是什么，哪些仍未验证？ | 可执行检查、实际观察和证据范围 |
| 交付与剩余责任 | 本人完成什么，尚缺什么，谁能继续处理？ | 真实产物、接收结果及具体接手责任 |

这些视角按本次责任选用，不能变成所有作者都要重复填写的固定五份材料，也不按答案长度或发现数量认证深度。专业工作已有充分说明时直接引用；新增问题应补足真实遗漏。结构检查核形状与必要依据，专业审查判断推导是否成立；两者分别承担责任。

## 3. 机制取舍与总成本约束

### 3.1 优先消除不必要的依赖

提出修复时先检查：能否删除无人消费的步骤，合并同一事实的重复生产，或直接复用平台和原领域消费者。剩余的真实缺口再作局部修复。新增状态、证明、索引、缓存、适配器或恢复层，必须说明为何上述方式不足，并定义来源、失效、消费者和失败后的执行归属。

“保持质量要求”不等于永久保留实现它的每一道内部手续。专业责任、必要的真实批准、可靠保存和已接受事实须有明确承担者；它们不要求系统重复验证来源、代做独立判断或逐项重算证据。重复校验、兼容封套和派生状态应删除或合并；削减机器核验会改变系统可证明的保证，应明确交给谁判断，不能宣称保证完全不变。

不得把“没有登记、没有引用、没有成为交付物”反向解释为禁止存在。门禁须对应具体质量义务和实际失败后果，不能仅因现有检查无法分类就要求作者补引用、补提交或删除工作副产物。已确定用途和责任边界的私人检查产物，与产品修改、正式交付和引用证据分别判断：辅助产物不必全部成为证据；被引用的证据仍须真实可用；产品变化仍按原范围、来源和实际检查接收。产品干净判断不单独授权删除文件，后续回收沿原责任和实际清理授权，不再以“全部文件必须被引用”为前提。

| 拟议措施 | 采用条件 | 应优先排除的替代做法 |
| --- | --- | --- |
| 增加提示或字段 | 提供当前责任缺失的必要问题或信息，明确原来源和消费者 | 复制整套协议；让作者抄机器字段；用文案承诺尚不存在的操作 |
| 增加自动化 | 消除已证实的重复操作或遗漏，总执行成本可接受 | 为减少一次操作而维护第二套执行生命周期 |
| 增加缓存或并行 | 真实测量说明瓶颈，准确输入与失效边界可验证 | 用缓存结果代替当前写入资格；并行修改同一权威状态 |
| 增加恢复能力 | 对应受支持路径的具体失败，原事实可识别且有人执行 | 为想象中的无限故障组合建立通用协调器 |
| 旧接线 | 删除已被现行责任链取代的旧入口、适配、消费者、格式和测试；实际用户与专业事实保留 | 为继续运行旧协议而扩建适配层、重复 Writer、回执或额外门禁 |
| 增加强制约束 | 存在明确风险，清晰指引和可判定检查仍不足 | 用禁止普通工具、反复确认或等待许可弥补接线问题 |

### 3.2 同时核算作者、运行和维护成本

成本至少包括作者的阅读、填写、命令、等待与返工；Hook 的读取、校验、锁等待和预算；维护者需要同步的权威来源、有效投影、分支及验证范围。少一个作者动作却显著增加后两类成本，不能直接称为减负。成本比较使用同一合法任务及相当规模；不得通过减少必要覆盖或制造额外作者步骤换取更好数字。

不设统一行数、文件数或状态大小上限，它们只能辅助诊断。实际约束是：同一规则有明确权威，同一责任在一次响应中只生产一次交付；普通观察不遍历无关历史、不重复接收产物；故障恢复只补未完成部分。新增机制需要带来可解释的净收益；涉及可靠性取舍时说明收益及代价，不能只展示功能增加。

### 3.3 Hook 的职责与自动化边界

Hook 在自然事件上交付必要上下文、调用适用消费者、投影实际结果。阶段门围绕原专业产物和资格工作，普通工具不因阶段未过而失去权限。平台负责子代理创建、运行、消息和继续；Main 负责分工、长检查、集成和异常交接；Writer 维护原权威事实。

已承诺的一次交接需要明确本次应完成到哪里：适用时接收、转换并准备下一材料；失败则保留已成立部分，给实际接手者原入口。不能用无关 Read、重复保存或唤醒已履职 Worker 来制造下一事件。也不能为了让十秒事件包办一切，把长检查、合并和通用调度移进 Hook。具体预算及当前接线仍由 [Hook 设计](L4-hook-platform-wiring.md)定义，本篇不扩大其能力声明。

**S2／S3 原题准备失败的显示边界**：进入阶段时沿原系统入口准备 Main 的题目；具体来源不可用时保留前一阶段已收事实，将实际失败及原恢复入口交给 Main。正常自然事件继续按原 issuer 保守重试，真实修复或 Git 提交后在同一事件交付已准备的原路径；不新增作者提交、专用触发动作、工具限制或来源证明。

同一会话中相同准备失败可以折叠的前提，是能确认该失败已成功交给本人，并能安全复用已有显示状态。仅按会话或 Agent 推导的缓存路径、文件名或内容格式，不能证明路径是框架创建，也不授权覆盖、删除或读取其中的未知用户文件。现有会话提示槽位没有原 Writer 的所有权登记，不能安全用于新增 Post 去重；现有失败诊断保存的是最后尝试，不证明提示已经送达。平台 stdout 写出本身也不会跨独立 Hook 进程保存送达事实。不得借此新建文件、扫描会话记录、追加 Git 操作或以缓存作为接收／阶段门。

因此当前保留原 issuer 的保守重试与完整可见提示，重复显示和重复计算如实作为未解决成本，不声称已减负。真实来源修复或 Git 提交后仍须由自然事件在同一响应交付原路径；缓存缺失、损坏或所有权未知不挡重试。将来若有平台原生、可证明已送达且不增加作者负担的安全会话状态，须从真实 Hook 验证首次失败、重复 Pre／Post、修复和提交后的同事件成功、状态不可用及输出失败；不得以禁止工具、手工提交、追加门禁或伪造成功换取去重或测试通过。

### 3.3.1 S7～S9：以原答卷接收和最小分流收敛

本节是 S7、S8、S9 的现行目标合同，不是描述现有代码已经完成。阶段专业工作及批准继续存在，但框架不再为接收每份答卷另行证明作者的工作。三阶段使用同一接收链：**原责任和本人答卷 → 自然事件观察 → 原消费者一次检查和保存 → 读取已接收结论 → 自动交给下一责任或准备下一阶段**。模板、Skill、brief、Hook 和答卷分别承担第 4.3 节职责；不能为简化消费新增 Main 证明答卷、补交动作或独立收据表。

| 环节 | 最小职责 | 不再作为接收或转换前提 |
| --- | --- | --- |
| 责任和材料 | 派发时提供现有责任、可读材料、本人原答卷路径和下一步；从已有派发／责任关联定位当前答卷 | 要求作者抄机器身份、返回路径、注册 worktree 或提供额外来源证明；按角色、模糊文本或唯一候选猜责任 |
| 答卷就绪 | 仅读当前责任原卷；检查能否理解本卷既有必要表达及作者已填写的专业结论；未表达可交接判断时保留草稿 | 新增 done／ready 标记；递归读其他责任、检查 Git 状态或 ignore、扫描产品树、重读证据、比对文件哈希、重算 Claim 覆盖或专业结论；字段非空不证明专业正确 |
| 接收和进度 | 原消费者将本次接受的内容及现有责任的接收结果可靠保存一次；同一交付重复观察不重复接收或转换 | flat／typed 多份原卷、第二套 Candidate 证明、强制逐文件摘要或新作者字段；读取已收事实时不依赖私人文件仍存在或字节未变 |
| 阶段分流 | 仅使用当前已接收答卷中直接表达的结论、原计划中仍需完成的责任和已有真实批准，作必要的有限状态判断 | 再由旁账重算 CleanRound、ObservationBatch、完整证据有效性、作者独立性或自动证明修复；不因未引用或无法归类的副产物设反向门禁 |
| 失败和后继 | 尚无可理解的交接表达则保留草稿；错误、blocked 和未完成按实交接，有实际必要缺项反馈准确题目和责任；已接收后后继准备失败，保留接收事实并由既有入口续未完成部分 | 用额外提交、重存、再 Stop、普通工具禁令、等待人工逐项许可或更长 Hook 超时换取接收；将 blocked、工具错误或 pending 伪装为 PASS |

自然事件先根据已有实际派发、原责任和当前可用的平台输入定位适用对象，再调用其原消费者。处理器确认与本事件无关时继续交其他适用入口；已有旧 route、brief 或阶段状态不等于该事件已处理。已有派发关系明确包含多项本人责任时分别接收；仅有多个路径共现而无法区分背景和当前责任时保留未知，交 Main／系统，不要求作者补身份或重存。Start 没有完整任务且已有关系不足时只给中性提示或静默，后续自然事件再按实际任务定位；不能按角色、当前阶段或唯一候选猜专属指引。已发行的 S7、S8、S9 原责任在阶段变化后真实晚到或本人自然继续，仍沿原关联接收；结果按原对象交 Main 判断，不充当新责任的结论。局部责任未知不能吞掉其他已明确责任；共享 Runtime／journal 的实际故障按原写入能力如实处理。

就绪检查不得发展成对字段内容的专业推理：枚举和结构为消费者能够理解并分流而设，不根据某条检查的失败自动推翻作者对其他责任范围的结论，也不由机器猜测因果、独立性或修复充分性。答卷中真实失败、未执行和 blocked 必须能如实表达；作者与 Main 负责解释其对当前责任和全轮的影响。必要结构只限于理解本人结论、定位原责任和有限分流，不能把题面所有栏目或专业义务变成机器必填。作者已填写可理解的专业结论或本卷既有必要表达，即按原消费者接收；非关键缺项、检查失败或未知不构成拒收理由，按实交给下游。没有表达判断的空值通常保留草稿；明确的“无／不适用”按作者原意交接。S9 原 Impact 的空数组兼有合法无变化与默认模板两种可能，按下述明确取舍接收，不推算 PASS。模板与 brief 说明既有表达会被自然事件观察，不新增结束语、ready 字段或填写顺序来证明作者心理。

S7 接收 ReviewPlan 与各 Reviewer 的原答卷，按原计划的必要责任是否已有结论和实际发现分流：适用责任完成且无 Finding 进入 S10；有真实 Finding 时将已收发现与未完成事项交 S8，普通情况下 Main 可继续安排安全可执行的检查，P0 可立即停止危险工作；环境受阻交 Main 处理。已派发的 S7 责任在进入 S8 后仍可用已有派发关联接收本人晚到原卷；新发现交 Main 决定补充当前调查或安排后续处理，既有批准不被自动改写，不另建晚到账本或重开 S7。这里的少量完成状态与结论判断是路由，不是重新计算覆盖或额外产出 CleanRound／ObservationBatch 证明；必要 Finding 内容可由已接收答卷直接交接。S8 接收 Investigator 与 Main 的原专业答卷，由 Main 判断因果、未知和处置；答卷提出的新假设只是建议，不自动签发责任或成为出口门槛。需要实际人批准时记录真实决定并关联其对象；批准不由模型代填，也不触发对全部证据的再次机械认证。S9 接收本人 Plan、Result、Main 原影响判断和独立 Targeted 原答卷；Plan 独立接收后作者连续工作，Main 完成实际集成与必要检查，Targeted 通过后准备新的完整 S7。结果 blocked／未完成时按原答卷交 Main，不伪造 Result、Final 或阶段完成。修复后的 S7 仍是完整新轮，S9 的局部复验不冒充干净轮。

**空 Impact 的明确取舍**：`change_types=[]`、`decisions=[]` 可沿 Pre、成功 Post 或 Stop 按当前原卷直接接收，即使无法区分系统预置模板与 Main 已判断的无变化；不要求精确保存事件、改写 `null`、新标记、重存或额外说明。允许可能提前接收或准备后继，放弃机器保证“绝不误收模板／绝不提前推进”。空卷只表达所观察到的内容，不证明 Main 已完成集成或检查、所有 Builder 已交付、Targeted 已执行或阶段已完成。实际工作和适用独立复验由 Main 与对应作者承担，沿原流程自然安排；不为机器区分作者心理新设完成信号或阶段前置。原 Impact 责任仍在进行时，自然事件继续观察其当前原卷的更新，保留先前接收并更新当前可用判断，不要求再次保存旧内容；责任结束后才快速返回。是否仍需观察依据已有 Main 原责任、在途 Builder 和实际专业流程；空卷已收、`impact_ref` 已存在或阶段切换均不能单独认定更新结束。已有信息不足时优先允许该原责任自然更新，接受额外观察成本，不要求作者登记活跃状态、另开尝试或证明结束。此必要观察有成本，但不新建状态表或将其扩展为所有已收卷的历史重读。

对仍需自然观察的原 Impact，系统以同一原消费者的专业语义比较当前原卷与其当前已收对象：覆盖作者可改变且实际保存的全部专业内容，包含变化路径、影响处置和说明；消费者已有缺省与等价 `null` 按同一语义解释，不以机器生成的 ID、时间或 Runtime revision 判作新判断。等价只跳过重复接收与写入，实际未完后继仍沿原入口继续；确有新表达则接收并保留先前事实。自然观察可各读取当前原卷和该责任当前已收对象一次，不遍历历史；实际并发冲突或恢复慢路径可以重新读取，须记录成本。已收对象不可读时保留已收事实和比较未知，不能转嫁为作者补交；必要时接受当前可理解内容及一次可能的重复接收。并发由系统复用原 Writer／事务协调，版本变化或文件创建冲突时重读当前事实与原卷并安全接续，不让较旧观察覆盖已经接收的新判断，不因冲突要求作者另做动作。原卷写入不受 Writer 锁控制；观察后新编辑可能等下一自然事件才接收，不能宣称无人自动监听的绝对实时保证。

早期 Impact 不关闭尚在途 Builder 责任；后续贡献继续按原责任交 Main，Main 在原责任内自然更新影响判断，不能因旧 `impact_ref` 固化空判断，也不能将旧判断替后续贡献背书。可提前准备或派发后继，但不把准备、空卷或 Candidate 齐全投射为未发生的专业工作。无法以机器验证实际工作是否及时完成是本方案接受的代价，由专业参与者与实际复验处理。

**S9 Targeted 到新 S7 的最小合同**：独立验证者只需在本人原卷表达可理解的总体结论，按已有原责任经 Pre、成功 Post、Stop 自然接收；实际复验与必要观察仍由作者承担，但单项观察、引用或可选原因分类缺失不应拒收本人结论。`fail` 没给出原因时是失败且原因未知，交 Main／S8 判断；系统不默认 `fail_same_cause`、不猜因果，也不强迫补分类来换取交接。`blocked`、未完成及实际新结论按实交接，旧结果不冒充恢复。

有限分流仅看原计划中实际适用的独立责任及本人已接收的直接结论；已取消或被真实替换的责任不因残留 owner 被要求 PASS。适用性未知交 Main，不补造取消证明或新增等待门；已知仍需履行的独立责任继续。原答案保存一次，必要时在当前 Targeted 引用行保存系统内部可选的 `performing_assignment_id` 与 `result` 以供分流；它们不是作者新字段、额外证据或机器认证。使用当前 Runtime schema 和当前消费者，不保留旧版本 schema、兼容解码或读取旧摘要的并行接线。

当前机制中仍需履行的已派发责任按其已接收事实与原关联接续；缺直接投影时按需读取该责任已保存的领域报告，不在普通事件重扫历史。材料不可用时保留已收事实，向 Main 说明具体未知，不伪造 PASS、不要求已履职作者重交。Targeted 只表达当时判断，Impact 更新或 Builder 晚到不改写其历史，也不自动宣称其 PASS 覆盖后续贡献。Main 按实际变化决定后续，不以摘要、新字段、强制新尝试或等待全部 Builder 设门。

最后适用的已收 Targeted 结论具备原出口条件时，系统自动接续 Handoff 与完整新 S7，沿当前事实准备原 ReviewPlan；不要求作者创建或提交 Handoff。Final、Changeset、Git 状态、证据摘要和历史认证不是后继资格，也不为兼容旧流程生成或读取其证明投影。Handoff／seed 使用当前消费者、类型、schema、转换及 S7／S10 交接。Targeted 已收而下游准备失败时保留事实，只续未完成部分；具名原入口仅供实际故障接续。

某次 blocked／未完成交接已收，不等于该专业责任结束。S7～S9 均从 Main 已有继续安排，或明确仍属原责任的本人自然继续，接上当前新尝试；本人在原未完成责任内继续无需 Main 另作强制动作；保留历史已收内容和后继，不能把历史 receipt 当成新尝试已收，也不能把私人文件任意变化当成新责任。未完成责任已自然继续时，后续自然事件观察当前原卷；内容仍是原交接时不重复接收，出现新的可理解结论时保存为本次新交接。此时的必要观察计入总成本，不要求作者恢复证明、resume／submit、复制身份或重存旧答案。已收且责任已结束、无新尝试与未完后继时快速返回，不再读取原稿；责任不明确交 Main，不猜选。

S8 的 `inconclusive` 只表示本次调查结论未决，不能单凭该值断言本人未履职或要求继续调查；本人是否结束由既有责任及实际交接判断。已收结果可从原回执继续，私人原稿丢失不撤销接收；真正仍需的调查交 Main 或本人原责任自然继续。S9 可理解 Plan 不因非关键 red check、证据引用或 proposed paths 缺项而拒收；实际前检仍是 Builder 专业责任。真实 blocked／contract_conflict Result 无须先接收 Plan，即可交 Main。

可靠写入的实际事务冲突或状态损坏属于系统故障，必须保留现场并处理对应写入；不能伪称成功，也不把它包装成作者须补专业材料或重交已收答案的门。普通观察不以完整历史恢复或重新认证签发／来源为前置。

质量门是否有定义与是否需要证据槽是两件事：已由当前原结论或责任进度实现语义的门可以没有证据要求。目录不得以空证据集合认定该门无定义，也不能要求作者补一份证明；当前出口仍按原有限条件判断。未实现的门应如实报告系统故障，不伪造通过；其他阶段目录问题不得作为当前出口的前置或转嫁为当前作者的专业缺项；仅当前出口实际需要的未实现语义报告系统故障。S0～S6、S10～S11 的既有专业规则不因此改变。

可靠保存、并发下不覆盖已收事实、重复事件幂等及实际下一责任是系统内部最低限度的执行语义，不是新增作者步骤，也不要求每次普通事件重验历史、重做来源捕获或运行完整事务。只处理本次已识别责任和其原答卷；不相关事件与责任已结束、无新尝试及未完后继的事件快速返回；活跃 Main Impact 按上述例外观察当前原卷。实际后继准备、真实集成和专业检查可能需要进一步工作，必须与答卷接收分别描述；没有执行者或后继事件时不承诺无人自动完成。接收成功或 Hook exit 0 不代表专业事实、业务检查或平台消息已经被独立证明。

此取舍将来源可信、真实执行、覆盖充分、证据仍适用、专业独立和结论正确交给作者、Main 与适用的真实审查，而不是声称框架仍逐项验证。接收内容必须保留为当时的事实；作者后来修改私人文件不自动改写旧事实，新内容按该责任原修订、返工或尚未完成责任的新尝试处理。批准、独立复验和 Main 的实际集成各有不同专业意义，不能把一个 Builder 的成功答卷冒充它们；是否适用由阶段责任和真实决定承担，不为此建立平行的机器证明链。

**成本与可执行验收**：无关事件不打开任何答卷或运行 Git；准确关联且未收的事件最多读取并解析当前原卷一次，不打开其他责任正文、不读取引用证据、不执行 Git/status 或对答卷、证据及其来源的 hash 认证，不在 Pre 和后续消费者分别重复相同验证。未表达可交接内容或 JSON 尚未写完整的草稿保留原样，不能每次保存都生成错误报告；已有可理解结论即按原意接收，不承诺知道作者是否尚想编辑。责任已结束且无新尝试、无未完成后继的重复事件仅读已知接收状态并快速返回；活跃 Main Impact 观察当前原卷更新，不重读历史；原答卷缺失、被 ignore、已暂存或后来被修改不撤销已收事实。首次实际接收才进行必要持久化；状态、回执和后继不要各自保存同一专业正文的完整副本。

最后一个必要责任接收时，可以读取本轮原计划已有的必要责任状态和直接结论一次，决定去向；不得为每个普通工具调用或每份新结果反复全轮扫描。下一阶段实际需要的题目或入口按原接收内容准备，不得新增 Batch／CleanRound／来源索引作为准备资格。可靠写入可使用既有锁或事务，不要求固化某种存储方案、hash 算法、重试次数或新增后台进程。Hook 所在的接收、Writer、事务恢复和后继均不计算、登记或校验散列；不得将同一用途改名为 fingerprint、checksum 或换用其他散列算法。原事务采用已有责任、实际内容和内部版本协调，不以散列作为写入配对或恢复条件。可靠性按正常可读、并发不覆盖、进程中断接续及适用历史继续分别验证；单文件损坏、整份状态丢失或历史防篡改不自动由旧全量快照推成永久保证。需要的灾损恢复须说明实际故障、可恢复事实、允许损失和代价，比较必要最小存储，不保留无人消费的历史副本。

同一权威 state／journal 中尚未完成且无法判定的 pending 是共享控制面故障，Writer 不能任意跳过后继续追加；由系统／Main 沿原入口恢复，普通专业工作继续，不要求作者重交，也不承诺损坏现场绝不阻塞写入。旧证明与无关历史不是新责任资格。

验证应记录同一完整任务从草稿、首次接收到 blocked 后继续的总事件数、原卷读取次数和字节、JSON 解析、Git／证据访问、锁等待及 Hook 墙钟，并对无关历史、平行责任数量增长比较；单事件只读一次不能证明整项任务最优；还须测量高频草稿观察与长任务的累计代价和日常工具延迟，优先减少无关初始化与重复工作，不以缓存掩盖错误接收状态。不得靠延长 Hook 预算、要求额外作者动作或取消必要的专业任务取得好数字。这些是目标及可观测验收，不宣称当前实现已满足。

实施前按第 4 节列出各阶段及共享机制的入口、模板、指引、原答卷、消费者、转换和恢复；删除被取代的旧接线、旧入口、旧格式与兼容适配，不保留新旧两套流程。保留实际专业记录和用户数据；同一现行机制中已经派发但晚到的责任由当前唯一接收链按原关联处理，不将历史版本协议继续作为运行时义务。

### 3.3.1.1 S7 Finding：原观察进入、接收和交 S8 的合同

进入 S7 的 Reviewer 接到本人责任、原 ReviewPlan、实际材料和本人原题，只做真实观察并填写原答卷。已有发现时表达本人预期、观察、可获得的现场和不确定性；未执行不能写成通过，无法复现就如实记录，现场缺失也如实说明。一个已收 Finding 可交 S8；无 Finding 时沿原已完成责任进入 S10，未完成和 blocked 交 Main。不得要求作者为接收附加证明、重新执行危险动作、编造可复现结论或额外提交。

各层共同组成一条链，职责如下：

- **原题与视图**：在本人实际填写处给出简短、可理解的 Finding 示例和必要结论选择，说明现场细节可按事实填写、缺失可留空；示例不是必须逐项填写的模板。机器身份由既有 packet、owner、Claim 和原消费者关联，不让作者猜机器字段。
- **Skill**：指导适用的专业观察与记录方法，不复制 schema、创造额外答卷或接收条件。
- **Schema 与解码**：识别必要的本人结论及原责任关联，允许无关扩展、真实无法复现和未知等专业表达；可选字段、字段拼法和枚举不得把已有真实观察变成拒收理由。不能把未知值猜成已复现，不新增 evidence、现场完整度、摘要、轮数或额外签发门。
- **原消费者与独立 Finding**：自然事件消费同一本人原卷，按原责任接收；保留本人真实观察及未知专业扩展，包括 encounter 的自定义内容，再按既有原责任发布及登记 Finding。不能只放宽前端 schema、随后经 typed 重编码丢字段；不以重建模板、全文认证或作者证明建立新资格。
- **S8**：以实际登记的 Finding 原路径和身份取得 S7 已收原观察，保留无法复现、未知和未完成信息；Investigators 使用该实际内容调查，不能把 S7 格式整理或证据齐全当入口条件。
- **Hook**：PreToolUse 监听，原有成功 Post/Stop 兜底均交同一原消费者；已接收时沿原出口自然推进。本人卷字段错误、原来源缺失、已收回执异常分别反馈真实原因；不能把本人可修正字段误说成 packet/source/receiver 故障，不要求禁用工具或手动提交。去重不得隐藏实际失败或阻断自动恢复；重复提示成本须如实记录。

验收必须从真实原入口贯通，而不只验证单个 schema：自然写本人原卷后由 Post 或下一个 Pre 接收；用原职责与实际路径读取已收 Finding，再通过 S8 原入口读到同一专业事实及未知扩展。覆盖真实不可复现、未知的 encounter 子字段、空缺现场、相同答卷重放、真实 malformed JSON、原来源缺失和已收回执异常，分别验证反馈、原责任与阶段出口；不能以新增模拟门或吞掉原文换取通过。若后继未完成，应报告具体已通过与未到达的链路。

### 3.3.1.2 S8：晚到 Finding 进入当前调查的合同

**进入和选择**：S7 已转入 S8 后，原 Reviewer 的在途责任仍按原路径接收；原 Finding 及其 Runtime 关联是已收到的事实。S8 Main 从当前已有事实看见原 Finding，判断将其并入当前调查或留待后续；未选入不自动成为当前 Case 来源或阻挡无关工作。Main 在现有 `hypotheses.json` 的新专业问题中引用已接收 Finding，即是将其用于当前调查的明确选择，不再要求另填一份接收文件、复制证明、另作提交或重存旧答卷。不同机制是否一起调查仍由 Main 的问题和判别表达，机器不代判根因。

**接收、历史与并发**：原问题消费者接收这个选择；原 Case Writer 在注册新问题的同一原修订中把新选中的已接收 Finding 加入当前来源和未解释投影，保留既有来源、问题、已收 Investigator 结论、历史修订和原作者关联。原 Runtime 指针随该事务反映相同实际来源；同一已登记问题重放不重复增加来源或任务，竞争更新沿原修订与 CAS 重读／续接，失败保留原答卷和已成立事实，不要求作者重新表达。来源必须确为已接收的 Finding，未知来源交 Main／系统，不能以 SHA、轮数、全历史认证或附加证据替代实际关联。已获批准的真实合同及其历史不因晚到事实自动改写或撤销；Main 按实际影响选择后续处理，不能把新 Finding 冒充旧批准覆盖内容。

**分层和出口**：S7 负责本人接收及交 Main；S8 当前指引显示可选择的已收晚到 Finding 及原路径，并说明在原问题中选用或留待后续；原题只表达专业问题及其真实来源，原消费者和 Case Writer 维护修订及接线；Investigator 原题按其问题提供选中的真实 Finding；Main 的因果判断、合同和真实批准各自按实际内容接续。未选入的 Finding 保持已收可见，不通过反向门要求补写；实际纳入当前调查的 Finding 参与当前专业判断及必要出口，原既有结论不因增加来源而被伪造或清除。

**验收**：真实 S7 在 S8 创建 Case 后晚到一份 Finding；Main 在原问题选择它后，自然接收同一修订中可见新来源和新问题，已注册旧问题及本人结果保持；原 Investigator 可读取原 Finding。覆盖未选择保留后续、同答重放与并发竞争、未知来源、历史/批准不被自动改写及实际 S8 路由；不靠新增人工动作、放宽已有责任或更严格来源门使测试通过。

### 3.3.1.3 S8 Investigator 原责任绑定与自然接收

Main 基于原 Case 和具体 Hypothesis 签发 Investigator 本人责任；原 Writer 登记 Case、Hypothesis、Assignment、owner 及真实题目和答卷路径。Main 派发平台 Agent 时传达原责任与实际题目，Investigator 在本人原答卷表达真实调查并保存，原消费者接收；不要求本人补身份字段、额外提交、证明或重做一次工作。

平台事件和工程责任是两类事实：平台的 Agent tool call、子会话及其 Pre/Post/Stop 属于同一次真实派发；Runtime 原登记建立 owner、Case、Hypothesis、Assignment、packet 的关联。在已确认属于同一次真实派发的原任务中，完整 owner 和原 Hypothesis/Case 或实际原题／答卷路径可用于选取本人原责任，允许原根下正确相对路径和绝对路径。路径转抄错误不应抹去原任务中已明确的本人责任；普通后续消息提及另一责任的准确路径也不改变这次派发的归属。不能以角色名、前后顺序、相似片段、单独字符串共现或工具输出猜人；明确冲突、多候选和无法关联保持未知，不串责、不伪造结果。无需新建平台身份账本或将 platform agent_id 当作工程 owner。

原 Worker 的自然 PreToolUse、成功 PostToolUse、SubagentStop 沿本人原任务选取原责任并调用同一原消费者，已收后保持幂等；该平台 Agent 的真实完成返回可沿其原 tool call、原任务和子会话接续同一责任，不能凭其他 Worker 或一般 Main 输出代填。一般 Main 工具事件不扫描其他 Worker 原卷，也不新增全项目、Git、证据文件或摘要扫描。本人卷未完成时保留草稿并等待自然事件；字段问题、原来源失败和身份未明分别按事实反馈，已收状态只以原消费者和原 Case 事实为准。

验收从真实派发到原出口：分别用两个 platform actor 和不同 owner/Hypothesis 的已登记原责任，覆盖 Main 原提示中的错误转抄、正确相对路径、完整标注身份、Worker 正常 Pre/Post/Stop 与实际 Agent 返回，断言本人结论各自落原 Case、可查 receipt 且没有额外作者动作；覆盖多身份冲突、无法关联的中性事件、已收重放、源缺失、草稿与字段修复后自然重试。明确验证普通 Main 事件不扫描其他 Worker 原卷，记录正常监听和真实返回的读取次数与耗时；真实 Claude 及 sidecar 仿真与包级原入口测试各自报告，不以某一层绿灯代替全链证据。

### 3.3.1.4 S7／S8 原生派发、跟进与本人责任

**进入与唯一事实**：Main 从已登记原计划／Case 中选择原 Assignment、owner 和实际已发行 view／answer，通过平台真实 Agent 派发该专业责任；原 Agent 调用及对应子会话提供此次派发的因果上下文，原 Runtime packet 和 Assignment 确定工程责任。平台 actor 只是定位此子会话的坐标，不是工程 owner、身份认证或质量证明。原 issuer 在同一既有 Writer／锁／pending 下发布并登记实际路径，向 Main 显示登记结果；登记前中断留下的未知候选不提供为可派发原题，不按相同文件内容认领或覆盖。缺真实登记或来源时如实保留未知，不以未知阻断无关责任。

**S7 原派发引用和本人选择**：原 Reviewer 的真实首派发可直接引用已发行原 view／answer；在该原责任已登记的控制根或实际来源根语境中，指向同一已登记路径的正确相对路径和绝对路径都能定位原责任，包括原 Writer 登记的备用路径。原控制根和隔离工作根按实际登记关联确定，不能一概用当前 cwd 猜相对路径的含义。原路径识别须区分完整路径、正常引号及句末标点，不以相似前缀、文件名、另一个根下的同名路径或任意路径片段冒充登记引用。路径是已有责任的定位，不单独证明是谁完成了工作或证明专业质量。

真实首派发的路径若有转抄错误，但明确表达单一 S7 Assignment 与其 Claim，且该成对责任结合原 Plan／已发行 packet 能唯一定位本人原责任，仍沿该原责任和实际登记路径接收本人真实保存的原卷，不要求作者重抄路径、补 owner、重新提交或另做证明。在途旧 Plan 的已发行责任按该次原派发和已登记关联定位，不能仅因当前 Plan 不同而排除；原 Plan 不可确定且跨 Plan 有多个候选、明确存在不同责任冲突或无法唯一关联时保持未知。不能把专业上下文中任意 Assignment／Claim 共现、相似角色名、后续协调消息或最终回复升级成新派发。若作者实际写入的是另一责任路径，保留原文件及已收事实，不将该写入认作另一作者的本人结论，不覆盖或代填；将能确定的路径差异和未知归属交 Main／系统处理，普通工具和无关责任继续可用。

本人 PreToolUse、成功 PostToolUse、SubagentStop 与 Main 的真实 Agent／Task 完成返回使用一致的原派发责任选择：本人事件从同一平台子会话的真实原任务选择，Main 返回从该次真实 Agent 调用的原任务选择，再沿同一已登记 packet、owner、实际来源和原消费者接收或复用 receipt。后台仍在运行时不冒充完成；原 Worker 的返回文字、其他 actor 或一般 Main 工具输出不能单独改绑或代填。原作者卷可理解但有专业字段错误时由原消费者如实反馈；已收只续未完成后继，Finding 按本人原责任交 S8，必要责任无 Finding 完成按原出口进入 S10。此处不增加身份台账、额外作者动作、工具限制或历史扫描。

**本人工作与自然监听**：Reviewer／Investigator 在本次原派发内读取原题、进行专业判断并自然保存本人原卷；原 PreToolUse 监听，成功 Post 和 Stop 兜底均沿该派发与原责任交同一消费者。普通 Main 协调消息可补充同一责任的说明、材料和后续问题，但不构成一次新 Agent 派发；消息、工具输入／输出或本人末次陈述中即使含另一责任准确路径，也不能单独改变此子会话的 owner，或促使 Hook 代另一作者接收。真实多责任冲突、无充分派发关联或路径转抄不明时不猜归属，保留原卷与已收事实并向 Main 如实提示；普通工具与独立责任不因选择未知被禁止。

**真实恢复与新派发**：同一原责任的真实平台恢复继续原本人工作；确有平台支持的新派发或重定向，沿可验证的实际 Agent 调用、恢复关系、原 Assignment 和当前 packet 建立对应关系，不能只靠后续消息含路径推断。当前已观测的 Claude 子会话首个派发任务与后续 `origin.kind=coordinator` 消息是不同事实；真实跨责任 resume 的平台 payload 尚需用实测证据确定，不能把任何单一文本或元数据条件预设为所有平台恢复的判据。无法判断时保持未知，不能猜成原任务、另一个 owner 或已完成，也不要求作者额外登记、证明或手动提交。

**Main 返回与异常**：原接收事实、平台运行／返回状态、本人专业结论和后继分别表达。Main 获取准确已登记路径并直接交付本人；若派发路径与登记不一致，保留作者原内容与既有回执，沿原系统责任处理，不指示无关 actor 复制或代填。已发生跨 actor 写入不能仅凭 receipt 或路径相符追认为本人独立结论。S7 的 Finding 和 S8 的 Case／Hypothesis 均沿原作者及原责任接续，真实已派发的晚到结果不冒充当前其他责任；Main return 不以普通聊天内容冒充本人提交。

**实际接线与验收**：`internal/cli/native_child_transcript.go`、`native_task_transcript.go`、`native_review_hooks.go`、`native_main_return.go` 及 S7/S8 原 issuer、原消费者和 Writer 按上述因果事实共用选择规则；删去把“最近一条含路径的 user 文本”直接升级为新派发的接线，不增加身份账本、全文／摘要认证、工具禁令、第二答卷或作者手续。原入口覆盖至少两个不同责任及真实子会话：正常本人 Pre/Post/Stop 接收，同责任协调补充、误发含另一卷路径的普通消息及跨 actor 复制均不串责；真实可验证新派发／resume 保持可用，身份不明和多候选保持中性；覆盖候选占位、发行中断／并发、原 Writer 实际路径与 Main 派发一致、已收重放、S7 Finding→S8 和 Main return。保存平台 payload、本人原卷、原事件与 receipt 的实际证据；真实 resume 未取到证据时明确待验，不靠手造 transcript 宣称整链完成。

**S7 路径与转抄验收**：从原计划接收、实际工作组登记和原 issuer 发行开始，分别以实际原 view／answer 的相对、绝对和已登记备用路径派发真实平台责任，验证本人自然 Pre／成功 Post／Stop 及真实完成的 Main return 均进入同一原消费者；同时分别验无 Finding 到 S10、真实 Finding 到 S8 的本人内容和原关联。对原首派发明确单一 Assignment＋Claim 但题面路径转抄错误的情形，验证原 Plan 与登记 packet 可唯一关联时仍接收本人在实际原卷的表达；同一 Assignment／Claim 跨原 Plan 有多个可行候选、明确不同责任冲突、任意上下文共现和后续协调消息含他人路径均不得猜选或串责。覆盖正确路径周围的引号／标点、相似前缀和不同根、真实错误字段／来源、后台未结束、已收重放及两个 actor 并发；校验普通工具可用、未知文件原样保留，记录实际事件、原答卷、receipt、阶段出口和耗时，不能以单个匹配 helper 或手写 Runtime 代替原入口。

### 3.3.3 实际验证身份与不计数的接续

新工作不生成、不累计、不展示审查轮数、调查重入次数或剩余额度，也不以默认轮数、不同摘要、新引用或证据 hash 证明进展。继续调查、修复或验证由 Main 根据实际问题、用户要求和真实授权判断。相同材料仍可支持新的专业判断；S8 原消费者须允许非终态 `investigate_more` 后在原问卷接收后续决定，同答重放保持幂等，真实终态和原批准对象继续受保护。默认配置中的数字不能被推定为用户设限或同意；真实用户约束和已有真实批准继续适用。仅在会话中的限制不一定对自动消费者可见，不据此声称系统已独立核实全部用户意图，也不增加用户登记手续。

区分实际专业责任仍是必要的，但不用第几次表示。系统复用 S7 原 ReviewPlan 身份：同次计划修订、普通事件和故障恢复沿用身份；再次实际进入 S7 则形成新的 Plan 身份，即使产品基线相同也能区分。首次生成题面前须确定该身份，使实际进入、当前计划与题面路径在原提交和恢复中保持一致。S7 Assignment／Result／Finding 沿本人原 Plan 和责任关联，S8 沿原 Case，S9 沿原 Session，S10 原报告与 S11 原申请沿它们的实际上游报告关联。不增加 Agent 字段、答卷、登记、证明、身份质量门或第二套生命周期。

共享进入 S7 的转换与 S9 直接 Writer 均须承接这一关系：提交后重试复用已保存身份，未提交的候选不表示已进入 S7。固定转换标签、每次 Hook 重算的可变 Runtime revision 或改名后的数字都不能代替稳定 Plan 身份。使用原实际进入事件是可调查的来源；当前先准备 seed 再提交 Handoff 的具体事务接线和中断恢复仍须核实，不在此宣称已实现或锁定某种事件身份方案。实现应先核实原事务能否承担目标，再同步原生产者与消费者，不让作者补手续。

只保留当前统一责任模型、当前 Runtime schema 和一个接收／转换链；旧数字路径、旧格式 schema、旧消费者及兼容分支退出运行接线。历史业务与专业记录保留原样供理解，不承诺旧格式由生产链继续执行；若仍有同一现行机制中的在途责任，按实际原关联交当前消费者处理，不追加作者登记、证明或重新提交。

验收证明同基线独立验证不串绑、同次修订和恢复不产生新责任、共享转换与 S9 Writer 一致、S8 继续调查后的实际处置可达、当前机制在途结果可接收，S10／S11 不借先前 PASS 或批准覆盖新责任。检查旧轮数、旧格式读取器和兼容接线已从运行链删除；文档不作为实现或全链验收证据。

**身份、重放和真实决定的落实**：事件身份由当前 Writer 在锁内使用 Runtime、原阶段进入事件、已有责任及必要内部序号确定，重放沿已保存身份接续；需要组合路径或内部键时使用无歧义可逆编码，不散列、截断或依赖内容。S7 ReviewPlan、S8 Case／合同、S9 Session／Plan／Targeted 均使用当前实际对象、责任及修订，当前类型由消费者与 Writer 同步，不让作者填写或登记。删除旧格式 ID／路径兼容接线，真实历史材料作为数据保留。

同一已收责任的重复事件复用原事实并仅续未完成后继；当前责任确有继续或真实新表达时，只比较当前表达和该责任已收的必要实际内容，按照原修订或新尝试处理，不扫描历史或凭一次编辑猜出新责任。批准仍由真实授权主体针对实际呈现的合同／决定对象作出：原消费者保存真实决定及其对应的实际对象和修订，不另建证明；如原有内容实际变更影响决定，沿原流程取得新真实决定，不伪造继承。没有保存足够事实时如实标未知，不声称自动发现所有外部改写。

**全阶段共同交接合同**：S0～S11 的进入、本人交付和出口均以本节阶段表中的原责任为准，依次由既有进入事件准备题面与路径、本人自然工作并保存、自然事件定位已有责任、原消费者接收本人表达、原 Writer 持久化并续原后继。Main、Worker 和真实授权人各自只承担原本的专业工作与决定；模板／Skill／brief 说清本人工作和原路径，Hook 说明当前责任并观察，消费者理解原卷，Writer 管理已有事实与中断，阶段出口使用适用结论、必要工作和真实决定。各层不得各自追加完成条件。原已发行责任及晚到结果依实际派发和原关联接续，不因当前阶段变化被丢弃，也不替另一责任背书；实际关联缺失只对依赖该关联的交接表达未知，不使其他明确责任等待或要求补证明。

S4 Main 和 S7～S9 已知原责任的普通 PreToolUse 按各自阶段合同观察本人当前原卷，成功 PostToolUse 和平台原生交付事件按实际信息补充观察；S5／S6 Worker 由当前原生 Stop 接收，其他阶段沿各自当前自然保存／Stop 入口。所有适用入口通向当前唯一消费者，不因使用 Bash、编辑器或其他普通工具而要求额外提交、重存或特殊命令。Pre 只观察当时已有表达；失败 Post 不冒充保存；无明确路径的成功事件按当前已知责任观察原卷，不解析命令猜写入路径。未形成可理解判断时保留草稿；已收事实只续未完成后继，真实继续按原责任接收，不扫描无关历史或运行专业长检查。没有后续自然事件不承诺即时观察；真实读取或共享 Writer 故障沿原入口恢复，不让本人重交。

**检查事实与无摘要复用**：实际检查的执行、已收结果和复用决定各有原责任。Main 必须执行其原配置的实际集成检查；原 Worker 的显式复用仅适用于既有 profile 允许的闭合静态检查范围，不扩展到独立验证、Main 必需检查、fresh 或新判别假设。既有 shadow 策略只报告可复用的原记录而仍执行；明确启用的复用策略允许按原 profile 和责任使用原已收结果，不因为不能以摘要证明输入相同而一律改为运行，也不把 shadow 擅改成跳过。未找到相关已收记录或已有事实表明原记录不适用于本次实际责任／检查时，按原策略执行实际检查；真实失败仍为失败。本人或 Main 已明确要求重新检查时执行，不把历史结果冒充本次新执行或新 PASS。具体既有 profile 限定与 no-hash 复用规则见[工作区执行与检查 Profile §7](L4-workspace-execution-profiles.md#7-有限复用为什么必须很窄)。

旧策略 `same_input_same_responsibility` 中“同输入”的机器等价证明不再作为复用前置：系统只使用已知的原责任、实际检查及结果和原策略，不计算、登记或比较散列、Git OID、整树内容或逐文件字节来补证；输入是否发生未记录的外部变化可能未知，不能报告为已验证不变。明确启用复用即接受这一可见取舍，原结果仍保留其原时间、责任和结论；专业参与者依据实际工作和原策略决定是否需要新检查，不要求新增作者声明、认证或另一个批准。已收原记录缺失、不可理解或已知不适用只影响该检查复用，不撤销本人结果、其他已成立检查或无关阶段事实；实际需要而尚未执行的检查保持未完成，不伪造成功。实现同步 `internal/checkexec` 的既有策略、`internal/workspace` 的实际调用与收据，以及 Main 集成、`internal/mainreceipt`／`internal/buildsurface` 的下游消费；不能通过一律重跑或一律跳过伪装复用。验收从原检查入口覆盖 shadow、enabled、明确要求新检查、原记录缺失或真实不适用、实际失败、旧摘要任意值及调用方可见结果，并确认原结果没有被写成新执行。

收敛与验收覆盖整条路径而不只验证一个 helper：每一阶段从实际安装材料进入、本人自然保存、原消费者接收、原 Writer 持久化、原后继及已发行责任恢复；检查运行中的 Hook 及其直接/间接消费者、schema、状态、日志、pending、题目、提示、Sidecar 和运行观测均不生成或登记散列，也不以旧散列作匹配/拒收。分别核并发、事件重放、真实新表达、保存后后继失败、旧责任晚到、真实批准对象与缺材料未知。测试可记录既有历史数据但不得以散列作为验收前置；不靠禁止普通工具、延长 Hook 超时、人工提交或模拟批准换取结果。无 hash 不再单凭原路径和版本独立证明字节未被外部改动；实际责任人和原专业复验承担判断，未保存原内容时不得宣称可以恢复或识别任意篡改。

#### 全链实施边界：原入口、本人交付与原出口同时接通

本节是上述 S0～S11 目标合同的实施和验收安排，不表示这些入口当前已经符合合同。每条链均从真实入口沿原消费者、Writer、实际后继和恢复走到阶段出口，提示、模板、schema、诊断与安装投影同步；只删除某一个比较而让下一层要求补摘要，或仅把字段改名、换算法、改为逐文件全量比较，均不算完成。旧材料的散列值缺失、空、格式不符合旧约定、与当前文件不一致或符合旧格式均不产生资格差异；历史原记录不为了兼容而重写。实际应读取的原对象不存在、责任无法关联、真实工具或检查失败，以及真实人尚未决定，仍按原事实表达，但不能把摘要缺失包装成这些事实。

**发行包与安装前入口**：构建实际文档、角色、Skill、Hook 和平台二进制；安装在隔离目标验证必要资源可读、路径安全和真实初始化后原子发布。构建与安装不生成或校验逐文件 SHA、摘要清单或安装摘要回执，不用全量字节比较替代；删除旧清单验证器、兼容安装分支和旧格式读取，不为旧发行包维持第二条运行路径。真实必需资源缺失、非法路径和初始化失败如实反馈；额外无关文件不构成摘要门。验收当前发行构建及 `install --source … --root …`，覆盖必要资源、额外无关文件、非法路径、已有目标和初始化失败。

**原题面与本人信封的发行事务**：S5 原 Runtime 已登记的 packet、本人责任、原 view／answer 及 task-analysis 引用是后续定位依据；自然重试复用该登记，不凭当前重新生成的全卷与旧文件逐字一致、旧摘要、同名或目录形状认证已发行事实。本人已有问卷及专业材料保持原样；已发行显示材料缺失但现存原责任足以重建时，仅补缺失的显示材料，不声称恢复历史字节。尚未发行的候选使用原 Writer 与实际责任，在原路径被未知文件占用时原子选择独立可用路径，实际采用的路径由原 Runtime Writer 登记；不读取、覆盖或删除占用文件。并发竞争时只有 Runtime 已登记的原责任及路径是赢家，其他候选不认作已发行、不冒充本人答案；重试从既有 Runtime 事实接续。登记前中断的未登记文件保留未知，不能据其内容或文件名猜测发行，也不能让它对后续无关责任形成反向门禁。

S7／S9 packetbody 由原 Runtime Writer 在自身事务中发布并登记准确的 `body_ref`，后续读取依该 ref 与原 packet、owner／Assignment 定位，不按 SHA、size 或全文相等认证。登记前崩溃或路径被未知内容占用时保留现有文件、给当前实际责任准备独立可用位置；只根据现存原 Runtime／pending／已保留 checkpoint 的准确引用识别已登记材料，不按目录形状、JSON 内容或与候选字节一致认领未知文件。工作区分类、后续恢复和清理须消费同一引用事实：可证实的系统材料按原路径处理，未登记文件保留且不变成阶段阻断；不能因备用路径就丢失题面，也不能凭未知文件授予覆盖或删除权。真实已发行题面与作者原答案不被新发行覆盖；真实修订沿新的原责任发行，不将旧责任结果冒充新结果。

**packetbody 分类与 checkpoint 的具体接线**：原 Writer 持锁发行新责任时，只原子创建空路径；默认路径或中间目录已被占用时不读取、不认证、不覆盖，改选独立路径并把真实路径写入同一 Runtime pending／状态。完成登记后的重放直接沿原引用，不从未登记残留重建发行；登记前中断留下的候选保留未知。对实际需要分类的候选路径，按需读取当前 Runtime 和已有 pending 中的准确 `body_ref`；checkpoint 副本仅沿已登记 checkpoint index 与对应原 state 的引用定位，不按文件名、临时文件形状或内容可解析猜为系统材料。已登记引用的定位不意味着可以删除或证明内容未变；未登记路径不是系统控制物，也不因其存在新增本人接收或阶段门，确需清理的未知工作区保持原样。正常产品路径不因目录相似被排除。普通不涉及该路径的工具事件不读这些材料，不遍历历史 checkpoint 或为分类递归扫描工作区。

checkpoint 使用原 Runtime 身份、真实 revision 和 journal sequence 接续已登记的同次事实。发行前遇未知文件或前次中断遗留目录时保留原物、由同一 Writer 在既有 checkpoint 目录内选择独立位置；不能把旧目录全字节相等作为本次资格。已完成索引的同次 checkpoint 按原索引和事件坐标复用，不靠正文散列或逐字比较。

恢复时，原批准针对的是实际展示的恢复对象及其专业事实；packet 的内部 `body_ref` 是系统为保存该对象选择的定位，不是要求本人确认的第二个专业决定。恢复准备使用已保存的原 packet、owner、题面、结论和原候选，从原正文直接准备可用路径并在候选中展示实际对象；遇未知占位则保留原物，由原恢复 Writer 选择独立位置并在同一恢复事务的既有 pending／候选中更新该 packet 的内部引用，不改变原决定或专业内容。可在准备阶段确定的映射随候选供原有审阅；批准后才出现的占位或并发竞争，由同一 Writer 安全重选内部位置、接续已批准的同一实际对象，不因此新增本人重审或作者动作。重放沿已保存的恢复 pending 和准确引用继续，登记前遗留候选保留未知，不以内容一致认领。恢复 guard 保持既有原责任、真实决定、Writer 并发及实际对象语义；不得以整个候选／journal 逐字相等禁止这种系统内部定位调整，或用新摘要、全量认证替代。

原题面、原责任关联或真实批准对象确实缺失时如实标未知，不能重建未保存的专业内容、猜测批准过什么、覆盖占位或伪造已恢复；仅实际依赖缺失事实的恢复工作交原入口处理，不撤销其他已成立事实，不另设来源证明或重新授权手续。验收覆盖审阅前和批准后碰撞、原物保留、并发及发布／pending 中断重放、实际恢复后从新引用读取原题面和已收事实，以及缺材料未知；同时核对原恢复入口、guard、Writer、状态／journal 和下游读取，不以单个发布 helper 通过代替整链。

当前原生 Worker 沿其本人题面和自然交付入口保存实际 Plan／Result，由当前消费者接收并续后继。删除 frozen Worker 的生命周期适配、旧工作区消息副本与兼容恢复入口，不新建替代来源证明；真实未接收或未完成的专业工作按当前责任及实际内容处理。

**S7／S8 Finding 补充的原责任**：本人通过原入口对已有 Finding 表达新的观察和证据引用；原消费者按实际 Finding、作者及现有责任保存该专业表达并接续原 Finding／Case，原卷和已有 Finding 保持不变。系统不得要求、计算、登记或校验补充正文、来源或回执的 hash／SHA，也不凭内容摘要生成身份；旧字段无论缺失或为何值均不作为接收／重放资格。新补充使用原 Runtime、实际 Finding／作者与已有 Writer 内部事件或序号生成可逆身份；真实同答只依据当前原表达及本人最近已收事实复用，不递归扫描所有历史或重读证据文件。真实新表达生成独立原补充，不能覆盖已收内容；不同真实作者、Finding 或责任不互相认领。缺原责任或真实身份冲突如实反馈，未能确定归属的现存文件保留并采用当前责任的独立路径，不能因未知残留反向阻挡正常提交。

该入口的原 Writer 在既有 Runtime 锁／CAS 下登记当前实际补充路径及本人责任；中断时沿已登记事实接续，未知占位保留，不要求作者删除、补证明或重复填写。模板、schema、CLI、原消费者、Runtime 索引与下游同步当前无散列合同，删除旧字段兼容接线。验收从本人输入至 Runtime 和下游，覆盖同答重试、真实新表达、未知路径、owner 冲突、并发与中断，不重读引用证据来证明可接收。

准备提示和 manifest 使用已有当前 ReviewPlan 身份、实际 Assignment、原 REQ／TASK 路径和业务版本及可用专业材料；不要求 `review.round`、审查次数、SHA／hash、Git OID、证据摘要或额外机器字段。旧摘要即使存在也不复制、登记或认证为新 manifest 的来源资格；旧材料沿原关联读取，历史字段不要求作者改写。实际所需材料不可读、原责任不明或真实身份冲突按准确事实交 Main／系统处理，不凭摘要缺失制造错误。生成的 manifest 是既有派发材料，不是第二份计划或专业验证结论；平台、原注册、题面和结果消费者对相同原责任使用一致关联。

**本次派发材料的责任边界**：当前 manifest 路径按实际 Plan 身份与 Assignment 区分，不以固定 `r0` 代替轮次，也不从内容或散列生成身份。计划修订复用原身份，已派发和未受影响的责任及结果按原关联保留；受影响责任按实际变更接续。删除旧数字路径及其运行兼容；归属不明的已有文件保留、不覆盖、不阻断无关责任，由系统选择当前安全路径。

受影响责任的接线使用已有 Plan 内容修订版本和原 Assignment：仅当其原责任已登记／发行且真实变化需要后续履行时，由系统自动区分新派发的内部 owner、workgroup 和材料；同一修订的重放复用原关联，连续修订不能覆盖旧 owner、原题面或在途结果。此内容修订版本不是审查轮数，也不是新作者字段、补证、审批或出口资格。未受影响的原责任及结果继续；原已发行受影响责任的晚到结果沿原 owner／题面接收并保存，不能冒充新责任的结论，晚到 Finding 交 Main 判断实际影响。尚未登记且内容未变的原准备材料可继续使用，不因其他责任变化要求作者重填；判断文字变化不能仅靠相同 Claim ID 猜成未变。原关联不明时保留未知及材料、让当前无关责任继续，不引入反向门。

**S7 已安装指引和层次归属**：Main 实际读到的原 guide 给出可用路径、自然保存与后续准备／登记／派发顺序，供需要时按原有契约填写的简短 JSON 字段示意；例如选用 `e2e_assets` 时解释每项 `case_ref` 和 `path` 的含义，其他可选项及该数组未使用时保持未决或省略的方式以实际 schema 为准。示意不把 E2E 分类或可选资产变成计划接收、分派或出口的额外资格。安装协议不能要求读取发布包不存在的源码 schema 或逆向二进制；模板与示例不教作者填写摘要或轮次。角色／Skill 提供专业检查方法，原 Plan 表达分工，Hook 监听并交原消费者，manifest／注册承接原分工，issuer 准备本人题面，Reviewer 原答卷及原消费者负责本人结论，TR-008／TR-009 负责按真实 Finding 或必要责任完成情况分流。各层不复制另一层的审批或证明职责。

**可选素材与恢复观察**：S7 预填／guide 可从已有 TASK、CASE 提供可用材料；未提供或不可读时如实表达未知，不凭摘要或缺可选 E2E 条目阻止计划。Main 可使用正常工具理解现场；删除 `review-plan frozen-diff` 及其历史恢复接线，不借缺失旧正文声称文件与过去相同，也不要求作者提供散列。

**接线与验收**：模板和阶段指引只交付本人职责与原路径；Pre／成功 Post 负责观察，原 ReviewPlan 消费者负责接收、必要的同义重放与真实修订，原 Writer 保证既有写入及中断恢复，原派发／结果消费者与阶段出口负责后继。S6 的清理归实际工作区管理，不归 S7 入口。对四个原进入路径分别验收：从实际原计划自然保存、可理解的无轮次派发提示、无摘要 manifest、原工作组登记、自然事件发行本人题面，到本人原结果自然接收及 Finding／无 Finding 分流；不以手写 Runtime、孤立 helper 或计划已收代替整链。另覆盖同 generation 不同 Plan 复用 Assignment ID、同计划修订、已有数字路径、归属不明残留、重复事件、在途及晚到结果、真实依赖和责任冲突、读取缺失与 S6 保留工作区仍能进入。验证安装后的实际 guide 足以理解可选字段，不要求搜索二进制；检查 Hook 及其直接后继不计算、登记、复制或校验摘要、OID，也不增加作者动作。发现不通过时定位真实阻断并优先删除超出原职责的门禁；环境或安装故障如实报告，不把每个失败都直接归因为 Hook。

**实际安装的前置接线**：安装创建的 Runtime 不登记 Definition／Hook policy 摘要，构建、安装及初始化不要求散列清单或回执，仍检查配置结构、路径安全和实际所需材料。当前发行与安装按 §3.3.4 接线，删除旧包兼容安装分支；文档变化不代表实现已移除。

### 3.4 先判设计与实现的关系，再选修法

故障是调查入口，不直接决定应增加什么机制。先区分偏差发生在哪里，再按现行设计和 L1 准入公理选择方案：

| 判定 | 取舍原则 |
| --- | --- |
| 设计已明确，实现或投影偏离 | 修正原生产者、消费者及受影响投影，使其回到已有职责；不因局部难接而另增一套规则 |
| 设计中的层次、时序或完成条件缺失、相互冲突 | 先补齐或修订相关 L3/L4 的现行正文，说明依据、代价和相邻影响，再推导实现；不把当前代码行为自动升格为设计 |
| 现有机制包含不必要的依赖或重复职责 | 优先删除、合并或复用，核实原质量义务仍有消费者；不为维持旧分支继续增加补偿层 |
| 属于专业判断、缺上游决定或已声明的能力边界 | 沿第 2 节交给相应责任，不制造机器答案；已有承诺内的失败仍须修复，不能重新命名为不支持 |

候选方案应同时满足架构符合性、工作有效性与总成本要求。能让当前反例通过但违反责任归属、增加重复事实或把系统义务转给作者的方案，应退回重选；仍在本轮范围内的原问题不能因此被搁置。真正需要演化设计时按原层级修订，并删除被替代的要求；不通过不断追加例外、优先级声明或恢复菜单让相互冲突的规则并存。

### 3.5 当前唯一接线与已成立事实

每个阶段只保留一套当前题面、派发、自然事件、消费者、Writer 和出口；被替换的 Hook／CLI、旧格式 schema、旧消费者、历史适配与只服务它们的测试一并移除，不允许新旧接线并存或借兼容保留第二套生命周期。清理代码和协议不等于删除用户业务数据、专业原卷、已成立结果或真实人类决定；这些事实按原义保留，不将旧格式本身升级成当前运行协议。

同一现行机制中，已派发责任跨阶段晚到时，当前消费者按原责任和派发关联接收；已接收工作只续未完成后继，不能冒充其他责任结论。材料或关联确实缺失时交 Main／系统说明未知，不猜测、强制作者重交或阻挡无关责任；共享 Writer 真故障如实处理。工作区资源回收独立于接收与出口，未授权或归属不明的实际文件保留。

S9 的当前原责任引用及准确 token 语义由 [S9 §6.2](../l3-stages/L3-S9-repair.md#62-自然事件接收原作者产物不代作专业判断)和 [Hook §3.2](L4-hook-platform-wiring.md#32-任务内容和转录各有用途)定义；多种路径表达不证明 actor、工作执行或质量。Main 交付当前真实任务与材料，独立 Targeted 沿自己的责任接收。模板／Skill／Hook／答卷／消费者和出口统一当前合同，不新增作者证明、额外提交或工具禁令。

## 4. 先确定完整交接，再拆分实现

### 4.1 设计以完整阶段及其交接为单位

先沿 L1 原则、L2 入口/出口、相关 L3 阶段工作和所引用 L4 机制理解责任，再调查实现。完整阶段设计包括参与者、输入、专业工作、产物、机制消费、完成条件及异常交接。模板、Skill、Hook 指引和答卷共同承载这份设计；各自职责由整体推导，不能分别完善后再假定拼接结果就是完整工作流。

整体考虑确定的是受影响阶段及共享机制的设计边界，不要求每轮重写全部 L3 或修改所有阶段。局部修复可以只改一个载体，但必须解释它在整体中的位置，确认其他有效投影和相邻入口、出口仍成立。文件数少不等于架构符合，修改面广也不等于设计完整。

### 4.2 从现行设计到实施的工作顺序

实施前在已有任务说明中形成下列推导；简单修复可以用简短文字完成，不另建维护答卷、追踪账本或例行审批。

| 步骤 | 应完成的工作 | 进入后续工作的依据 |
| --- | --- | --- |
| 理解设计 | 找到本阶段目标、责任、原产物、完成条件及共享机制的权威定义 | 能说明哪些要求必须保留，哪些属于专业裁量，哪些由系统派生 |
| 调查偏差 | 保留实际输入、接收者、反馈、执行结果，追查原生产者及全部有效消费者 | 按第 3.4 节判定设计缺口、实现偏差或其他问题；复现现状不等于已选修法 |
| 推导完整编排 | 明确每项义务由谁承担，信息由谁定义，经何载体、在何时交给谁，结果由谁消费 | 正常、未接收、部分已收及相关恢复能连成一段可执行工作；不让作者裁决冲突规则 |
| 选择并核对方案 | 比较删除、合并、复用和必要新增；核对原则、成本及相邻阶段的影响 | 能解释为何该方案符合整体设计，合法交付可满足全部适用检查，且没有无依据的作者义务或无人消费的字段 |
| 确定落点与分工 | 列出需要修改、保留和删除的来源、投影、代码与验证，明确共享接口和整合责任 | 实施者无需自行设计另一套流程；未知的关键合同先调查或修订，不留给并行整合时猜 |
| 实现与组合验收 | 先完成原入口和适用反例，再核安装材料、事件、原消费者及相邻后继 | 分别证明符合设计及实际可运行；未验证部分按原承诺说明，不用局部通过替代整体完成 |

这段推导应能串起“设计义务 → 各层职责 → 实现落点 → 组合验收”。遇到实现困难时仍以它裁决方案；不能为了通过当前用例，悄然改变义务、受众、输入集合或完成含义。实施中发现前提不成立，回到对应设计步骤更新方案，随后再调整任务范围。

### 4.3 先编排内容，再选择载体

以下四类是阶段设计的常见交付载体，其完整权威分工见[指引分层](L4-agent-guidance.md)。它们共同承载 L3，不能各自定义另一份阶段合同；原领域消费者和 Gate 按该合同认定接收与转换。

| 载体 | 从阶段设计推导的职责 | 组合时要排除的偏离 |
| --- | --- | --- |
| 模板 | 引导作者形成所需专业产物，明确问题、表达形状、判据和适用条件 | 新增没有消费者的栏目；在字段或示例里藏一套额外完成条件 |
| Skill | 解释完成专业工作的必要方法、取舍和自审方式 | 把方法建议变成额外提交、审批、机器身份抄录或工具许可 |
| Hook 指引与反馈 | 在实际事件向正确接收者交付当前责任、准确引用、已成立事实和可执行后继；按设计调用原消费者 | 重定义作者字段或阶段门，向普通 Worker 广播 Main 责任，要求无关操作制造下一事件 |
| 具体答卷/brief | 给出本次真实输入、允许填写的专业字段、准确产物位置和原交付方式 | 要求从源码、Runtime 或上游转述猜协议；遗漏已由阶段设计确定的交付义务 |

对每项必要信息，明确唯一职责来源、承担的载体、出现条件、接收者和消费者。只为当前责任交付适用内容；同一规则可在必要语境中解释，但派发转述、示例和恢复提示都不能擅自删减或加严原要求。系统已知的集合、身份和来源关系由原生产者带出，不让各层重新推导成不同版本。

组合核对既要发现遗漏，也要发现叠加：作者实际收到的材料是否足以完成工作；是否被多层重复要求登记同一事实；某层新添的限制是否改变其他层的合法操作；某条恢复建议能否通过原消费者的全部适用校验。不能以各层分别说得通，代替这些要求可以同时成立。

### 4.4 交接场景、所有权与并行实施

以具体场景串起“入口 → 实际收到的信息 → 原消费者 → 持久结果 → 下一动作”，再确定受影响文件。场景至少覆盖本次涉及的正常交付和失败窗口；延迟、重放、历史、部分接受等按实际影响选择，不穷举无关能力。

| 设计对象 | 必须回答的具体问题 |
| --- | --- |
| 正常交付 | 作者只凭已安装材料能否工作？实际保存或返回怎样进入原消费者？ |
| 接收与后继 | 哪个事实已成立？下一材料由谁准备？专业完成者什么时候可以结束？ |
| 故障交接 | 专业缺项回谁，系统故障交谁？对方实际能收到原因并执行所给动作吗？ |
| 原来源与投影 | 哪处定义规则，哪些提示、Skill、模板和命令实际消费它？被替代要求在哪里删除？ |
| 验证 | 哪个公开入口用例证明整段交接？哪个负例能检出遗漏或错误接收？ |

若拆分并行任务，按已有完整交接划分所有权，指定整合责任人。按层或按文件只是实施切片，整体设计责任不随任务拆分而转移。整合者在派发前确定共同语义、共享接口和不能改变的边界；子任务负责实现既定投影，遇到尚未决定的合同先交回整合，不自行增加作者手续、判定规则或恢复协议。既有授权内的等价实现细节由实施者处理，不为每个日常选择新增批准。

分别完成接收器、文案和测试不构成交付完成；早返回分支、普通进度及具名恢复必须对同一责任表达一致事实。整合者对照完整阶段设计复核组合，发现跨层冲突应修原来源及消费者，不能只在最后拼接提示或追加兜底。没有必要改变全部层次时只改受影响部分，不为“按层修复”固定展开全仓扫描。

例如 S2→S3 的专业工作是形成供契约消费的设计。模板引导形成设计依据，Skill 提供专业方法，答卷给本次实际产物集与保存位置，Hook 在原交付事件调用消费者、投影登记及 S3 准备结果。若登记成功而 S3 准备失败，接续准备即可，无需重做设计、换答卷或等待无关工具调用。应从这段完整交接推导各载体的内容，不能先在 Hook 写“恢复”，再让作者从其他层寻找恢复究竟需要什么。

## 5. 整改范围与新增发现的处理

每轮整改在实施前固定问题、受支持路径、预期终点、受影响消费者及验收场景，同时写明不在本轮承诺内的能力。使用现有任务或 PR 描述承载，不新增登记文件。局部缺陷不自动升级为全生命周期改造；共享根因影响多条已支持路径时，应在原机制统一处理。

新增发现先分类，再决定是否进入本轮：

| 发现 | 本轮处理方式 |
| --- | --- |
| 改动引入的回归，或原问题仍阻断已承诺终点 | 修复并补最小必要验证；范围显著扩大时先重新选择机制和更新方案 |
| 原有缺陷，与当前终点有直接因果关系 | 纳入修复；不能以“存量”掩盖本轮主线无法完成 |
| 与本轮无关的存量问题或理论增强 | 记录影响及归属，另行排序，不自动成为本轮完成条件 |
| 已有能力尚无验收证据 | 标明待验并补适用验证；不能仅凭待验状态判成生产缺陷或新增能力 |
| 新平台、格式、无人执行恢复等新能力 | 作为独立范围选择，说明收益、成本和验收；不借补 gap 隐含加入 |

如果连续修补暴露相同原因、多处生产相同事实，或实施开始需要新增一套协调协议，应先回到第 3 节作删减、合并与复用判断。审查者不能只增加缺口列表而不判断机制必要性；实现者也不能通过放宽真实质量条件让列表消失。按已有授权处理必要修改，真正改变目标、兼容承诺或重要成本取舍时再交相应决策人，不对日常可回滚选择新增审批。

## 6. 验收方法与停止扩展条件

验收同时回答两个独立问题：方案及全部有效投影是否符合现行架构，实际执行是否达到承诺终点。架构符合性核对每项设计义务的承担者、来源、接收者和消费者，确认组合后完整且无冲突，新增约束具有准入依据，被替代要求已从有效投影删除。实际执行验证下述原入口、反例和相关后继。当前用例通过不能豁免架构偏离；设计一致也不能替代运行证据。

### 6.1 固定代表性工作，再选择检查项

验收首先证明执行者能够完成专业工作，以及质量检查能够发现实际遗漏。实施前从受影响路径中选定场景、合法输入、期望终点、预算和负例，使用 [Hook 验收清单](L4-hook-acceptance-checklist.md)选择适用断言。清单是验证方法库，不是自动增加功能范围的待办列表；同样不能因不选某项就抹除既有承诺。

| 场景类别 | 验收方法与终点 |
| --- | --- |
| Main 正常保存 | 只凭安装材料完成当前专业交付，从公开保存入口核接收及适用后继，不注入额外提示或事件 |
| 原生 Worker 正常返回 | 区分后台启动与真实完成；原作者交付、Main 获得接手信息，独立责任保持独立 |
| 质量遗漏 | 对本次实际检查的缺字段、错误来源或不满足判据提供负例；确认准确拒收及修正指引，而非只测 PASS |
| 提交前后系统故障 | 在原问题涉及的真实窗口注入故障，以新请求核原事实及恢复动作；已收产物不重交，系统故障不转成作者字段义务 |
| 延迟、重放或冲突 | 按变更影响选择：原接受不重复、旧返回不认领新责任、同身份异文不覆盖 |
| 成本与规模 | 在已知问题规模及事先确定的代表性增长规模运行实际入口，核预算余量、重复工作与作者操作，不用组件速度代替整链 |

这些类别按变更适用性选用，不要求每次修改重跑所有阶段及故障组合。涉及真实平台行为和模型渠道的承诺需要真实平台证据；领域测试、真实平台执行及产品业务验收分别说明范围。文档修改只验证设计一致性和引用，不据此宣称机制已落地。

测试同样按责任分层：少量原入口整链证明真实接线和必要后继；格式、来源、质量负例及中断规则在实际消费者附近验证，只有分流不同时才分别验证各事件。迁移或合并测试前，核对原义务、合法输入、失败后果及实际消费者；不能用人工伪造的已接收事实、只验证某组件或删掉独立性等质量条件冒充等价。资源清理成功和清理待处理分别验证，不将待处理当成未接收，也不因测试要求 clean 扩大删除授权。比较同一合法场景的执行及维护成本，重复准备和跨产品层组合本身也计入成本。

### 6.2 同时判断有效、可靠与成本

对同一代表性任务，至少核对三个维度：专业问题和检查是否捕获已声明的遗漏；支持路径能否连续交付并在相关故障后接续；协议阅读、机器字段、重复交付、等待及运行成本是否符合原目标。已有证据可按真实输入和影响范围复用；新增验证须对应变更、风险或失败，不能为提高通过数量重复跑无关集合。

模拟专业答案可以隔离机制，但不能认证思考深度和业务质量。真实平台或环境不足时如实保留待验，不将缺环境转换成继续开发更多机制的理由。新增提示行数、测试数量、阶段终态和 Hook exit 0 均不能独立证明优化有效。

### 6.3 完成、待验与后续工作的边界

当架构符合性与组合复核成立，固定范围内的正常终点及相关恢复成立，质量负例有效，指引与机制匹配，作者与运行成本符合事先目标，且仓库要求的适用检查完成，本轮可以结束。记录剩余问题及其归属，不因发现无关增强再次打开范围。后续只有新事实、回归或影响原承诺的缺陷，才触发对应复审。

实现完成但必需的平台、增长或中断证据缺失，应记为“实现完成，验收待完成”，不能宣布通过；也不应无限开启新设计分支。验收失败回到具体原因；若根因是职责过重或协议重复，优先缩减机制，保持原质量与来源要求。

本篇约束后续取舍，不宣称当前所有机制已经符合这些标准，也不直接关闭既有开放缺陷。具体落地与待验范围仍从各阶段、机制正文及缺陷记录读取。
