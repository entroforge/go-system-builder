# L4 共享模型与契约治理

本机制说明跨端共同数据、操作协议和阅读依赖怎样保持同源，并在规划、执行与验证之间准确交付。阶段工作见 [S3 契约](../l3-stages/L3-S3-contracts.md)与 [S4 任务拆分](../l3-stages/L3-S4-task-split.md)；目标项目入口见[共享模型规则](../../docs/rules/shared-model-contracts.md)。

## 1. 为什么共同设计之后仍会发生两端分叉

S2 已明确系统行为，并不意味着各执行端会自然得到同一份接口解释。前端可能把“没有结果”当作空数组，后端把它表达为 null；双方都能通过本地测试，却无法联调。即使字段完全相同，对“取消成功后能否重试”“权限拒绝是否改变状态”的理解也可能不同。

如果 FE、BE、Mock 各抄一份字段表，差异会在不同时间发生，难以判断谁是作者源。若要求执行者通读整个项目再自行推断，又会把共同设计的责任转嫁给每个实现者。因此本机制同时解决两件事：让共同结构与共同协议各有准确权威，让当前任务取得足够而有边界的阅读路径。

采用原生模型、合同索引、TASK 和已有来源登记承载这些关系，不另建模型注册中心、通用依赖图或多语言生成平台。自动化集中处理明确的引用与结构；领域含义、兼容性及真实行为仍由专业工作和独立验证负责。Hook 不以散列或历史字节复核认证来源。

## 2. 不同事实分别由谁拥有

| 事实 | 作者源 | 下游如何使用 |
| --- | --- | --- |
| 业务目标、范围与验收承诺 | REQ | 细化而不擅自改变 |
| 领域含义、规则、状态与结果判据 | S2 设计及模块场景 | 翻译成操作和分端责任，缺口回设计层 |
| 共同字段、类型与数据约束 | 项目原生模型或 Schema | 引用、生成或边界校验，不在各端另抄结构 |
| 操作、时序、错误、幂等与恢复 | SYNC 契约 | 形成调用方与提供方共同承诺 |
| 各端具体行为 | FE、BE 契约 | 在共同语义内实现本端职责 |
| 本次范围、执行依赖与完成条件 | TASK | 组织实现与验证，不反向改写规格 |
| 本次实际使用的材料和版本 | 原来源、实际责任与已收专业内容 | 供原下游按实际路径使用；不声称坐标能独立认证历史字节 |

项目维护当前共同模型体系，REQ 记录为什么使用它以及改变什么，不按需求复制另一份模型。领域、传输、持久化和展示是不同职责层次，不要求每个项目创建三套 Schema。确有转换才声明映射、缺省、信息丢失与测试；同构关系直接复用。

同名不等于同义。不同领域的“状态”可能拥有不同生命周期，不能为了统一字段名强行合并。反过来，同一共享概念不能由 FE 与 BE 各自给出互相竞争的定义。SYNC 表达共同协议，不要求系统采用同步调用，也不由这个文件名决定架构。

## 3. 按业务切片共同收敛，再分端展开

### 3.1 字段与操作相互约束

从当前需求与 S2 场景进入，先确定受影响操作、输入输出位置、状态、副作用与恢复，再与模型来回校准。取消操作若要区分“已取消”和“因状态不可取消”，模型与错误协议必须足以表达；模型中的状态集合又限制协议可以承诺什么。

这不要求先建完全项目模型。按足够小、能够独立判断的业务切片收敛共同事实，然后让 FE 与 BE 分别展开本端职责；无法对齐的部分回到共同源，不在两个合同里各补一个解释。

| 工作 | 需要作出的判断 | 交付关系 |
| --- | --- | --- |
| 识别现有源与消费者 | 这是已有概念、真实转换还是新领域对象 | 复用或修改准确作者源 |
| 收敛模型与 SYNC | 哪些数据、时序、错误与副作用构成共同承诺 | 同一操作的数据与行为基线 |
| 派生分端责任 | 前端怎样呈现、后端怎样执行和拒绝 | FE/BE 引用共同源并细化职责 |
| 组织任务与阅读 | 当前执行者需要哪些条款、定义和先决实现 | TASK 的有序清单与依赖 |
| 验证实际消费 | 生成、边界校验和真实交互是否遵循基线 | 实现与独立验证证据 |

### 3.2 以取消订单说明三类不同约束

共同请求定义 `order_id` 为非空字符串。传入数字是结构错误，边界应拒绝；订单已经完成时传入合法字符串，数据仍符合结构，却应按业务状态拒绝且不发生取消副作用；正常取消后重复请求怎样回应，则属于幂等与恢复协议。

三者不能都塞进 Schema，也不能只靠一个合法 JSON 样例说明完成。Schema 约束数据，SYNC 与 S2 约束行为，FE/BE 履行各端职责，CASE 和契约测试证明实际拒绝、状态与副作用。

## 4. 合同索引怎样声明可执行共同来源

### 4.1 策略明确能力，不替代适用性判断

当前 JSON Schema 适配器使用以下声明：

```text
> Shared model policy: json-schema-v1
```

索引的 H2 章节 `Shared model baseline` 使用六列：

| Operation | Slot | Schema | Consumers | Valid example | Structural negative |
| --- | --- | --- | --- | --- | --- |
| cancelOrder | request | [请求定义](../../docs/examples/shared-model/project/docs/architecture/data-model/orders.schema.json#/$defs/request) | FE、BE、SYNC 的相对 Markdown 文件链接 | 合法 JSON 文件链接 | 结构不合法的 JSON 文件链接或 N/A |

这是列含义示意，真实文件中的链接相对于该索引定位。Operation 使用已有操作名；Slot 标明 request、response-200 等实际数据位置；消费者列链接本批适用合同，不写没有实际文件的角色占位符。

同一 REQ 内，包含跨索引声明在内，相同操作与数据位置只能有一个作者源。相同来源重复引用允许存在；不同路径或片段不能冒充同一权威。不同 REQ 的操作名不自动视为冲突，跨需求复用的真正身份仍是项目原生源。

不涉及共享数据时声明 `Shared model policy: none`，并提供具体非空 `Shared model reason`。机器检查理由是否存在，不证明事实确实不适用。已有其他协议格式不能假装为 none；应保持原生权威，并在规划与独立审查中明确当前自动覆盖限制。

没有策略的兼容索引会产生未验证警告，畸形或不支持的策略报错。新规划批次需要明确适用决定；不能利用兼容警告绕过本批责任，也不能静默重写旧冻结批次。

### 4.2 消费者引用同一来源，不重复字段

Schema 列是一个仓库内相对 Markdown 链接，可以带 JSON Pointer 或原生锚点。FE、BE、SYNC 在 H2 `Shared model inputs` 中引用同一路径与片段。引用关系说明“本端消费这一共同定义”，分端正文继续说明行为，不再维护字段副本。

检查器核对声明的消费者类型、文件、必要锚点和相同 Schema 引用；对这些消费者，也识别与它们关联的已登记样例，避免把样例当成额外模型。它不会自动扫描应用代码，发现所有未列出的真实消费者，也不会仅凭字段同名判断两个定义语义相同。

模型入口可按[共享模型模板](../../docs/architecture/data-model/MODEL-template.md)定位领域与原生定义，不要求再手写一份 Schema 摘要。原生格式没有适配器时，不能将“保留原权威”写成“已经自动验证”。

## 5. 编译、样例与依赖怎样构成可复现闭包

### 5.1 记录实际加载的源

检查器通过调用者指定的同一文件视图编译 Schema，记录编译器实际加载的根文件、本地传递依赖与样例。闭包不是手写 `$ref` 清单，也不是扫描全仓库 JSON；合法原生递归由编译器处理。

Schema 资源标识不能在同一批范围内指向不同作者文件。检查沿真正承载 Schema 的位置识别资源，不把样例、缺省值或枚举实例中的普通 `$id` 字段误判为第二权威。

依赖必须可从仓库本地取得；加载器不通过网络补齐远端资源。外部契约事先固定到项目，并明确更新责任。编辑期磁盘读取也限制在权威根及工作区边界内，不能用逃逸链接或另一个执行工作区补出缺失来源。

### 5.2 正样例、结构负例与业务负例分开

每行有一个合法 JSON 正样例，并且通过指定 Schema。可选结构负例写 N/A，或给出能解析为 JSON、但应被结构校验拒绝的实例。破损 JSON 只能证明解析失败，不是结构约束测试。

如果负例也通过，检查器要求重新分类：要么确实缺少结构约束，要么这是权限、状态或并发等业务负例。业务负例保留在既有 CASE、SYNC 断言和契约测试中，使用相同场景分母，不创造模型专属验收集合。

样例链接指向整个 JSON 文件，不能截取片段掩盖其实际内容。样例是基线实例，不能因为出现在模型闭包中就获得 Schema 作者权威。

## 6. 发行、接收、登记和冻结分别守住什么

### 6.1 先给作者真实输入，再接收本阶段输出

S3 资料发行承接已绑定 REQ、S2 设计及实际需要的来源，不以尚未创作的合同或模型为前提。Main 形成合同、共同模型与样例，正常保存专业答卷；原消费者读取本次必要材料并按原阶段职责执行结构和专业检查。Main 对实际依赖及真实变化负责，不因移除机器来源证明而免除专业判断。

编辑期 `contracts check` 可对当前文件进行诊断；需要正式提交视图时由作者和 Main 按原专业工作安排。Hook 不计算、登记或校验材料散列、Git 对象 ID 或完整历史字节来授予接收资格。若实际来源缺失、已知实质改变或专业判断发现冲突，按原责任处理；系统不声称仅凭路径能检测未记录的外部修改。

### 6.2 原材料及接收怎样交给 S4

接收使用合同、模型及样例的原路径、实际专业内容、阶段责任和原结论；PTR-PLAN-02 关联本批需要的合同，S4 使用已接收的原材料。不为模型另建登记表或新证明信封，不计算、登记、重算或校验 `documents[]` 的内容摘要。历史记录原字段可以按原路径读取，不因旧摘要重验或要求重交。

接收、状态写入和下一责任准备是不同事实。后继中断时沿已收事实和原待续继续，不以今天的同名内容补造历史。真正需要的原材料不可用时说明未知并交 Main 处理，不强迫作者重造历史。

### 6.3 S5 审查实际模型及样例

Main 向独立审查责任提供实际模型、合同和样例，审查者依真实材料判断范围与一致性。若专业阅读发现真实缺失或有影响的变更，Main 安排相应处理和必要返工；不通过散列、全量历史字节比对或重新登记证明冻结资格。正常进入和技术恢复不要求作者另造来源证明，历史已收审查不因移除散列而自动失效。

具体接收、并发和恢复由[状态内核](L4-state-transition-core.md)和[修订机制](L4-revision-usage.md)承载。本节为目标合同；当前模型 subjects、documents、登记与冻结消费者中仍有散列依赖，需要与 schema、S4／S5 后继一起调整，不表示实现已经完成。

## 7. 渐进式阅读怎样让执行者获得充分上下文

### 7.1 不同职责从不同入口进入

Builder 先读 TASK 的目标、写范围、依赖、完成条件与检查责任，再展开本端条款、相关 SYNC 操作、共同定义和必要状态或场景，最后回 TASK 执行。规划者从 CONTRACTS 进入整理条款；审查者反查 REQ 与 S2；集成验证者从 SYNC、CASE 和真实边界进入。

这是一条工作路径，不是要求把每份文档的所有链接递归展开。背景材料按实际问题读取；缺少影响判断的来源应明确补齐，不能以有界阅读为由省掉关键语义。

### 7.2 TASK 的有序清单表达阅读目的

新 TASK 使用 `Reading policy: linked-v1`，Document Manifest 保留 Order、Kind、ID、Path、Clauses，并加入 Purpose 与 Mode：

| 字段 | 用途 |
| --- | --- |
| Order | 作者安排的阅读顺序，体现从当前责任向必要共同事实展开 |
| Kind、ID | 说明材料的角色及准确对象 |
| Path、Clauses | 相对 Markdown 文件链接及需要展开的条款或稳定锚点 |
| Purpose | 为什么这份材料影响当前工作；条件材料要写触发条件 |
| Mode | required 必读、conditional 条件适用、optional 背景 |

检查器要求必要表格结构与至少一条必读链接，解析必读文件和锚点，按路径加片段去重。同文件不同片段可以分别阅读；完全相同的必读对象重复出现则提示修正。JSON 片段通过 Schema 编译解释，Markdown 优先使用显式稳定锚点。

conditional 与 optional 不被自动当成必读。当前机器不会求解条件是否成立，也不会证明 Order 已形成最佳语义顺序；Main 与执行者须按实际工作判断适用性。历史背景失效不应阻止无关交付，已适用的条件来源缺失却不能被忽略。

### 7.3 阅读关系不拥有执行调度权

文档可以回链，Schema 可以递归，这些都不是 TASK 依赖环。只有真实先决工作沿既有 TASK DAG 表达，由原任务检查处理。下游声明上游引用，反向消费者从合同和任务索引查询，不在已锁合同里手填未来任务或验证行。

任务上下文分析可以对声明片段去重、估算阅读量并呈现未知；它不能证明 agent 实际读过，也不是全仓库真实 I/O 测量或自动调度许可。原生任务交付仍由 [Main 与 Claude Code](L4-agent-dispatch-governance.md)负责，不为模型建立首写激活或读回批准层。

## 8. 共同实现依赖怎样影响并行与集成

共享设计只读输入不天然构成实现前置。FE 与 BE 从同一 Schema 独立生成到不同目录，可以并行；无关数据库迁移也不应自动阻塞前端。

只有真实共享实现需要基础 TASK：例如后续任务必须导入本次新建的共同包。该贡献先由 Main 接收、集成并完成对应检查，再向依赖者提供包含它的实际工作起点。Schema 存在和源任务责任 done 都不能替代真实集成。

执行者不能擅自改共同模型来适配自己的代码；发现规格不足时沿原规格处理。Main 在实际集成时结合交付与工作现场判断影响，发生真实规格变化则安排必要返工，不自动重置执行者工作区。Hook 不通过扫描 Git 或计算、登记、比对 OID／散列作接收或集成资格，也不声称自动发现所有外部修改。完整工作区与接收规则见 [L4 工作区治理](L4-worktree-governance.md)。

## 9. 实际消费与独立验证怎样配合

文本中的 `model_ref` 只能证明声明关系。真实 FE、BE 与 Mock 应通过项目已有生成器或边界校验器消费共同源，固定工具版本与配置，并提供能识别错误数据的检查。只有存在生成物时才要求重生成一致性，不能强迫所有项目改用生成平台。

| 验证位置 | 需要证明的事实 |
| --- | --- |
| S3 | 共同定义、消费者引用、结构样例和本批来源可执行 |
| S4 | 任务覆盖与阅读入口充分，真实执行依赖明确 |
| S5 | 模型忠实于需求，协议与分端承诺一致，审查对象准确 |
| S6 | 实际实现同源，生成物或边界校验工作，共享贡献完成集成 |
| S7 | 真实认证、时序、状态、持久化、副作用与恢复符合场景 |
| S10 | 按原验收标准解释交付与证据，暴露未知与风险 |

独立审查必须挑战模型本身是否错了，而不是再用同一份错误 Schema 生成客户端和测试后宣布一致。真实联调还要观察结构合法的业务拒绝是否保持状态、重试是否重复副作用、Mock 是否掩盖真实协议差异。

仓库提供的[合成消费示例](../../docs/examples/shared-model/README.md)实际校验 HTTP 请求、响应和 Mock，并区分结构与业务拒绝。它证明适配器能被代码消费，不证明目标产品已经接入或真实联调已完成。

## 10. 漂移、冲突与变更怎样恢复

| 情况 | 处理责任与恢复位置 |
| --- | --- |
| 两端引用不同路径或片段 | 回 S3 对齐作者源与分端声明，不选一个实现当真相 |
| Schema 或本地依赖缺失 | 补准确来源与正式提交，重新检查同一视图，不临时联网下载 |
| 正样例不合法或结构负例通过 | 修真实定义或正确分类样例，不能把业务拒绝伪装为结构错误 |
| 同槽多源或 Schema 资源 ID 冲突 | 查清领域归属与重复作者源，修定义及所有实际消费者 |
| 必读链接或锚点失效 | 在 TASK 所需范围修准确链接；适用条件缺证由 Main 判断 |
| 专业工作发现模型发生实质变化 | Main 判断真实影响，必要时沿原规划返工并安排受影响独立审查；不以散列判定变化或要求补来源证明 |
| 实现发现业务含义不足 | 回 S2 补规则或状态，再经 S3/S4；真实需求变化需要人决策 |
| 生成与运行不一致 | 定位工具、配置、消费或实现，不直接修改模型迁就输出 |

兼容性需看真实消费者：可选新增也可能改变穷尽匹配、缓存、默认值或错误处理；删除字段、收紧约束和状态变化则可能破坏旧客户端。当前机制不自动作语义兼容裁决。迁移与适配计划应明确先后、兼容窗口及退出条件，按原需求变更和发布授权边界处理。

接收或集成失败要保留准确对象与原因。重复保存、待续与旧答卷按原阶段恢复，不能为了模型一致性再新增一套批准回执。工具暂时允许继续编辑，也不等于冻结基线已获准改变。

## 11. 观测应帮助定位哪种分叉

模型检查报告应能指出索引、操作与数据位置、实际源、消费者和失败样例；实际来源与检查结果帮助维护者定位“声明不一致”“漏依赖”与“实际视图没有文件”；无法从现有事实判断历史字节是否改变时说明未知。阅读诊断说明哪条 required 引用或锚点断了，不能只给一个总失败数。

沿原任务、Finding 与验证证据观察缺陷在哪个阶段被发现、实际返工问题与范围、阅读补问和误报。检查耗时可用于判断常驻成本，但不新增日常报表或把条目数量当成质量分数。

原生 Start/Stop 只衔接本责任的任务与结果，不承担模型语义裁决。接收、阶段迁移、冻结和集成各有原记录；定位时应看实际事实停在哪里，不能因 Hook 输出成功就推断所有下游检查已完成。

## 12. 实现落点与尚未统一的边界

| 落点 | 当前职责与限制 |
| --- | --- |
| [sharedmodel](../../internal/sharedmodel) | 声明策略、同源关系、Schema 编译与本地闭包、样例、必读链接；不解释任意协议或业务充分性 |
| [S3 产物接收](../../internal/runtime/contract_batch.go) | 当前依赖冻结来源认证；目标沿本批原材料、原责任与专业结论接收，不计算或核验散列 |
| [共享来源登记与冻结](../../internal/transition/shared_models.go) | 当前以散列比对内容与闭包；目标只关联原材料和责任，并同步 S4／S5 消费与旧记录读取 |
| [已接收来源投影](../../internal/qualitygate/contract_packet_subjects.go) | 读取原接收事实；不是每次重新验证完整目录或产品语义 |
| [合同检查](../../internal/semantic/contracts.go)、[任务检查](../../internal/semantic/tasks.go) | 承接模型与必读诊断，并保留原条款、场景、任务依赖职责 |
| [任务阅读分析](../../internal/semantic/task_context.go) | 解析声明片段、读量和未知，不认证实际阅读或替代调度 |
| [集成前复查](../../internal/integration/integrate.go) | 现有 Git 与来源检查需按 Main 实际集成合同调整，Hook 不以 OID／散列或 Git 扫描认证交付 |

需要明确三项指引与能力边界。第一，正式合同检查使用原交付集和准确 REQ 来源确定本次 CASE 义务；模块完整集合继续供前向引用读取，其他需求正文不能替本批履职。无绑定的全项目编辑诊断不能证明任意单批完成。第二，模型适配只验证已经声明的关系，不能自动发现未列消费者、证明转换忠实或认证兼容。第三，[API 契约技能](../../skills/api-contracts/SKILL.md)按准确原生任务与共同定义开展工作；原登记冻结执行才使用具名恢复契约，不能把其读回或激活步骤带给新责任。

条款号的结构检查复用目标契约已有表格：在带表头和分隔行的普通 Markdown 管道表格中，只从“本合同条款”列读取裸 `§n` 或本合同 ID 限定的编号。代码围栏、旁注和其他合同引用不构成本合同的声明。这样可以定位索引与声明脱节，无需新增登记表；它不解释承诺语义，也不认证条款粒度、CASE 映射或产品质量。S3 的具体用法及失败后的责任见[阶段条款设计](../l3-stages/L3-S3-contracts.md#8-让验收case条款和任务接成同一条链)。

磁盘编辑检查、正式 Git 来源检查、合成 HTTP 验证和目标产品验收分别提供不同证据。机器保证不能从一种调用路径泛化到全部消费者，测试名称也不能代替实际执行范围。

## 13. 什么情况下可以交给下一责任

下一执行者应能明确回答：本任务依赖哪个共同定义和操作，哪个版本与来源有效，本端承诺如何从共同事实推导，哪些拒绝属于结构或业务，怎样证明实际消费，以及发现冲突后回哪层修复。Main 应能解释并行与依赖的依据，独立验证者应能沿原场景反查实际行为。

这落实 D1 的共同来源、D2 的自然入口检查、D3 的可定位指导、D4 的产物推导和 D6 的独立证明；成本控制来自有限适配与有界阅读。合同、模型和任务各有真实消费者，才能维持一致；再加一层没有执行者使用的元模型不会解决分叉。
