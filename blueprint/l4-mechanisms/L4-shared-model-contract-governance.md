# L4 — 共享模型、合同依赖与渐进式阅读

> 版本：1.0.0；日期：2026-09-19。上游：[L1](../l1-principles/L1-design-principles.md)、[L2](../l2-lifecycle/L2-lifecycle-plan.md)。消费者：S2–S7、S9/S10、合同检查、任务派发与基线登记。

## 1. 权威与边界

业务目标属于 REQ；领域边界、规则和状态属于 S2；共享模型拥有字段结构和数据约束；SYNC 拥有操作、时序、错误和恢复协议；FE/BE 拥有分端责任；TASK 拥有本次执行范围。下游细化而不覆盖上游。每种事实只有一个作者源，既有原生 Schema/协议可直接作为源，不另建注册中心。

项目维护当前模型体系，REQ 记录来源而不拥有模型副本。领域、传输、持久化/展示是职责层次，不要求三份 Schema。只有真实转换才需要映射。相同语义复用，不同领域概念不因同名强行合并。

## 2. 推导与阅读

REQ/S2 → 模型与 SYNC 按业务切片共同收敛 → FE/BE 可并行定稿 → TASK。请求响应由具体操作塑造，不先完成全项目模型再做协议。

Builder 从 TASK 的目标、范围、依赖和完成标准进入，依次打开本端条款、SYNC 操作、共享定义、必要的状态/场景解释，再返回 TASK 执行。Planner 从 CONTRACTS 进入；Reviewer 反查共同基线和 REQ；验证者从 SYNC/CASE 进入。

相对 Markdown 文件链接附阅读目的，使用稳定锚点。必读清单有限、有序、去重；背景链接不默认必读。执行先决条件沿既有 TASK DAG 校验，导航回链及递归模型允许存在。下游声明引用，反向消费者从既有索引查询，不手工双向登记。

## 3. 首版可执行契约

新 CONTRACTS 索引声明 `Shared model policy: json-schema-v1`。`Shared model baseline` 表逐行声明 Operation、Slot、Schema、Consumers、Valid example、Structural negative。Operation/Slot 是现有协议中的操作及数据位置，例如 cancelOrder/request；相同键只允许一个源。Schema 使用相对 Markdown 链接，可带 JSON Pointer 或原生锚点。Consumers 列链接 FE/BE/SYNC 文件；这些文件的 `Shared model inputs` 章节必须引用所消费的同一 Schema。引用是关系，不复制字段定义。

首版机器适配严格 JSON Schema，通过现有 jsonschema 库校验，不假装支持任意 OpenAPI/Proto。已有其他格式可以继续保持原生权威，待有实际适配器后采用对应策略，不自动转换或声称已验证。新批次无法适用此格式时由规划审查明确覆盖限制，不能以未声明策略冒充新机制已完成。

不涉及共享数据时声明 `Shared model policy: none` 并填写非空 `Shared model reason`。无策略的既有合同以 legacy 诊断保留，不静默重写既有冻结批次；新模板及 S5 审查要求明确策略。

每行需要一个合法 JSON 样例；结构负例可为 `N/A`，若提供则必须被结构校验拒绝。权限、状态和并发导致的业务负例仍是合法数据，沿既有 CASE/CT 验证业务拒绝。模型依赖通过原生引用读取，所有加载均使用同一文件视图；禁止运行时网络下载补齐源。外部契约应预先固定在项目中。

## 4. 基线与冻结

S3 的模型检查按 bound REQ 匹配索引的 `需求`/`REQ`/`Requirement` 元数据；无该字段时使用 CONTRACTS-{REQ 后缀}.md。编辑期不传 REQ 的检查会检查所有已声明策略的索引，既有条款检查范围不在本机制中改写。S3 合同检查读取该批次显式 Schema 和样例；编译器实际加载的本地传递依赖一并记录。S3 登记将这些文件作为 `design` 文档纳入现有 documents[]，按路径稳定标识和内容哈希登记；不会因模型漂移自动刷新冻结 subject。S5 审查必须包含这批 documents，S6 写保护复用现有设计锁。

阶段检查、发现、读取和登记使用上游指定的 Git tree；编辑期命令显式读磁盘。S5 冻结前重新对比已登记源的哈希，漂移返回合法设计变更路径，不用新内容重写旧审查依据。比较共同源文件闭包，不要求双方 checkout commit 相同。

真实共享实现必须先回收到绑定开发分支，再派发依赖者；若双方从同源 Schema 独立生成到不同目录，可并行。无关迁移不天然阻塞前端。遵循 [Worktree 机制](L4-worktree-governance.md)。

## 5. 消费与验证

FE/BE 必须通过已有生成器或边界校验器实际消费源，Mock 同样受约束；只有文本引用不算实现完成。生成工具/配置固定，有生成物才检查重生成一致性。真实联调验证认证、时序、持久化和恢复；生成测试不能替代独立 REQ/S2 审查。

S3 检查共同定义与样例，S4 检查必读链接与 TASK DAG，S5 冻结准确 subject，S6 交付同源实现，S7/10 沿原有 CASE/条款回证。检查失败给出修复位置，不新增工具调用审批或 worktree 硬门。

## 6. 成本边界与验收

首版复用合同索引、TASK 清单、文件视图和 documents[]，不增加 registry、通用图、映射 DSL、多语言生成平台或自动语义兼容裁决。只检查已声明输入及必读链接，历史可选背景不阻断本次推进。

必须验证：两端引用不同源、未提交模型、传递依赖漂移、无效正样例、无效结构负例、业务负例、断开的必读锚点、合法递归模型、不同 commit 同一模型、实际消费者和真实交互。收益观察采用既有缺陷与任务证据，关注返工轮次、发现阶段、阅读补问、检查耗时及误报，不新建日常报表。

## 7. L1 映射

D1：模型和基线外置；D2：消费校验进入既有合同/任务自然路径；D3：阶段未就绪给具体指导；D4：模型/协议/阅读模板逼问歧义；D5：首版只增加确定性检查；D6：独立审查与真实联调；消费/成本公理：每个声明均有检查者或执行者，不建设无消费者的元模型。
