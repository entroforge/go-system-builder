# L4 Worktree、交付集成与恢复

## 1. 隔离工作区解决什么问题

多位执行者同时修改产品时，需要分别保留本人改动、检查与失败现场；Main 又必须把这些贡献组成一份真实、可验证的交付。若大家直接写同一目录，难以区分来源和冲突；若把子工作区提交或退出当成完成，Main 中可能仍没有成果，也没有检查过合并后的树。

Worktree 提供隔离的 Git 工作目录。工程机制在其上明确来源、目标、接收和恢复，让专业交付、Main 集成、必要检查与资源清理各有明确责任。S6 保留原接收和确认工序；S7～S9 按[工作流收敛 §3.3.1](L4-workflow-convergence.md)接收原答卷并按完成事实分流，清理独立处理。这些事实分别发生，不能用一条 completed 消息相互替代。

本机制服务 S1 的目标绑定、S6／S9 的写入贡献及 Main 集成，也支撑 S7 读取真实产品基线。它不管理 Claude Code 进程，不给原生 Worker 增加启动许可；原生派发与两端接入见[子代理工程衔接](L4-agent-dispatch-governance.md)。

设计依据是 [L1](../l1-principles/L1-design-principles.md) 的外置权威、自然路径观测和独立背书。集成检查与独立专业验证分别承担责任：合并树上的命令通过，不自动等于需求已兑现、完整审查通过或获得发布授权。

## 2. 三种位置与四类目标怎样区分

### 2.1 控制根、执行根与 Git 公共目录

| 位置 | 保存什么、承担什么 | 如何确定 |
| --- | --- | --- |
| 项目权威控制根 | 当前 REQ 绑定、Runtime、journal、原责任、接收与集成事实 | 原 REQ 的 workspace binding |
| 本人执行根 | 隔离产品、测试、私人专业计划／结果及现场 | 平台实际 worktree 或已登记冻结来源 |
| Git 公共目录 | 多个 checkout 共享的仓库对象与引用 | 用于核对是否同一仓库，不决定工程控制根 |

Main 自身可以是 linked worktree。此时它仍是本次绑定的控制根，不能因为 `git common dir` 指向另一 checkout，就将 Runtime 或集成目标搬过去。

Worker 不复制 Runtime／journal 形成第二写者，也不靠 Git 合并活跃控制状态。私人计划和结果可以先保存在执行根，再由原消费者持久化需要的工程事实。文件来源与 Writer 的权威边界见[事务核心](L4-state-transition-core.md)。

### 2.2 需求开发目标与最终发布目标

原绑定明确声明 `project_root`、`dev_branch` 和 `release_upstream`。开发贡献集成到 `dev_branch`；最终发布目标由 `release_upstream` 表达。Main 依据当时实际工作区安排任务来源；旧记录可能含 `bound_commit`，只作为历史数据保留，不由 Hook 登记或校验 Git OID。

开发分支没有 develop／main 等默认值，也不从 tracking upstream 推断发布目标。涉及远端时，需要明确实际远端与引用；保存目标字符串不等于已验证外部发布环境。

当前目录切换、Main 临时换分支或 manifest 出现另一目标，都不会自动改变绑定。集成前 Main 要回到正确目标，保留当前本地工作；S6 集成器核对实际分支；S9 由 Main 对正确目标负责。不自动 checkout、stash 或替用户重命名。

### 2.3 一份交付的实际工程事实

| 专业事实 | 它说明什么 | 不应与什么混同 |
| --- | --- | --- |
| 任务的实际输入和工作区 | 本人工作从哪些材料开始 | Main 后续产品或本人最终成果 |
| 本人交付与 Main 集成 | 谁完成了什么，以及 Main 是否实际合入 | 平台返回或独立审查结论 |
| 本人自检与 Main 检查 | 谁对当时实际产品执行了什么检查，结果如何 | 对后续变化自动有效或由系统证明的专业正确 |

Main 和作者在真实工程工作中判断输入、集成与检查，不需要 Hook 生成、登记或核对 Git OID 作为证明。原接收可保存责任、实际工作和结论；旧 `bound_commit`、`source_head`、`target_head`、`merge_commit`、`tested_head` 等保留在历史记录中，不重算或作为新接收、恢复与资格条件。正常 Git 工具及 Git 自身内部表示不受限制。

## 3. 原生创建怎样取得正确输入

### 3.1 平台创建，工程固定材料

新 S6／S9 写入责任由 Main 携带准确 brief 原生派发，Claude Code 创建本人 worktree。当前仓库设置 `worktree.baseRef: head`；Main 仍须确认自己在绑定开发分支，必要输入已经提交，实际 HEAD 包含本次任务所需材料。

设置 head 不会携带 Main 未提交或仅暂存的内容，也不能纠正 Main 站在错误 checkout／分支上的问题。嵌套工作区的 HEAD 可能与绑定 Main 不同，因此“来自 HEAD”必须结合实际目录与工程起点解释。

S6 由 Main 准备实际输入并发布 brief，返回后按已有责任接收实际交付并处理集成；不要求作者登记源提交，也不让 Hook 记录或核对 Git OID。

S9 的 brief 提供本人原 Plan／Result 的准确路径、必要材料、单元和依赖，作者只保存原专业答卷。系统不建立 typed／flat 双份答案、不要求 Git 原始 `??`，不因 tracked、staged、ignored、项目／info／global ignore 或 index 状态拒收答卷。路径仅定位本人原责任，不作为所有权、防伪或平台保树证明；本人日志和中间产物无需逐一引用、提交或登记。

Main 负责确认实际工作区取得适用输入与已满足依赖，负责工程目标和后续集成；框架不在每次事件核共同 Git 基线、HEAD／branch、source pin、摘要或证据字节。自然事件只定位原责任并读取本人原卷，单次核解析、必要字段、就绪与结论后保存，直接交下一责任。Plan 可独立接收，Builder 连续工作；没有 Result 不阻止 Plan 或真实未完成返回。

删除历史 C source-v1、D、冻结材料及其旧接收／恢复接线，不新建来源链、typed 副本或 SHA 证据捕获。用户业务数据和已成立专业事实保留；同一当前机制在途责任按实际原关联接续，材料不足交 Main，不要求已履职作者重交。

平台创建、回收和保树行为按实际环境说明，不承诺普通路径必然保留工作区或 branch。Main 应在真实交接中保存必要材料，清理授权与阶段分流分别处理；不要求空提交、无关修改、seal 或额外动作换保树。历史合成平台报告只说明当时有限场景，不能证明新合同或完整 S9→S7 已实现。

### 3.2 正式输入与运行证据分别交接

代码、测试与按阶段要求提交的正式文档，从声明提交中读取。明确不入 Git 的运行证据可以按原依赖引用读取，或在支持的边界交付只读副本，说明来源与适用性；不能据此复制或软链接整个 `.claude`。

Main 派发前整理本次所需输入，不能自动提交用户无关改动来制造干净状态。缺上游时，反馈准确材料与准备责任；Worker 不应从 Main 未提交文件猜出一份未声明基线。

### 3.3 创建能力不是第二执行生命周期

原有 `runtime worktree-create`、冻结 workspace 及其准备／恢复能力各有既定用途；它们不是新原生 Worker 必须先走的路线。当前 settings 没有注册 WorktreeCreate 来替代平台创建，不能声称框架已经接管每次 worktree 的创建。

如果采用创建替代 Hook，必须真实创建并按平台协议返回路径，同时承担失败恢复；只输出提醒不能代替该事件的创建义务。现行新任务继续使用平台原生创建，工程记录只关联真实输入与返回来源。

## 4. 目录与文件边界怎样保持一致

### 4.1 临时工作区不混入项目扫描

项目级资产发现和文档扫描需要排除临时工作区，否则同一份文档或代码会被发现多次，生成错误分母、重复职责或无关差异。排除依据包括约定目录、Git 已登记路径及实际目录边界。

当前 `pathscope` 排除根内 `.worktrees/`、`.claude/worktrees/` 和 Git 登记的其他工作区，支持根内自定义目录及外部路径；符号链接与尚不存在的输出路径也解析其真实祖先。路径 `scratch/worker` 不应误伤 `scratch/worker-other`。

指标摘要原子发布使用保留的 `.claude/.loop-metrics-v1-<32 位小写十六进制>.tmp`，旧发布器遗留的 `.claude/.loop-metrics-<uint32 十进制>.tmp` 也按此暂存处理。这里只识别准确文件：父目录必须存在且不是符号链接，现存叶必须是普通文件；状态观察后仅叶消失可以是 rename。S6 等原产品扫描消费者先保护 HEAD、暂存区、冻结对象或已有基线成员，只把符合其未跟踪条件的文件视为控制面暂存；不扩大到邻居、子目录或相似名称。这个内部命名不是所有权证明，同名未跟踪普通文件可能被当作暂存，识别不授权删除或回收文件，也不改变 Worker 工作区回收授权；S7～S9 不为答卷接收运行这项分类核验。

根本身是 linked worktree 时，扫描不能把自己排除。成果合入 Main 后，按 Main 产品路径参与检查，不因它最初来自临时目录而隐藏。

### 4.2 扫描、S6 干净检查和专业差异判断各有目的

项目扫描排除临时工作区用于避免重复发现，不代表目录中所有内容都无关。S6 集成器按实际产品及当前本人原结果处理；删除旧安装覆盖层的兼容接收，不将任意 ignored 目录推断为交付或自动删除。

S7～S9 答卷接收不依赖 clean 投影、私人目录排除规则或 Git 文件分类，不检查原稿是否 tracked／staged／ignored，不回读证据或生成摘要。私人答卷和辅助日志与实际产品修改的区别，由 Main 和作者在专业工作中说明；不能因文件未引用或未登记就禁止存在或要求删除。系统不借产品检查重新建立答卷资格。

当前 Git 产品读取器的排除范围与 `pathscope` 不一定相同；维护扫描器须说明其真实用途和阶段。S6 产品差异读取仍履行原职责，S7 的完整审查范围由 Main／Reviewer 依实际材料判断，不将全量扫描、基线证明或逐路径摘要提升为接收前置。

这些边界不恢复新原生 Worker 的逐工具 ACL、首写门或通用激活；资源删除仍需独立的实际授权。

## 5. Main 怎样接收一份实际贡献

### 5.1 先看原领域交付，再安排集成

S6 Stop 将本人专业 Plan／Result 交原完成消费者，继续按原完成合同。S9 的自然事件将本人 Plan／Result 按原答卷最小合同接收；这记录作者陈述与就绪结论，不证明真实修改、自检或集成。Main 继续承担实际合并和必要检查，不新增集成证明答卷。

Main 应读取原责任与回执，核对真实成果来源、未完成事项、目标和必要检查。不能只凭 Worker 说“完成”、子分支存在或平台已退出就清理现场，也不能让本人等待 Main 后续集成才结束原生执行。

### 5.2 S6 与 S9 的范围消费不同

S6 的原 Assignment Result 与集成链依据正式 TASK、有效写范围和真实差异检查交付；计划路径只是预测，最终事实来自 Git。必要只读来源与冻结材料也按原契约核对。

S9 按批准修复意图开展专业工作，接收时只核原答卷的解析、必要字段、就绪与结论，Candidate 表示已交付待 Main 处理。真实差异、范围偏差、正确目标和必要检查由 Main 判断；不套 S6 路径 ACL，也不因旧 domain delivery 配置保留系统锁链、候选摘要或执行证明门。

不能因此统一宣称“所有阶段都逐路径硬拒”，也不能把没有这道通用门误解成允许修复任意扩张。专业范围约束与机器已实现的拒收范围需要分别说明。

### 5.3 无变化也是一种需要准确解释的交付

S9 的合法测试或复核责任可无产品差异和新提交，Main 仍做必要检查与影响判断，独立验证者仍复验必要断言。系统接收原答卷并沿保存的完成事实分流，不制造空 merge 或假提交；worktree 已回收不撤销已接收专业事实。

这不是所有路径都支持的通用豁免。canonical S6 首次集成仍要求真实 source 提交；修订和前驱已合并情形按原 Main 来源证明处理。S9 全批无差异仍需 Main 影响判断与独立必要断言的实际复验，完成事实成立后自动交新 S7。具体边界见 [S6](../l3-stages/L3-S6-build.md)与 [S9](../l3-stages/L3-S9-repair.md)。

S6 已接收的 checkout 缺失时，原诊断给出准确路径、分支和 accepted SourceHead，由 Main 恢复该 Git 来源再沿原 task-integrate 接续。原消费者已经保留 Plan／Result，不需要重造私人作者缓存，更不能补一个新提交来“恢复”已接受来源。精确恢复后仍按 S6 实际提交范围和必要检查判断；资源恢复不自动扩展为零提交范围支持，也不授权伪造产品变化。

## 6. S6 检查点怎样把集成拆成可恢复事务

### 6.1 集成阶段不是平台运行状态

```text
pending → ready → merged → verified → acknowledged → cleanup_pending → complete
```

这是 S6 原 Integrator 的持久化工序，不是 S7～S9 答卷接收状态机，也不要求 S9 为推进 Final 经过 ready／verified／ACK。S9 已有旧检查点仅保存其历史事实，不成为新链资格。`blocked`／`preserved` 保留失败与已完成边界，`resume_state` 说明从哪一步继续；它们不等于成果失效或不可恢复终态。

| 工序 | 持久化的事实 | 仍未发生什么 |
| --- | --- | --- |
| ready | 当前交付坐标已准备进入合并 | 不代表 Git 已合并 |
| merged | 记录实际 merge 或受支持无变化交付的目标 | 不代表必要 Main 检查通过 |
| verified | 实际检查及被测树、原 Result 关联 | 不代表原领域已确认和资源已清理 |
| acknowledged | 原确认工序成立 | 不代表目录删除已完成 |
| cleanup_pending | 已准备回收确切已接收资源 | 允许清理失败后单独重试 |
| complete | 本项集成与原回收闭合 | 不等于整批通过或发布完成 |

检查点保存原责任、Result 关联、实际已完成工序、检查引用、错误与恢复位置，不计算、登记或匹配 source／target／merge／tested 的 Git OID。采用明确 Assignment Record 的 S6，检查点按原责任 revision 区分，后继不能借前驱的一份 PASS 或 ACK；历史已有坐标仅保留为旧数据，不以其匹配作为继续的资格。

### 6.2 Git 操作与检查点写入不能伪装成同一原子动作

Git 合并、文件系统操作、检查点 CAS 与 Runtime 确认分别持久化。进程可能在合并后、写入 merge receipt 前中断，也可能删除目录后尚未写 complete。

机制按原责任与已保存工序继续，而不是通过重做所有动作恢复。未知事实保留未知；一个“幂等键”或目录消失都不足以证明接收。Runtime 事务原子性见事务核心，不能把它扩大为 Git、测试与清理的跨系统原子事务。

## 7. S6 Inspect 与实际合并怎样配合

### 7.1 Inspect 提供可复核的当前观察

S6 Main 处理原责任与 Result，在实际工作区判断可用输入、修改、冲突、集成目标及适用检查；实际工程问题应带具体反馈。框架不将 Git OID 登记、比对或来源证明作为原答卷接收资格。

Inspect 不靠自报路径推断差异，也不把清空写范围当成一份新授权。S6 canonical 读取原 Record／Result，验证其专业 closing 条件。S9 Main 可用实际 Git 工具和必要诊断处理工程问题，但 Inspect、候选验证器、锁与完整来源核验不是接收原答卷或进入后继的前置。

### 7.2 同一 Main checkout 串行变更

S6 原 Integrator 的实际合并、Main 检查和清理使用原 Main 工作区锁串行化。锁归正在变更的 checkout，即便检查点另存，也不能按证据目录分出两个并发 Git 写者。目录别名解析到同一锁根，同一操作通过 context 复用锁。

当前锁竞争有短等待预算，忙时反馈重试同项原集成。只读锁观察报告 busy／available／unknown 等瞬时资源事实，不认证 PID、Assignment、完成或检查通过，也不创建另一集成进程。

观察只是当时的事实；Main 在实际执行集成时判断当前目标、差异和冲突。后续工作或实际产品变化可能使原观察不再适用，不能仅凭先前 Ready 合并；Hook 不计算、登记或匹配 Git OID 判定适用性。

### 7.3 合并到绑定开发分支并保留真实历史

S6 改变产品的正常集成使用 `git merge --no-ff`，保留本人提交和普通合并关系。目标必须是绑定的开发分支，Main 工作区保持干净；集成器不 squash、自动切分支、提交无关内容或代做 release。

冲突与未提交修改保留现场。解决问题需要 Main 或原专业作者作实际判断，不能用 reset／stash／强制覆盖来把检查结果凑成成功。检查点记录已经发生的 merge，重试不能另造第二次相同合并。

## 8. 必要检查怎样绑定真实被测树

### 8.1 本人自检、预合并检查与 Main 检查分别表达

Worker 按 TASK／修复责任完成真实自检，并如实给出命令与结果。Main 的集成检查验证合并后的实际树；二者不能互相代替。

S6 原兼容 manifest 未声明检查模式时，保留预合并 Worker 树与合并后 Main 树的两处检查；显式 `post_merge` 可省去该预合并命令重复，但仍保留本人的专业自检与必要静态检查，且必须有实际理由和恢复安排。

S6 canonical Record 的 `required_checks` 当前由 Main post-merge 承担，原生准备也明确生成 `post_merge` 配置；它不把 Main 命令复制成一份 Worker runner 合同。Worker 仍按真实 TASK 自检，Result 如实引用。这与兼容 manifest 的默认双位置行为需要分开解释。

### 8.2 命令从原责任或真实 Main 选择取得

S6 Main 检查消费原 Record 及其 Main CheckProfiles，按原领域配置记录所检提交和回执。底层通用 Integrator 允许空检查集合，不能仅凭 `verified` 字符串声称执行了真实测试。

S9 Main 按批准修复目标与实际变化选择必要检查，在真实集成产品执行，记录实际命令、结果与所检对象。Builder 前检是已发生的专业工作，不自动冻结未来 Main 命令；Worker 自检与 Main 集成检查不能互相替代。未执行和失败如实报告，Main 不能把旧 PASS 当当前产品通过。

删除旧 `workspace integrate --check-command` 兼容接线；Main 沿当前原工序实际集成和检查，原答卷接收不以命令配置、检查点、非空日志或机器证明为前置，不新增 Main 证明答卷。

检查执行工具的环境和超时说明见[执行环境与检查](L4-workspace-execution-profiles.md)；其旧机制不为 S7～S9 增加原答卷以外的资格。

### 8.3 实际被测对象与机器保证的边界

S6 保留实际命令、退出结果、日志引用、原责任与 Result；Main 判断检查所覆盖的实际工作，专业内容变化时决定是否需要重验。Hook 不登记 `tested_head` 或校验 Git OID 作为检查资格，不把原检查结果冒充对后续变化的专业保证。

S9 Main 对实际检查覆盖的产品负责，条件变化后专业判断是否重验。框架不在接收前后重复核 HEAD、branch、原稿、Final 或证据摘要，不机器认证实际命令执行、来源字节完整性和实时漂移。独立 Targeted 与新的完整 S7 继续做实际观察；这些专业责任不能由机器接收替代。

## 9. 确认、依赖释放与清理怎样衔接

### 9.1 S6 确认与 S9 完成分别认定

S6 Main 确认消费对应 Record／Result 与 verified 检查点；同 owner 承担多项责任时，原确认检查其余交付，不能确认第一份就关闭全部责任。S6 依赖释放继续消费工程 done 与 verified integration，单独提交、接收或合并不足。

S9 Candidate、Main 完成与 Final 表达不同真实工作。Main 负责实际集成与必要检查；已有 Final 可按原工序事实复用，但不作为新链接收或后继的前置；不重核 typed、候选摘要、当前 HEAD、Main 检查证明或 CAS ACK 资格。不要求作者额外确认或另交证明表。

Main 接手 Candidate 时即可准备原 ChangeImpact，沿 [S9 §7.2](../l3-stages/L3-S9-repair.md#72-main-执行真实集成与必要检查)复用已有专业表达或自然记录承接实际集成与影响，不以 Final 先行作为准备或接收前提，也不把提前准备题目当成整批已完成。实际专业责任和原答卷结论接续独立 Targeted；Targeted 通过自动 Handoff→新 S7。旧检查点或 ACK 仍可保留历史，但不是影响准备、接收和阶段分流前提。准备失败保留已成立的 Final、已有 ACK 与本人原稿，续原准备入口，不重做已完成检查、不重收 Final、不覆盖 Impact 草稿。清理 pending 单独报告，不撤销专业完成或让已交付作者重交。

### 9.2 清理只处理确切已接收资源

资源删除与专业接收分开认定。Main 在实际清理前确认本次有权回收的工作区及其内容，保护未交付成果、其他责任、未知邻项和需要保留的材料；私人目录、日志字段、Git clean、ignored 分类或目录名都不是删除授权。授权不足或现场不明就保留并报告具体资源与接手人，不要求作者逐文件补引用、登记或手删以换取业务完成。

S6 原 verified／ACK／cleanup_pending、checkpoint 与来源核对继续在其原回收范围适用；不扩大删除授权，不全局 prune，不以 force remove、git clean 或递归删除未知内容制造完成。旧安装覆盖层和私人文件只按实际原授权处理。

S9 不为清理额外建立 source HEAD、目标合入证明、原稿字节、证据 capture／SHA、typed 文件或全量目录干净核验链。Main 依据实际授权决定保留与回收必要材料；必要证据若尚未交接或原稿可能承载未完成工作，应保留现场。清理工具的保守拒绝可以作为资源故障报告，不能升级为重新拒收原答卷或阻挡已就绪后继。

内部写入幂等和安全持久化不要求作者再动作。文件系统、Git、平台回收与记录更新并非跨系统原子事务；发生并发写入或内容冲突时保留具体现场，不能声称所有外部进程已静止。树删除不表示 branch 回收，长期阻塞资源及磁盘成本单独报告，不自动 GC 未授权资源。

### 9.3 清理中断不改变原专业结论

清理失败保留已接收事实和真实恢复位置，解决资源问题后仅继续清理，不重复合并、检查或交卷。目录消失不代表先前专业接收成立；已收后平台回收也不撤销完成。孤立且无授权的资源只报告，不自动删除。S7～S9 的状态查询只投射事实，不为补清理而重验旧卷、证据或历史。

## 10. 失败与响应丢失怎样继续

| 情形 | 应保留什么 | 原恢复方向 |
| --- | --- | --- |
| Main 或 Worker 有未提交修改、source 新提交 | 实际目录、差异和原交付 | 查明内容归属，按原修订／重新检查处理 |
| 合并冲突 | 原 source／target、冲突现场、检查点 | Main 处理真实冲突，不自动 reset／stash |
| 合并后检查失败 | 已合入树、命令／日志、失败工序 | 环境问题重验原候选，代码问题返工产生真实新交付 |
| 已接受而响应丢失 | 原接收、检查点与已记录的实际工序 | 查原事实，不重复交付和合并；不重算或匹配旧 Git OID |
| 删除目录后 complete 未写 | 原 cleanup_pending、来源与目标关系 | 确认确切回收后补完工序 |
| 目标历史被重写 | 原合并、检查与当前实际变化 | 交 Main 判断当前产品与必要重验，不撤销历史接收，不以 Git OID 建立来源资格 |
| 控制根／执行根移动或来源丢失 | 原绑定、登记和已有持久产物 | 使用具名迁移／恢复能力，不从同名目录猜回 |

`preserved` 保留的是精确失败边界。检查点有 `resume_state` 时按原已完成工序继续；需要修代码时，S6 走原 Assignment revision，S9 依据原答卷与实际缺口由 Main 安排原责任继续或返工，不增加机器来源证明。不能直接把旧失败改成 PASS，也不能通过换 worktree 丢掉原失败。

## 11. S6 历史集成恢复边界

### 11.1 已有 merge receipt 与丢失 merge receipt

已有原接收和实际集成记录时，按原责任继续未完成工作，不重做已发生的集成；记录里旧 Git OID 原样保留，不重新计算或用作资格。

若系统在实际合并后、记录完成前中断，而现存原记录不能确认合并是否发生，保留待续和现场，明确未知并交 Main 用实际 Git 工具判断、继续对应工序。不能按提交消息或时间猜测已集成，也不要求作者重交；不能在 Hook 中建立或比对 Git OID 证明链，不能把专业判断描述为框架已自动证明。原资源锁、实际错误与未交付工作继续保留，集成与持久化不是跨系统原子事务。

### 11.2 确认前与确认后，目标前进的含义不同

S6 首次确认前如实际产品已经发生变化，Main 根据变化判断原检查是否仍适用并决定必要检查，保留原合并而不重复合并；Hook 不登记或匹配 `tested_head`。已经确认后的正常后续提交与纯清理重试，保留原历史事实，不无限重验每位已完成作者。

S9 以已保存原答卷与完成事实为接续依据。旧集成器的目标前进重验、Main 证明、Final／ACK 恢复和清理检查描述历史实现，不定义新接收资格。已完成工作保留，未完成实际集成或检查交 Main 继续；目标或产品变化的影响由 Main、Targeted 与新 S7 判断，不通过反复机器验源拖回已交付作者。

历史贡献与当前质量分别判断。后续变化不继承旧 PASS，也不把既有接收抹掉；系统对不能识别的原责任或损坏的保存事实报告准确缺口，不从同名文件猜回。

## 12. 如何交给下一完整验证轮

S6 的共同产品起点来自原 TR-003，S6 来源和历史贡献记录继续按其原合同保存。现有 `buildsurface`、原 Runtime／journal、TASK、Assignment、Result 和 Main receipt 可作为读取已有工程材料的实现；不能把重建整条链、全量 Git／SHA／clean 验证升级为 S7／S9 答卷接收资格。

### 12.1 完整变化与覆盖由专业责任判断

Main 为新 S7 提供实际完整产品、适用需求与任务、已有工程材料及变化线索。范围包括删除、配置、依赖、失败残留、原交付、后继修订与本次修复，不能只取当前成功者或最后一个文件。Main／Planner 形成实际审查命题和分工，Reviewer 独立判断覆盖与观察是否充分。

Main 基于当前任务、已收结果、实际集成及可用材料判断审查范围；删除 `frozen_subjects`、`coverage_inventory` 的旧审查证明接线。added／modified 按实际产品审查，deleted 审查删除行为及影响，不为删除另造 SHA、Git blob、不存在证明或逐项机器命题。

S7 原 Plan 与 Reviewer 答卷按解析、必要字段、就绪及结论接收：有 Finding 交 S8，无 Finding 且原计划必要责任完成交 S10。系统不重算 Claim 分母、覆盖库存、CleanRound、ObservationBatch 或证据有效性证明，不以实时工作区漂移核验替代 Reviewer。原索引缺少路径或专业覆盖不足，由 Main／Reviewer 调查与修正；新增字段不能变成第二份机器覆盖证明。

S9 Targeted 通过后自动给出新的完整 S7 原答卷与已有材料，seed 不是已登记专业计划或任何 PASS；Main 保存真实专业规划一次后继续，无手动 submit 或重存。新轮以实际完整交付为对象，框架不声称凭 seed 证明基线与覆盖完整。

S10 继续按其原阶段合同消费交付与真实授权，不因本节自动改变发布范围；涉及与 S7 新保证边界的接口，须在对应阶段正文明确。不得在 S7 为维持旧 S10 reader 而复建已删除的 SHA／CleanRound 机器证明链。

### 12.2 历史来源、失败事实与正式规格边界

前驱证据失效不表示其产品内容已撤销，保留历史贡献也不恢复旧 PASS。S6 的 Writer／Reader、Assignment revision、原 TASK 和原生准备继续服务真实工作，但不为这些环节登记或校验散列及 Git OID；失败与成功事实分别保存，规格变化交原规划责任处理。

S7／S9 直接复用这些已有材料的专业内容和责任关联，不重跑 S6 完整来源验证作为自己的接收前置。必要材料实际缺失则由 Main 恢复或说明未知，不要求作者刷新 hash、构造证明、重锁 TASK 或重交已收答卷。旧正式来源尚未接通不应被冒充已具备完整机器保证；本轮实际范围与输入正确由 Main／Reviewer 承担。

## 13. 观察与提醒如何帮助 Main

| 观察位置 | 要回答的问题 | 行动归属 |
| --- | --- | --- |
| 当前绑定与实际分支 | 是否站在正确控制根与开发目标 | Main 保留现场后显式纠正 |
| 原领域回执与待集成投影 | 哪份真实交付已接收、哪项仍缺 | Main 选择原集成入口 |
| S6 检查点与实际 Git；S9 已保存完成事实 | 哪些实际工程工作或资源回收仍未完成 | S6 沿原 Integrator；S9 交 Main 续实际未完成责任 |
| Main 检查记录 | 实际测过什么、在哪个提交、为何失败 | Main 或原专业返工责任 |
| 原工作区锁及资源积压 | 当前是否忙、有哪些已验证待回收资源 | Main 安排顺序，诊断只读 |

提醒应给准确 REQ、责任、来源、目标、缺项和下一动作。相同事实可去重，交付／合并／积压变化再反馈；未回收不是继续运行 Worker 的理由，后台启动也不是待集成完成事实。

新原生 Stop 负责接收已有产物和短事务，不运行长合并、检查或清理。Main 使用实际可见返回、原回执与当前指引接续，不依赖再触发一次 Stop。当前 native 成功诊断并不保证每条父会话消息已到达，不能仅因 Hook 输出过一句提醒就宣布反馈闭环成立。
