# L4 项目级设计基础

本机制解释跨需求的交互与视觉共识怎样形成、被执行者继承，并通过真实使用继续演进。需求中的使用入口见 [S0 需求设计](../l3-stages/L3-S0-requirement-design.md)和 [S2 设计](../l3-stages/L3-S2-design.md)；实际操作由[设计基础规则](../../docs/rules/design-foundation.md)与[设计基础技能](../../skills/design-foundation/SKILL.md)承载。

## 1. 为什么需要跨需求的设计基础

### 1.1 局部完成不能自然长成统一产品

需求通常按模块和批次实现，用户却会把这些模块理解为同一个产品。若每次设计只问当前页面怎样好看，执行者就会从组件库、上一页截图或自己的偏好出发，各自选出局部最优。等多个页面完成后再统一颜色、按钮和间距，只能修表面；信息先后、服务姿态、承诺方式与错误恢复仍可能互相矛盾。

项目设计基础提前回答另一组问题：产品以什么身份面对用户，什么信息值得被强调，用户在什么条件下作出承诺，哪些类别惯例应该继承或拒绝。它把这些判断变成可引用、有消费者、能被反例挑战的长期约束，使不同需求与执行者可以独立工作而保持共同方向。

“简约、专业、有温度”可以帮助讨论感受，却不能单独充当基础。有效基础必须能够生成具体选择、排除不合适方案、组合成页面、适应不同场景，并追溯到产品事实。否则 agent 读完仍只能重新猜一次风格。

### 1.2 与生命周期、架构和设计系统分工

设计基础位于单个需求的生命周期之外，不新增 S0.5、执行阶段或 Runtime 状态。有界面产品可以先建立基础，也可以由首个相关需求触发建立；后续需求按适用范围继承。

它约束信息、视觉、内容与交互选择，S2 仍负责模块、数据、架构、业务行为和测试预期。设计系统则用 Token、组件、模式与工具实现已经作出的选择。三者互相约束，但不存在“选了组件库就完成产品定向”或“有了设计内核就不必做系统设计”的替代关系。

无界面产品可以声明不适用。当前需求不改界面，只意味着不重做界面设计；不能据此把整个产品已有基础改成不适用。

## 2. 对象怎样构成一条推导链

| 对象 | 解决的问题 | 对下游的作用 |
| --- | --- | --- |
| 产品证据 | 哪些用户关系、业务事实、服务方式和约束值得被表达 | 支持方向及取舍，区分事实与想象 |
| 设计内核（Design Kernel） | 产品是谁，有哪些长期信念和明确拒绝 | 生成并筛选具体方案 |
| 设计语法（Design Grammar） | 信念在不同场景中怎样成为稳定关系 | 约束信息、构图、行动、内容与状态 |
| 表面配置（Surface Profile） | 消费者端、运营端或其他终端怎样共享内核又有所区别 | 记录相对共同语法的受控差分 |
| 语义角色、Token、组件与模式 | 已决定的关系怎样进入实际施工 | 提供可复用、可检查的实现绑定 |
| 需求推导（Derivation） | 当前需求具体消费什么，在哪里兑现 | 把全局约束落到模块、页面和操作流 |
| 证明集（Proof Set） | 这套关系能否承担真实内容与困难状态 | 检验方向、适应性和实际效果 |

这些对象不是七份必须分别创建的长文档。精简路径可以在约束卡中表达内核、必要关系和主表面，在当前需求推导中写消费与证明。分文件是阅读与维护选择，不能把同一条规则复制成多个权威源。

推导方向是“证据 → 内核 → 语法 → 表面与实现绑定 → 当前需求 → 证明与反馈”。反馈可以挑战上游，但需要明确改变哪层。不能因为某个局部页面好看，就直接把它的配色或布局提升为全局规则。

## 3. 先决定投入，再决定研究深度

### 3.1 根据复用、换手与风险选择投入

首次理解有界面产品、首次相关需求、新增表面、多人换手、出现共享组件或跨模块漂移时，先在项目地图记录投入档位及理由。

| 档位 | 适用条件 | 应留下什么 |
| --- | --- | --- |
| Local 局部设计 | 一次性交付、单一表面、没有换手复用计划，也不建立共享语义或组件 | 模块内推导、临时值、适用范围及不得直接推广的说明 |
| Core 核心基础 | 长期产品、后续相关需求、多会话换手或需要共享 Token、组件 | 可换手约束卡、实际绑定、主表面差分、最小证明与当前需求推导 |
| Extended 扩展基础 | 多表面、复杂或高风险状态、强服务表达、设计系统建设或反复漂移 | 核心基础加完整关系语法、跨表面与压力证明、项目规则及反馈安排 |

Local 的条件需要同时成立。出现第二消费者、共享组件、交接维护或重复漂移，就重新评估 Core；不能不断增加“临时页面”来规避跨需求共识。升级依据是实际关系与风险，不是按需求数量打分。

Local 不发布项目级 DESIGN，不把模块临时色当作品牌锁；Core 也不要求先建齐全部目录才能开始。纯后端或无相关界面变化的工作读取已有适用约束即可。

项目确实没有用户可见界面时，可以在项目地图声明 N/A。检查器在跳过界面语言检查前，会复用正式需求顶部的 `locked` 与 `UI impact=changed` 声明；若两者同时存在，逐个指出需求路径与地图的矛盾，由 Main 核实原事实并纠正相应来源。工具不据此自动选择投入档位、建立设计基础或要求无界面证明包。默认检查仍为建议性，`--strict` 沿原警告规则返回失败；矛盾提示不等于已经完成完整界面检查。

### 3.2 薄路径与完整路径是另一个维度

薄路径（thin）适用于证据已经明确产品角色、服务仪式和主要取舍的情况：直接提出有依据的推荐，将它与真实的类别默认比较，解释保留和拒绝什么。它减少重复定向，不减少可执行约束、真实绑定和换手责任。

完整路径（full）适用于事实不足或存在真实价值分歧的情况：补研究、形成不同候选、独立批评，再选择方向。不能为了完成流程强造三个近似皮肤，也不能把明显荒谬的类别默认当作陪衬。

因此，长期产品可以采用 Core 加薄路径；多表面产品已有清晰方向，也不必重复制造候选。投入档位决定要承担多大的长期责任，研究深度取决于还有多少方向不确定性。

## 4. F0～F6 怎样建立一套可使用的基础

### 4.1 F0 识别：确定这次需要建立或改变什么

先读现有基础、项目地图与已确认决定，识别当前消费者和缺口。记录投入档位、研究路径、依据、适用表面与升级条件。已有覆盖本次工作的 published 基础应被继承；真实新表面或新业务关系才触发增补。F0 是判断，不要求为每次读取基础新增人类确认。

### 4.2 F1 发现：把产品事实与设计想象分开

调查六类事实：产品本质、用户关系、业务事实、服务仪式、类别惯例、现实约束。服务仪式指产品反复承担的关系，例如“先展示可核对依据，再请求用户确认”，不等于给流程起一个漂亮名称。

材料中区分事实、推断、参考与未知项。参考产品需要说明观察到什么机制、迁移需要什么条件、在本产品中如何改写；不能把别人的视觉表面当成本产品证据。薄路径可直接引用需求简报与项目地图已有事实，不为齐表复制六份材料。

F1 的出口是足以支持方向选择的依据和仍需人决策的问题。若候选只能靠形容词区分，应先补事实，而不是继续画更多页面。

### 4.3 F2 定向：比较真正不同的价值表达

完整路径通常用少量候选比较不同的产品角色、信息顺序、用户关系、美学世界、交互姿态或品牌表达。候选应在多个轴上有实质区别；颜色、圆角和字体的排列组合不能证明方向不同。

方向可以来自证据放大、服务仪式、对类别惯例的有据反转、可解释类比，或把真实限制转成特征。每个方向都要说明用户得到什么、放弃什么、需要验证什么。

方向样本（Style Tile）位于情绪参考与完整页面之间：使用真实内容展示排版关系、行动、状态、色彩角色和关键风险。此时不急于冻结每个数值，也不允许只有色板没有业务关系。

[设计批评技能](../../skills/design-critic/SKILL.md)从真实性、辨识度、生成能力、适应性、可用性与实现可行性提出独立判断。推荐应说明成本、缺证和可保留元素；人选择的是产品价值与取舍，不是替 agent 调按钮像素。

### 4.4 F3 收敛：把方向变成能约束后续工作的内核

内核说明产品角色、中心命题、关键张力、原则、反原则与标志性关系。中心命题要能回答“因为什么事实，因此怎样组织体验，以帮助谁完成什么”，不能只是把几个赞美词串起来。

关键张力用真实选择描述，例如“解释更多可以减少误解，但也可能掩盖关键行动；何时先解释、何时直接行动”。原则随后给出稳定的处理方式、适用条件、代价与反例。反原则明确哪些看似常见的做法会破坏产品关系。

每条原则保留来源和可观察后果。数量服从真实矛盾，不靠凑条目证明成熟；尚不能影响选择的灵感可以保留为储备，不能假称已经生效。

### 4.5 F4 编译：让信念变成可寻址、可施工的关系

把内核中会改变选择的判断写成约束卡，再展开必要语法、表面差分、角色与 Token 绑定。先说明关系和条件，再决定实现值。语法无法生成页面、角色没有消费者或 Token 无法解释来源时，回到产生缺口的层修正。

Core 薄路径可以暂欠独立语法文件，但卡中的规则必须足以指导当前工作；使用人工评审绑定时明确写出，不能引用尚不存在的 `GR-*` 来制造完整外观。第二表面或扩展档位需要把共用关系显式展开。

### 4.6 F5 证明：让真实内容和困难状态挑战方向

使用与投入匹配的样本检验内核，而非只挑最有利的一屏。锚点证明主要关系；压力状态暴露长内容、错误、空态、权限、密集数据或高风险操作中的失效；关键流程证明状态转换；跨表面对照证明变化没有破坏共同语义。

制作样本的 agent 不能仅凭自己的好评宣布成立。引入独立批评、任务走查和可反驳的观察标准。像素稳定可以检查回归，但不能证明信息顺序正确、用户理解承诺或业务效果改善。

### 4.7 F6 发布：使下一个执行者可以正确继承

发布前检查确认、约束卡、实际绑定、证明、表面、当前需求推导与债务处置。Core 至少有方向样本、主表面和一份真实推导；同一页面可以同时承载锚点与压力证明，但要分别说明观察对象。Extended 再提供独立压力、关键流程、表面对照及高风险约束证据。

完整路径通常分别确认方向、内核和发布；薄路径可把这些内容完整展示后合并确认。已经明确的人意无需重复索取。这些确认是专业协作，不是新增 Runtime 闸门。

证据推翻假设时按来源回退：方向空泛回 F1；内核不能生成选择回 F2/F3；关系冲突或压力失败回 F4；一致但无效则重审事实与命题。只重做受影响下游，避免每个细节都重启全部研究。

## 5. 可执行约束怎样避免变成死文档

### 5.1 稳定 ID 连接原因、消费与证明

需要跨需求引用的对象使用稳定 ID：

```text
EVD 产品证据
  → LAW 原则 / ANTI 反原则 / INV 不变量
  → GR 关系语法
  → ROLE 语义角色 / PAT 模式
  → SUR 表面 / 当前需求推导
  → PROOF 证明 / 反馈与修订
```

约束卡不仅列 ID，还说明状态、类型、可执行陈述与正反例、适用范围、来源、绑定、检查方式及证明或复查条件。有效约束需要真实消费者；没有下游绑定的主张应标为储备或债务，而非 active。

检查方式区分人工判断、静态检查、运行证据。比如“重要承诺可被用户解释”需要走查；“指定页面导入语义 Token”可以做静态检查。不能因为一句话写了 `static` 就获得机器可证明性。

### 5.2 用一个例子看完整推导

假设真实观察是：用户担心确认后无法挽回，客服经常解释已在页面上的限制。由此提出 `LAW-01`：“请求承诺之前，让用户看见能够核对的依据”；`ANTI-01` 排除用状态色或大按钮掩盖未解释的条件。

`GR-01` 将它编译成关系：在不可轻易撤销的操作中，依据与影响先于确认入口；可逆的低风险操作可以缩短说明。消费者端选择简明条件与一次确认，运营端选择影响摘要与批量范围；两者密度不同，保留同一不变量。

`ROLE-01` 表示承诺行动，绑定实际语义 Token 与组件。当前需求推导指出它在哪个操作流出现，哪些说明不能被伪装成按钮，并给出超长条件、失败恢复和权限不足的证明。若用户仍无法解释后果，就回查信息关系或证据，不能只把按钮颜色调深。

例子展示的是推导方法，不是要求所有项目采用这个原则或固定行动数量。项目规则必须来自该项目已确认的约束。

### 5.3 一份规则源，两种读取方式

`foundation-contract:v1` 标记与稳定表头使同一份 Markdown 能被人和机器读取。正文解释来由与取舍，标记表格承载可索引对象；不能在散文、JSON 和卡片中分别维护三套相同规则。

当前索引识别约束、维度、语法、绑定、表面、证明、债务和需求推导等有限表格，按表头而非固定章节号解析。标记不是自然语言理解器；随意改表头可能使表格失去可检查性。下游引用 ID 并增加本地具体化，不复制全局条款。

## 6. 语法怎样同时支持一致与变化

语法应说明“因为什么，在何种条件下，优先什么关系，避免什么，允许怎样变化，用什么证明”。32px、12px 或 hex 是实现值，不能独自解释这些关系。

| 维度 | 需要作出的设计判断 |
| --- | --- |
| 信息 | 证据、行动与解释的先后，渐进披露的条件 |
| 构图 | 焦点、阅读路径、密度、留白与节奏 |
| 颜色 | 内容、行动、状态与品牌强调怎样分工 |
| 排版 | 层级、声音、长短文本、数字和元信息怎样区分 |
| 形状与表面 | 边界、层次、材质与空间怎样传达关系 |
| 图像与图标 | 真实性、构图与标记怎样服务信息 |
| 交互 | 选择、确认、权限、错误和恢复怎样发生 |
| 内容 | 解释、承诺、措辞与禁语怎样表达产品关系 |
| 动效 | 注意力、因果、频率与节奏何时有帮助 |

九维是路由目录，每维标为 active、inherited、debt 或 N/A。启用项有实际规则与绑定；继承项说明来源与冲突处理；债务有影响、责任和复查时机；不适用项说明理由及重新评估条件。不能为了齐表虚构动效，也不能把已经使用的维度标为不适用来免除责任。

一条语法同时表达不变量、可变项、选择条件与例外。消费端与运营端可以有不同信息密度，但不能各自重新发明“成功”“风险”或“确认”的含义。遇到新场景时应能根据条件选默认；选不出来就是语法缺口，不应让执行者自行猜测。

表面配置只写差分：引用基础与版本、当前用户和任务、继承项、变量选择、增减项、例外的范围与期限、对照证明。未变化的内容直接继承；抑制共同约束需要明确理由和例外，不能悄悄产生第二个品牌内核。

版本核对从需求推导顶部的 `Surface` 引用出发，沿内核的表面表找到实际 Profile，比较引用版本、表中已有的版本与 Profile 顶部的 ID、版本；Profile 已声明的内核继承版本也与当前内核比较。表中只写文件路径时可直接读取原 Profile 的版本，不要求另抄一份版本。单表面 `inline` 以内核版本为依据，无需为了检查另建 Profile 或独立版本；Local 不因此升级为全局表面。

当前检查只处理这些已声明来源和 `v数字.数字.数字` 格式。未知表面、不可读取的 Profile、来源 ID 不对应或无法解析的版本明确报告未验证，交 Main 核实原引用；不自动选最新版本或改写引用。发现版本不同先判断设计关系是否变化，不能仅刷新版本号消除告警。版本相同只证明这条有限声明链一致，不证明内容兼容、发布授权或其他消费者已经完成传播。

## 7. Token、组件与受限规则怎样承接设计

### 7.1 从关系到实现值

实现链是“原则 → 关系与角色 → 原始值 → 语义 Token → 组件主题 → 产品代码”。原始值服务统一计算与生成，产品消费语义或组件层，避免直接从施工色板推定品牌含义。

Token 源位于 `docs/design/tokens/tokens.json`，使用 `$type`、`$value` 和引用表达值；生成器解析引用、拒绝缺失或循环引用，产生 `tokens.css`。生成 CSS 是派生产物，修改应回到源；颜色原始值登记并不等于页面已经遵守语义角色。

内建颜色检查只识别 `docs/design` 下小写 `.html`、`.css` 文件中的有限 hex、rgb、hsl 字面量，沿原扫描边界排除模板、README、方向样本、便携快照和受管工作区。它不遍历 `src/` 等产品代码，也不计算运行中的 CSS。发布后的带标记基础另外检查已声明 `color.primitive.*` 的 `var(...)` 引用文本；变量定义、名称前缀和生成 Token CSS 不作为产品消费。其他原始值、动态样式及语义使用仍需原专业检查，可选项目规则则按自己的显式目标运行。

Proof／Prototype HTML 中的 `tokens.css` 或 `Generated from ...` 文本只是来源提示，不是可认证摘要，也不证明浏览器加载了该样式。项目已有 `tokens.css` 时，检查器复用原生成器在内存生成结果并与现有文件逐字比较，报告一致、漂移或读取失败，绝不在检查中覆盖文件。没有现成生成物则说明未执行比对，不因此要求新增文件或接入扫描平台。一致只保证这个文件与当前生成器输出一致，不替代实际效果或语义消费证明。

每个生效角色连接规则与实际 Token、组件或模式；组件库默认值需要被适配，不能反向推翻产品内核。组件提案说明为什么现有模式不足、影响哪些消费者、如何证明复用。一个需求中的局部成功样本先是提案，不自动成为全局冠军组件。

绑定检查只承担有限结构责任：核对已有颜色 Token 路径，并对声明中可字面定位的项目相对文件检查是否为普通文件。逗号列表中的有效 Token 不会掩盖另一个缺失的明确文件。无扩展名组件标识、模块别名、URL、链接和模式 ID 不经模块解析或组件注册验证；检查不猜扩展名，也不要求为这些引用补一份登记。

文件存在只证明该字面来源存在，不证明其中导出的组件、产品代码是否使用它或语义是否兑现。部分前缀与薄路径允许没有独立登记，不能把豁免理解为证据已经认证。真实消费与适用性沿现有需求推导和证明完成专业检查，不另建逐条 Proof 流程。

### 7.2 机器只执行项目已声明的有限规则

可选 `docs/design/design-checks.json` 将已确认的项目约束投影为受限检查，规则必须追溯到真实约束 ID。目前支持角色数量上限、禁止绑定、Token 范围、必要导入与禁止字面量五类。

例如某项目明确限制承诺角色的使用位置，才可以生成相应规则。框架不内置“绿色不专业”“等宽字体只能用于代码”或“每屏只能一个按钮”这样的通用审美裁决。

无法解析的规则、缺少来源或无法观测的目标应报告不可验证，交回专业判断。规则的机械范围必须在输出中说清楚，不能把静态通过解释为真实布局证明。

`max_role_count` 只支持 `file` 文本范围，省略范围时同样按文件处理：读取 `data-design-role` 属性中的角色声明，每个匹配属性至多计一次，按完整分项或原有点、斜线限定名识别，不用近似子串多算。它不计算隐藏、互斥状态、响应式布局或实际渲染元素；`viewport` 及其他无法观测的范围明确未验证，不能用文件计数代判视口超限。没有文本标记或无法读取的目标也明确未验证，不要求为了检查建立角色登记。

`token_scope` 是文件文本预检：保留现有 `allow` 字段，将简单 `.class`、`#id`、`[attribute-name]` 或字面标记作为文本提示，复杂 CSS 选择器不解释。Token 与允许标记在同一文件出现，只形成共现观察，元素绑定仍未验证；缺少允许标记时也只说明文本前置条件未满足，不声称已经证明 Token 在某个 DOM 元素外。真正的视口效果与元素关系沿原有证明判断，不为每条规则另建浏览器检查或 Proof 登记。

## 8. 资产组织与换手：足够具体，按需展开

| 资产 | 权威与用途 |
| --- | --- |
| `docs/design/DESIGN.md` | 内核、下一执行者约束卡、主表面、证明索引及债务 |
| `docs/design/design-language.md` | 展开的共同关系语法与角色绑定 |
| `docs/design/surface-profiles/` | 按需独立存放表面差分 |
| `docs/design/derivation/REQ-*.md` | 当前需求的消费清单与具体落点 |
| `docs/design/research/`、`proof/` | 按需展开证据、方向样本与证明 |
| `docs/design/decisions/` | 已确认决定、组件提案和局部例外 |
| `docs/design/tokens/` | Token 源与生成结果 |

Core 薄路径优先维护两份活文件：DESIGN 与当前需求推导，主表面可以内联。研究已有明确来源就直接引用；第二表面或 Extended 才按需拆开语法、独立配置与更完整证明。不能把资产目录当作强制生成或全量阅读清单。

默认换手包由 DESIGN §0 约束卡、当前表面差分与本次需求推导组成，目标约 120 行、12 KB。卡中优先写会改变下一次施工的判断：行动角色、数字与状态色、哪些承诺能成为按钮、哪些只是解释、必须拒绝的类别默认。背景按 ID 展开，不要求冷启动会话读整份研究白皮书。

预算促使表达清楚，不授权删关键条件、截断路径或信息不足时继续工作。检查器按当前需求推导顶部的 Surface 引用定位原表，统计约束卡、该表面声明的实际 Profile 文件与本次推导，不取固定 SUR-01 作为其他表面的代表，也不扫描整个设计树。

内联表面只计入索引能定位的当前表格行，并明确列出未计入的表头、表外说明；缺卡、推导、表面或文件也列为未计入，不按零字节宣称完整包达标。输出是已声明来源片段的范围估算；已计入部分本身超出目标可以提示精简表达，但不能据此删掉必要信息。Main 核对真正发送的材料，额外展开、包装及其他上下文不由这个静态计数代表。预算不成为新的阶段硬门、作者打包手续或独立批准。

便携导出、组件展示环境和基准页面都是消费或证明视图，不能成为第二权威。便携导出只传递原 Token 路径及解析值、内核的约束卡与方向摘录，以及语法中的规则、变量、绑定和可提取的维度片段。每段标明来源，缺项明确说明未提取；不会补字体、行高、间距、强调色或阴影规则。Token 有值不等于已经批准，原始模板值不会因生成快照成为产品决定。

快照是有明确摘录范围的参考，不能替代发布状态、适用表面、条款激活状态和完整性的判断。没有提取到同名章节或维度行，不表示该维度 N/A，也不要求为了导出补造材料；实际选择仍回到内核、语法和当前需求推导。组件 API 留在现役组件来源中，专业效果由原 Proof 验证。源文件不存在时可以生成带缺项说明的局部参考；实际读取错误则报错并保留旧快照，避免把失败的读取伪装成完整导出。

## 9. 当前需求如何消费，而不重新发明

后续执行者先确认基础状态、版本和表面适用性，再用[需求推导模板](../../docs/design/derivation/DERIVATION-template.md)形成具体消费清单：

- 当前表面、页面角色与设计姿态：继承、扩展、例外或局部设计。
- 实际启用的约束 ID、需要展开的语法及本地禁止项。
- 角色、组件、模式与 Token 在真实模块或操作流中的绑定。
- 宏观构图和压力状态怎样验证，证明位置与观察标准是什么。
- 需要新增的语言、例外、债务及仍未决定的问题。

推导不是抄写全局原文，也不是只列“遵守设计基础”。应能从某个实际页面选择反查其来源，从某条 active 约束找到本次消费者。先用主要构图与压力状态验证关系，再扩展页面，避免实现很多页面后才发现整套姿态不适用。

当前需求需要不同选择时，先判断它是否落在已有变量范围；不能解决再提出例外或全局修订。上一需求留下的临时 hex、组件库默认主题或某次演示截图都不足以替代这个判断。

## 10. 发布与版本怎样维持共识

设计文档状态 draft、in-review、provisional、published、superseded 表达领域成熟度，与[工程责任五态](L4-state-transition-core.md#unified-work-state)分开。

published 表示当前范围内已有真实确认、可执行卡、实际绑定、最小证明和未决项处置，不能同时保留“待确认”却宣称已锁定。provisional 只服务明确记录风险的当前试验，不自动传给下一需求；superseded 用于追溯，不能当当前依据。

版本跟随语义变化：修正文字且不改变选择属于澄清；增加兼容关系属于扩展；改变现行约束或消费者含义属于破坏性变化，需要人重新确认并评估影响。局部例外有自己的范围、期限和退出条件，只有被正式吸收时才改变全局基础。废弃 ID 不复用成另一条新规则。

页面与现行语法冲突，先修局部；组件库与内核冲突，先适配组件；真实业务推翻基础，走例外或修订。基准截图落后时更新相应证明，不能让旧像素成为压倒新共识的权威。

## 11. 验证、观测与反馈怎样闭环

### 11.1 四种证明不能互相替代

| 验证层 | 核心问题 | 方法与边界 |
| --- | --- | --- |
| 引用与绑定完整性 | ID、版本、角色与证明能否被解析 | 静态索引和有限规则可提供部分证据 |
| 推导忠实性 | 页面选择是否来自约束，禁止项是否真的被拒绝 | 专业审查、独立批评与反向追踪 |
| 系统一致性 | 页面、状态和表面是否共享同一语义 | 组件样本、跨表面对照及视觉回归 |
| 体验有效性 | 是否改善理解、信任与任务结果 | 真实任务走查与用户观察 |

换手证明尤其关注：新会话在下一个需求中，能否只凭有界包正确继承关键关系并拒绝不合适默认。引用存在、截图一致和主观评价都不能单独替代这一结果。

### 11.2 用信号定位漂移发生在哪一层

反复重新问风格说明换手卡不够具体；工程调色板变成产品品牌说明实现越过权威；active 约束无绑定或角色无消费者说明编译链断开；像素通过却任务理解失败说明证明层级不足。阅读材料不断膨胀则需要修交付组织，而非减少必要设计。

记录应关联当前需求、表面、基础版本、受影响约束和实际证明。观察的目的是定位“事实、规则、消费还是实现”出了问题，不能用引用数量或告警数量代替设计质量。

### 11.3 回到正确权威层，回放后才关闭

反馈按五步处理：记录真实观察与来源，识别受影响 ID，分类并修改正确权威，重查引用与消费者，回放证明后关闭。分类区分局部模块修复、组件或模式提案、全局澄清或兼容扩展、有限例外、内核破坏性修订。

反馈回执保留来源观察、受影响约束、分类、改变的关系、回放证据、开放或关闭状态。可以附着在原 Finding、组件提案、决定或例外中，不新增独立反馈数据库。报告写完不等于关闭；临时例外也不能在无人负责的情况下永久存活。

这里的闭环是专业协作协议，当前没有一个自动完成全部反馈步骤的 Runtime 原子事务。S7 的发现处理和 S10 的结论仍由各阶段负责；基础更新后，受影响需求是否需要重审按真实影响判断。

## 12. 与阶段、原生代理及项目惯例怎样配合

| 使用位置 | 应做的工作 |
| --- | --- |
| S0 | 识别 UI 影响、设计投入、Foundation 引用、表面和继承姿态 |
| S1 | 绑定当前需求与开发目标，不借绑定重新裁决设计方向 |
| S2 | 保留架构轨，另将基础推导为当前模块、行为、原型与证明 |
| S3～S4 | 契约与任务显式携带相关依据，明确施工和验证责任 |
| S5 | 审查设计包是否真正可执行，不能把基础存在当一致性结论 |
| S6 | Main 交付相关约束，执行者按本次推导实现并报告例外 |
| S7～S9 | 以真实发现验证、调查和修复；涉及全局关系时反馈基础 |
| S10～S11 | 解释遗留风险与交付结论，不将工具静态通过变成人类授权 |

设计基础不需要第二套代理派发机制。Main 通过[原生任务交付](L4-agent-dispatch-governance.md)提供准确引用和必要上下文，专业结果由原阶段消费者接收；普通 Hook 不自动替执行者完成设计推导，也不能从角色名猜出适用表面。

工程惯例与设计基础共享“从已批准来源生成有界参考视图”的思路，但各有权威。可选 `docs/rules/project-conventions.json` 按主题和范围索引原 Rules、架构或设计决定及真实实现样本；索引写着 approved 不足以批准一条新规则。当前解析器核对原规则索引、锁定状态、版本、摘要与正式输入，示例也要能追到相应开发视图；冲突全部保留为问题，不选一个默认赢家。

没有惯例索引不能成为新增开工门。TASK 中显式阅读材料可以形成待确认候选；正式任务分析中的投影与源摘要沿原输入冻结，派生卡不复制业务契约。现有 TASK 分析与兼容上下文路径支持这些视图，不表示每个新原生 brief 已自动注入全部设计基础或工程惯例；Main 仍要检查实际交付内容。

## 13. 当前实现能保证什么，缺口在哪里

### 13.1 工具入口及适用范围

`loop-harness design-foundation check --root .` 默认提供建议性报告，告警仍返回成功；`--strict` 才将告警作为失败，`--json` 输出结构化结果。它不属于 `validate --all`，也不是规划出口对完整设计基础的强制语义门。项目若选择严格检查，应有稳定、可归因的失败证据，不能把任意审美主张升级为全局硬门。

检查区分模板工厂、兼容文档和带标记契约三种模式。能力包括部分发布状态提示、引用关系、维度路由、绑定、推导、Token、设计目录颜色与组件重复启发式，以及可选项目规则。无告警只说明本次识别到的检查未发现问题。

`emit-css` 实际生成 Token CSS；`export-portable` 产生便携消费视图。`migrate --to contract-v1 --dry-run` 是只读诊断，按原文件列出对应模板、缺失标记和现有解析器要求的列。作者据原文确定表格对应关系，保留有效 ID、未知列与设计依据；工具不猜投资档位、自动生成债务、改写继承关系或把截图提升为 Proof。

自动迁移写入没有受支持的实现，`--write` 或关闭 dry-run 均明确返回 unsupported 和非零退出；即使显示 JSON，它也只是 `dry_run=true` 的预览，不是写入记录。缺文件先判断适用性，不为齐表创建无消费者的材料。实际映射完成后可用原 `check` 诊断结构，不能凭退出成功或标记存在宣称设计已经正确迁移。

### 13.2 不能包装成已落实保证的边界

| 边界 | 当前行为与使用影响 |
| --- | --- |
| UI 不适用 | 地图 N/A 与已有 locked UI changed 声明会被提示为矛盾，界面语言检查仍跳过；有限文本不能认证产品实际无 UI，Main 负责核实来源 |
| 人类确认 | 可提示 published 与 PENDING 的明显矛盾，但只按有限文本识别，不认证真实确认 |
| 引用闭合 | 部分证据、例外、债务前缀允许缺少独立登记；存在 ID 不等于证据真实有效 |
| 版本继承 | 核对已有 Foundation 文本引用，以及需求推导所引用 Surface 的原表、Profile 版本与已有内核继承声明；范围外格式明确未验证，不证明语义兼容或全部消费者传播 |
| 角色绑定 | 可字面定位的项目相对文件检查普通文件存在；其他组件/模式引用仅识别形式，均不证明产品实际消费或语义兑现 |
| Token 消费 | 内建检查限设计目录的有限颜色字面量和已声明原始颜色 var 引用文本；来源提示不是摘要，已有 CSS 可与原生成器内存比对，不保证产品执行或浏览器实际消费 |
| 项目规则 | 角色数量限文件属性文本；Token 与允许标记只查文本共现，复杂选择器与 viewport 未验证，不能据此认定实际布局或 DOM 越界 |
| 换手预算 | 按本需求已声明来源统计，inline 只计当前表格行，缺失及未计入内容明确列出；不是实际发送包的完整性或字节保证 |
| 反馈与阶段门 | 反馈靠专业协议；规划事务不自动完成基础语义审查、发布确认或全部影响回放 |

这些缺口限制的是机器保证，不取消设计责任。发现矛盾时按实际对象修复来源、消费或证明，不通过虚构 ID、补一句“已验证”或制造多余页面消除告警。

## 14. 完成判据与阅读入口

本机制成立的标准是：新的执行者知道当前产品为什么这样设计，能从约束生成并排除方案，能在不同表面保持共同语义，能把本次需求落到真实绑定和证明，并知道反例出现后找谁、改哪层、怎样回放。

阅读按工作展开：先读约束卡、当前表面与需求推导，再按 ID 打开[内核模板](../../docs/design/DESIGN-template.md)、[语法模板](../../docs/design/design-language-template.md)、[表面模板](../../docs/design/surface-profiles/surface-profile-template.md)、[证明说明](../../docs/design/proof/README.md)和[决定与例外](../../docs/design/decisions/README.md)。实现查 [designfoundation](../../internal/designfoundation)、[命令入口](../../internal/cli/design_foundation_command.go)与[工程惯例解析](../../internal/projectconventions)。

本机制以跨需求来源落实 D1，以关系推导落实 D4，以独立且分层的证明落实 D6，以定位正确权威和局部回退落实 D7。完整文件、工具通过和成功截图都只是证据的一部分，不能单独代替上述共识。
