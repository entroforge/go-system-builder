# L4 手续收敛

## 1. 为什么要把手续作为独立设计问题

框架可以在字段、命令和门禁上都成立，却让实际执行者不断猜测：现在做什么、题目在哪里、怎样交付、是不是还欠一次批准。每增加一份无人消费的报告、一次手抄关联或一个意义相近的命令，都会占用本应投入设计、实现和验证的上下文。执行者也更容易沿错误入口反复尝试。

手续收敛要消除无效工作：系统已知的事实由系统维护；真正需要专业工作的部分，连同理由、输入、形状和交接方式一起送达；完成后由原消费者接收并说明剩余责任。机制取舍及作者、运行、维护的总成本由[工作流边界与收敛设计](L4-workflow-convergence.md)统一约束。不能将作者少一次操作直接视为整体减负，也不能把协议复杂度全部转交给作者。

这一要求覆盖 Main 与 Worker 的全部正常入口。让 Main 从 Runtime 抄 SHA、版本、内部身份、校验时间和计数，或要求它另写脚本组装这些机器事实，同样属于未收敛手续；不能以“专业答卷已经简化”作为保留上游手工封套的理由。具体字段归属、来源固定与各阶段落实方案见[阶段答卷的机器事实边界](L4-stage-form.md#24-机器事实必须由系统承接)。

本篇规定如何判断、减少和验证手续，不新增解析器、运行时对象或流程门。题目与接收的具体机制见[阶段答卷](L4-stage-form.md)；原子事实与恢复见[事务核心](L4-state-transition-core.md)；版本与重放见[修订机制](L4-revision-usage.md)。

这一安排承接 [L1](../l1-principles/L1-design-principles.md) 的自然路径观测、正向反馈、引导性产物、分工、消费与成本公理。好的机制让执行者在正常工作中履职，并能理解为何需要这些工作。

## 2. 先区分重复手续与必要工作

### 2.1 为一项要求找到真正消费者

审查一项填写、命令、确认或等待要求，首先追问：它提供什么新事实，由谁在什么时候消费，防止哪种实际失效，失败后由谁恢复？如果只是把同一事实换个文件或命令再交一次，通常应由原适配器派生或直接引用。

但两个步骤拥有不同对象、作者、判断或真实时序时，合并可能破坏工程职责。不能只按操作次数决定删留。

| 要求 | 提供的实际价值 | 收敛方式 |
| --- | --- | --- |
| 作者手抄当前 Runtime、代际、轮次、哈希与接收键 | 关联已被系统确定 | 原发行、接收或 Writer 维护，作者保留实际专业字段 |
| 保存专业答案后再手工注册同一信封或重复总结 | 重复记录同一交付 | 原消费者派生所需领域记录和可读投影 |
| 实施前制定计划，实施后报告结果 | 前者指导工作，后者记录真实发生 | 保留两项专业事实，取消重复通用 PLAN 或激活握手 |
| Worker 自检与 Main 集成检查 | 各自验证本人贡献和真实集成树 | 按原责任分别执行，不用一份 PASS 相互替代 |
| 独立验证与作者自评 | 获得不同执行者的专业判断 | 保留真实独立责任和实际材料 |
| REQ → 设计 → 契约 → TASK | 将意图逐层转成可协作、可执行的约束 | 保留推导与追溯，减少全文复述 |
| 人决定需求、修复授权或发布处置 | 形成专业作者无权推断的意图 | 消费已有真实决定；尚无决定则明确等待 |

### 2.2 减少记录负担，保留判断深度

专业作者仍须给出真实计划、覆盖、观察、因果解释、风险和未完成原因。路径和枚举帮助表达，不能代替阅读、实验和推导。填写一个“已检查”字段，也不能证明检查真的发生。

例如，S7 的 Claim 需要专业 oracle，即能判断断言成立的具体观察。系统可以列出已知 TASK 和变化文件，却不能从清单自动证明覆盖充分。S8 要辨别原因而非重复症状；S9 要按批准意图修复并独立复验；S10 要解释承诺怎样兑现。这些都是收敛后仍须保留的工作。

增加约束时，也应沿引导、结构检查、必要强制的次序分析。真实阶段前置由原领域消费者和门判断；普通工具不因为阶段尚未通过就被额外限制。机械校验只能证明它实际检查的内容，不能充当语义、独立性或人的授权证明。

## 3. 当前工作入口怎样闭合

### 3.1 让零上下文执行者能开始工作

执行者收到任务时，应能从当前交付理解目的、适用输入、实际工作、准确输出位置和交接方式。业务规格与源代码仍需阅读；格式、提交步骤和当前 owner 不应要求它先到多份流程手册中拼接。

正常工作说明至少要连接以下关系：

1. 当前处于哪个 S 阶段，本人承担其中哪项专业责任。
2. 需要读取哪些真实材料，每项材料用于哪项判断。
3. 当前工序要回答什么，哪些内容尚未发生，何时需要真实前置或人的决定。
4. 本人实际写入什么、写到哪个完整准确路径，采用哪条原接收路径。
5. 本人完成后由谁接续；系统或其他 owner 未完成时，本人如何结束。

这些信息可以分层交付：短提示保留当前责任、准确入口和下一动作，较长说明放在原 view、brief 或题目中。不能因上下文预算裁掉关键路径，也不能把整套历史协议放在专业材料前面。

### 3.2 Main 与 Worker 的交付入口不同

Main 本人的当前规划、影响、验收等责任，正常保存准确专业答案，由对应保存监听调用原消费者。新原生 Worker 则由 Main 真实派发，携带准确 brief 或 view／answer；本人保存专业产物并原生返回，`SubagentStop` 调原消费者。原生事件的细节见[子代理工程衔接](L4-agent-dispatch-governance.md)。

这两条路径不能混写成“任何答案保存后都已接收”。普通 Worker Write 不激活、不接收责任；Main 也不能替 Worker 填卷或通过普通工具抢收。Claude Code 管理执行、消息、等待和恢复，工程 owner 负责标识专业责任，平台 actor 只作为实际观测事实。

已有冻结 execution 的具名兼容接收保留其原根和恢复规则。兼容字段、命令和生命周期函数仍然存在，并不使它们成为新原生责任的开工手续。

### 3.3 原命令保留用途，正常路径不重复提交

发行、consume、receipt、直接登记证据、显式 CAS 和恢复命令可以有诊断或原领域用途；它们不应在一次正常交付后，再组成作者必须执行的第二条命令链。

并非所有 CLI 都是多余手续。Main 真实选择任务、登记专业分工、安排集成及执行必要检查，仍可能使用已有明确命令。只读状态可以帮助排查，不能要求每次调用工具前先跑一次 status／next 作为开工许可。

若当前环境没有自动接线，应准确说明可用的原入口及其边界。不能声称“文件保存等于接收”，也不能把寻找二进制、猜 Schema、手写内部状态当作恢复方案。

## 4. 一处作者源怎样支撑多个消费者

### 4.1 专业内容写在其原位置

同一专业判断应有明确作者源。原证据封套、索引、回执、报告和兼容投影引用或派生这份内容，避免作者维护两三份会漂移的副本。

这不要求把所有产物合成一份 JSON。设计文档需要解释推导，代码需要实际实现，结果需要记录观察，人类决定需要真实来源；同一阶段也可能有多个互相独立的责任。各自产物按其消费者保留。

并行作者各有独占输入，原 Writer 合并各责任的事实。Main 的汇总基于原事实生成或作专业综合判断，不能让多人覆盖同一份整卷，也不能把汇总再变成每人要重复提交的材料。

### 4.2 追溯依靠引用与增量解释

S2 应把需求推导成系统设计，S3 解释协作边界和协议选择，S4 解释任务职责、依赖与完成条件。已有目标和约束可以引用，不需要逐层全文复制；本层新增加的决定、取舍及适用关系仍须说明。

去重不能把设计压成一串路径。下一执行者需要理解“为什么这样安排”，相关上下文应随责任保留。维护者应检查引用是否实际可读、当前适用，专业增量是否足以供下游工作，而不是只统计文档数量。

### 4.3 原接收承担机器记录

以一次 S5 审查为例：Main 提供原独立审查责任及准确题目，reviewer 阅读材料、填写结论与可定位发现，再返回准确引用。原消费者记录原领域事实并反馈本人完成及后续返工或等待；作者不再生成第二份 evidence 封套、消息编号、哈希和接收回执。

Main 取得这些题目之前的准备也必须闭合：S5 原入口准备分工材料的机器段和准确来源，Main 判断真正的专业分工；不能要求它先手工填写完整 manifest、转抄文档摘要和任务内部编号，才能享受 Worker 答卷简化。内部完整 Schema 可继续用于领域校验，不能直接作为整份作者输入要求。

S9 的 Main 影响判断和独立定向验证则是不同工作，应各自交付。完成必要专业工作后，原出口记录 Handoff 并提供新 S7 种子；不增加一份作者 Handoff 答卷或手工 create／commit 链。新的 S7 仍要真正规划和验证，种子存在不代表验证通过。

## 5. 生成稿应把缺口说成可回答的问题

### 5.1 三类空缺分别处理

| 内容来源 | 应怎样交付 | 执行者要做什么 |
| --- | --- | --- |
| 系统已知事实 | 带出当前准确关联、材料、路径和必要机器字段 | 按真实输入工作，不手算或重抄 |
| 缺少上游材料或环境 | 点名缺项、影响及准备 owner，保持未知 | 由对应责任补齐，作者报告实际阻塞 |
| 需要专业判断 | 给出问题、允许形状、必要依据与未答状态 | 本人调查、推导或执行后作答 |

未答状态应符合本领域载体，不统一规定所有字段必须为 null。重要的是能区分“还没做”“做了但失败”“有证据不适用”和“已经通过”。空数组也不能自动表示所有检查通过。

字段示例要帮助理解嵌套形状与条件，不应像已经发生的业务事实。示例观察必须明确是示例；未知来源不能由模板补成一条看似真的日志、命令结果或批准。

### 5.2 占位标记与真实缺输入要分开

当前 S7 的 ReviewPlan、Manifest 草稿以及修复返回的新轮种子仍可能包含 `TODO(planner)` 或 `PLANNER-REFINE`。这些标记公开表示需要 Planner 补充；相关登记会拒绝未完成的专业内容。生成稿可以用于开始工作，不能直接当成合格计划派发。

这一实现仍有改进空间：已知内容应直接带出；真正的缺上游要点名责任；需要判断的字段应有相邻问题、形状和实例。不能将“所有生成稿已没有占位”写成现有能力，也不能为了去掉标记就自动编造 oracle、场景或专业 owner。

S7 草稿中按 testid、route、模块等信息生成的检查说明，只是机械起点。是否存在可运行的验证、场景语义是否完整、覆盖是否适用，仍需专业规划。把一段机器字符串填进环境字段不会完成这项判断。

### 5.3 错误反馈直接回到原工作

错误应指向具体字段、材料或依赖，解释为何缺少、由谁修正，并保留已经完成的回答。例如缺 Finding 的实际观察，应定位 `observed` 及其要求，而不是让作者搜索全部 Schema。

系统准备或接线失败时，责任归 Main／系统维护入口；专业字段不完整由原作者补；人的选择未到则明确等待人。未知 token 或没有参数的命令不是可执行修正方案，不能继续把内部适配缺口转嫁给 Worker。

## 6. 减少等待时怎样保留真实时序

### 6.1 本人完成和阶段完成分别表达

原回执要区分答案已接收、本人履职完成、后继尚待处理和全阶段出口。S5 reviewer 已完成但同伴未交，S6 Builder 已交付但 Main 未集成，S10 报告已记录但仍有 unknown，分别对应不同剩余责任。

不能把阶段未通过自动变成本人再次填写或重新派发的指令。等待项应包含 owner、真实缺项和下一动作；已完成者结束本人执行，Main 按原集成与闭环责任接续。平台执行结束也不自动代表领域接受。

### 6.2 专业计划先于本人工作

S6／S9 本人计划仍须在实施前形成，普通计划不增加一次通用 Main 批准。原生 Stop 接收最终产物时，能够记录计划和结果，却不能仅凭最终文件认证真实先后。遗漏应如实报告，不补造时间、事件或批准。

有明确原批准要求时，沿其原领域等待真实决定。例如 S8 修复合同的批准不是“答卷填完自动授权”。没有额外批准要求时，也不能从旧激活协议恢复一个开工门。

前台 Agent 尚未返回不代表不能工作，后台已启动也不代表已经完成。等待与 resume 使用平台原生能力，不增加平台 ID 预留、Team、读回或启动许可。

### 6.3 按实际依赖释放工作

S4／S6 的任务依赖、S7 的验证波次、S9 的修复及复验先后各有专业依据。Main 按真正需要的交付安排下一责任；某位 Builder 已完成写前计划，不应仅因同批其他计划未交就被附加全批开工屏障。

可用容量、文件冲突和集成积压会影响实际安排，不能据此删去必要验证视角。状态建议说明可做什么、等待什么；平台调度由 Claude Code 承担，原工程依赖和 Main 的专业安排仍然有效。

## 7. 简化人的交互，仍完整承接意图

人的注意力用于方向、范围、价值取舍、原批准和终局处置。Agent 应先完成可推导的调查与方案，说明推荐、理由及实际代价，再就真正未决的选择请人决定。明确的人意可以承接，不为每一层文件再机械确认一次。

S0 的需求讨论仍需澄清理念、方向、约束、范围、场景和成功标准，相关设计基础也可能需要实际判断。不能将交互收敛解释成需求设计只允许两问，或声称已有工具能自动决定全部投入与审美取舍。UI 影响也需要结合实际变化判断，不能只靠文件分类树。

S1 的执行绑定、S8 的修复批准和 S11 的六选一处置，分别消费其真实人意及原关联。没有选择则等待；文件存在、填了 approve、测试通过或等待超时都不产生批准。S11 授权不执行实际发布。

具体方法与消费边界见 [S0](../l3-stages/L3-S0-requirement-design.md)、[S1](../l3-stages/L3-S1-bind.md)、[S8](../l3-stages/L3-S8-finding-investigation.md)、[S11](../l3-stages/L3-S11-release-gate.md)和[项目设计基础](L4-project-design-foundation.md)。

## 8. 用准确投影代替反复解释流程

入口、合同、专业方法、具体责任、事件交付和恢复反馈分别承担什么，见 [Agent 指引的分层与交付](L4-agent-guidance.md)。先确定信息的权威来源，再决定正常交付、变化提醒和中断恢复的位置；不能靠每个入口重复整份协议来补偿职责不清。

### 8.1 对外先说责任与动作

当前提示优先显示 S 阶段、本人责任、准确材料和可执行下一步。内部 lifecycle／phase、转换编号、修订、哈希和事件身份保留用于机器关联及必要诊断，不要求作者在多套名字间翻译。

“一个清楚的下一步”指对当前责任有明确指向，不意味着并行工程中只能有一个任务。Main 可以同时看到多个 owner、集成项和人的等待；Worker 则应先看到本人实际待办。不能为统一文案把不同责任压成“继续填写 JSON”。

### 8.2 普通观察、准备与交付分别接线

普通事件的作用应按真实入口解释。新原生 Worker 工具保持安静，Start／Stop 衔接工程材料。Main 的保存接原消费者，已有准备入口和具名恢复还可以补当前缺题或原出口；不是每次观察都扫描、重发或执行长检查。

当前 S5 Main 可沿原幂等 issuer 补已登记题目，S7 Main 非 Stop 上下文可准备缺失计划草稿，S2～S4 真实 Post 也有有界准备；S2 保留原模板和已有答案，已接收答案丢失不恢复为空白草稿。S4 已接收且原出口 pending 时，成功工具事件还可接续原出口。这些能力不能泛化成普通工具可以接收新 Worker 答案。细节由阶段答卷篇和对应 L3 定义。

接收、阶段转换和下一材料准备分属原边界。反馈要说明实际成功到哪一步、剩余 owner 及恢复动作，避免作者为了等下一条提示再调用一个无关工具。Hook 不负责长时间合并、测试或新的平台启动。

### 8.3 提示摘要与必要上下文分开

重复展示可以去重，必要错误和完整行动信息仍须到达。当前 Hook 的界面摘要有长度限制，`PrepareNotice` 只对成功 PreToolUse 的展示字段去重。S2 另有按会话、执行者、责任与完整内容判断的模型上下文去重：相同内容只提醒继续原工作，新的缺口、路径或错误重新完整交付；会话恢复重置。其他阶段不因 S2 接线而获得同样能力，原审计与业务事实也不因去重消失。

这也意味着界面安静不能作为“没有缺项”或“已完成”的依据。准确接收及剩余工作应从原领域事实和当前回执读取，不能把提示缓存升级成工程权威。

## 9. 重复、停滞与故障应怎样收敛

### 9.1 接受历史保留，原接续继续

同答按原消费者重放，复用原接受；已接收但出口未完，继续原关联。内容变化、旧轮、旧代、已替换责任有各自修订规则，不为“少一次报错”静默重绑旧 PASS。

一个逻辑交付可以包含多个内部写入。原子领域记录、转换和下一投影不必全部在同一锁中；可靠性由原 Writer／pending／原接续保证。作者不应补写 Runtime、制造 evidence 或另建重试表来跨过失败。

读原回执和再次保存有不同前提。例如 S8 的独立回执可不读私人答案，但当前 Save 仍需读取。源已丢失时，应反馈受支持的读取与恢复边界，不能重复催作者交一份无法证明来源的新副本。

### 9.2 有限观测识别反复尝试

持续操作不等于工程进展。当前存在可选工作进度采样：按责任、会话、专业事实和实际必要材料的读取范围记录有界诊断。新的事实或必要新范围可重置计数；重复读取同一范围、只查询状态而缺项不变，可以形成停滞提示。

当前采样默认 shadow，即记录诊断而不向模型发送提醒；显式 notify 才显示通知。它只在实际支持的成功 PostToolUse 与可解析责任上工作。未知观测、缓存饱和、正常运行、等待或本人已完成会抑制重复计数；原生责任普通事件的短路与未覆盖类型，也使它不能充当全阶段活性判据。

当前相同缺口的重复 Read／status 达到五次时可产生一次诊断。这个数字是本采样器的提示阈值，不是完成期限、阶段次数预算或开工条件。通知的 `authorizes=false`，不会批准、转换阶段或代替专业结果。

缓存有锁等待与容量限制，竞争或故障可能使本次观测缺失。缺失遥测保持未知，不能用时间流逝或没有通知判执行者失职。另有兼容 TeammateIdle 的有限重复提醒预算，也只减少其指定提醒，不改责任完成和原安全规则。

### 9.3 停滞后移交实际问题

收到诊断后，Main 应结合原材料判断：题目不清、上游缺失、环境不可用、原接续故障，还是专业方案没有形成新证据。反馈应落到具体 owner 与恢复入口。等待人的决定或正在运行的真实检查，不应被催成一次虚假交付。

若需要调整目标、范围或人类批准，使用原变更路径。仅为消除诊断而重启 Agent、改 owner、增加 revision 或提交占位答案，都不会补上实际工程缺口。

## 10. 怎样验证手续真的减少

### 10.1 从首次使用的实际行为检查

给执行者当前责任、题目和必要工程资料，让它按正常入口履职，观察以下现象：

- 能否找到实际输入、答案和交接位置，是否还需猜内部命令或格式。
- 专业内容是否只写在原作者源中，是否又被要求抄机器字段或重复总结。
- 字段错误能否在原卷局部修正，已有工作是否保留。
- Main 保存或 Worker 原生返回后，是否立即知道原接收结果及真实剩余责任。
- 同事未交、Main 待集成、系统恢复或人意未到时，是否准确区分本人的完成。
- 重放、并发输入、阶段重入与旧卷，是否保留历史且防止错绑。

这些观察要结合专业结果检查。快速填满、工具少调用几次或 Hook exit 0，都不能证明工作正确。收敛收益应体现在少猜格式、少重复交付、少无效等待，同时仍保留真实覆盖、检查和判断。

### 10.2 三种证据分别提供什么

领域与事务测试验证接收、幂等、状态和恢复；公开 Hook 测试验证实际事件路由、反馈和上下文边界；真实 Claude Code 运行再验证派发、阅读、返回、结束及 Main 接续的实际行为。

只检查提示中的命令存在，能够发现坏命令，但不能证明该命令是当前阶段的正确入口。文档一致性、模拟专业答案和产品验证也不能互相代替。模拟测试必须明示没有真实实施，实际平台结论须带真实源码及执行范围。

修改手续时，要沿“要求生产者 → 交付事件 → 原消费者 → 原事实 → 失败 owner”复核。先形成能正确接收与恢复的实际路径，再移走重复指引；不能只删提示，把原责任留成不可见缺口。
