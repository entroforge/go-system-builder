# Agent 指引的分层与交付

## 目的与设计依据

Agent 需要知道当前责任、可用材料、专业工作和交付方式。把同一流程分别写进入口、技能、答卷和每次 Hook 输出，会让一次变更留下数套互相冲突的步骤；仅删减文字又可能使中断恢复丢失必要背景。因此先确定每类指引的权威，再决定在哪里交付、何时更新。

指引编排遵循[工作流边界与收敛设计](L4-workflow-convergence.md)：准确交付系统协议，保留专业判断的开放性，明确缺来源与未支持能力。先判断步骤和机制是否必要，再补其投影；不能以“消除猜测”为由预填专业结论，或为每种理论情况增加流程提示。下文的层次与分支用于落实已支持责任，不自动成为本轮整改的新增范围。

本文的六层是指引的职责分工，与 blueprint 的 L1～L4 文档层级不同，也不替代 AGENTS 中 Driver、Wake-up、Listener 的三层运行关系：前者回答内容由谁定义，后者回答工作怎样持续和交付。Blueprint 解释设计，不安装到目标项目；运行时必须通过已安装入口、专业材料和当前责任上下文交付足够的信息，不能要求目标项目的 agent 回来寻找 blueprint。

## 六层职责与权威来源

| 指引层 | 回答的问题 | 权威来源与实现落点 | 下游怎样引用 |
| --- | --- | --- | --- |
| 入口与恢复 | 我是谁，现在先看什么，怎样继续原责任 | `AGENTS-template.md`、`loop-template.md`；安装为 `AGENTS.md`、`.claude/loop.md` | 路由到当前阶段、准确答卷和相关技能；不另写一套阶段完成条件 |
| 阶段合同 | 本阶段谁负责什么，输入、产物、交接如何成立 | L3 阶段设计；安装侧 `docs/control/agent-protocol.md`，可执行转换定义与 Gate | 技能和答卷解释本阶段的具体用途；迁移资格由原消费者判定 |
| 专业方法 | 怎样把需求变成合格的工程成果 | `skills/specification-planning/SKILL.md`、设计规则、架构和 ADR 等模板 | 按当前工作引用必要方法；工具自由不由阅读清单或阶段序号决定 |
| 具体责任 | 此次读哪些材料，在哪里填写哪些专业答案 | `internal/workpacket/planning.go`、嵌入的阶段模板、已签发 packet 与私人 answer | 提供准确路径和作者字段；Runtime 标识、来源摘要和接收记录由系统维护 |
| 事件交付 | 何时把当前责任或变化交给谁 | `settings.json`、CLI 事件路由、Hook 平台适配器 | 平台事件调用原接收者或只读投影；Hook 不成为第二个状态机或权限管理器 |
| 结果与恢复反馈 | 什么已成立，什么仍缺，下一步具体修哪里 | 原接收者、Controller、Runtime 权威事实及其 CLI 投影 | 同时区分接收、迁移、下一材料准备；展示真实错误及准确恢复入口 |

同一规则可以在不同语境解释，但只能有一个判定来源。例如答卷中的 `conclusion: pass` 是作者结论，不能替代设计文档锁定的 Gate；Hook 输出“已接收”也不能证明 S3 输入已经准备完成。生成的 `loop-harness.md` 来自可执行定义，不手改生成结果来掩盖来源中的旧叙述。

转换定义中的候选触发元数据与原答卷接续入口也须分别理解。PTR-PLAN-01 保留的 `auto_trigger.event: PreToolUse` 不表示启用阶段答卷的 Main 必须等下一次 Pre 才推进；正常 S2 保存直接接续已登记的原出口，普通 Pre 保持只读。使用指引应解释真实入口，不能把兼容元数据重新编成作者步骤。

## 从责任推导提示，而不是逐文件补提示

指引必须在实现前编排。其内容由阶段合同、真实输入、当前责任与已有接收事实推导；不是看某份文件还有空间，就再加入一套步骤。文案可以有不同表达，信息的归属、出现条件、接收者和后续动作必须确定。

每次设计一项交接，先回答以下问题，再选择载体：

1. 谁现在负有责任，其专业判断是什么，哪些事实已经由上游成立？
2. 执行这项判断必须获得哪些准确材料、适用方法和作者字段？哪些属于系统可派生的身份、来源与关联？
3. 交付由哪个原消费者接收，接收后还需要谁完成什么？实际阻塞交给谁，是否真的需要人作决定？
4. 哪个事件首次交付这些信息，什么变化需要重新交付，普通观察能省略哪些已知内容？
5. 改动这一规则会影响哪些安装文件、生成材料、事件输出和恢复路径？怎样通过原链路证明它们一致？

专业判断与系统事实必须分开。架构取舍、发现适用模块和补足场景属于作者的专业工作；系统实际消费的文件批次、事件是否构成提交、下一责任的准确路径及恢复入口必须由原消费者及其投影提供。不能要求作者读框架源码、从多份冲突提示选规则，或先失败一次才知道另一份文件也属于出口义务。

六层内容通过七组实际载体交付：入口模板、阶段协议、流程技能、角色及专业技能、具体问卷/brief、Hook 事件提示、进度及错误反馈。载体数不等于权威层数。角色定义属于专业责任与方法，不能再声明独立的权限或阶段机；Hook 的 Start 提示属于事件交付，Stop 回执则投影原消费者的结果。一个载体可以承载多层信息，但必须保留其权威来源。

| 内容 | 唯一职责来源 | 常态交付位置 | 不应要求执行者承担 |
| --- | --- | --- | --- |
| 阶段目的、出口与实际人闸 | L3 合同及原 Gate/Action | 阶段协议；入口只链接 | 从多份提示裁决哪套完成规则有效 |
| 角色专业责任、恒常方法 | 角色定义与对应 Skill | 最小角色预加载 | 因角色名称获得或丧失普通工具权限 |
| 本次适用专项与准确输入 | 原任务/责任及技能选择结果 | 原 view/brief 的路径和用途 | 从内部清单、Runtime 或角色名猜缺失的技能 |
| 当前可执行的下一步 | 原进度、接收与集成事实 | Main 的阶段投影 | 在“准备”“等待”“集成”三种矛盾命令间选择 |
| 专业答案及真实 blocker | 原作者工作与原消费者 | 私人 answer/Plan/Result、原生返回 | 为退出而编造 PASS，或抄机器身份、摘要与已知关联 |
| 已接收、迁移、后续准备和恢复 | 各原事务的真实结果 | 原回执及变化后的 Hook 反馈 | 因后续失败重复提交已接收结论 |

入口只负责路由，专业技能只解释怎样做好工作；责任材料给足这次工作的准确引用；事件提示解释交接时机，反馈说明实际结果。不要通过“新规则优先”追加段落掩盖旧步骤，应修改规则的来源及其全部有效投影。旧冻结执行的特殊步骤只放在具名恢复入口，不进入新原生责任的常态预加载。

Hook 性能与内部中断按[机制减负合同](L4-hook-platform-wiring.md#101-机制减负的作者契约)处理。系统维护的快照、索引、暂存归属和有限恢复不成为新题目；超时不请求作者补字段、例行重存、删证据或换 ID。专业缺项、来源／环境故障、接收未完成及已接收后继待续分别投递原事实；同次完整交接的承诺不能被一句“等下一次工具调用”替代。尚无跨进程执行者时不得宣称无人运行也会自动完成，也不能通过新的等待指令把这一限制变成作者手续。

接收失败的操作、错误载体和提示唯一生产者按 [Hook §10.9](L4-hook-platform-wiring.md#109-接收失败的具名续接失败交付与单次提示)编排：实际执行时点、原接收事实、已经捕获的失败分别投影；flat／typed／pending／已收后继各有对应的 Main 操作。正常交付与显式系统恢复分别解释，恢复命令在原机制实际支持后才交付。运行时、协议、Skill 和帮助使用同一窗口选择，不能一处只允许专业遗漏续作者，另一处要求系统失败也让原 Worker 重返。

同一公开响应中的同一责任由一个组装者生产，测试同时核输出唯一性和调用／读取次数。具体失败须从原尝试交到下一接手人的实际模型渠道；同一进程 stderr 有错误、检查器看到完成通知、或文本包含正确关键词，均不足以证明这条边已交付。

## S5→S6 的指引编排

S5 的具体审查范围和 S6 的实现/集成条件分别由 [S5](../l3-stages/L3-S5-document-verification.md) 和 [S6](../l3-stages/L3-S6-build.md) 定义。本机制据此确定信息何时交给谁，不另设阶段门。

| 真实时点 | 接收者与必须交付的信息 | 下一步及完成边界 |
| --- | --- | --- |
| S4 接收后准备 S5 | Main：两项独立责任、各自准确 view/answer、准备错误或就绪事实 | 携带各自原引用派入独立原生上下文；准备不等于已启动 |
| Reviewer 首次取得责任/恢复 | Reviewer：整批冻结输入、责任问题、分析资料、适用技能路径、作者字段和原返回方式 | 独立审查、保存本人答案、返回准确引用；不增加激活和逐工具许可 |
| Reviewer 普通工具调用 | 无变化时不追加工程手续；新错误通过原责任反馈 | 继续专业工作；普通工具不接收答案、不替 Main 推阶段 |
| Reviewer 返回结论或真实阻塞 | 原消费者/Main：本人原答案及返回；分别说明接收与未接收原因 | 有效结论沿原 Gate 路由；未能形成结论交 Main 恢复或重分配，不能算 PASS |
| 最后一项当前有效 PASS 被接收 | Main：S5 接收结果、TR-003 是否提交、S6 准备/派发的实际下一步 | 原出口满足才进入 S6；不要求再读文件来“触发”转换 |
| S6 任务就绪但尚未准备 | Main：具体就绪 TASK、原准备入口、真实前置缺口 | `s6 prepare` 准备准确 brief；不得说“等待已派发 Builder” |
| S6 已准备但尚无交付 | Main：准确 brief、原生 Agent/worktree 派发及恢复方式 | 工程登记不是平台启动证据；结合真实平台任务判断派发或继续等待 |
| Builder 取得责任 | Builder：TASK/来源、适用技能、Plan/Result 路径及字段、本人检查与提交方式 | 先计划后实现、自检、提交产品并返回；保存 Plan 后连续工作 |
| Result 已接收但未集成 | Main：实际接收的交付、集成入口和待完成检查 | Main 集成、核验和闭合任务；不要求 Builder 重交已接收结果 |

S5 只有真实专业结论才能形成审查证据。失去独立性、缺来源或无法执行时，原生返回可以把阻塞交 Main，而不必为了通过退出校验选择一个结论。未接收仍是未接收；允许结束平台回合不代表责任完成。反馈必须说明责任归属，不靠错误文案或自然语言关键词推导 PASS，不新增必填的退出登记或批准手续。

S6 的“未准备、已准备、已接收、已集成”取自现有工程事实；平台是否已启动另由原生上下文证明。下一步投影复用这些事实，不能另建提示专用状态机。专业证据与完成条件的关联应尽量消费原 Plan 中已有关系；任何字段减负必须保持一一对应、真实证据和原接收校验，并继续接收既有合法材料。

### 边界内的信息完整性

分层正确还不足以证明指引可执行。每个合法分支都必须在该执行者实际收到的材料里交付完整合同，不能依赖执行者读源码、寻找 blueprint 或裁决新旧文案。专业裁量包括选择具体实现、判断适用专项和评价证据；确定字段路径、来源根、提交形状、错误原因和接手人属于系统编排，不能留给模型猜。

| 边界 | 必须明确交付 | 实现约束 |
| --- | --- | --- |
| S5 当前问卷与旧冻结 view | 当前 packet 的 `draft.read`、`answer_path`，以及通过 `task_analysis.path` 读取的分析资料；旧 ExecutionView 的 `packet` 包装及 `authoring_path`、`frozen_input_root` 只在具名旧恢复中使用 | 方法按实际对象解释；不能要求读取不存在的顶层 `read` 或内嵌分析，也不能把旧包装字段写成新 packet 的常态字段 |
| S5 发现与无法审查 | 准确材料可读时，规格缺漏、冲突、范围问题形成 findings；失去独立性、准确来源不可得等导致无法判断时交真实 blocker | 不以“冲突”“缺层”等宽泛词直接要求停工；不能强迫选结论，也不能把可成立的 finding 退化成未交付 |
| S5 未接收返回 | Main 收到原责任、具体字段或来源原因及对应下一步；诊断可由原输入只读重建或从原诊断读取 | 不只说“尚未接收，请检查诊断”；若必须另读，给出准确入口。观察不得代收答案、重做专业检查或新建流程账本 |
| S6 来源与执行根 | 控制材料/方法的准确入口、固定源提交，以及在本人 worktree 中读取的 TASK、规格和产品相对路径 | Main 控制根不作为活动产品读根；不要要求 Builder 从未提供的 `source_root` 等字段推导来源 |
| S6 正常与阻塞返回 | 正常 Plan/Result 形状；形成 Plan 前和形成 Plan 后真实阻塞的最低产物、准确保存位置及 Main 接手方式 | 阻塞不得要求虚构断言证据或完整完成报告；已有 Plan/证据保留。无 Result 时指出可填写的最小阻塞形状；阻塞交接不成立接收/集成/阶段完成 |
| 方法中的规范性要求 | 专业检查依据及其适用条件；项目特定默认值的真实规则/决定来源；可解析的记录位置 | 不用无来源的“owner 裁定”添加业务默认值，不把负空间章节当债务记录，不要求作者寻找未提供的 request schema |

方法可以要求检查兼容策略是否明确、有理由、有责任和退出路径，但不能凭方法中的一句默认值替代项目已批准的策略。没有惯例登记时，执行者仍可在已有授权范围内作普通工程选择；是否缺少必要决策取决于实际 TASK 和原规范，不能由缺少 registry 单独决定。

这些信息应修正在原角色、方法、生成器与反馈中，不叠加“以此为准”的补丁段落。分支表只描述原有责任，不新增工具权限限制、必填登记或阶段闸。

## 方法交付与信息预算的推导

接收后的交接按 [Hook 接线 §10.8](L4-hook-platform-wiring.md#108-从原接收事实到全部接手入口的接线)逐边编排。Main 返回、普通进度监听与具名集成入口必须对同一原责任表达一致的已知事实、未知边界、准确引用和下一责任；缺 candidate 不能退化为底层空路径错误。消息发送、平台回合结束、专业接收和工程责任完成分别判断。阶段已改变时仍按当前读者分配工作；Main 的下一步不能成为晚返回 Worker 的新任务，合法空动作也不能渲染成空指令。

角色只预加载其恒常必需的最小技能。专项从责任、TASK 的实际风险及适用技术推导，向执行者交付准确的已安装 Skill 路径与用途；登记了 `skill_refs` 不等于模型获得了技能。实际安装的角色 frontmatter、原 view/brief 和运行时选择必须相互符合。未确定专项可以在工作中按明确触发条件读取，不需要重新授权，也不删除专业检查义务。

固定角色材料说明恒常责任，具体 view/brief 说明当前工作，Hook 只补当前事件所需差异。普通观察不重复证明来源闭包或重签已接受事实；接收、材料变更和具名恢复仍执行原真实验证。无变化内容去重以会话、Agent、责任及实际内容为边界；新会话、压缩恢复、责任或错误变化必须重新获得足够指引。缓存失效只允许多说一次，不能隐藏缺口、改变权限或承诺接收。

信息预算以能否正确连续执行来判断，不以任意文件数、字节数或 token 阈值决定 TASK 必须拆分。减少的是重复指令、无关预加载、机器事实抄写和等待手续，不能减少独立判断、实际测试、真实失败与必要证据。

## S2→S3 的完整指引链

S1 完成绑定后，系统准备 S2 当前责任。Main 获得已绑定 REQ、当前 packet 与私人 answer 的准确路径、架构和 ADR 模板、适用的场景与 Foundation 规则。专业材料的范围由需求决定：服务行为需要对应场景包，有界面变化还需要界面设计及其推导；必要的方向选择沿用已有人的决定，仅实际未解决的方向问题再交给人。

Main 完成架构、必要 ADR 和场景设计，执行适用的生成与验证，将正式上游材料提交到绑定的开发来源，然后在原 answer 填写 `architecture_path` 和 `conclusion`。Git 提交服务 S3 的正式来源读取，不是答卷作者要复制的机器字段，也不是 Hook 自动替作者提交的事务。

具体责任同时说明两个不同集合：本次架构登记批次，以及 S3 将消费的正式来源范围。前者沿原登记动作的归属和状态规则投影准确路径与未锁定缺口；后者包括原桥使用的全项目模块集合，不能简写成“只读取当前架构引用的模块”。首次交付及集合变化时提供可检查的实际路径；普通观察不重新构造完整冻结来源或重复输出全部清单。清单由系统派生，不新增作者填写字段或提交前批准手续。

专业方法中的停止条件必须服从阶段合同：普通追踪缺项、缺 CASE 或可在既有需求内解决的架构冲突继续设计；只有实际需求/产品语义改变、授权外取舍或真正未决的人类方向决定才进入人闸。不能在技能末尾把未完成的专业工作重新扩大为必须找人的条件。

保存事件触发原 `SaveDesign`。三个结果分别解释：

1. **接收。** 当前答卷的专业答案被接收并形成证据。草稿不算失败；接收不承诺所有迁移条件已经成立。
2. **迁移。** Controller 检查当前责任、锁定 REQ、锁定架构等真实条件，经原 Writer 提交 PTR-PLAN-01。未通过时指出具体缺口，例如架构未锁定，而不是让作者重复填写已接收的答案。
3. **下一材料准备。** 根据 S3 的正式来源闭包签发 S3 材料。它可能在迁移成功后失败，例如上游文件没有进入绑定的 Git 来源。反馈必须明确“已经进入 S3，但准备失败”，保留或能重新获得具体来源错误及修复路径。

S3 准备成功后，Main 获得新的实际路径。失败后修改真实来源并完成适当提交，由后续成功的材料变更事件重试原准备入口；显式恢复命令只用于具体技术缺口，不变成每个阶段都必做的手续。接收历史不得因恢复被改写；原答卷重放不得产生重复证据或新责任。

S2 已接收但原出口仍未完成时，修复具名缺口后由原答卷保存或具名 `runtime stage-answer recover` 接续；普通读取和任意工具成功都不自动重跑 S2 Gate。保存与显式恢复共用原出口及 S2 磁盘来源判断，不能让恢复因为读取另一份 Git 内容而产生不同锁定结论。下一阶段准备仍遵循 S3 的正式 Git 来源合同。

## S3→S4 的指引编排

[S3 阶段合同](../l3-stages/L3-S3-contracts.md)定义契约责任和出口，本节定义这些内容怎样交付。目标项目不安装 blueprint，因此这里的分工必须落实到已安装协议、方法、模板及公开 Hook 输出，不能仅在某个提示生成函数中存在。

| 指引层 | 本阶段的权威内容与载体 | 交付边界 |
| --- | --- | --- |
| 入口与恢复 | `AGENTS-template.md`、`loop-template.md`、`loop-orchestration` 路由当前 Main 责任 | 当前责任已知时直接使用原 view/answer；Runtime 和全库阅读仅用于具体诊断，不作为正常开工手续 |
| 阶段合同 | `agent-protocol.md#s3`、原契约 Gate、PTR-PLAN-02 | 一个绑定 REQ 的完整适用契约集；区分专业完成、接收、迁移与 S4 准备，普通交接无人闸 |
| 专业方法 | `specification-planning` 的 S3 入口、`api-contracts`、共享模型规则及四份契约模板 | 从冻结 S2 输入判断适用性；有共享数据/共同操作时先收敛其模型/SYNC，再派生适用 FE/BE；不重跑 S2，不预建 Builder，不虚构契约、浏览器场景或未来验证结果 |
| 具体责任 | 原 S3 view/answer、四项专业问题及来源记录 | 给准确输入、作者字段、输出候选/实际路径、模板、声明的正式来源与绑定分支；机器身份和指纹由系统维护 |
| 事件交付 | 原阶段准备出口、SessionStart/PreToolUse、成功保存监听器 | 首次交接及会话恢复交付完整必要信息；普通观察只读、去重；保存沿原消费者，不能靠下一次无关工具才能看见新责任 |
| 结果与恢复 | 接收回执、当前责任投影与具名恢复入口 | 从同一接收事实选择唯一下一步；已接收结果覆盖通用缺项，不要求作者重新证明系统已有事实 |

以下编排是公开输出必须满足的合同；内部 helper 的单元测试不能代替交付验证。

| 时点 | Main 实际应获得的信息 | 下一步与不变条件 |
| --- | --- | --- |
| S2 出口完成并准备 S3 | S3 view/answer、契约索引和分端候选、四份模板、正式来源及绑定分支、专业方法入口 | 选择真实适用性并编写本批；候选不强制三类齐全，不读取 Runtime 猜分支 |
| 已发行 S3 的 SessionStart/普通 Pre | 相同责任的原准确路径、交付要求、原输入阅读入口及具体已知诊断 | 不重建来源闭包、不重验全批、不先读全库；无新事实可压缩展示 |
| 保存未完成或不合格的答卷 | 未接收事实、准确字段/文件/来源错误、原答卷路径 | 完成或修正真实工作，必要时提交到所示来源，再保存原答卷；单独修改其他文档不自动把既存未接收答案当成新提交 |
| S3 已接收但 PTR-PLAN-02 待续 | 已接收事实、实际出口错误、原恢复命令及交付来源 | 保留已接收答案，解决具体问题后恢复原出口；不提示重填/重存答案来制造事件，普通读取不续跑 |
| PTR-PLAN-02 成功 | 已进入 S4，以及 S4 view/answer、TASK/index 模板、正式来源和拆分责任 | 消费已接受契约、条款与来源；若准备失败，明确迁移已成立并给原准备恢复入口 |
| 文件丢失或技术中断 | 缺失路径、已成立事实、准确 issue/recover 入口 | 复用原责任、保留现有作者内容；恢复是异常路径，不新增正常提交手续 |

提示不得同时要求“保存同一答案”与“不要重交”。S3 已接收时不再无条件显示 `planning_contract_record` 或 `locked_contract_set`，真实登记来源冲突仍须明确展示。恢复动作不能泛称“Main 处理”或“监听器会继续”，必须给当前可执行的原入口和原错误；不把契约作者变成事件触发器。

来源校验区分三种对象：本批索引/契约、实际引用的模型/样例依赖，以及为防漏交识别的契约候选。前两者必须与正式来源和接受记录一致；候选检查不能把契约目录中无关笔记、编辑器文件或任意子目录变成本批义务。当前 REQ 漏交、新增未声明契约或来源歧义必须继续被报告，不能为减少阻拦而缩小验收分母。S4 沿用同一集合语义，不在交接时恢复整个目录成员一致的隐性要求。

提示只表达专业约束和接收事实，不限制普通工具。作者可以按需要运行检查用于自审或诊断；系统已经执行的检查不需要再作为提交手续重复。S3 没有证据支持的契约数量上限不应迫使拆 REQ；资源限制由现有回答大小/读取预算承担。空契约交付目前不受支持，应在问题附近明确说明并报告阶段适配缺口，不能虚构一份 BE 取得流转。

### S3→S4 边界复审：下一步必须可以执行

本轮复审以合法业务场景为边界，检查 Agent 能否只凭已交付信息完成工作。以下分工先定义行为，再由各载体投影；不能用新增禁令、提前填写 pass 或让作者查源码来补缺口。

| 层次 | 已确认缺口 | 修复合同与验收 |
| --- | --- | --- |
| 阶段合同与迁移 | S3/S4 要求修正冻结设计或已接收契约时“走正式返工”，现有向前阶段迁移与 S5 `revise` 不承接这一责任 | Main 使用具名规划返工入口，明确目标 design 或 contracts 及专业原因。仅限当前 S3/S4、同一 REQ 基线；通过原 Writer/迁移校验进入新的阶段入口，使旧责任失去当前接收/接续资格，保留历史问卷、回答和接收事实。REQ 语义变化仍走原人类修订；普通观察不返工，技术 recover 不改写专业判断 |
| 具体责任与路径 | 提示展示绝对路径，回答却只接受仓库相对路径，错误不说明转换 | 同时区分“工具访问路径”和“答卷填写值”；index_path、contract_paths 及交接后的 task_paths 明确以项目根为基准，并给实际合法值。保留原路径约束，错误指出具体值及修复方式 |
| 错误与恢复 | Schema 的具体字段原因仅在当次 FieldErrors 中存在，后续 Pre/Session 退化为泛化错误 | 指引与持久诊断保留字段路径、具体原因、修复说明；同一已知失败在恢复会话后仍可直接定位。展示诊断不产生接收或阶段事实 |
| 草稿与事件交付 | 未填 pass 或适用性未完成，会丢掉已经填写的实际产物路径，退回默认文件名 | 草稿展示独立于最终接收资格。可明确识别的原作者路径保持展示，缺项单独指出；不合格路径明确诊断而不冒充合法路径。空结论表达自审未完成，不能为获得路径提示诱导提前 pass；正式接收仍要求完整专业回答 |
| 专业方法与模板 | SYNC/shared-model 可不适用，但方法和分端模板仍无条件要求它们 | 在实际步骤、依赖表和字段旁说明适用条件；无 SYNC 或无共享数据时，删除不适用占位/引用并记录必要依据，不制造契约、Schema 或测试结果。覆盖仅 FE、仅 BE、无共享模型及真实跨端场景 |
| 静态权威与历史兼容 | 正常路径免手续和异常恢复混写；题干仍笼统说 human decisions required | 普通工作无需 issue/consume/recover，具体异常按反馈执行 issue/recover，专业返工使用独立具名入口。仅真实需求变化/超出授权决定交人；不得扩大为每批 S3 的审批。历史已发行问卷按原字节/身份继续识别，新指引不能使旧合法答案失效 |

规划返工使用 `runtime stage-answer rework --target design|contracts --reason <具体专业原因>`，四条显式手动阶段迁移在 Loop Definition 中声明，并由原 transition/Writer 执行。contracts 目标继续校验原 S3 的冻结 S2 输入与目录成员，不能把上游漂移重新冻结为新事实；design 目标允许重新开展设计但仍核对同一锁定 REQ。

规划返工成功时，响应必须交付新的阶段及其准确责任路径；新责任准备失败时分别说明迁移已成立、具体缺口和原 issue 恢复命令。同一请求在新入口尚无专业接收时重试不能重复开启入口；新入口已产生另一份专业接收后，同一原因可再次发起返工。旧已接收内容不能借 recover 重登记到新入口，旧待续记录也不能占用当前恢复预算；失败事务不能留下半完成的阶段切换。回归从实际 CLI/Hook 出口检验这些行为，并覆盖非 Main、错误阶段、缺少原因、旧责任重放和真实上游修改后的重新交付。

路径/草稿/错误回归以最小作者输入验证：复制公开提示中的填写值可被原解析器接受；conclusion 为空时仍保留已填的实际路径；非法字段在首次响应和恢复会话中均可定位。人类边界和适用性修正须同步方法、模板与正常公开指引，不只修改 blueprint。

| 重入原命令 / 重复执行已完成工序 | 明确允许按反馈重入原 task-integrate 恢复未完成的集成、检查或出口；原检查点保证不重复合并和接收。S7 已迁移后的材料缺口使用原 s7 draft 恢复，不靠额外普通工具制造事件 | 技能、阶段协议、集成/错误反馈使用同一含义；原命令重试保留 merge、接收和轮次幂等；不增加新的恢复登记 |

本轮修复输入为：固定源说明误把已有工作归为 blocker；Builder 核心方法无条件引用 ReviewPlan/Claim；workspace-integration 仍要求当前 Plan 的 dependencies 与 Result 文本抄写；完整 blocked 接收后 Main 投影缺实际原因；“禁止重复集成”与具名重试 task-integrate 混用。修复归属分别为具体责任、专业方法、安装侧指南、结果投影、恢复措辞，不通过放宽 Gate、删除检查或扩大 Hook 预算解决。

原检查失败留下 `preserved/blocked` 检查点时，环境/检查原因解决后的重验命令需要原 `--retry-preserved` 参数；裸命令只保留旧失败。反馈须给出这个条件与参数，不把“重入原命令”写成无条件裸命令重试。已成功集成仅恢复出口的重入仍沿原完成检查点，不重复 merge。原生 S6 已有当前责任的具体结果指引时，通用 worktree reminder 不再附加无条件 merge 提示；其他执行合同保留自己的提醒。

已接收未完成报告需要修改实现或答案时，反馈应提供原 `s6 prepare --revise-assignment` 入口及当前责任参数；不能用“恢复或修订”让 Main 猜测是否可以改写已接收答案。当前修订入口需要原返工检查点：尚无此依据时先通过原 `task-integrate` 登记真实 closing blocker，由原未闭合校验保留检查点且拒绝 merge，再走具名修订；已有依据则直接修订。此处命令用于记录阻断，不代表报告可集成，也不需要新增登记机制。验收须覆盖阻断、HEAD 不变和随后修订可达。仅接收失败、同一责任仍有效且产物未接收时，才恢复原作者返回已保存产物。修订意图的 stable key 在同次恢复中复用，TASK 规范变化仍回原规划路径。

### 本轮发现与分层验收

修复输入：S7 Stop 的实际错误没有进入 Main 回执投影；未知 Start 收到问卷要求；单责任重复工具收到相同长上下文；E2E 角色把非浏览器工作浏览器化、把轮次覆盖下放成每人的全模块覆盖；冷启动与 web/e2e 路径冲突；共用方法混入规格作者指令；负向 PASS 观察误指向 Finding 字段；CleanRound 仍等下一次 Pre、TR-009 文档残留手工绑定、S10 缺稿只有报错没有恢复动作。

验收包括：精确/未知/歧义 Start；字段失败与真实缺源的 Stop→Main 回显；不读取私人未接收答案；相同上下文去重与新错误/会话/轮次恢复；浏览器与非浏览器责任、冷启动与既有资产均有可执行且不越权的方法；真实最后结果接收同次进入 S10并给出材料；失败门不放行；迁移失败与准备失败分别可恢复；重放不重复结果、转换或覆盖报告。已有非本轮工作和冻结合同须保持；测试不通过删校验、放宽权限边界或增大 Hook 预算实现。

### S7 边界内第二轮审查：实例与回传必须兑现总则

总则不能要求 agent 覆盖生成物中的错误默认值。专业判断仍由 Main/Reviewer 作出；系统必须交付已知事实、确定的字段映射和原下一步，不将未观察的事实预填成结论。

| 差距与负责层 | 编排合同 | 验收边界 |
| --- | --- | --- |
| 无 UI 被草稿推成 E2E N/A；计划生成层 | 浏览器发现只说明浏览器候选集合。无 UI 或没有浏览器 CASE 时，其他行为适用性保持待 Main 判断，不预填“无用户可观察行为变化”或要求保留泛化 N/A；有依据的正式 N/A 继续允许 | 必需非浏览器 CASE 不被默认结论遮蔽；真正 N/A 可由 Main 完成原字段并登记 |
| 非浏览器 Assignment 默认浏览器职责；实例/方法选择/校验层 | 依据原计划中明确的行为适用事实选择职责和方法；未声明时交还 Main 具名待决项，不解析任意 prose 猜浏览器。通用 E2E、浏览器专用职责和历史登记保持可区分，真实浏览器义务不能因减负被删去 | API/命令/状态责任可用适用方法完成原登记；浏览器责任仍保留原浏览器方法；旧已登记 manifest 不被迁移或改写 |
| 未列资产依赖被当作无依赖；原结果接收与复核层 | 执行日志证明观察，脚本/夹具引用说明支持该观察的实际资产，两者不互相替代。沿原 answer 的 evidence_refs 说明实际使用路径，原消费者绑定摘要；系统已知的原资产绑定直接复用，不要求作者抄 hash 或另建清单。工作区变化且依赖未知时明确缺口，不将沉默解释成不依赖 | 实际依赖改动不能沿用旧 PASS；不同 Reviewer 合法新增无关资产仍可并行；缺依赖给出原字段/路径的恢复指引，历史结果不被静默升级 |
| 部分接收只报本人完成；Main 返回投影层 | 个人回执保持已交付；Main 同次只读收到剩余准确 Assignment、已知 owner/引用、队列与依赖及原动作。未登记给原 manifest 入口，已登记给原问卷/来源恢复，实际平台运行状态须核对原生执行，不能由登记推定 | 第一份有效结果返回时可定位其余责任；不代收、不启动、不修改 Runtime，也不要求已完成 Reviewer 等整轮 |
| 选择器方法互相冲突；专业方法层 | S7 浏览器执行遵守原 data-test 契约，通用 Playwright 的 role/label 建议明确适用范围，不覆盖该契约；缺钩子只停止受影响检查并交 Main | 同时加载两个方法时没有相反操作指令，不为通过检查改产品 |
| PASS/FAIL/BLOCKED 报告未映射；专业方法/题面层 | S7 只填原答卷：正常结论 pass/fail，真实 Finding 阻断进 blocked_claims，环境未执行说明实际缺项并交 Main，正常负向通过进 observed；不另造流程报告或状态枚举 | 方法步骤、示例、checklist 与原字段含义一致，环境缺失不伪造成产品阻断 |

这轮按计划与实例生成、资产依赖与原复核、Main 反馈三层修复；方法近端指令与题面由主代理对齐。任何新增可选专业字段须在原题面说明、兼容历史冻结字节；不增加通用审批、工具 ACL、重复报告或 Hook 时间预算。证据不足时明确事实缺口，不靠要求作者揣测内部校验来完成流程。

当前实例编排在原 E2E Plan Assignment 中使用 `behavior_surface=browser|non_browser`。新计划在原登记前校验这项专业选择，缺失时回原草稿，不等计划不可变后才要求修订，也不从 method/target 自由文本推断。字段对历史冻结 JSON 可省略；已登记缺字段的历史计划及其未派发责任保留原浏览器合同。已知浏览器 CASE 可供应 browser，其他行为由 Main 指定。non_browser 使用通用 `E2E-BEHAVIOR` 与现有通用方法；browser 保留原浏览器职责。历史 `e2e_browser` workgroup kind 是兼容容器，不再单独决定新计划的专业适用性，已登记冻结责任沿原合同恢复。

## 事件选点与信息预算

### 先确定实际读者，再选择阶段内容

接收者选择使用本次平台事件的实际调用上下文、原责任引用及已有 session/owner 关联，在请求内区分 Main、已绑定原责任的 Worker、普通 helper 和身份未知者。CWD 位于 Main 仓库、工程 owner 与平台 actor 同名、或 native 分支未匹配，都不足以将调用者认作 Main。原生 payload 缺少某字段时沿已支持的实际平台上下文解析；不能靠要求 agent 注册/抄身份或新建平台执行账本补齐。

显式 Subagent 事件/调用上下文优先于全局阶段和共享目录；有准确原责任引用则交该责任，没有正式责任的普通子代理仍是 helper。合法官方顶层事件按原平台入口语义识别，不因没有 `agent_id` 就要求 Main 额外登记；有子代理证据时也不能反向用空 owner 当 Main。解析只用本次已有输入及适用的原关联，不为每个工具遍历完整 transcript 或新建 actor 映射。

| 读者 | 当前事件可交付的方向 | 不可推导的责任 |
| --- | --- | --- |
| 已确认 Main | 本阶段主责、真实交接和相关 Worker 返回摘要 | 不把后台启动当专业完成，不把历史失败当本次新失败 |
| 已关联原责任的 Worker | 本人原题面、适用方法、本人的接收结果/缺口 | 全局退回 S2 不使仍在收尾的 S5 Worker变成设计作者；原责任已被替换则说明该事实，不交新 Main 菜单 |
| 普通 helper | 原委派范围与可用的一般上下文；无新信息可静默 | 不因同 CWD 或未登记正式任务而接管 Main 答卷、阶段出口或额外完成手续 |
| 无法确认实际身份 | 保留未知；如实给必要的一般诊断 | 不替 Main/Worker 认领、接收或派发；普通工具仍按原非阻断路径执行 |

这项选择共同约束 native 路由、Main 问卷/Controller、pending 提示和普通进度/错误投影；不能只在最外层过滤一次，然后在早退或 fallback 中重新默认 Main。受众筛选不改原答卷保存的真实作者/责任校验，不得为了消除误提示漏掉合法 Main 交付。

### 读序、专业字段和原合同只表达一次

首次进入责任或上下文恢复时给有限必要读序；同一责任无变化时直接继续工作。`status`/`inspect` 等只读入口用于实际不明、变化或诊断，不作为每次读写、派发或保存之前的例行动作。已有可丢弃提示缓存按会话、读者、责任和内容去重，不新增“已读确认”、提示账本或工具前握手；丢缓存最多多说一次。

原题面承载本责任完整机器可确定的集合和作者形状，Main 派发携带准确引用及本次专业补充。S9 的实际 Assignment 断言全集不能被父 prompt 的 RED 子集替换；`before_fix_results` 逐项记录真实修前观察，包括原本满足者。有意改变分工先走原分工路径，发现父 prompt 与原题面矛盾须指出冲突，而非让 Worker 猜验收集合。模板引导专业内容、Skill解释方法、Hook补事件差异，三者不再各列一套断言。

未接收的专业 JSON 允许正常填写、重排和修正，原消费者核定字段及语义；派发不得额外要求全卷 byte-identical、镜像文件或逐次 roundtrip 自检。题目的不可变部分、技术适配已经固定的输入、已接收对象及 pending 的同答重放，仍按原精确内容边界处理。这个区别应出现在实际作者入口，而不是以一条全局“不要改 JSON”覆盖不同对象。

| 时机 | 应交付的信息 | 允许的业务动作 |
| --- | --- | --- |
| 首次进入、会话开始或恢复上下文 | 当前责任、准确路径、必要阅读入口、作者字段、完成方式 | 观察本身只读；进入责任的原事务负责准备材料 |
| 同一责任中的普通工具调用 | 新出现的缺口、真实变化或必要的简短提醒 | S7／S9 在唯一准确责任、原稿和原消费者条件成立时可自动接收并接续适用出口；其他纯观察不凭工具调用推进阶段。未就绪及已收重放不重复完整接收事务 |
| Main 成功保存原答卷 | 草稿缺项或接收回执；明确迁移及下一材料准备结果 | 调用原接收者及其已有控制出口 |
| Main 成功变更有关材料 | 当前准备缺口是否解决、必要时新的准确路径 | 通过已有准备入口恢复缺失材料；不覆盖作者已有答案 |
| Main Stop / Idle | 未完成责任的有限提醒与恢复方向 | 不代收 Worker 答案，不把阶段未完成转换成普通工具禁令，不构造无限 Stop 循环 |
| Worker SubagentStop | 准确原产物、真实阻塞及原接收反馈 | 调用原领域消费者；依其合同继续原阶段出口，未接收不算完成 |
| Main 收到原生 Agent 返回 | 原责任当前回执、平台实际返回及 Main 的下一步 | 只读观察已有接收事实；后台启动返回不等于 Worker 已交付，不扫描代收私人答案 |
| 失败或身份、责任变化 | 原错误、受影响对象、可执行的下一步；需要时重新完整交付 | 错误反馈不能以泛化的“继续完成材料”代替原因 |

上下文去重只能消除相同责任、相同内容的重复交付。缓存属于展示机制，不是业务权威；会话开始、责任切换、新错误和新路径必须重新交付。缓存失效最多造成多输出，不能隐藏事实或阻止接收。不得把进程退出码、是否显示提示或是否命中缓存用于判断阶段完成。

普通 PreToolUse 不承担工具 ACL。未完成设计、缺来源或未准备好答卷，应让 agent 知道要修什么，不能禁止其使用 Read、Write、Bash 或其他修复工具。事件注册应覆盖真实可用的保存工具，包括自定义工具；消费者仍核对成功状态、当前 owner 和准确答卷。Worker 普通工具调用不能意外接收 Main 或其他 Worker 的责任。

携带 `file_path` 只证明工具涉及一个路径，不证明保存发生。明确的保存事件可沿原接收入口处理；脚本及未知自定义工具依真实前后变更识别，不能把未知工具一律当成写入，也不能仅排除几个内置读取名称。缺少观测、失败、无变化与成功变更是不同事实；未知不能充当成功变更。S7／S9 不依赖工具名称认定保存：Pre 高频监听本人准确原答卷的专业就绪，成功 Post／Stop 兜底；原消费者认定接收，不新增完成标记。其他阶段普通读取不接收答案，失败事件不签发或恢复材料。未接收的普通观测只维护可丢弃的诊断/变化缓存，不修改工程阶段，不增加 agent 的激活或许可步骤。

S7／S9 按已签发责任、原答卷内容和原消费者的专业条件判定可接收：保存的答案满足原合同即可自动交付；文件存在、可解析 JSON、verdict、平台返回或停止本身均不代替专业判定。系统不推断作者未写入的隐含意图；接收后的专业变更沿原修订合同处理。未完成稿不阻止普通工作，原字段错误、身份／来源缺口与系统接收故障分开表达；只对同一责任、同一内容的展示做可丢弃去重，不以展示缓存授予接收或隐藏新的错误。

接收、恢复及下一材料准备产生的新路径和可执行错误，须在本次事件的模型可读响应中交付。`stderr` 是诊断通道，不能以“进程输出里出现了文字”代替 Hook `additionalContext` 的交付；也不能要求 agent 再制造一次工具调用来取得已经准备好的下一责任。合并同次反馈时保持单个合法平台响应，避免几个 JSON 或过期阶段提示互相冲突。

## 恢复与诊断

已签发的 view 或未接收的 answer 缺失时，恢复沿原责任的受支持签发入口补齐，不让作者猜 JSON、复制身份字段或新建另一份责任。已有文件必须保留；已经接收的答卷不能静默回填成空白草稿。若无法自动恢复，指引必须如实指出缺失文件和具体技术入口，不能同时宣称“文件已经存在、无需恢复”。

原 S2 接收证据已经成立时，显式恢复可以继续其已登记出口，无须重建私人答案。只有需要再次保存原答案时才恢复其原作者内容；不能把文件丢失变成重新做一次专业判断的理由。

已接收但出口待续的会话仍须获得准确材料批次和绑定开发来源。修复正式材料后，向该分支提交并接续原出口；不能因为“报告已接收”就省略下一消费者仍需要的 Git 来源信息，迫使恢复者自行查 Runtime 猜提交目标。

反馈所用诊断可以持久保存，也可以从原权威输入重新计算，但不能建立另一份流程事实账本。普通观察不做完整 scenario 验证或来源闭包重建；需要重算的技术诊断应在失败后的原准备或显式恢复入口完成。专业验证仍由专业工作及实际 Gate 承担，轻量提示不冒充验证通过。

已接收结果必须覆盖旧静态缺项。例如 S2 已接收但锁定检查未通过，应显示锁定缺口，而不是同时显示无条件的 `architecture_record`。短反馈仍须保留错误原因、路径和下一步，不能以字数目标删掉恢复信息。

## 变更怎样沿层传播

| 变更类型 | 必须共同检查的来源与消费者 |
| --- | --- |
| 阶段输入、产物或交接条件 | L3、阶段协议、可执行 Gate/Action、技能、答卷模板、下一阶段来源消费者 |
| 专业方法与设计模板 | 方法所属技能/规则/模板、packet 阅读入口、相关阶段说明 |
| 作者字段或提交方式 | Schema/嵌入模板、packet、原 receiver、准确路径 Hook、回执与恢复、已签发旧材料兼容性 |
| 事件或提示策略 | 平台 settings、CLI 路由、owner/成功过滤、Hook 输出、会话恢复、平台接线验证 |
| 技术恢复方式 | 原接收与准备入口、入口指引、技能、诊断输出；不得仅增加一条新的禁令或通用重试口号 |

修改前先沿表定位权威来源，再同步其投影；完成后扫描同一概念的旧叙述，而不是在文件末尾追加“以新规则为准”。已签发 packet 保留原责任和原模板边界，新的模板措辞不能让历史合法答案突然失去接收资格。

## 验证与实现边界

验证以真实链路为单位：平台 matcher → 事件输入 → owner 与保存过滤 → 原接收者 → Runtime 迁移 → 下一责任准备 → 后续会话反馈。只直接调用 CLI 的测试不能证明平台已注册对应事件。

S2 回归应覆盖普通保存与脚本/自定义工具保存、未锁定架构、未提交正式来源、已签发文件丢失、同答案重放、错误后的材料修复、重复普通观察和新会话恢复。验证同时检查没有意外写 Runtime、没有工具权限拒绝、没有重复专业验证，以及下一次反馈仍能指出真实缺口。

边界回归另须证明：自定义读取不接收预先填好的答卷；失败/无变化/未知观测不会被解释为材料修复；成功修复当次响应包含准确下一路径；架构批次中的额外草稿在提交前可见；其他模块属于来源集合这一事实被明确交付，合法大集合不会因任意文件数量迫使作者删资料或拆需求。stdout 的平台协议与 stderr 分开断言，不能拼接后搜索字符串代替交付验证。

S3→S4 回归须覆盖 S2 成功保存当次交付完整 S3、首次 S3 与会话恢复、已接收待续、成功进入 S4 当次交付以及 S4 准备失败后的具体恢复。公开 Hook 断言实际 stdout 中单个 JSON 的 `additionalContext`，并检查没有工具权限拒绝；普通 Pre 即使遇到来源漂移或已发行视图丢失，也只投影原责任与准确恢复动作，不改 Runtime 或重新验证来源闭包。来源回归同时保留无关目录成员可共存、真实未提交契约仍拒绝、历史 S4 责任身份不变、大批次完整继承和索引二次读取漂移拒绝。

S5→S6 的验证从编排表推导，而不以提示中出现某个短语替代行为：

| 验证位置 | 必须能证明的行为 |
| --- | --- |
| 安装入口、角色与方法 | 新原生工作无旧激活手续；实际 frontmatter 是核心集；专项路径可解析，角色条件与专业方法一致 |
| S5 发行与修订 | 两项责任收到各自登记方法及原材料；旧合法 packet 字节/身份保持，修订不借当前技能替换原责任 |
| S5 原生返回 | 单人结论可完成本人责任；双 PASS 且真门满足才进入 S6；真实 blocker/空答不能被迫编造结论或产生完成事实 |
| S6 初次与后续 Main 指引 | 未准备给具体准备动作；准备不冒充平台运行；接收后指向集成；前置未满足指出真实依赖 |
| 专业字段减负 | 简化输入仍绑定原 Plan；显式错值、遗漏、重复或越界映射仍拒绝；旧合法格式继续接收 |
| 普通观察与恢复 | Worker 安静；Main 不签发、不代收、不改阶段；同内容去重，新会话/责任/错误恢复足够信息，缓存损坏不会隐藏失败 |

边界回归还须读取实际生成的对象：验证方法所指字段可以解析到原材料；两种不同 S5 拒绝不能在 Main 侧丢成同一无原因提示；S6 在形成 Plan 前后均可诚实返回阻塞而不产生完成事实；Main 后续变化不能悄悄改变 Builder 的固定源读集。历史合法 brief 继续按原版本识别，不能为新文案覆盖旧责任。文本检查用于发现悬空引用，不能代替这些行为验证。

另用不额外指定“首个工具必须是什么”的原生场景检查 Agent 能否仅依靠安装指引开始和交接。预置 PASS 的模拟只能证明机械接收，不证明专业审查质量；强提示驱动的流程不能单独证明自然下一步指引充分。源码/接线回归与真实执行分别报告。

运行边界是：S2 的专业设计、S3 的契约收敛和 S4 的任务规划由 Main 执行，S5 的独立判断由各 Reviewer 执行，S6 的实现和本人检查由 Builder 执行；自动接收不证明专业语义质量。没有真实 Claude Code 执行记录时，只能声称源码和接线测试通过。普通观察的降噪应按已验证阶段启用，不能由单个阶段的结果外推全部阶段。
