# 工程蓝图

blueprint 是人类与 agent 建立设计共识的入口，也是框架维护者的全局开发指引，只保存 L1～L4 的现行设计。它应完整传达工作流程、动机、设计思路、理念、细节、机制用法和观测安排。它不随模板安装到目标项目；目标项目的操作指引由 docs、角色定义和技能承载。

| 层级 | 回答的问题 | 入口 |
| --- | --- | --- |
| L1 原则 | 为什么这样设计，哪些边界必须守住 | [设计原则](l1-principles/L1-design-principles.md) |
| L2 生命周期 | 一个需求从提出到发布授权经过哪些阶段 | [生命周期规划](l2-lifecycle/L2-lifecycle-plan.md) |
| L3 阶段 | 本阶段由谁完成什么工作，怎样交接与收口 | [阶段索引](l3-stages/L3-README.md) |
| L4 机制 | 多个阶段共用的机制怎样工作，失败怎样恢复 | [机制索引](l4-mechanisms/README.md) |

## 阅读与维护

首次阅读按 L1 → L2 → 相关 L3 → 所引用的 L4 展开。修改机制时，先理解设计推导与职责边界，再调查实现及其证据，判断设计和实现各自需要怎样调整，并同步受影响的阶段、角色、技能、模板与测试。

跨阶段整改先使用[工作流边界与收敛设计](l4-mechanisms/L4-workflow-convergence.md)确定支持路径、机制取舍和完成标准，再进入相关实现。框架围绕辅助思考、质量下限与连续迭代设计；修复一个断点不自动授权扩展更多能力，减少作者操作也不能以无限增加内部协议为代价。该篇是机制成本、整改范围和停止扩展条件的统一设计入口，其他机制引用并落实，不各自追加一套规则。

每项规范在所属层定义，其他层引用，并在本层语境中解释其用途和配合方式；不能以避免重复为由删掉理解设计所需的上下文。L3 不另建跨阶段协议，L4 不替代阶段的专业判断。字段结构和命令参数须核对 Schema、模板及实现；出现冲突时分析偏差，不能默认实现就是设计标准。

文档统一使用中文叙述。必要的代码、命令、字段和产品名称保留原名，术语在首次出现时解释；同一概念不反复切换中英文或另造简称。正文直接描述现行约束，不用追加“新版优先于旧版”的方式修订。

历史方案、迁移计划、调查记录、版本日志和测试证据不放在 blueprint。维护历史按[仓库归档约定](../packaging/README.md)保存，Git 保留已提交文档的演化。验证报告必须说明实际源码、平台与执行范围，不能由设计文档的存在推导实现已通过。

## Blueprint 编写与调查范式（禁止删除本节）

> **禁止删除本节。** 本节是人类与 agent 共同维护 blueprint 的长期约束，覆盖以下全部子节。整理、去重、精简、重构或迁移文档时，禁止删除本节、将其缩成丢失要求的摘要，或移出本 README 后仅保留链接。修改本节必须保留其完整约束；改变这些约束须由用户明确指示。

### 1. 设计共识是编写目标

Blueprint 应延续早期文档严密、深入的设计表达方式，内容则应体现经过改进和优化后的设计。早期文档用于理解设计逻辑和推导方法，不是逐字恢复的目标；当前代码用于调查落地情况，也不能直接充当设计正确性的依据。

设计先说明问题、理念、选择和相互关系，再指导实现。文档应让人类和 agent 理解：为什么这样设计，各部分如何配合，机制怎样使用，以及落地时必须守住什么。清理噪音是去除迭代流水账、重复补丁式说明、失效规则和无意义的语言切换，不能删掉仍然有效的设计动机、推导、细节、例子和约束。

不以字数、行数或压缩比例衡量整理效果，也不按固定工具调用次数决定一个阶段已经调查完成。工作深度取决于设计复杂度、机制依赖与未解决的问题。篇幅简短、章节齐全或代码能够运行，都不能单独证明 blueprint 已写完整。

### 2. 先建立整体脉络，再逐阶段调查

先阅读早期 L1、L2 和 L3 总纲，理解理念怎样形成生命周期、为什么这样划分阶段、各阶段如何交接。随后对照后续完整文档，识别有效改进及被迭代记录掩盖的设计主线。不得直接从零散代码或压缩后的文档开始批量补写。

每个阶段依次完成以下工作，必要时回到前面的步骤继续调查：

1. **读设计。** 阅读早期阶段文档和后续完整版本，提取阶段目的、核心问题、设计选择、职责边界、输入输出及上下游依赖，先理解这些安排的理由。
2. **追踪变化。** 查明后来改进了什么、为什么改、解决了什么问题，以及哪些概念已被替代；追踪同一术语的含义变化。保留有效改进，不将旧设计整体恢复成现行规范。
3. **读使用入口。** 阅读主会话指引、相关技能、角色说明、模板和答卷，检查实际交给 agent 的任务能否准确表达设计。
4. **查实现链路。** 按真实执行顺序追踪入口、上下文交付、专业工作、提交接收、状态变化、退出与恢复，明确原生平台、主会话、子代理、Hook 和 Runtime 的职责。
5. **核对证据。** 阅读相关测试和真实运行记录，区分设计意图、已实现行为、已知偏差与验证缺口。测试通过只能证明相应行为，不能自动证明设计合理。
6. **整理推导，再写正文。** 将调查结果组织成连贯的设计解释。实现与设计发生冲突时，先分析原因，不能直接把当前行为写成规范，也不能只因旧文档这样写就否定后续改进。

调查记录与证据按仓库约定归档，正文保留经梳理后的设计推导、现行规则和必要的实现边界，不搬入调查流水账。尚未解决的冲突应明确呈现其影响，不能包装成已经成立的设计或能力。

按 S0～S11 逐阶段推进，每次深入理解并审查一份文档。阶段不能孤立调查：例如研究 S4 时要检查 S6 是否能使用其输出，研究 S7 时要理解 S8、S9 的返回路径。交叉阅读用于核实边界，不意味着同时批量套写多份正文。

### 3. L3 各阶段的调查主线

下表规定调查视角与阅读顺序，不预先替代调查结论，也不限制阶段正文只能包含这些内容。

| 阶段 | 设计主线与整理角度 | 重点阅读和调查顺序 |
| --- | --- | --- |
| S0 需求设计 | 人的意图如何形成可执行的需求共识；理念、方向、范围、成功标准之间怎样推导；哪些问题需要人决策；怎样利用已有项目基础；需求锁定的含义。写清讨论过程及最终需求的具体形态。 | L1 → 早期 S0 → 后续需求与项目基础设计 → 需求模板和主会话指引 → 当前锁定、修订及进入 S1 的行为。 |
| S1 需求绑定 | 为什么需求共识之后还需要执行绑定；需求成立、执行授权、开发目标和发布目标如何形成明确的执行范围；绑定、暂停、恢复、变更与终止各有什么语义。 | S0 输出和 L2 生命周期 → S1 设计 → 当前绑定答卷 → 绑定事务、Runtime 初始化及恢复路径 → 异常和重复操作测试。 |
| S2 设计 | 需求如何变成共同遵循的系统设计；架构、关键决策、业务规则、用户故事、场景、数据和测试预期如何关联；有界面和无界面的设计路径；项目基础如何约束本次设计。不能只描述答卷字段。 | 有效需求 → 早期 S2 的设计推导 → 后续场景与基础设计 → 设计方法和模板 → 当前提交、证据及下游消费。 |
| S3 契约 | 为什么架构设计还需要协作契约；模块边界、接口、共享模型、错误语义、兼容性和行为约束如何统一；怎样避免不同执行者各自解释同一对象。 | S2 设计产物 → S3 原始职责 → 共享模型与契约机制 → 当前契约模板和校验 → S4、S6、S7 如何使用这些契约。 |
| S4 任务拆分 | 设计和契约如何变成可执行、可验证、可协调的工作；任务粒度、依赖关系、职责划分、完成条件、验证责任和并行安排的依据；解释任务为何这样拆。 | S2、S3 输出 → 任务拆分设计 → 当前任务与分派材料 → 任务检查和依赖处理 → S5 审查及 S6 执行消费方式。 |
| S5 文档验证 | 为什么实现前需要独立审查；各审查视角要消除哪些不确定性；发现如何反馈；怎样形成可执行基线；审查结论与后续执行依据如何关联。 | S2～S4 设计包 → S5 审查模型 → 审查角色和答卷 → 原生子代理启动、返回与接收 → 反馈、重新审查和退出条件。 |
| S6 实现 | 主会话如何交付确定的工作，原生子代理如何获得充分上下文、制定计划、实现并验证，主会话如何接收和集成贡献；解释并行、工作区、依赖、阻塞、交付和集成边界。 | S4 任务与 S5 基线 → 早期实现设计及后续改进 → 当前分派指引和实现角色 → 原生派发、启动与结束事件 → 结果接收、集成和阶段完成；追查多余的执行抽象是否残留。 |
| S7 验证轮次 | 为什么实现后还需要独立验证；多个验证视角如何判断交付质量；验证对象、基线、覆盖范围、轮次、发现项、有效证据和干净轮次的含义；怎样进入调查或验收。 | S6 集成结果 → S7 验证设计 → 验证角色与任务材料 → 派发、接收和轮次管理 → S8 入口及 S10 前置条件。 |
| S8 问题调查 | 如何从观察到的问题走到有证据支持的原因判断；发现项、假设、调查任务、证据、问题归并、影响范围和修复建议如何关联；避免未经验证就开始修复。 | S7 发现项 → 调查方法和原设计 → 调查角色、假设与答卷 → 原生调查派发和证据接收 → 调查结论如何交给 S9。 |
| S9 修复 | 如何把调查结论变成范围清楚、可验证的修复；修复计划、执行责任、影响分析、独立复验与阻塞处理；为什么修复后要返回相应验证环节。 | S8 结论 → S9 修复闭环设计 → 修复和复验角色 → 原生执行、结果接收与集成 → 问题关闭和返回 S7 的规则。 |
| S10 验收与审计 | 需求验收和过程审计分别回答什么；怎样利用产物和证据形成可解释的交付结论；未知项、风险、阻塞项和验收决定的关系；避免汇总指标替代实际判断。 | 原始需求与成功标准 → S7～S9 有效结果 → S10 双重职责设计 → 当前报告和结论生成 → 判定及交给 S11 的内容。 |
| S11 发布门禁 | 验收结论如何形成明确的发布决策；发布对象、目标、授权、风险处置和生命周期收尾；区分达到发布条件、获得发布授权和实际执行发布。 | S1 的目标与授权 → S10 结论 → S11 原始设计 → 当前门禁与状态变化 → 完成、归档和后续需求的衔接。 |

### 4. L4 按机制依赖梳理

L4 应解释机制为什么存在、如何工作、在各阶段怎样被正确使用。调查 L3 时同步记录机制问题，再按以下依赖关系梳理 L4；这些是调查主题，不要求强行合并现有文件。

1. **状态、事务与修订机制。** 厘清哪些是权威事实、谁有权修改、如何保持一致，以及重复提交、失败和恢复怎样处理。
2. **阶段答卷与流程推进。** 解释专业产物、答卷、证据和状态转换之间的关系，说明自动接收的边界与主会话的判断责任。
3. **原生子代理与工作区机制。** 完整描述任务交付、上下文、启动、执行、返回、接收和集成，明确 Claude Code 原生能力与项目治理能力的分工。
4. **Hook 与运行控制。** 逐个解释事件为什么接入、观察什么、允许做什么、产生什么结果、失败怎样呈现。埋点应说明帮助定位哪类问题、与哪项责任或状态关联，不能只列日志字段。
5. **项目基础与共享契约。** 说明跨需求复用的设计知识怎样形成、引用和演进，以及怎样与当前需求的局部设计配合。

L4 不能只列接口和禁止事项，也不能在多个文档中重复发明执行流程。每份机制文档都应有明确职责，相关 L3 文档则在具体阶段解释为什么、何时使用它，以及它如何支撑专业工作。

### 5. 正文应形成完整的设计推导

阶段正文应连贯回答：**阶段面对什么问题 → 为什么这样设计 → 参与者和产物是什么 → 工作如何展开 → 机制怎样承载 → 怎样判断完成 → 失败后如何继续 → 与上下游如何交接。**

按阶段特点安排章节，不强行套成相同长度的模板。需要展开的内容包括：

- **目的与设计依据：** 阶段存在的必要性、要解决的矛盾、选择依据和取舍，以及与 L1、L2 的关系。
- **具体对象与示例：** 输入输出长什么样，关键概念之间是什么关系；在有助于理解时给出产物示例、流程图、职责表或状态变化示例，并解释其含义。
- **工作过程与协作：** 专业工作怎样逐步完成，谁负责判断和执行，哪些步骤有依赖，哪些可以并行，什么时候需要人类参与。
- **机制使用与观测：** 每个关键环节使用什么机制、为什么使用、输入输出是什么；Hook 在哪里衔接，哪些事件和埋点能够证明进度、定位失败与支持恢复。
- **边界、完成和恢复：** 完成条件、交接约定、异常分支、重试与恢复，以及专业判断和机械校验各自能保证什么。
- **实现对应与差距：** 指向相关实现和使用入口，准确说明已经落地的能力、适用范围及尚未解决的偏差。不能用实现细节淹没设计主线，也不能把设计意图写成已经验证的事实。

审查完成与否，应看读者能否据此理解并正确开展该阶段的工作、解释机制选择、判断交接是否成立，而不是只检查标题、字段或链接是否齐全。尚未完成调查和审查的正文只能作为草稿，不能因为已经写入文件就视为完成。

## 实现边界

框架以 Claude Code 原生子代理为执行机制，在 `SubagentStart` 和 `SubagentStop` 衔接专业输入与产物；Runtime Writer 维护工程事实，Main 负责分工、集成和阶段闭环。普通工具事件不承担子代理激活或结果接收。

L3、L4 的“实现落点与边界”指向对应代码，并说明现有适用范围。保留的旧执行恢复能力只服务原记录，不是新责任的启动要求。自动化测试、真实 Claude Code 测试和产品质量验收分别验证，不能相互替代。
