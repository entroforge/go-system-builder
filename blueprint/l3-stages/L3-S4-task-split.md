# L3-S4 任务拆分

S4 将已经成立的契约承诺，推导为可以分别交付、验证和协调的工作包。每个 TASK 说明交付什么、为什么这样划分、需要哪些输入、改变哪些范围、怎样证明本人完成，以及哪些真实前置会影响执行。

本阶段承接 [S3 契约](L3-S3-contracts.md)，向 S5 交付任务与整体派发计划供独立审查；审查通过后，S6 才按锁定批次实际派发、实现和集成。总体依据见 [L1](../l1-principles/L1-design-principles.md)与 [L2](../l2-lifecycle/L2-lifecycle-plan.md)，操作入口见 [S4 使用指引](../../docs/control/agent-protocol.md#s4)。

## 1. 为什么契约之后还需要任务设计

### 1.1 共同承诺还没有成为具体工作

契约说明系统各端必须做到什么，却没有直接回答“一个执行者这次交付什么、从哪里开始、依赖谁，以及怎样结束”。把整份契约直接交给 Builder，会让执行者重新调查范围、补依赖、决定验证责任；不同执行者可能同时修改同一入口，也可能各自完成局部而无人接通真实调用链。

任务拆分必须在实现前解决五组问题：

1. **交付单位：** 哪些条款共同形成一个可解释、可独立判断完成的结果。
2. **必要上下文：** 执行者需要理解哪些本端条款、共同协议、模型和场景，哪些背景只在条件成立时展开。
3. **变更边界：** 真实入口、业务处理、持久化、类型、测试和必要接线由谁承担，是否存在遗漏或冲突。
4. **完成判据：** 本人需要交什么、检查什么、留下什么依据；后续哪些判断属于 Main 或独立验证者。
5. **协作次序：** 哪些前置产物必须先集成，哪些可并行，哪些可变资源需要有理由的顺序。

S4 的价值在于让这些判断成为明确规格，而不是让每位 Builder 再做一次隐含规划。任务可以触及多个文件，但应围绕一个可判定的交付目标形成闭合。

### 1.2 几种“完成”分别成立

| 事实 | 含义 | 不等同于什么 |
| --- | --- | --- |
| TASK 文档 `complete` | 任务书已写完，可以交给阶段检查和 S5 审查 | 不表示代码已经实现，也不表示责任工作状态为 done |
| S4 答卷已接收 | 系统保存了本批规划结论与实际材料关联 | 不表示 TR-002、S5 审查或实现已经完成 |
| S5 审查通过并锁定 | 两路独立责任认可当前规格链与可执行性，建立准确执行批次 | 不表示任何 Builder 已经交付 |
| 本人实现交付 | 执行者完成本人约定产物、自检和专业结果 | 不表示 Main 已集成或全阶段完成 |
| Main 集成有效 | 当前交付已合入实际开发目标并完成必要检查 | 不自动代替独立验证或完整交付验收 |

TASK 文档状态使用 `draft / complete / cancelled`；实际责任进度使用共用五态。专业结论、静态计划状态、平台进程和集成事实不能压成同一字段。共用语义见 [L4 状态机](../l4-mechanisms/L4-state-transition-core.md#unified-work-state)。

### 1.3 S4 负责计划，S5 审查，S6 执行

S4 负责粒度、条款归属、读序、范围、完成条件、依赖和整体派发安排。它不创建实际 Builder，不预填平台 agent_id，不生成团队激活手续，也不填写未来执行结果。

S5 独立判断这些工作包是否忠实于规格、是否真能执行，并审查并行和串行的理由。S6 使用 Claude Code 原生子代理执行，Main 负责实际分工、容量和集成。S4 不能为了“准备派发”把原生平台之外的读回、激活或启动许可重新塞进任务。

## 2. 当前输入、参与者与交付形态

### 2.1 从已接受的契约进入

正常入口是 `planning.tasks`。系统承接已接受 S3 的契约及来源闭包，准备当前资料与答卷，给出准确的 REQ 任务索引、TASK 候选位置、模板、绑定开发分支和具体下一动作。

| 输入 | 要读出什么 | 使用边界 |
| --- | --- | --- |
| 当前绑定 REQ | 目标、范围、验收、负空间和风险 | 任务不能扩大或降低需求承诺 |
| CONTRACTS 索引 | 当前批次的准确条款集合与各端关系 | 不另抄一份任务自有条款宇宙 |
| 实际 FE/BE/SYNC 契约 | 本端责任、操作、模型引用、失败与恢复 | 不在 TASK 中重新定义共同对象和协议 |
| S2 模块当前包 | CASE、判据、fixture、故事与操作流；适用时包括 PATH 和原型 | 保留业务分母和完整模块回归义务 |
| 现有代码及工程规则 | 真实入口、调用链、持久化路径、构建与测试方式 | 用于划定必要改动，不能反向改写正确结果 |
| 当前责任和已接受来源 | 权威控制根、开发目标、原材料引用、当前 view/answer 路径 | 不用新的目录扫描替代上游已接受事实 |

上游明确但无法拆出可执行任务时，先判断是任务划分问题，还是契约、设计或需求本身有缺口。发现上游问题回对应层收敛，不能把“执行者自行决定”写成完成条件。

### 2.2 谁承担什么判断

| 参与者 | 责任 |
| --- | --- |
| 主会话 Main | 调查真实实现面，设计任务、条款覆盖、读序、完成判据和派发计划，自审并交付当前答卷 |
| 人类负责人 | 决定真实需求变化，以及超出既有授权的价值、风险或方向取舍 |
| 结构检查器 | 对账条款、任务状态、计划成员、依赖和格式，呈现有来源的建议 |
| Hook、接收服务与 Writer | 接收本人规划、保存实际关联、处理幂等和 TR-002 接续 |
| S5 两路审查者 | 分别检查规格链一致性、任务可执行性及编排是否合理 |
| S6 Main 与执行者 | 按已审查任务原生派发、连续执行、自检、返回成果并集成 |

普通拆分不需要逐任务人类批准。Main 在既有授权内连续开展专业工作；真正改变需求或风险承诺时再提出具体决定。机器建议不构成一层额外开工审批。

### 2.3 产物及其消费者

```text
docs/dev/tasks/
├── index-REQ-017.md       # 本需求整体派发计划，包含波次和必要资源顺序
├── TASK-017-01.md         # 一个具体交付目标及其任务书
├── TASK-017-02.md
├── TASK-017-03.md
└── TASK-017-04.md
```

路径示意沿用订单导出例子，实际 TASK 数量、编号和交付边界由专业判断决定。当前规范任务标识使用至少三位数字，可带两位子编号，例如 `TASK-017`、`TASK-017-01`；不能把 REQ 全名塞进任务 ID 后假定下游 Runtime 也接受。

| 产物部分 | 表达的事实 | 主要消费者 |
| --- | --- | --- |
| Objective 与 Primary contract | 本任务交付什么，主要承诺归属哪里 | Builder、Main、S5 |
| Document Manifest | 有序、带目的的必要阅读及适用条件 | Builder、上下文分析、S5 |
| Delivered Clauses | 本任务兑现哪些实际条款 | 覆盖检查、S5、后续验证 |
| Module Impact 与 Scope | 影响哪些模块，必须读写什么，排除什么 | 派发、执行、集成和回归规划 |
| Outputs 与 Closing Contract | 本人交付物、检查、结果判据及后续独立责任 | Builder、Main、S5、S7 |
| Dependencies 与 Resources | 真正的产物前置和互斥资源 | 整体计划、S5、S6 |
| REQ 任务索引 | 精确成员、并行波次、必要资源顺序和执行入口 | 结构检查、S5、S6 Main |
| 当前三项答卷与接收事实 | 专业结论、真实材料位置及交接进展 | 接收服务与恢复流程 |

当前[任务模板](../../docs/dev/tasks/TASK-template.md)已将实际 Assignment、owner、集成和生命周期记录交给 Runtime。未来 QA、E2E 和修复结果不回填冻结 TASK；[索引模板](../../docs/dev/tasks/index-template.md)的复选框也不是执行看板。

## 3. 怎样从条款推导可交付粒度

### 3.1 先找一个结果，再确定文件和角色

先选择需要共同成立的一组条款，说明它们形成什么交付结果。再调查真实改动面和检查方式，判断是否应由一个职责连续完成。不能先按目录或文件数量平均分，再拼出一个看似合理的任务目标。

一个 TASK 使用一个 Primary contract，并在 §3 声明实际交付条款。SYNC、模型或其他契约可以作为必要输入，不意味着该任务拥有所有上游责任。若一个工作包确有两个可分别验收、可以独立交付的结果，应考虑拆开；若改动必须共同保持一个事务或不变量，则不能只为增加并行数量拆散。

“一句话说明交付物”是判断工具，不是按“以及”“然后”关键词自动切任务。短句也可能隐藏巨大范围，多个必要步骤也可以共同形成一个交付目标。判断依据是责任、完成条件和真实变更耦合。

### 3.2 用实际调用链检查接线归属

每项能力都应能追踪：用户动作或外部调用者 → 注册入口 → 权威服务/事务 → 响应或持久化状态 → 所属 TASK → 必要写路径 → 可证伪检查。

订单导出如果需要新 HTTP 处理器，就不能只有一个“实现导出服务”的任务而无人注册路由。授权定义、共享类型、数据访问、错误映射和测试入口也必须有人承担。范围里的文件都合法，并不能证明全部必要文件已经列出。

保持必须原子成立的变化在同一责任中。例如同一数据库事务里的状态与记录更新，不能拆给两个互相等待的任务，最后只在集成阶段才尝试拼成一致性。若上游协议无法说明正确结果，先回 S3 或 S2。

### 3.3 订单导出的拆分示意

以下假设 S2/S3 已明确：既有命令通过 HTTP 服务取得订单导出结果，本次无网页变化；BE-017 承担范围、授权和订单保护，SYNC-017 承担请求、结果与拒绝协议。文件名只展示划分思路，不替真实项目决定实现。

| TASK | 单一交付目标 | 主契约及条款 | 本人改动与自检 | 真正前置 |
| --- | --- | --- | --- | --- |
| TASK-017-01 | 服务按组织和月份生成授权范围内的结果，拒绝非法请求并保持订单不变 | BE-017 §1、§2、§3 | 服务实现及本人单元测试，覆盖允许和拒绝结果 | 无；共同 Schema 已由 S3 提供 |
| TASK-017-02 | 正式 HTTP 入口正确调用导出服务并兑现协议 | SYNC-017 §1、§2 | 路由/处理器、错误映射及本入口自测 | TASK-017-01 的服务实现已集成 |
| TASK-017-03 | 通过正式服务入口建立导出范围、拒绝与副作用的回归检查 | BE-017 §1、§2、§3 | 独立测试文件和所需合成前置，不改生产实现 | 所用服务和 HTTP 入口已集成 |
| TASK-017-04 | 既有命令按共同协议发起请求并正确处理结果和拒绝 | SYNC-017 §1、§2 | 命令调用与本端测试，可使用受共同模型约束的 Mock | 不因共享 Schema 而依赖服务实现；真实联调另有安排 |

同一条款可以由实现任务与测试任务共同兑现，覆盖按条款集合对账，不能用重复计数冒充更多覆盖。专门的测试任务不免除实现者的本人自检，也不替代 S7 独立质量判断。

若 TASK-017-02 的完成不需要新服务实现，只消费已存在接口，就不应保留示例中的依赖。若命令任务真实依赖一个新生成客户端或共享实现，则必须补该产物的实际前置。依赖从事实推导，不能照抄示例。

### 3.4 支持任务、取消与覆盖

基础设施、测试环境或其他支持任务可以没有交付条款，但要有真实目标和完成判据。支持任务进入本批计划，不为条款覆盖凑数。只有下游实际需要它的实现产物时，才建立依赖。

取消任务保留 `cancelled` 事实，退出执行计划和条款覆盖聚合。若它原来独占某条款，覆盖缺口必须重新出现并分配；依赖已取消任务的活动工作也需调整。不能通过取消来缩小已经承诺的需求范围。

## 4. 为执行者组织有限而充分的上下文

### 4.1 Document Manifest 是阅读路径

任务先说明目标、范围和完成条件，再引导执行者按本端条款→共同操作→共享定义→必要场景和规则展开，最后回 TASK 执行。不要求先递归阅读整条文档链，也不能只给一个仓库目录让执行者重新探索全部设计。

当前 `Reading policy: linked-v1` 的清单使用 Order、Kind、ID、Path、Clauses、Purpose、Mode。Path 使用 Markdown 链接指向相对当前 TASK 的真实文件，必要时附可定位锚点；Purpose 说明为何阅读，Clauses 指向实际条款或 CASE。

| Mode | 使用方式 | 必须保留的判断 |
| --- | --- | --- |
| `required` | 当前任务必需的输入 | 必须可读，并足以支持当前责任 |
| `conditional` | 条件成立时必须展开 | 在 Purpose 明确条件；机器不能替作者判定所有条件是否成立 |
| `optional` | 需要时使用的背景 | 不应靠隐藏在背景中的关键约束才能完成任务 |

优先引用具体操作、条款、模型和 CASE。共享模型本身可以递归，文档可以有导航回链；它们不是任务执行环。当前 TASK DAG 只表达真正的产物前置。

例如 TASK-017-01 的清单可以先定位 BE-017 的范围、授权和订单保护条款，再读取 SYNC-017 的对应操作及错误映射，随后定位实际共享请求定义与适用 CASE。每一行分别说明为什么读、读哪一段，而不是给这些材料各贴一个“相关”标签。若一个模型已有精确原生定义，应指向该定义，不要求执行者从整份架构概述重新寻找字段。

必要读集与条款交付集不是同一集合。任务可能需要读取拒绝协议和共享模型，但只交付 BE 行为；也可能为验证某个条款读取多个 CASE。不能将所有读到的条款自动列为本人交付，也不能因为不是本人主契约就省掉必要输入。

### 4.2 粒度观察怎样帮助判断

工具按读取模式、实际文件和可定位章节分析去重字节、共享读集、写入耦合及未解析项目。它能帮助 Main 看见哪些任务重复背负同一大段背景，或哪些看似分开的任务共享同一写域。

字节不是 token、业务难度或上下文耗尽概率。目录未展开、锚点无法定位、条件未知不能按“零成本”当作已知可读。文件数、改动行数或一次 compact 都不能自动决定拆分；应结合实际上下文、独立判据和返工观察判断。

建议指向具体 TASK、条款和路径，Main 决定是否调整，S5 独立审查。运行中不会因为某个建议自动拆并冻结任务；真实变化走规划、审查和影响处置流程。

### 4.3 行为示例和工程惯例的边界

任务清单实际引用模块 `cases.json` 并在 Clauses 指明 CASE 时，工具可从已校验源包投影输入、判据、fixture 和来源。一个模块链接不表示给本任务指派模块全部 CASE；投影也不是执行证据或新需求批准。

工程惯例投影只帮助定位已有规则、架构或决策的来源及适用范围。只有被实际来源支撑的默认及例外才可采用；候选、过期或冲突内容需回原责任确认。正常 S4 在 TASK 读集中直接选择原规则、已登记架构或 ADR 的具体路径、条款与锚点，沿原专业材料说明适用选择、范围及例外，不另建或维护一份需要手抄摘要和版本的惯例索引。真正的新决定仍回原架构和变更流程。没有惯例索引时，Main 仍可在既有授权内作正常工程判断，不能把空索引变成新的准入门。

阅读分析、行为示例和惯例建议都不能替代缺失的业务判据，也不要求作者制造系统能识别的 checker 命令来让建议消失。实现与专业判断的关系见 §12。

## 5. 声明必要改动范围与责任归属

### 5.1 范围覆盖实际交付

Scope 说明读取、预期产品写入、实际禁止改变的产品边界、适用检查/操作和产品输出路径；检查示例不是普通工具白名单。它应覆盖本人 §6 的产品交付：实现、本人测试、必要接线和实际需保存的专业证据。不能承诺一份产品测试报告，却不给它一个真实可写位置。运行时 Plan/Result 等报告使用后续实际责任供应的原入口，不要求 S4 作者预造 Assignment、消息路径或未供应的 schema。

`waves-v1` 使用具体的仓库相对写路径，按实际文件或有边界的目录声明，不写 glob，也不以整个仓库掩盖尚未调查的改动面。共享只读模型不进入互斥资源；必须改变共享来源时，应先判断是否触及已冻结规格。

路径格的正式表达与说明文字分开。新模板优先使用逐项 inline code、逗号分隔的路径清单；为接收已有清晰材料，也支持纯路径清单，以及在完整的 code 路径清单后附一段成对圆括号说明。说明不进入写域；语法由同一个 Scope 提取器解释，不能由各阶段自行截字符串。

| 路径格形状 | 写域含义 |
| --- | --- |
| `internal/a.go, tests/a_test.go`（此处展示纯文本清单） | 两个实际文件；保持既有纯路径材料的含义 |
| `` `internal/a.go`, `tests/a_test.go` `` | 同上；code span 之外只允许分隔符和空白 |
| `` `simulation/products/`（仿真产品输出区） `` | 仅该有界目录；允许末尾 `/`，圆括号文字仅解释用途 |

附注只允许位于整份 code 路径清单之后，用一组配对的中文或英文圆括号包住；不允许逐项夹注、混用裸路径与 code 路径或无法消费的尾随文字。解析按 code span 和附注边界分项，不从任意 prose 中收集“看起来像路径”的词。路径必须非空、仓库相对且不逃出根；不得包含 glob、未闭合反引号、模板占位或本清单语法无法无歧义表示的分隔符。文件名确需超出该语法时应先明确原表达能力，不能静默扩大或截断路径。其他解释优先放在 Scope 表后的现有段落，不增加作者栏目。

这一语法属于模板/派发规则与原 Scope 提取器的共同合同：S4 自查及原接收在冻结前给出准确 TASK、Scope 行、非法片段与合法例子；S5 的执行分析、S6 原 Assignment 和 brief 消费相同的路径结果。S6 不再从说明文字推导另一套范围。`read paths`、`output paths` 和 `forbidden paths` 不能因名称含 `write` 或提取器扫描顺序意外扩大 `prospective write paths`。

既有合法纯路径和 code 路径保持原含义；未接收材料按这份明确语法检查。已经锁定的 TASK、签发的 Assignment 和接收事实不因解析修复被改写。若原 TASK 字节未变而旧 Assignment 固化了错误派生范围，Main 可在适用条件内使用既有 Assignment 执行修订形成准确后继，仍保留原锁定 TASK，并遵守原 owner 替换、贡献处置及批准边界。当前不支持重新绑定批准的模式须明确限制，不能以解析修复为由静默换 owner 或就地改旧记录；真实 TASK 内容或专业范围改变仍须原规划/审查，不能借技术修正重锁。本段统一路径表达、原提取器与后继消费者的语义；已签发来源仍遵守上述冻结与修订边界。

TASK 范围用于专业交接、派发和集成检查，不授予普通工具身份或首写许可。S6 实际写入面还需遵守已审查 TASK 和原生任务记录；Assignment 的 write_paths 与 output_paths 都不能扩出该边界。

### 5.2 本人交付与后续责任分开

| 责任 | S4 怎样写入任务 | 不能转嫁的工作 |
| --- | --- | --- |
| Builder | 本人实现、适用测试、实际自检和专业交付 | 不得让其他人的后续验证成为本人必须伪造的报告 |
| Main | 接收交接、合并开发目标、集成检查与依赖释放 | 不以 Builder 子分支自测替代集成 |
| 独立 Delivery/QA/E2E | 后续适用验证的输入、范围及承接关系 | 由独立责任产生结论，Builder 不能代签 |
| 系统 | Runtime 关联、接收和来源记录 | 不要求任务作者填写未来执行身份、指纹或回执 |

本人完成不需要等无关同事或未来 S7；但其约定自检也不能被留给以后的人补做。服务 CASE 使用正式服务入口，浏览器适用者保留 PATH 和真实交互责任，不能因为任务拆开就缩小模块回归分母。

## 6. 让完成条件可以被逐项判断

### 6.1 Closing Contract 连接条款、本人检查和交接

收尾契约（Closing Contract）不是一句“实现完成”，而是本人返回时必须逐项回答的条件。它应覆盖四个方面，并与 TASK 的目标、条款、Scope 和 Outputs 对齐：

| 方面 | 要说明什么 | 订单导出任务示例 |
| --- | --- | --- |
| 行为成立 | 哪些契约结果必须可观察，成功与失败分别如何判断 | 授权请求只得到本组织本月份订单；越权请求返回契约拒绝结果 |
| 本人验证 | 本责任需要实际执行哪些适用检查，结果怎样记录 | 服务测试覆盖范围、拒绝和订单未变；保留实际命令与结果 |
| 改动边界 | 哪些实现、测试和证据路径属于本人，怎样处理偏离 | 本人改动及交付证据落在任务约定范围，未擅改冻结契约 |
| 可交接性 | Main 接收时能定位什么，哪些工作完成、哪些仍受阻 | 返回实际提交与专业结果，逐项解释未完成条件和真实阻塞 |

这四类是设计检查角度，不是“四行断言”的硬限额。复杂条件需要拆清楚；大量彼此独立的条件也可能提示粒度过大。不能为了满足行数合并掉失败路径，或把一个事务拆成无法各自完成的工作。

例如 TASK-017-01 可写为：

```text
assert BE-017 §1、§2的导出范围与拒绝行为满足共同判据
assert BE-017 §3的订单保护在成功和拒绝后均成立
assert 本人服务测试实际执行，覆盖上述成功、拒绝与状态检查
assert 本人交付位于约定范围，结果逐项说明完成情况与真实偏离
```

每条还要能落到输入、可观察结果和证据，不能只重复“条款满足”。例如授权范围应由明确的组织、月份和合成订单数据判断；订单保护应比较有关持久化状态，不能用“请求返回成功”代替。

### 6.2 判据与命令各司其职

自由文本 `assert` 表达专业承诺，不是系统会解释执行的测试语言。检查命令应来自真实工程入口，预期结果来自契约、CASE 和规则。`go test` 返回成功只证明实际执行的测试，不能自动证明所有业务条件、真实接线或后续集成都成立。

任务可以指向有来源的检查工具，也可以要求执行者通过代码检查、状态比较或其他适用方法给出证据。未能识别为某个 checker 的自然语言条件不能因此被删掉；但不可观察、没有阈值或没有判断对象的表述必须补清楚。

模板中的范围条件指已审查 TASK 和实际分派中登记的写入范围，不是“激活后才能首写”的手续，也不要求作者另填一份范围。S6 的计划和结果让执行者逐项对应完成条件，如实说明范围偏离，并沿原范围和变更流程处置；报告偏离本身不授权扩展范围。保存计划本身不激活普通工具，也不替 Main 作集成判断。

### 6.3 为诚实的完成和阻塞都留出出口

本人完成需要交付本人承诺的实现、自检与专业结果，不以未来独立审查或其他无关任务完成为条件。若检查确实失败，必须说明哪个判据未满足、已经得到什么事实、哪些工作尚未交付；不能以“稍后 QA 会测”宣称本人完成。

若缺外部服务、测试环境或必要上游产物，说明真实阻塞、影响条件及承接责任。阻塞应能交接，不要求伪造 PASS，也不将别人的后续工作写成本人已经产出的证据。Main 决定补输入、改变执行安排，还是按影响返回相应规划层；冻结规格不能由执行者自行改低。

## 7. 从产物依赖推导协作顺序

### 7.1 依赖说明消费者在等什么

先问“后项缺少前项的哪个实际产物就不能完成”，再写依赖。TASK Dependencies 以 `TASK-*` 为节点，并说明需要的产物以及集成、验证要求。一个文件链接、Assignment 标识或“先看看别人怎么做”不等于机器能够追踪的任务依赖。

| 情况 | 如何安排 | 理由 |
| --- | --- | --- |
| 两端共同读取 S3 已提供的 Schema | 各自 Manifest 引用，可并行 | 共同知识已经存在，没有新的产物等待 |
| 消费者需要新实现、生成代码或迁移结果 | 声明产出该结果的 TASK 前置 | 只有规格不能替代实际需要的实现产物 |
| 客户端可按契约 Mock 完成本端，真实联调由后续责任承担 | 本端不因提供方尚未完成而自动串行 | 本人完成条件与后续集成责任已分别成立 |
| 两个步骤必须共同维护一个原子不变量 | 优先保留为一个完整责任 | 人为拆开会制造互相等待或不可独立成立的交付 |
| 只是担心同时工作不好管理 | 调查写入或资源事实后再定 | 便利管理不能代替依赖理由 |

依赖目标必须存在、未取消，联合顺序不能成环。没有声明但实际需要的边会让任务提前派发；复制粘贴来的假边会让可并行工作无谓等待。二者都属于 S4 的设计缺陷，不能留给调度器猜测。

### 7.2 资源顺序解决真实互斥

除产物依赖外，还可能存在同一可变外部资源的排他使用，例如不可隔离的共享测试数据库。TASK Resources 只登记这样的资源，使用一致的 `resource:<stable-name>` 标识，说明用途。

优先通过独立所有权、独立工作区或可隔离资源消除冲突。确实不可隔离时，在 REQ 索引的 Resource order 中写明 Before TASK、After TASK、Resource 和 Reason。资源顺序与产物依赖共同构成一个有向无环图，前项安排在后项之前的波次。

```text
TASK-017-01 ──产出服务──> TASK-017-02 ──产出正式入口──> TASK-017-03
       └────────────────所需服务──────────────────> TASK-017-03
TASK-017-04：按共同协议独立实现命令端
```

该示例没有共享可变资源，因此不应凭空添加资源行。若两个任务确实共用 `resource:export-test-db`，需明确谁先用、为什么不能隔离，以及由谁确认释放；不能用一个未解释的“共享资源”替所有任务串行。

### 7.3 写入重叠需要专业处置

同一文件、重叠目录或同一排他资源可能让“同波可并行”的承诺失效。先缩清实际范围，再判断是否能拆开所有权；确需顺序时把理由和顺序明示，不能只调整波次却留下隐含冲突。

当前计划分析会呈现同波写入与资源重叠，但重叠本身按警告处理，不等于结构检查已拒绝。Main 与 S5 必须判断是否可安全并行，不能将“没有硬错误”当作并行证明。S6 对冲突采取保守调度也不能反过来证明 S4 已给出合理编排。

## 8. 在一个 REQ 索引交付整体派发计划

<a id="dispatch-plan-delivery"></a>

### 8.1 波次表达编排，TASK 保留详细规格

整体派发计划回答“本批有哪些工作，它们怎样协作”，不重复每个 TASK 的读集、改动范围和检查条款。它位于 `docs/dev/tasks/index-REQ-<id>.md`，使用 `waves-v1`，绑定准确 REQ；进入审查前，文档 `Status: complete`、`Revision` 为正整数。

每个未取消 TASK 在连续的 `## W1`、`## W2` 等标题下恰好出现一次，使用未勾选的 Markdown 文件链接。TASK 明确声明 Source REQ refs。漏项、重复、失效链接、取消项混入或任务归属不明，都不能靠索引自身的列表掩盖。

订单导出示例的最小计划如下；完整索引继续使用模板中的阅读入口和适用资源说明：

```markdown
# REQ-017 任务与整体派发计划

> REQ: REQ-017
> Dispatch policy: waves-v1
> Revision: 1
> Status: complete

## W1

- [ ] [TASK-017-01](TASK-017-01.md)
- [ ] [TASK-017-04](TASK-017-04.md)

## W2

- [ ] [TASK-017-02](TASK-017-02.md)

## W3

- [ ] [TASK-017-03](TASK-017-03.md)
```

示例中 TASK-017-03 的 Dependencies 同时声明 01 和 02；04 不消费服务实现，因此不被 01 阻塞。波次按依赖推导，不是先平均装进几个桶再补一串理由。

### 8.2 波次不是等待前一整批结束的屏障

同波表达计划允许并行，实际是否派发还受依赖集成、资源和真实容量约束。前波有无关工作尚未结束时，后波已经具备前置的任务可以继续。

例如 01 已被 Main 集成并完成必要检查，而 04 仍在工作，02 已具备自己的前置，不必等待整个 W1。若只有 01 的 Builder 返回“完成”，但 Main 尚未集成，则 02 仍应等待。03 同理，要等自己声明的前置，不是只看 W2 的复选框。

S6 的依赖释放以当前有效交付已接收、责任完成、必要集成和匹配检查点成立为依据。子分支测试通过、原生子代理退出或一条提交记录，分别都不足以替代这组事实。

### 8.3 静态计划与运行视图分离

索引的未勾选框是冻结规格的一部分，不在实现时勾成运行看板。执行进度、排队、阻塞、待集成和当前可派发项由 Runtime 投影；未来 owner、实际 Assignment、结果和集成记录也不回填 TASK。

S6 使用 `loop-harness s6 status --capacity <总并发槽位>` 查看实时安排。公开参数是实际总容量，不是当前剩余名额；未声明容量时可以查看就绪情况，但不据此声称已经选出实际派发批次。平台实际启动成功仍是另一项事实。

容量变化、运行进度和清理临时工作区不修改计划。成员、依赖、范围或产物责任发生真实变化，则要回到相应规划与审查流程。完整执行语义见 [L4 整体派发计划](../l4-mechanisms/L4-agent-dispatch-governance.md#dispatch-plan)和[派发规则](../../docs/rules/dispatch-plan.md)。

## 9. 完成自审，明确交给 S5 的问题

### 9.1 结构检查对账什么

S4 在整批任务完成后进行对账，而不是只证明每张 TASK 单独存在。结构检查帮助定位：

- 当前条款集合是否被未取消任务覆盖，引用是否真实存在；支持任务不虚增覆盖。
- 活动任务是否全部写完，主契约、收尾契约和必要写入声明是否具备；读集及其他交接资料的缺口结合分析与自审定位。
- 当前 REQ 的任务与计划成员是否闭合，每项恰好出现一次。
- TASK 依赖和资源顺序是否有效、无环，波次是否尊重前置。
- 计划读取、路径与写入声明是否可解析，哪些重叠、上下文缺口需要专业判断。

问题必须指向真实 TASK、条款、路径或约束。不能让维护者先补一份手工全量清单、登记 checker 身份或运行额外“证明仪式”，才允许检查真正的交付。

正常答卷接收会调用原任务检查器；TR-002 的 `tasks_checked` 也会检查阶段条件。原 `tasks check` 可用于有针对性的诊断，但作者不需要把手工执行该命令变成另一份准入证据，更不应为了同一责任反复生成不同的报告。

### 9.2 Main 先做专业自审

机器能够确认图无环，却不能确认边的理由正确；能够找到 `assert` 文本，却不能确认判据足够、命令真正覆盖目标或任务可由一个执行者完成。Main 应代入 Builder，沿目标、读序、改动、检查到交付走完一次。

重点追问：真实入口有没有人接；是否遗漏迁移、错误映射或测试资料；共享只读输入有没有变成假依赖；本人测试与独立验证有没有混为一谈；收尾条件能否实际产出证据。对上下文分析中的未知条件、来源缺口和耦合建议给出具体处置，不追求清空所有建议数字。

### 9.3 S5 独立审查什么

S5 继续保留两项独立责任：

| 审查责任 | 使用 S4 输出要回答的问题 |
| --- | --- |
| SPEC-CONSISTENCY | REQ、设计、场景、契约、TASK 和收尾判据是否一致；验收到最终工作是否闭合；非功能、拒绝和权限路径是否静默遗漏 |
| TASK-EXECUTABILITY | 单一交付、必要上下文、依赖语义、自包含交接和可测性是否成立；附加检查关键路径上有无不必要串行，并按实际输入检查迁移、外部依赖和高风险验证安排 |

这就是“五问与附加半问”的用途：审查机器无法判断的可执行性，不是再给每个任务加一个启动批准。文件数、断言行数和资料字节都只能提示调查，不能单独决定通过或拆分。

S5 消费原批次冻结的结构检查、任务上下文、行为示例及适用惯例分析，保留原来源和解析版本。冻结资料缺失、不可读或漂移应报告 Main/system，不能临时重算后把新结果冒充原审查依据。机器摘要已经存在时，不要求独立审查者重复运行整套 S4 检查。

## 10. 交付当前答卷及其实际材料

### 10.1 三项答案表达一次规划交接

完成全部 TASK 与计划后，将正式材料提交到绑定开发分支，按当前提示填写并正常保存现有答卷。答案只表达 `conclusion`、`index_path` 和 `task_paths`。下列 JSON 仅展示问卷中的 `answer` 值，实际保留系统提供的外层文件结构及题干：

```json
{
  "conclusion": "pass",
  "index_path": "docs/dev/tasks/index-REQ-017.md",
  "task_paths": [
    "docs/dev/tasks/TASK-017-01.md",
    "docs/dev/tasks/TASK-017-02.md",
    "docs/dev/tasks/TASK-017-03.md",
    "docs/dev/tasks/TASK-017-04.md"
  ]
}
```

`pass` 是 Main 对本次规划已经完成的明确结论，不是 S5 的独立 PASS，更不是实现完成。空白、占位值或其他结论不能冒充完成。索引使用准确 REQ ID，即便需求文件名带描述后缀，也不把后缀搬进索引名。

`task_paths` 填写完整的本批规划路径，使用真实仓库相对路径且不重复。系统还会从当前实际批次保留取消任务等事实，不能因答案遗漏取消项就从接收材料抹除它，也不另要求作者证明一次全量目录库存。

正常工作保留题干以便理解责任；当前 S4 校验主要约束专业答案、文件结构与绑定，不能把“题干文字逐字相等”描述成该阶段的接收资格。题干编辑不授权改变需求、材料或既有责任。

### 10.2 接收处理材料事实，作者不维护来源指纹

接收服务核对当前责任与专业答案，调用原结构检查，从实际批次读取任务和索引，由 Writer 保存规划答案、材料关联、领域证据和后续事件。版本、来源摘要、证据标识与原接收身份由系统生成；作者不手抄、不自行发行第二份问卷，也不手工登记第二套 envelope。

当前正式读取遵循调用者所用的文件视图。正常分支链使用其 Git 来源，答卷自身仍从当前确切答卷路径读取；工作区里尚未提交的材料不能被假定已经进入正式批次。接收服务不是在每次保存时都遍历全部历史上游、重建问卷或比较每份材料的磁盘与 Git 字节。

已接受 S3 的契约及来源是 S4 的输入依据，当前 REQ 的实际输出是 S4 交付。其他明确归属不同需求的材料不应被整体登记成本批任务；归属缺失或含糊的材料也不能在目录发现时悄悄隐藏。实际返回的来源错误需按准确材料和读取视图处理，不能靠复制摘要或补手工资格修复。

### 10.3 接收与推进可以暂时分离

保存成功后应阅读回执：本人交付可能已接收，而原 TR-002 接续仍在等待。此时不能把 `work_complete=true` 解释成已进入 S5，也不能要求 Main 重做已接收的规划来替代系统恢复。

相同专业答案重复保存应关联原记录；路径集合顺序变化不构成另一份专业判断。原接续未完成且仍处本次阶段入口时，系统沿原事件继续。原接续已完成的重复返回只读原事实，不再推进下一责任。已经换代或被替换的旧卷不完成当前责任。

改变已接收的专业答案或实际规划材料，不是简单重放。应按影响回到原规划和审查路径，保留原事实；不能覆盖旧记录，假装它始终审查的是新材料。

## 11. 从 S4 接收进入 S5，再形成 S6 基线

### 11.1 TR-002 接住整批规划

原控制流程根据接收事实与阶段条件尝试 TR-002，从 `planning.tasks` 进入 S5 文档验证。它继续检查批次完整和任务质量，并将原接收材料用于登记当前任务与派发计划。

这一过程中保留 S3 已登记的契约来源，不把目录里后来出现的其他契约重新并入本次。实际 `complete` TASK 登记为待审规划任务；`cancelled` TASK 保留在原接收材料中，但不成为活动执行任务。索引作为实际派发计划登记。

TR-002 接续需要确认当前任务与索引仍对应原接收材料。仅仅领域证据门满足，不表示后续登记一定成功；接收后又改变材料可能使原交接无法继续。原专业交付的历史仍成立，但不能用它给变化后的规格背书。

### 11.2 S5 审查决定执行依据是否成立

S5 两路审查使用准确冻结的设计、契约、TASK、计划和相关来源。发现项回到其所属层解决：任务遗漏或假依赖回 S4，协议缺口回 S3，设计事实问题回 S2，真实需求歧义或变化交人。

普通修订不是偷偷编辑冻结文件后沿用原 PASS，而是让受影响材料与审查责任重新对齐。两路通过及其他原阶段条件成立后，TR-003 注册执行批次、锁定准确 TASK 与派发计划，并建立 S6 所需起点。

文档注册的锁定是执行基线事实，不要求把每张 TASK 的 `Status: complete` 改成另一个执行进度词，也不意味着文件系统自动禁止所有写入。后续操作仍要遵守变更、范围和恢复规则。

### 11.3 S6 如何使用 S4 的工作包

Main 先看计划和实时清单，选择当前真正就绪的 TASK，再按任务有序读集准备交接。使用 `s6 prepare` 提供的实际 brief，并让 Claude Code 原生子代理按该次 Main HEAD 使用工作区隔离；不能复制模板中的未来执行 ID 代替真实上下文。

执行者读取自己的专业输入，先形成对应本任务的计划，再实现、自检、提交本人实际产物，保存专业结果。计划把 Done when 与具体判据对应，结果说明实际证据和未完成项。Main 从原生返回接收贡献，按原流程集成到绑定开发目标、运行必要检查并确认检查点，再释放真实消费者。

`SubagentStart` 和 `SubagentStop` 承接实际原生执行的上下文与返回事实。S4 的任务书不增设 Team 启动、readback、launcher 或普通工具激活层；Main 不因少一个额外抽象字段而无法派发。详细执行流程由 [S6](L3-S6-build.md)和 [L4 原生派发](../l4-mechanisms/L4-agent-dispatch-governance.md)承载。

## 12. 观察进度、定位偏差与恢复

### 12.1 观察应能回答责任问题

| 观察位置 | 要解释的问题 | 不可据此推断 |
| --- | --- | --- |
| 当前阶段与资料投影 | 正在为哪个 REQ、哪次入口做规划，准确 view/answer 在哪里 | 出现提示不等于已经创建或接收专业工作 |
| 任务检查结果及分析来源 | 哪个条款、任务、依赖、路径或读集存在具体问题 | 无结构错误不等于专业设计正确 |
| 原 submission 与领域证据 | 哪份专业答案与哪些实际材料已被接收 | 本人接收不等于 S5 完成 |
| 原 followup、转换结果和登记记录 | TR-002 是待处理、未满足、已推进还是被替换，卡在哪个阶段条件或动作 | 有领域证据不等于登记和转换已经原子完成 |
| S5 冻结责任和发现 | 谁在审哪份准确材料，问题属于哪层 | 单路 PASS 不完成另一责任 |
| S6 就绪、结果与集成视图 | 谁能派发、谁待接收、谁待集成，依赖为何还不能释放 | 子代理返回不等于消费者已具备前置 |

这些关联由 Writer 和原事件保存，用来区分“没有交付”“已交付但接续失败”“材料已经变化”“尚待独立责任”等情形。人类和 agent 应拿到具体原因与下一责任，而不是补一套手工哈希、历史回放或身份口令。

### 12.2 按问题归属恢复

| 情况 | 正确处理 |
| --- | --- |
| 缺条款、字段、计划成员或真实依赖，尚未接收 | 修复原材料及准确答案，提交后正常保存 |
| 同波重叠、粒度或读集建议 | Main 调查真实理由，调整或明确解释，交 S5 独立判断 |
| 冻结上游变化 | 回所属设计或契约责任处理影响，不伪造原来源 |
| 原答卷已接收但转换未完成 | 保留本人完成，按原回执和 followup 定位系统接续；不另造证据冒充推进 |
| 已接收后仍在 S4，需改变 TASK 或索引 | Main 使用 `runtime stage-answer rework --target tasks --reason <具体规划修正>` 开启新 S4 入口；保留 REQ/S2/S3 冻结事实，旧规划接收保留为历史；上游变化须回其所属层 |
| 已进入 S5 后需要改变材料 | 沿原独立审查及文档返工责任处理，不用 S4 返工命令越过审查 |
| 原责任换代或被替换 | 使用当前提示给出的新责任，旧回执不能完成新入口 |
| 冻结分析或原材料丢失 | 报告 Main/system 恢复原来源，不静默重算替换原审查依据 |
| 需求判据本身不确定 | 将具体歧义和影响交人，不能自行减少覆盖或更改承诺 |

普通 PreToolUse 和 Stop 不发行、接收或修复 S4 责任。当前资料准备和答案接收沿原阶段衔接及实际成功的 PostToolUse 路径发生；读取投影不能冒充新答案保存。已持久接收的原系统待续可以在后续成功 Post 继续，但只使用原接收记录，不把 Read 视为新交付，也不要求作者反复读取来推进。实际接收/迁移失败须给具体原因和原 recover 命令；迁移已成立但 S5 准备失败须给准确缺口和原 issue 命令。正常保存与显式接续共用 S5 交接，不要求作者重交已接收答案或手填分工元数据。必要状态诊断仍可使用。

指引按入口、阶段合同、专业方法、具体责任、事件接收、结果交接六层编排，详见 [S4→S5 指引编排](../l4-mechanisms/L4-agent-guidance.md#s4-s5-guidance)。其中数量上限、tasks 返工及错误恢复是本轮修复合同，落地状态须以对应实现和公开回归为准，不能仅凭本段宣称已完成。

### 13.2 机械保证到哪里为止

当前实现已经具备实际批次接收、覆盖及联合顺序检查、计划登记与冻结、分析资料交付和原生执行消费。以下边界不能靠文档的规范语气补成已经存在的机械保证：

- `Primary contract` 与 Delivered Clauses 的业务归属需要专业核对；找到契约和条款不证明它们共同构成单一职责。
- `Closing Contract` 的现有结构检查识别标题与断言文本，不完整解释四类承诺，也不执行自然语言断言。真实可测性、必要接线和本人检查仍由 Main、S5 和执行者承担。
- 同波范围和资源重叠会产生警告，不能据此声称已经硬拒绝全部并行风险。
- 上下文字节、行为投影和惯例来源能够辅助判断，不能证明任务必定在某个上下文长度内完成，或证明产品行为已通过。
- 已有工程惯例索引及其分析继续按原摘要、登记来源和冻结输入读取。当前解析器只有只读来源校验，没有为新索引首次保存自动固定元数据的消费者；不能让作者补 SHA／版本来填这个缺口，也不能每次读取省略值时重新计算当前来源后冒充历史固定。正常作者使用原 TASK 和专业源，不承担这份索引。
- S4 新答案接收调用原正式来源校验，核对当前绑定及已接收 REQ/S2/S3 来源，再检查实际 TASK/index 输出。已发行 S4 的 TASK 模板与 dispatch-plan 方法说明保留历史引用，说明文字更新不成为新的接收资格；新责任发行仍验证当次方法来源。已接收重放读取原接收事实，TR-002 登记和 S5 来源消费保留各自校验，不能把这些出口或普通观察混称为每次都重新接收整份历史材料。
- 接收事实、领域门满足和 TR-002 动作完成是可分别观察的事实。已接收后材料漂移可能阻止登记；不能承诺所有同答案重放都无条件进入 S5。
- 模板按结果粒度、实际读集与登记范围组织工作。句式、一次 compact 或断言行数都不能替代专业判断；Runtime 关联由原消费者维护，作者不填写内部身份，也不补额外开工许可。

S4 的交付成立，是整批任务与计划已经表达清楚、专业自审完成、原答案和实际材料被接收；进入 S5 还需原阶段条件及登记完成。S5 进一步确认这套规划能作为可信执行依据，S6 才用真实交付与集成检验它。各层共同支撑设计落地，不由某一份结构检查报告独自代表全部共识。
