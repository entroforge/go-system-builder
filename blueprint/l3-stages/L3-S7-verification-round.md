# L3-S7 完整验证轮

## 1. 为什么实现之后仍需独立验证

S6 回答“各项实现是否完成、自测并集成”，S7 回答“集成后的产品是否完整兑现承诺，工程质量是否可靠，实际使用是否成立”。实现者最熟悉自己的选择，也最容易沿着这些选择验证。单元测试通过、Builder 自测通过或 Main 合并成功，都不足以消除遗漏、共同误解和集成后的行为偏差。

因此，S7 对同一个产品基线组织三个互补视角：交付符合性、工程质量和端到端行为。它们分别检查“承诺与交付是否相符”“实现方式能否长期成立”“从实际入口使用会发生什么”。三个视角互相补充，不能用三份措辞相近的总评代替，也不意味着固定派三个子代理。

完整验证的单位是本轮应回答的全部具体问题。一个视角可以拆成多个责任；紧密相关的问题也可以由同一独立审查者承担。分工由专业问题、阅读上下文、方法、环境与独立性决定，不能为了控制人数而删除覆盖。平台容量只改变执行顺序。

S7 只确认观察到的偏差、保留现场并判断本轮是否完整。它不顺手修改产品，不将猜测直接登记为根因，也不把审查建议直接变成修复任务。原因调查交给 S8，修复和定向复验交给 S9；本轮完整通过后，验收与过程审计交给 S10。

本阶段承载[设计原则](../l1-principles/L1-design-principles.md)中统一来源、独立完整验证和轮次收敛的要求。它与 [S6 实现](L3-S6-build.md)、[S8 问题调查](L3-S8-finding-investigation.md)、[S9 修复](L3-S9-repair.md)共同构成质量闭环。

## 2. 一轮验证由哪些对象构成

一轮验证围绕一份 ReviewPlan 展开。计划把产品对象、覆盖问题和分工固定下来；实际结果逐项回答这些问题；领域消费者据此形成发现批次或干净轮。不能在这条事实链之外再维护一份手工角度登记簿，靠人工勾选决定阶段完成。

| 对象 | 含义与责任 |
| --- | --- |
| ReviewPlan，验证计划 | 本轮唯一的覆盖与分工依据，包含基线、命题、适用性、责任、依赖和验证资产安排 |
| Claim，验证命题 | 一个具有来源、对象、断言、判据和方法的具体问题 |
| ReviewAssignment，审查责任 | 由一个工程 owner 承担的一组同视角、上下文相容的命题 |
| ReviewResult，审查结果 | 本人责任内逐命题的实际结论、观察、证据、发现和明确判定 |
| Finding，发现项 | 一项失败命题对应的不可变观察事实及真实现场，不携带已确认根因或修复授权 |
| ObservationBatch，发现批次 | 系统封存的本轮发现、命题处置、原发现者路线和调查准备情况，作为 S8 输入 |
| CleanRound，干净轮 | 系统根据当前完整命题集合和有效结果形成的通过记录，是进入 S10 的必要依据 |

必须区分四种“完成”：审查者结束专业工作、结果被原消费者接收、整轮取得完整处置、整轮满足干净轮条件。个人完成不必等待全局门；整轮完整也可能包含失败和客观不可执行项，因此不等于通过。

Runtime 的 `baseline_generation` 标明当前需求执行基线代际，`review_round` 标明验证轮次，计划指针中的修订号标明本轮计划和责任版本，Runtime `revision` 则用于状态事务的并发控制。这些编号用途不同，由系统绑定。Main 与审查者不手抄编号来制造“当前有效”的结果。

Main 负责专业计划、独立性分工、原生派发、环境协调和阶段交接。`delivery-verifier`、`qa`、`e2e-tester` 分别执行所属观察面；角色名称表达专业职责，实际任务仍以本人的准确题干与命题集合为准。Runtime Writer 维护权威事实，Hook 只在原生事件与原领域消费者之间衔接。

S6 原集成出口通过 TR-006 后，应在同次交接交付当前轮 Main ReviewPlan 和 guide 的准确路径及专业规划责任。转换成功与材料准备成功分别反馈；材料缺失通过原准备入口恢复，不让 Builder 重交结果，也不让 Main 猜路径或制造额外工具事件。完整编排见 [S6→S7 指引分层](../l4-mechanisms/L4-agent-guidance.md#s6-s7-guidance)。

## 3. 先固定到底在验证什么

### 3.1 产品基线与完整变化面

S7 的对象是 S6 集成后的 Main 产品基线，而不是某个 Builder 工作树、最后一个任务的提交，或当前目录看起来存在的文件集合。

对于原生 S6 形成的规范贡献链，产品基线从原 TR-003 确认的共同实现起点到最终 Main 提交计算，绑定准确 TASK 源、贡献、集成与自测事实。覆盖必须包含新增、修改和删除，也包括失败实现留下但仍存在于产品中的变化、后续修复以及 Main 集成时增加的变化。不能只抽取成功任务最近一次差异，从而让残留行为脱离审查。

ReviewPlan 的 `product_baseline` 保存这份机器投射，`frozen_subjects` 固定本轮实际登记的审查对象与相应内容指纹。规范贡献链要求该集合准确对应原 TASK 源和完整变化路径，不允许手工增删后仍声称是同一机器基线。删除项在冻结集合使用已有 `kind=deleted`，摘要对应原产品快照证明的删除前态，同时保留最终不存在的事实；它仍进入覆盖分母，不要求作者提供不存在的“当前文件 SHA”。具体对象关系及首次/新轮/S10 的统一消费见 [Worktree 治理 §12.1](../l4-mechanisms/L4-worktree-governance.md#121-同一变化面在计划冻结与覆盖中的表达)。`subject_digest` 将该对象集合与产品基线关联，结果必须绑定同一来源。

这份集合不等于系统已经把所有需求、设计、契约和业务判据自动列齐并冻结。审查仍须使用原权威链中的准确版本；Main 应检查命题依据与原 S5、S6 来源是否一致，不能把一个自由填写的 `source_refs` 当成内容已经验真的证明。权威材料需要改变时走原规格修订与基线处理，不能在审查中悄悄改判据。

计划草稿、登记、结果接收和退出门分别在各自需要的地方证明来源成立。普通状态查询只展示已有事实；不能为了展示进度不断重放整个 Git、指纹和历史回执证明链，也不能因查询显示“clean”就跳过真正退出门的复核。

并发接收可能看到指标摘要的原子发布暂存文件。结果接收沿[工作区治理 §4.1](../l4-mechanisms/L4-worktree-governance.md#41-临时工作区不混入项目扫描)识别准确、未跟踪的系统暂存，已跟踪或已暂存状态及冻结对象仍按原来源检查；它不因内部写入窗口把计划标为 stale，也不要求审查者操作这些文件。

### 3.2 验证依据与覆盖分母

覆盖同时来自承诺和实际变化。只读 TASK 会遗漏跨组件承诺，只扫代码差异又可能遗漏尚未实现的要求。Main 应把以下来源组织成互相可追溯的问题：

| 来源 | 需要追问的内容 |
| --- | --- |
| 需求与成功标准 | 用户目标、范围、非目标、不可退让的成功条件是否兑现 |
| S2 设计与场景 | 正常、拒绝、边界和恢复路径是否成立，真实角色是否能从声明入口走通 |
| S3 契约 | 接口、共享模型、错误、兼容性和跨组件接缝是否一致 |
| S4 TASK 与完成条件 | 每项交付是否完整，验证责任是否落实，是否遗漏消费者或集成步骤 |
| 完整产品变化面 | 每个实际变化是否有解释和审查，删除是否破坏调用方，计划外变化是否扩大风险 |
| 历史问题与本次修复 | 相同失效路径、受影响邻接面和已承诺回归是否被覆盖 |

系统的 `coverage_inventory` 提供当前实际变化面的规划分母，不能由 Main 任意删掉。它不自动推导全部业务风险；Main 仍要补足语义上的覆盖和非功能要求，并解释不适用项。

### 3.3 从修复返回时仍是新的一轮

S9 的定向复验回答“已批准的修复是否消除了所调查的问题”，不能代替整轮验证。修复集成后，系统为新一轮生成带真实修复来源和新产品基线的计划种子。种子是 Main 的规划输入，其中待细化部分必须经过专业判断；它不是已经通过的 ReviewPlan，更不自带新的审查结论。

新的产品代码或权威输入需要新的有效轮次。不能让审查者继续给旧产品补一份 PASS，借原轮次身份覆盖修改后的产品。若实际代码未改变、发现经 S8 有证据地排除，也应走原无修复返回路径组织新轮，保留为何重验的来源。

## 4. 把覆盖写成可判定的命题

### 4.1 命题不是待办标题

“检查订单模块”无法确定读到哪里、什么现象算通过、需要保留什么证据。一个有效 Claim 至少交代：

- `source_refs`：为什么必须检查，来自哪项需求、条款、TASK、CASE 或实际变化。
- `target`：具体对象、入口或受影响面，避免含混的“全部代码”。
- `assertion`：要判断的承诺，既包括应发生的结果，也包括禁止的副作用。
- `oracle`：判断实际观察是否满足承诺的依据，不能与断言循环解释。
- `method`：如何取得足够观察，静态阅读、契约追踪、真实请求或浏览器操作各有适用范围。
- `required_evidence`：计划明确要求保留的证据引用；实际执行仍须报告真实观察。
- `applicability`：本轮必需，或有来源支持的不适用；未知不能写成不适用。

例如，下面是一项命题的结构示意；其中业务路径和 ID 必须来自目标项目的真实材料：

```json
{
  "claim_id": "claim-delivery-rejected-order",
  "lens": "delivery",
  "target": "POST /orders 的余额不足分支及其持久化消费者",
  "assertion": "余额不足时拒绝创建订单，且不产生订单、扣款或通知",
  "oracle": "契约规定返回 INSUFFICIENT_BALANCE；请求前后订单和余额不变，通知出口没有新增消息",
  "method": "追踪契约到处理器、事务及消息出口，并用实际拒绝请求核对行为",
  "applicability": "required",
  "source_refs": ["TASK-012", "CASE-order-insufficient", "docs/contracts/order-api.md"],
  "focus_key": "rejection-side-effects"
}
```

这里的拒绝响应和禁止副作用属于同一业务承诺。若持久化、异步通知分别需要不相容的执行环境或大量专门上下文，应进一步拆命题，并明确依赖；不能让一句“事务正确”掩盖几个从未检查的出口。

命题粒度应让审查者能够给出明确结论，也应让失败项保留清晰现场。同一命题包含数个彼此独立的失效问题时，应在规划时拆开。当前结果模型对每项失败 Claim 接收恰好一个 Finding，过度合并会直接降低交接质量。

### 4.2 三个视角各自深入到哪里

**交付符合性**从承诺追到实现和实际消费者。它检查需求与 TASK 完成条件，核对设计、契约和代码是否一致，追踪接口是否真正被调用、状态是否真正落地，以及前后端、服务、存储与消息之间的接缝。只证明某个函数存在或测试通过，不足以证明完整交付。

**工程质量**检查实现方式及其长期影响。六个基础问题需要明确处置，而不是把所有 QA 工作缩成一次 lint：

| 基础关注点 | 应形成的判断 |
| --- | --- |
| 设计与边界 | 归属和依赖是否清楚，跨层调用、共享模型与契约有没有被绕过 |
| 模式与项目惯用法 | 所用抽象是否减少耦合与风险，是否符合项目已经成立的惯用法 |
| 逻辑、状态与错误 | 正常、边界、失败和重试是否自洽，状态转换和错误责任是否完整 |
| 可维护性 | 命名、阅读路径、抽象层级与认知复杂度是否支持后续维护 |
| 可测试性与判据 | 测试是否断言真实行为，拒绝和边界路径的预期是否有效 |
| 债务与可运维性 | 是否引入无主债务、不可观察失败或没有交接的后续工作 |

这些是不同的问题，不要求为了“使用模式”增加模式，也不允许以项目没有某种模式为由跳过适配性判断。安全、性能、可靠性、并发、迁移与兼容性等专项由实际风险触发，按相应技能执行。Main 必须说明哪些风险已由基础命题覆盖，哪些需要额外责任。

**端到端行为**从真实角色的声明入口执行旅程，观察可见结果、持久化、错误反馈、禁止副作用和恢复。浏览器流程应包含真实页面交互及关联请求；不能用数据库直写、未声明的直达链接或单独调 API 冒充用户走通。API、命令或状态型产品同样需要与真实入口相称的行为验证，不能把“没有 UI”误解为“没有可验证行为”。

三个视角允许引用同一证据，但仍要回答各自的问题。交付者确认某拒绝条款已落实，QA 判断错误传播与事务边界是否健全，行为审查者实际遇到拒绝并检查副作用，这三项判断并不重复。

### 4.3 不适用必须在计划中说明

不适用是有依据的计划处置。Claim 保留 `applicability=not_applicable`、`source_refs`、`na_rationale` 和 `na_checklist_id`，说明检查了什么影响、为什么不存在该验证对象。它不进入审查责任，不派一个空 Worker，也不通过提交一份 N/A ReviewResult 来补数。

无 UI、纯文档或没有跨服务调用，都只能作为适用性分析的事实，不能单独代替结论。缺环境、缺权限、没有时间和未知影响属于未完成或阻塞，不属于不适用。确无必需交付或 QA 命题时，也必须给出计划级覆盖解释，不能用空数组默默消去整个观察面。

## 5. 用专业上下文决定分工与顺序

### 5.1 从命题到审查责任

Main 先建立完整命题，再按相同视角、关注点、阅读集合、方法、环境、资源冲突和独立性组织责任。每项 required Claim 在当前计划中恰有一个责任承担，同一责任不能混用 `delivery`、`qa`、`e2e` 三种视角。

`focus_keys` 说明责任关注点，`non_overlap_boundary` 解释它与相邻责任如何分界。例如质量审查者可以共享订单模块阅读上下文，但“事务错误语义”和“安全鉴权”若需要不同专业方法、较大阅读量或互相独立的判断，应分别承担。不能把一组没有边界的“全面审查”同时派给多人，也不能让一个泛化 QA 会话吸收所有工作而失去深度。

当前草稿通常为交付追踪生成一项责任，为六个 QA 基础问题分别生成责任，并按可发现的浏览器 CASE 拆行为责任。这是便于 Main 开展规划的起点，既不是固定人数配额，也不是可直接登记的专业计划。合并必须限于同一视角且上下文确实相容，保留完整命题与真实边界；拆分则应说明减少了什么上下文负担或执行冲突。

例如小型无界面模块的几项 QA 命题若读取同一组材料、使用相容方法、没有相互结果依赖，可以由一个 QA 责任持有多个 `claim_ids`，逐项给出结论。Main 在首次专业计划中调整原 `assignments` 的命题归属，保留全部命题及其原身份、判据和证据要求，并使 `focus_keys`、阅读范围与边界准确反映工作；不用增加人数策略字段或另建分工表。交付视角仍独立，真正需要不同专长、环境或结果依赖的 QA 命题继续分开。减少重复上下文的依据是本次工作本身，不能由“只有一个模块”推出必然只派一名 QA。

冷启动行为验证同时包含准备资产和真实执行，尤其容易过载。应按角色、入口、流程簇、状态或拒绝路径组织相容工作；不能把多种独立上下文全塞给一个“全需求 E2E”责任。当前校验会拒绝已声明多个关注维度却全部交给单一冷启动责任的明显过载；没有声明足够维度时仍依赖 Main 判断，不能将“校验未拒绝”当作分工合理的证明。

### 5.2 两个执行波次

交付与 QA 属于 `static` 波次，行为执行属于 `behavior` 波次。静态工作先取得完整处置，再进入行为执行；这里要求的是每项静态必需命题有结论或合法的客观阻塞说明，不要求静态全部 PASS。

普通 Finding 已使本轮无法成为干净轮，但仍应完成其他安全可执行的检查，尽量一次保留完整问题面。若一发现失败就停止全部审查，后续修复会不断暴露本可在原轮发现的问题，轮次将因收集不完整而膨胀。

环境探测、账号和数据前提确认、验证资产准备可以提前并行，但不能提前登记或执行尚未解锁的正式行为责任。Claim 的 `depends_on` 表达具体结果依赖，必须存在且无环；需要消费前置命题结果的命题不能与该前置命题塞进同一个责任，否则依赖会变成自我等待。

共享可变账号、数据集或测试环境通过声明的 `resource_locks` 排序；互不冲突的责任并行。`dispatch_capacity_policy=coverage_complete` 表示覆盖完整优先于人数配额。平台暂时容纳不了的责任进入队列，不能改写为不适用或假装完成。

### 5.3 独立性属于工作分配

实现者不能审查自己在当前代际交付的产品。Main 应分配独立原生上下文，保留准确工程 owner，并在 manifest 中声明所需独立性。平台实际子代理身份是执行事实，不等于可以随意重命名的工程责任。

当前接收器按工程 producer 与本代已登记 Builder 交付证据检查冲突。这能拒绝同一登记实现者自审，但不能仅凭两个不同字符串证明平台会话和实际作者完全独立。Main 的真实分工与原生上下文边界仍然承担这项责任，不能靠换 ID 绕过。

## 6. 为真实行为准备环境与验证资产

### 6.1 场景先于脚本

对于有界面的模块，`cases.json` 是当前 CASE 清单，`flows.md` 定义旅程与 PATH 的操作过程；场景覆盖汇总只能检查总体门，不能代替清单。审查者应读取所分配模块的完整当前场景包，核对 CASE 的角色、分支、极性、判据与独立的 Flow／PATH 引用。需求是来源线索，不能据此忽略本次变化影响的跨需求模块回归。自动发现沿需求的原型引用提供起点，并不声明完整回归边界。Main 从实际 provider／consumer、共享模型、接口、事件、鉴权配置和旅程／数据路径解释影响；删除依赖或变更归属时仍检查变更前的消费者。已有架构、契约和冻结来源足够承载判断时，不新增必填模块图；关系或环境资料不足则明确缺口，由 Main 补材料或安排必要调查，不能静默排除，也不无条件全仓扩散。

原计划的已知场景分母由同一个有界投影提供给草稿、登记与修订：绑定 REQ 的模块引用，以及当前代际冻结 TASK 的 `Module current truth` 和 `Module Impact` 声明。TASK 的 `Modules touched` 沿原模板列出模块，该声明亦可直接引用实际模块路径；普通 Manifest 阅读链接不表示整个模块受影响。读取这些明确模块的 `cases.json`，取 `required=true` 且 `browser_required=true` 的完整场景引用。没有明确模块声明时保留专业范围判断，不扫描全项目来填分母。

每个已知场景必须在 E2E Claim 的 `source_refs` 中得到准确处置：需要验证的 Claim 由原 Assignment 覆盖检查保证分配，不适用的 Claim 仍填写原 `na_rationale`、`na_checklist_id` 和来源。已有脚本或 `e2e_assets` 不代替这个处置，也不产生 PASS；合法结果复用仍按原证据条件消费。`ui_impact=none` 是分析输入，不能用一条笼统 N/A 隐去已知场景。例如 REQ 只涉及股东模块，而冻结 TASK 已声明证书模块消费其变化，则两个模块的已知必需浏览器 CASE 都要处置；无关模块不因此加入。

这是一条防止遗漏明确义务的下界，不是自动计算任意代码的全部业务消费者。TASK 的可选背景阅读、共享模型的消费者清单和没有明确关联的自由文本，都不能直接变成所有 CASE 必测。Main 仍要判断尚未显式声明的跨模块影响，在原计划或有来源的受控修订中补充。固定产品基线沿原来源声明读取 REQ、TASK 和场景；旧磁盘模式的缺失 REQ 不会被解释成全库范围，其历史恢复边界也不证明影响分析完整。明确的 TASK 或模块场景来源缺失、漂移或损坏，应恢复原来源，不能当作零 CASE。

验证要覆盖允许与拒绝路径，尤其是拒绝后的终态、持久化、禁止副作用与恢复。只证明页面打开、响应成功或某个 CASE ID 出现在脚本里，都不能证明该场景成立。具体浏览器方法见 [e2e-browser-testing](../../skills/e2e-browser-testing/SKILL.md)，脚本、夹具与定位实践见 [playwright-e2e](../../skills/playwright-e2e/SKILL.md)。

Main 提供真实服务地址、认证策略、数据前提和环境责任。缺少这些条件时先处理环境阻塞，不能改产品绕过认证、伪造数据结果或把未执行标成通过。验证资产准备不能改变被验证产品的行为。真实浏览器/API 观察还要说明实际服务版本与依赖边界：沿已有 build ID、版本入口、容器身份或受控构建/启动记录，把正在服务的实例关联到所声明的产品版本，并说明数据库、队列和外部服务哪些真实、哪些 mock。当前 checkout 的 HEAD 或接口 200 不能单独证明正在运行该版本。关联不明时保留已观察证据并说明范围，由 Main 处理环境或来源缺口，不冒充当前产品 PASS；静态审查不因此要求启动服务或新增探测接口。

### 6.2 三种资产状态

| `e2e_coverage_state` | 含义与安排 |
| --- | --- |
| `cold_start` | 没有足够可复用资产；在计划声明的独立验证资产目录准备所需脚本与夹具，再执行真实行为 |
| `regression_available` | 有与当前 CASE、入口及环境匹配的可执行资产；登记准确指纹并读取、运行既有资产 |
| `not_applicable` | 有证据证明本轮无需该 E2E 维度；计划保留明确 N/A 命题，不产生空行为责任，验证资产目录为空 |

冷启动目录由 `verification_artifact_workspace` 声明，位于仓库 `e2e-workspace/` 下。它是验证脚本和夹具的写面，不是另一份产品工作树。产品代码、既有回归脚本与证据目录各有用途：既有 `web/e2e/<module>/` 资产在 S7 读取和执行，冷启动资产写入已声明目录，实际证据保存到本轮原证据路径。不能把产品测试复制成按 BUG 或轮次命名的另一套产品规范。

发现脚本与确认资产是两件事。发现器只交付脚本路径、观测摘要和可能关联的场景，文本或注释命中不能证明脚本可执行，也不能证明覆盖充分。草稿在复用尚未决定时将 `e2e_coverage_state` 留空；Main 阅读候选和真实环境后，在原计划里选择三种正式状态之一。空值仅存在于未决草稿，不能登记、创建执行工作区或派发。

可复用资产的 `e2e_assets` 使用完整场景引用，例如 `docs/design/prototypes/orders/cases.json#CASE-001`。不同模块都可以有 `CASE-001`；PATH 同样归属于原 cases 路径和 CASE，不能用裸编号混合模块。系统为 Main 选中的准确场景与脚本补齐缺省 `asset_id`、`sha256`；Main 提供真实的 `selector_ref`、`route_ref`、`environment`，说明驱动哪些元素、从哪里进入、在哪种环境执行。补齐沿原来源声明与固定产品视图读取，随后核对实际复用文件；显式错误摘要不被自动刷新。专业审查仍须确认脚本实际执行正确旅程。

旧裸 CASE 在新登记时只能从该计划实际声明的场景来源中唯一解析；存在同名场景就列出准确候选，由 Main 选择。已登记历史计划和回执保留原字节与编号，不按今天的发现结果迁移。一个脚本确实覆盖多个场景时分别准确声明，不能靠重复编号推导覆盖。

`cold_start` 允许复用已经确认的部分资产，只在原验证目录补实际缺失的脚本和夹具。选中的既有资产在登记、结果接收和收口时继续检查，不因轮次叫冷启动就跳过来源核对。三种状态描述资产安排，均不代表行为已执行或 PASS。

### 6.3 产品指纹与验证资产指纹分开

冷启动期间增加测试脚本与夹具是预期工作，不能一写验证资产就宣告产品基线失效。结果接收器绑定实际执行来源中的验证资产摘要 `verification_artifact_digest`，轮次收口时再校验已接收结果所依赖的资产，防止脚本执行后被替换而旧 PASS 继续有效。

审查者保留答卷内的机器预填值或 `null`，由原消费者在真实来源上适配与校验，不自行抄哈希。若执行后修改了脚本或夹具，应重新执行相关流程，不能仅更新摘要。资产继续变化影响了已接收结果时，由 Main 处理一致性与重验；不能为了维持整轮状态保留过时结论。

执行输出与资产依赖分开表达：原答卷的 `evidence_refs` 引用实际使用的冷启动脚本/夹具路径，摘要由原消费者补齐；已有计划明确绑定的复用资产沿原绑定检查。没有脚本引用并不能证明没有使用工作区，工作区改变且依赖未知时应给出明确恢复缺项，不能自动通过。其他责任只新增无关资产时，已有准确依赖可继续核验，不要求全轮无差别重跑或为此另交清单。

当前自动发现主要面向 `required` 且 `browser_required` 的 CASE；脚本中的完整 CASE 文本边界匹配只产生候选，保留同名场景的全部可能关联。它不生成定位器、路由、环境或正式资产，不自动判断回归可用或冷启动。Main 仍须补齐后端/API/命令行为覆盖，并处理不可读来源与环境缺项；该发现范围不能代替完整专业影响分析。

## 7. 从计划到原生子代理的实际工作链

### 7.1 Main 完成并登记计划

进入 S7 后，系统在当前 Runtime、代际和轮次下提供 Main 的准确计划文件，例如 `.claude/submissions/<runtime>/g<generation>/S7/r<round>/review-plan.json`。这是完整 ReviewPlan JSON，不是 Reviewer 的 `answer` 包装。相邻的 `review-plan.md` 交付同次准备得到的来源、候选、歧义和待判断事项；Hook 提供两个准确路径。这份说明是派生阅读材料，不是第二份答卷、批准或权威事实。普通观察保留 Main 已编辑的 JSON；说明丢失时可由会话准备入口恢复，不重新生成专业答案。命令行 `s7 draft` 则以 stdout 输出可解析 JSON，以 stderr 输出同源说明。

原 `DraftPlanForRoot` 消费 S6 来源、变化面和可发现场景，提供系统已知内容；Main 完成命题、判据、方法、适用性、风险、分工与依赖，消除 `TODO(planner)` 等占位。Main 保存到所提供的原路径，原 `RegisterPlan` 补齐缺省资产机器字段、执行正式 Schema 和专业结构检查，并登记不可变文件及指针。系统不改写作者原稿；同答再次保存依据原已登记计划比较缺省机器值，不重读今天的脚本来制造新登记。已接收后发生资产变化，由原资产一致性和修订路径处理；同答回放不表示当前文件仍等于当年的资产。不要在收到准确草稿后手工另起一份计划，再走一轮重复登记。

原登记中的检查按依赖组织：结构可解释后，分派策略、未完成专业内容和证据种类可以并行形成诊断；身份与引用准确后才解释命题分工、重叠与资产安排。同次保存返回可独立确认的问题；前提缺失的检查明确标为未检查，不据损坏的 Claim 映射推导覆盖结论。诊断只是本次调用的阅读结果，不持久化为另一份计划，也不要求先执行独立预检。提交边界仍执行原来源核对与 CAS，预检查通过不等于已经登记。

专业内容错误由 Main 修改原问卷。Main 在实际控制根的 Pre、SessionStart 或成功 Post 遇明确 Runtime pending 时，系统在原 Hook 预算内恢复一次原 Writer，刷新后继续同一真实事件；同次成功保存仍交原准确 ReviewPlan 路径和消费者。SessionStart 不凭已有文件重构首次交付；S7 Pre 监听准确当前 ReviewPlan，在原消费者认定专业答案就绪后自动接收，成功 Post／Stop 兜底，不要求重存。来源不可读、原准备缺项、恢复失败与并发冲突保留具体系统诊断，不能通过重写正确的专业答案修复。已登记计划读取失败时先恢复原记录再比较同答；明确改变专业内容才走原命名修订路径。

登记会检查当前代际和轮次、冻结来源、TASK、变化面与明确模块 CASE 的覆盖、required Claim 的唯一归属、命题依赖、视角与波次、责任重叠、资产条件及必要字段。这些检查约束结构和已知分母，不会替 Main 判断断言是否抓住了真实风险、方法是否足够或不适用理由是否可信。

当前 Main 的非结束类 Hook 可以首次准备这份计划草稿；重复提示不覆盖已有专业内容，Stop 不负责临时补造草稿。Main ReviewPlan 与 Reviewer Result 使用各自原消费者；自然事件监听只选择本人准确当前责任与就绪答卷，不把所有普通工具都解释成提交。

S9 返回的未细化种子已有指针，需按原种子首次专业登记入口提交完善后的计划。该入口只允许原 TR-012 对应、身份与产品基线一致、尚未派发或接收结果的原始种子，允许真实适用性判断调整资产安排。它不是任意覆盖已登记计划，也不占用后续发现驱动的那一次受控修订。已经开始执行的种子必须走原恢复或修订路径。

### 7.2 Main 登记责任，再由平台执行

Main 从登记后的实际 Assignment ID 使用原 `loop-harness s7 manifest-draft --assignment <id>` 准备分派材料，选择工程 owner 和专业分工。系统提供能够证明的来源、登记时间、真实 TASK 候选和完整登记命令，并从原 Assignment、代际和轮次准备工程 owner／group 标签，沿原角色与责任方法补齐默认技能。标签不代表原生子代理已经运行，也不能证明实际作者独立。Main 保留真实替代作者、额外方法与专业分工选择，不为内部编号或默认方法再填一轮题。原登记来源的路径、版本或摘要缺失时，反馈系统准备缺口，不能让 Main 猜一个锚点、抄指纹或填占位值补齐。

原 `runtime register-workgroup` 登记的是工程责任和专业边界，不代表已经创建了平台 Team，也不代表子代理已经运行。已解锁的责任取得准确题干与私人答卷路径；同次准备沿原发行器补齐全部已经登记且已解锁的责任，不能只提示第一位，让 Main 通过反复读取状态来凑齐答卷。已有作者答案保持原样，排队责任在原队列释放后取得其当前答卷。行为波次尚未解锁时不能通过提前注册绕过，Stop 也不负责临时发卷。

Main 将以下内容交给 Claude Code 原生 Agent：

1. 本次实际专业目标、所属视角、必须遵守的独立性和写面。
2. 原系统给出的准确题干与答卷引用，要求保留题干、读取真实冻结材料。
3. 执行相应专业检查，只填写本人实际观察与结论并保存原答卷；自然事件沿原消费者接收。正常汇报可引用该卷，不把再次返回引用作为额外接收动作。

Claude Code 负责创建、运行、暂停与恢复子代理。新只读审查责任以共享 Main checkout 的独立原生上下文为本轮正式接线主线，不要求额外的框架工作区、launcher、bootstrap、平台 ID 映射、首写激活或通用 PLAN_REPORT。独立性来自真实分工与上下文，不能由磁盘共享或隔离单独证明。确有原 `plan_approval_required` 的责任仍遵守其领域批准条件，不能据此把所有审查重新放进统一激活流程。

新签发 Reviewer 只填写系统准确发行的 `.loop-submissions/s7/<packet-id>/<owner>/answer.json` 原卷；它仍保留 `title/instruction/read/questions/answer` 五字段，作者只填写 `answer`。这不是第二份 flat 答卷，Main 不代填、不复制成另一作者稿。路径由原 packet 固定，不让作者选择、计算或为保树增加文件、提交、done 或封存动作。普通工具照常可用；敏感路径无法写入不能靠改用 Bash 或放宽平台权限绕过。

题干与路径协议由原模板 SHA 固定：新发行使用当前题干和普通路径；受支持历史模板按其原字节重建完整 packet，包括原路径。修改当前模板的接收文案前，须把改变前的完整模板字节纳入原 SHA 重建列表，不能只留路径兼容或根据作者答案反推版本。旧 packet 的 ID、固定题干、路径、答案和 accepted receipt 保留原字节与来源，不重新签发；仍执行的旧卷通过实际派发／恢复提示解释适用的现有接收方式，不改其题干或声称旧执行已迁移。新旧发行、完整重建、安装投影和真实正常权限均须分别验证，不能仅凭本节视为已经实现。

Main 共享根的准确原卷属于控制写面，产品面仅凭原 issued packet 的有效证明识别该单文件，并核对它是普通未跟踪文件、未进入 HEAD/index、未与冻结对象或产品范围冲突。不得全目录忽略或宽排 `.loop-submissions`；未知 sibling、tracked/staged 同名和产品改动仍走原漂移检查。原稿不入产品提交，产品变化分母和冻结对象不因此缩小。接收时若另一张原卷的损坏来源恰为当前实际漂移路径证明所需，保留本次未确认和已有接收事实，将准确系统来源缺口交 Main；不能将不可核验当成已证明产品漂移，也不能绕过检查接收。原 ReviewPlan 的 stale 表示当前资格失效；恢复同一原来源后，Main 使用原 `runtime review-plan revive --root <Main>` 重验基线并接续原轮，实际产品基线改变则走原新轮路径，不要求 Reviewer 改答卷或重新规划原计划。

原已登记 frozen execution 保持准确来源。另行实际使用 native worktree 时，现行消费者只接受其已成立的原 source binding；没有绑定则反馈准确未接收和所缺来源，不把任意 cwd、返回目录或 Main 同名原卷当替代。该模式不能直接套 S9 Builder 的 Plan/Result adapter，未验证的 native 接线不作为本轮共享 checkout 能力的承诺。

### 7.3 启动提示与结束接收各做什么

`SubagentStart` 给出简短工作约束，不根据角色名、启动次序或不透明平台 actor 猜测责任。准确引用由 Main 的真实任务交付，不能期待 Start 自动重建完整任务。

Worker 读取题干、冻结材料和所选方法，实际检查并保存本人原答卷。S7 的 `PreToolUse` 有界观察当前责任；成功 `PostToolUse` 补足工具保存后的时序；`SubagentStop` 在普通观察未完成时兜底。三者使用同一原消费者和专业条件，失败工具不能被解释成保存，普通读取也不能冒充写入。Main 的 Stop、Agent 返回与会话恢复按 Main 自己的责任投影或接续，不因 Worker 结束就推定结果已收。具体事件可用性、子卷可读时机及模型反馈渠道须以真实平台验证，不以本合同宣称所有兜底均已成立。

自然事件先使用当前权威 Runtime 的既有责任索引定位，再读取本人原卷：索引提供 packet、owner、view／answer 等候选坐标，实际子会话任务中的准确引用或已绑定的 owner 必须唯一关联当前责任；索引只帮助选择，不授予接收资格。选定后由原 packet reader、来源校验和 `SaveReviewResultFrom` 核对该卷的 canonical 内容、原绑定、独立性与专业条件。不得为选择本人而物化全部无关 body：不参与本人责任验证、也不参与当前实际产品漂移路径证明的 body，其损坏不能阻断本人；需要证明的其他原卷来源不可用时按 §7.2 反馈并恢复，不能抹掉本人的责任或跳过全轮基线检查。普通 helper 未获本阶段任务可静默；准确责任的 body／source 不可用、共享索引出错或任务／owner 冲突须保留具体系统缺口交 Main，不按角色、唯一候选、最近文件或 Main 同名卷猜选。Main 返回与路径查询使用相同边界。

仅当原字段、必要观察、证据、来源及领域校验全部满足时自动接收。文件存在、可解析 JSON、有 verdict、工具成功或平台停止均不足以单独证明完成。系统不猜作者未来是否还想编辑：满足原合同且已经保存的答案可被接收；已收后改变结论走原修订／返工。分步草稿允许继续编辑；普通观察不反复把同一暂未填完的问题当作新故障刷屏，必要专业拒错按原字段和具体位置反馈。展示去重沿已有机制按会话、责任与实际错误变化处理，不成为接收权威、不隐藏新错。工具始终可用，不增加 submit、done、marker、状态字段、重存或无关工具调用。已收只投影原事实，不在每个 Reviewer 事件重交结果或重跑全轮 Gate；Main 的长检查、集成与专业判断仍由 Main 承担。Main 阅读或转述 Worker 答卷不能代写本人结论。

`SubagentStop` 在初始 Snapshot 遇到明确 Runtime pending 时，由系统在原 Hook 绝对截止点内调用原 Writer 恢复一次、刷新状态，再按当前 S7 的同一真实任务／返回引用接回上述原消费者；不要求 Main 手工接收、Reviewer 重存或额外工具事件。pending 本身不能证明 S7、作者或交付完成。该恢复的共享 Writer 副作用与其他阶段的停止边界见 [Hook 实际路由](../l4-mechanisms/L4-hook-platform-wiring.md#42-真实路由顺序就是边界的一部分)。恢复失败、超时或无后续可用事件时如实报告未完成，不能承诺后台自动最终接续。

S9 D 仅迁移新 Builder 的本人 Plan／Result，不迁移本阶段 Main ReviewPlan 或 Reviewer 题卷。Main `.claude/submissions` 的正常写权限差异仍须单独处理，不能由普通 Builder 路径宣称已解决。S7 不新增 Builder 产品交付角色，不要求 Reviewer 改产品或写 marker 保树；若未来使用 isolated Reviewer，必须为其原题、owner、准确作者根和真实产品基线单独设计与验证。当前新原生只读责任使用原 Main 根下的私人答案；已有登记的独立执行继续使用原冻结来源根和准确答案路径。独立根不可读或证据缺失时不得退回 Main 借用答案。实际路径引用是来源索引，工程责任的有效性、独立性和答卷结构仍由原消费者校验。详见[原生子代理治理](../l4-mechanisms/L4-agent-dispatch-governance.md)与[工作区治理](../l4-mechanisms/L4-worktree-governance.md)。

## 8. 审查者怎样形成专业结果

审查者先核对自己拿到的实际 Claim 集合与冻结材料，再按计划方法取得观察。普通结果必须对自己的每项命题给出唯一处置，不能多答、漏答，不能用一段总评替代逐项判断，也不能为完成流转把未执行事项写成 PASS。真实 P0 中止遵循 §11.1：只交已观察项，由原批次保留未观察集合，不把中止伪装成产品前提阻塞。

Reviewer 只修改答卷的 `answer`，保留机器题干和绑定。答卷顶层仅保留 `title`、`instruction`、`read`、`questions`、`answer` 五个字段，不要把 view packet 的 `packet_id`、`template_id`、`binding`、`inputs`、`draft`、`view_path` 或 `answer_path` 抄入答卷。主要内容如下：

| 专业字段 | 内容与限制 |
| --- | --- |
| `claim_results` | 实际 `pass`／`fail`、采用的方法、观察与证据；这里没有 `blocked` 或 N/A 结论 |
| `blocked_claims` | 仅适用于被本轮已确认产品 Finding 破坏执行前提的命题，详见 §10 |
| `checks` | 真正运行的命令及 `pass`／`fail`；未运行的计划不填成已完成检查 |
| `findings` | 每项失败命题恰好一项真实发现，保留模式相符的现场 |
| `deviations` | 实际执行偏差的字符串数组，没有则 `[]` |
| `site_lost` | 普通发现现场确实无法恢复时的阻塞声明，不代表已完成 |
| `verification_artifact_digest` | 保留机器预填或 `null`，消费者根据实际来源处理 |
| `verdict` | 明确选择 `pass`、`finding`、`req_change_required` 或 `release_blocked` |

逐命题失败写 `conclusion=fail`，整份结果写 `verdict=finding`，不能混用为 `verdict=fail`。有普通发现应继续可安全执行的必需检查。确需改变需求或阻止发布才使用对应判定，不能把一般发现升级成暂停来跳过剩余工作。

证据引用应让接收器和后续调查找得到原事实。作者选择真实的 `path:<仓库相对路径>`，原答卷适配器在首次接收时从本人准确来源根读取并固定 SHA，随原 Result 和 Finding 一起提交。SHA 不是作者题目，不能要求手算、抄 Runtime 或写脚本补元数据。接收之后以原固定内容核对来源连续性；同答重放只恢复原已接受引用，不重新读取今天的文件来刷新摘要。旧记录缺少当时的内容证明时，不能用当前字节补造历史，须明确原来源恢复责任。

作者引用 `command_output:<原实际捕获路径>` 时，适配器从本责任原捕获缓冲读取已经取得的摘要、实际字节数与截断信息，不从文件存在推导命令已执行，也不猜截断值。缺原捕获就反馈准确来源缺口；原执行窗口、产品基线、截断／保密与 PASS 资格检查仍由原消费者执行。普通本地证据在已登记的本人实际根读取，不借 Main 同名产品文件。原 `capture exec --root Main --cwd Worker` 则把捕获缓冲与命令输出保存在原 Main 控制证据树，以 provenance 单独绑定真正执行的 Worker 根、责任与执行窗口；这类已知捕获沿原存储位置读取，不能误当成需要搬迁到 Worker 的产品文件。Runtime 证据 ID 及 `runtime:<id>` 继续解析原索引和原文件，不复制成通用别名。控制台、请求等按真实原类型引用，不能用看似合理的字符串冒充采集事实。

计划的 `required_evidence` 会约束相应结果提供的引用与类型。即便没有额外的机器必填证据，作者也应说明足够具体的实际观察；结构接受不等于专业结论可信。一次可确定追踪的问题可使用 `once_with_deterministic_trace`，只有实际反复成立才写 `always`，不需要为修改这个枚举重复危险操作。

## 9. Finding 应把真实现场交给调查者

### 9.1 先保留偏差发生的经过

Finding 要回答“原本要做什么，依照什么期望，从哪里开始，在哪里首次偏离，最后停在什么状态”。它是本次真实遇到问题的记录，不是留给下一位执行者的未来复现脚本。

作者选择本卷真实失败的 Claim，提供严重性、应有与实际行为、依据、现场和证据。固定 Schema 版本、由原 Claim 确定的 lens，以及内部 Finding 编号由原答卷适配器补齐。现行领域约束本来就是每个 fail Claim 恰好一个 Finding，因此默认编号稳定关联原 packet 与 Claim，不增加数量限制或作者输入。确需同卷 site_lost／其他真实关联时，作者可以显式选择 Finding 标签；显式错误 lens、冲突编号和真实专业缺项仍由原 Schema／消费者拒绝。适配不改作者文件、固定题干或已接受历史，同答沿原身份和回执重放。

`expected` 和 `authority_refs` 固定应有行为及其来源，`observed` 描述实际偏差。`encounter` 将目标、运行上下文、操作过程、证据与失败边界连接起来：

- 最后正常点 `last_good_checkpoint`：什么事实仍符合预期。
- 暴露偏差的动作 `wall_action`：实际执行了什么请求、操作、命令或读取。
- 首次异常点 `first_bad_checkpoint`：最早可以确认的偏差，而不只是最后的错误提示。
- 结束状态 `terminal_state` 与被阻断后续：本次停在哪里，还有哪些步骤没有发生。
- 逐步证据、状态变化、尝试变体、副作用和清理状态：调查需要知道现场是否仍在、哪些观察能够复用。

`visible_impact` 位于 Finding 顶层，副作用位于 `encounter.side_effects` 字符串数组。`runtime_context`、`actor_context` 和 `symbol_trail` 使用字符串，不能随意改成自造对象。证据应脱敏，不记录凭据或不必要的个人信息；自动脱敏也不能替作者判断内容是否适合保存。

### 9.2 按观察模式记录，避免所有问题套浏览器步骤

| `observation_mode` | 模式需要保留的关键现场 |
| --- | --- |
| `user_flow` | 入口、真实操作时间线和终态，并关联页面、控制台及请求证据 |
| `api_flow` | 实际入口、请求与响应摘要和终态，必要时关联持久化与异步出口 |
| `command_flow` | 实际命令、整数退出码与终态，关联真实输出 |
| `state_transition` | 转换前后状态和终态，说明触发转换的实际动作 |
| `code_inspection` | 阅读入口 `inspection_entry` 与调用或数据流 `symbol_trail`，标出偏差边界 |

所有模式均保留 `journey_summary`、`wall_action` 和 `first_bad_checkpoint`。普通发现还需要最后正常点和终态；凡记录了时间线，每步均应有对应证据。静态阅读发现不必伪造 UI 操作，但必须让下一位调查者找得到具体入口和失效路径。

### 9.3 采集是辅助机制，不能制造事实

原 `capture step` 保存已发生的操作与证据引用，`capture exec` 包装实际命令并保留执行来源。缓冲按 Runtime、代际和 Assignment 隔离；多项发现共享缓冲时，步骤还需通过 `finding_id` 或 `claim_id` 准确关联。不能把一份责任级时间线无差别附给每个 Finding。

结果接收时，缓冲只补入尚无作者时间线的发现，不重写作者已经记录的经过。采用自动命令采集证明 PASS 时，还要满足原执行窗口与来源约束。浏览器网络、控制台、截图和 trace 只有工具实际采到才可计入，Hook 不能补造。

缺少某类附加证据，应在 `capture_gaps` 说明缺什么、为什么无法取得、对调查有什么影响。若普通发现连必要的失败边界与现场都不完整，应在原处安全补齐；确实无法恢复则通过 `site_lost` 记录责任阻塞，留在 S7 处理。不能用“有缺口”一句话将不可调查的表象直接扔给 S8。

P0 或继续采集会引发安全、数据破坏风险时，应立即停止危险操作，保留已有证据并列明缺口，不为补卷重做破坏。当前消费者自动立即封存依据是 `severity=P0`，不会仅凭文字包含“安全”自动停止；Main 与审查者仍需做准确严重性判断及现场止损。

Finding 被接收后不可覆盖。原发现者新增观察使用 FindingSupplement；必要时由明确授权的替代者追加。作者交付新观察、真实证据及其回答的判别问题，原消费者补齐 Schema、内部补充编号、接收时间和内容摘要，仍形成原持久化对象，不增加一层答卷或登记表。新本地证据在首次接收固定。原专业输入与原责任先定位稳定补充身份；同答重试复用原记录中的时间、摘要和冻结证据，不再产生事件，源漂移时拒绝，不能重新签当前字节成为第二份观察。真实新增专业观察才追加新记录。已接受的旧补充保留原字节和摘要，不改原 Finding，也不改变封存批次的发现集合。

补充的真实作者资格不能由旧 Finding 的 `original_finder` 默认推导。有原准确责任绑定时承接实际作者；保留的显式 `runtime finding-supplement` 入口仍需要真实作者归属声明，替代作者仍需原 `authorized-by` 授权。这一入口当前没有独立的原生补充责任准备器，不能声称选择 Finding 就完成了实际作者认证，也不能因此要求作者组装完整机器封套。S8 要求的追问应绑定具体待区分的假设和判别问题，不能无限要求原发现者重跑整个流程。

## 10. 接收结果、处置命题与继续发现

### 10.1 原消费者承担的事实检查

自然事件上的自动接收不等于直接采信答案。原消费者核对已发行责任、工程 owner、准确来源根、原题干、当前计划修订、轮次、代际和对象摘要，再检查命题集合、判定一致性、证据、独立性与现场。

结果文件与 Finding 先以不可变内容准备，Runtime Writer 在同一事务中接收结果、更新本人责任和逐命题处置、登记发现，并在条件满足时生成本轮收口事实。提交前置失败不得留下被当作已接受的状态；并发修订由 Writer 裁决，失败后的临时文件也不能授予权威。

原提交、回执验证和阶段出口分别认定，不增设持久状态机：

| 已知事实 | 对外表述及责任 |
| --- | --- |
| 原提交未确认 | 保留原错误和未确认事实，不能由文件、临时产物或超时猜测已收；专业缺项交本人，系统／并发问题交 Main 核原记录 |
| 原 `SubmitIssuedResult` 明确成功，但 receipt 重建／校验失败 | 保留本次提交成功、准确 packet／owner 及原持久坐标；未经验证的回执不冒充完整成功，也不改称作者未交。Main 沿原 receipt 复核及原出口恢复，不重交作者稿 |
| 原 receipt 验证成功 | 投影本人已接收、本人工作完成；轮次收口、Gate／转换和下一材料准备仍各由原消费者认定 |

原 service／submission 接口及所有回执调用者必须保留上述差异；`Accepted`／`WorkComplete` 不能被用来掩盖提交后回执故障，也不证明全轮或阶段完成。这是接口合同，当前实现是否能准确表达及恢复须用提交前／后的故障反例验证。

本人结果被接受即结束本人责任，不需要等全轮完成才能返回。队列根据已接受的结果、依赖和资源冲突继续释放；暂停、紧急封存或干净轮已经关闭入口时，不再释放新工作。本人专业缺项由本人依据具体反馈修正未接受答案；准备、来源、Writer 和回执故障由 Main 核对原事实后恢复，不要求作者改写正确答案，也不能由 Main 帮忙写 PASS 或绕过领域校验。

### 10.2 普通失败、产品阻塞与环境阻塞不能混用

| 情形 | 正确处理 |
| --- | --- |
| 实际检查失败且现场完整 | 记录 fail 与对应 Finding，继续其余安全可执行命题 |
| 本轮已确认产品 Finding 使后续无法构建、启动、进入或满足前提 | 使用 `blocked_claims` 绑定该 Finding 和前提失败证据，声明修复后必须执行 |
| 服务未启动、凭据缺失、工具或测试环境不可用 | 保留责任阻塞并由 Main 协调，留在 S7；不能伪装成产品 Finding 或 N/A |
| 时间、上下文或平台容量不足 | 调整执行顺序或专业分工，保留必需覆盖，不能制造客观产品阻塞 |
| 基线或题干已失效 | 停止旧结果接收，Main 按来源恢复或新轮路径处理 |

合法 `blocked_claims` 至少包含 `claim_id`、`blocking_finding_ids`、`failed_precondition`、`evidence_refs` 和 `after_repair_required=true`。`failed_precondition.kind` 仅使用 `build`、`start`、`entry`、`precondition`，详细说明为何该产品问题使命题无法执行。所绑定 Finding 必须在本轮已被确认，或与本次结果在同一事务内确认；前轮问题和猜测均不足以支持。

被阻塞命题不再重复出现在 `claim_results`。领域消费者将其投射成 `blocked`，表示本轮已如实交代未执行原因，并将修复后的验证债务交给后续轮次；它永远不等于 PASS。

### 10.3 计划状态表达发现进度

| 状态 | 含义 |
| --- | --- |
| `running` | 正在取得本轮必需命题的实际处置 |
| `cannot_clean` | 已有确认发现，本轮不能成为干净轮 |
| `discovery_draining` | 继续完成剩余安全可执行的必需检查，收集完整发现面 |
| `observation_sealed` | 发现批次已封存，等待原调查交接 |
| `clean` | 本轮结果已满足消费者的无发现收口条件，仍需通过退出门 |
| `stale` | 来源或相关资产漂移，本轮结果不能继续按原身份接收 |
| `paused` | 需求变更或发布阻断判定已保存恢复检查点，等待原暂停路由 |

这些状态是权威事实的投射，不能由 Main 手改以让流程向前。普通发现不会立刻取消整轮；同样，状态变成 `clean` 也不能当作发布授权。

## 11. 轮次怎样交给 S8 或 S10

### 11.1 完整发现批次

普通轮次须让所有 required Claim 得到 `pass`、`finding` 或合法 `blocked` 的处置，才能封存发现批次。封存保留准确 Finding 集合、覆盖统计、被产品问题阻断的命题、已完成责任、原发现者路线、调查准备情况和证据缺口。普通封存不能悄悄留下未观察命题。

P0 可立即封存，不等待其余责任，也不要求同一 Reviewer 继续完成尚未观察的 Claim。本人保留已经真实取得的结论、对应 P0 Finding 和安全采集缺口；删除未执行 Claim 的空白答案项，不伪造 pass/fail 或产品前提阻塞。未观察集合由原计划减去实际处置计算，不新增一份作者必须填写的覆盖清单。批次显式列出 `unobserved_claim_ids`、停止原因及安全采集缺口。只有通过原消费者校验的本次 P0 Finding 才能启用这一例外；普通结果仍须完整回答自身 Claim，重复、外来 Claim、来源漂移和证据错误仍拒绝。这样停止危险工作仍可追溯，也不会被解释成已经完成全部验证。

S7 不因多个 Finding 看起来相似而语义去重，不在封存时创建新的 BUG 身份或给多个表象强行指定一个根因。S8 接收完整批次，再开展问题归并、竞争假设和原因判断。封存时的 `investigation_readiness` 应依据每份实际现场重算，不能一律填 ready。

原消费者形成 `ObservationBatch` 与 `observation_sealed` 后，原流程通过 TR-008 将有效批次交给 S8。结果接收和批次形成可以是同一 Writer 事务，跨阶段转换仍有自己的校验和事务；交接失败应恢复原转换，不要求已经完成的审查者重做结果。

### 11.2 干净轮是严格合取

没有任何单一角色有权凭总评宣布干净轮。成立条件包括：

1. 当前代际、轮次和产品基线有效，当前 ReviewPlan 已完成无发现收口。
2. 当前 required Claim 集合全部有已接收的 PASS；N/A 命题保留有依据的计划处置。
3. 责任分配与已接受结果满足独立性、来源和证据要求，没有未结束的必需工作。
4. 本轮没有确认 Finding，没有阻止交付的开放问题；已关闭的阻断问题具有有效定向复验证据。
5. 结果及其依赖的验证资产仍有效，没有用失效证据支撑当前结论。
6. 机器生成的 CleanRound 快照已经登记，能够关联实际计划、对象摘要及结果引用。

消费者在最后一个必需结果到达且无发现时生成快照，`EvaluateCleanRound` 计算状态门。TR-009 再消费干净轮、复核当前规范产品基线，并对适用的原 E2E 执行资产进行检查，之后才进入 [S10 验收与审计](L3-S10-acceptance-audit.md)。只读状态面板显示的标签、Reviewer 自写的总评、一次定向复验均不能代替这个过程。

正常最后结果的完成出口应在接收后接续原 Gate/TR-009，并在本次交接中反馈 S10 验收问卷的准确位置，不要求 Main 再用普通工具触发进度。接收、迁移与材料准备分别成立；原门或准备失败时保留前序事实，给 Main 具体原因及原 `runtime review-continue --root <Main>` 接续入口；已经进入 S10 而材料未准备好时，给准确预期路径和 `runtime audit-prepare --root <Main>`。首次接收沿原 `continueS7AcceptanceResult` 尝试出口；后续 Reviewer 普通事件只投影个人事实，不能每次重跑 Gate。Main 的实际返回／会话恢复及具名入口接续未完成部分，真实平台如何送达 Main 仍须验证；没有执行者时不承诺无人触发完成。Finding 分支继续按原 Batch／TR-008／S8 合同，不套用 clean 出口。旧 Pre 自动触发仅保留原兼容恢复，不要求手工复制 clean_round 绑定或重交 Reviewer 答案。专业边界、事件矩阵与本轮验收见 [S7→S10 指引编排](../l4-mechanisms/L4-agent-guidance.md#s7s10-的分层与事件编排)。

干净轮判定区分当前义务与原计划修订明确退下的历史 Result。原修订 Writer 将受影响的旧结果标为失效，记录同一计划的准确修订来源，并清除受影响责任的旧引用。只有同代同轮、来源对应当前计划已接受修订、当前 Claim／Assignment／回执均不再引用的这类历史 Result，才退出当前失效资格集合。它仍保留失效状态、原文件与审计历史，不会重新变成有效 PASS。

这项区分不接受“有一个更新的 PASS 就忽略旧项”。没有明确替代标记、属于别的计划或代际、指向尚未成立的修订、仍被当前结论使用的旧结果，都继续阻断；Finding、ObservationBatch 和 CleanRound 的失效也不由计划修订豁免。受影响责任尚未重验时，原完整 Claim 集合和计划收口条件继续拒绝；真实 Finding 仍使本轮无法走干净出口。

`EvaluateCleanRound` 读取原 Writer 维护的状态投影，不能单独认证任意手改 Runtime 或代替全部 journal 校验。正式接收、事务一致性、产品基线与适用资产检查仍由原消费者执行。Main 根据准确缺项恢复当前责任，无需删除历史或为了已解决的旧结果重开一整轮。

### 11.3 需求与发布阻断

`req_change_required` 和 `release_blocked` 是明确专业判定。原结果事务保存唯一恢复检查点并将计划置为 paused，后续通过 TR-010／TR-011 走相应暂停路线。不得为这两条路径另建第二份暂停载体，也不得把一般工程缺陷都解释为需求需要人类重新拍板。

人类参与用于真实需求取舍、发布阻断处置和轮次预算决策。已经授权的安全检查、证据补齐与原路径恢复继续执行，不反复请求人类批准常规审查动作。

## 12. 修订、重放与异常恢复

### 12.1 新发现允许有界补充覆盖

执行中可能发现原计划未覆盖的真实受影响面。Main 可基于已接收 Result／Finding 的准确 `source_ref` 与 `affected_surface` 发起一次受控发现修订，说明新命题与来源的关系。修订不是为了删掉失败命题、降低判据或躲避已经取得的结论。

计划保留原身份、轮次、代际和固定产品基线；不能在同轮替换产品提交，也不能随意更换冷启动写面。被改变的命题，以及因责任边界、归属、资源锁或波次变化而受影响的命题，需要失效处理和当前责任重验。未受影响结果能否保留由原投射与退出门共同决定，不能手工复制旧 PASS 到新答卷。

当前来源检查也接受带准确 SHA 的本地 `path:` 证据，受影响面通过规范化后的目标路径归属检查。路径可读、摘要匹配和目标位于该写面，只能证明修订有具体锚点；为何必须增加或改变覆盖、是否保留原失败事实，仍由 Main 的专业判断负责，不能将机械可接受范围当作随意删改命题的授权。

当前 `stale` 恢复分支允许在确认原漂移已消除后使用受控修订，不受普通发现修订次数的同样限制；它仍不能移动固定产品基线，不能借此获得无限扩展本轮的权利。原 S9 种子首次专业登记与这里的发现修订也不能混为一谈。

### 12.2 区分来源失效与可修正的答案

| 异常 | 恢复责任与边界 |
| --- | --- |
| 准确题干或私人答卷没有准备出来 | Main／系统修复原责任准备，不猜路径，不让 Worker 手工发行、消费另一套答卷 |
| 答案缺字段、类型错误、Claim 集合不符或证据缺失 | 原作者依据具体反馈修正同一未接受答案，由自然事件沿原消费者观察；不增加结束标记或再 Stop 手续 |
| 已有独立来源根缺文件或不可读 | 修复该来源的真实文件和登记关系，不从 Main 借证据填补 |
| 并发接收发生快照 CAS 冲突 | 原答案保留，由 Main 核原提交、回执和当前责任；未确认时沿原 Writer／接收入口处理，不能把恢复原子代理或重存当作系统故障修法。已收复用原回执，真实责任变化走原修订，不手抄数字或等待 CleanRound 自行出现 |
| 原提交明确成功但回执故障，或已收后反馈丢失 | Main 复核原 receipt 与不可变 Result，只恢复未完成回执／出口；保留已成立事实，不重交作者稿，不重复 Submit／CAS、登记发现、完成责任或封存轮次 |
| 已接受判断需要改变 | 使用原 Main 明确修订／返工路线，不能覆盖不可变记录后假称重复提交 |
| 漂移判断因临时不可读而触发，实际固定内容未变 | Main 通过原 `review-plan revive` 重新证明来源后恢复；不改修订和旧结果 |
| 产品提交或权威内容确实改变 | 旧轮不能继续代表新对象，走原失效与新轮路径；复活不是基线替换入口 |
| 普通现场丢失 | 原消费者登记责任阻塞，Main 安排安全补证或原恢复；不能假装已交调查 |
| 阶段转换失败 | 保留已经提交的原结果与收口事实，按具体门失败恢复转换，不重跑已完成审查 |

恢复来源是 Main 的有范围工程操作；框架的 `revive` 只复核与恢复计划状态，不还原、删除产品文件。恢复前保存当前改动及新增／未跟踪文件，逐个比对准确 pinned commit，不能把“恢复”解释成整树 reset／clean，也不能删掉 pinned 中不存在的文件。`revise --file <ReviewPlan-v2.json> --source-ref <已消费 Result/Finding ID> --affected-surface <仓库相对范围>` 读取 JSON 文件路径，不接收内联 JSON 或 Markdown。它只修订有实际来源的 Claim，保留 pinned S6 产品基线；新产品提交走原返工／新轮入口。

产品基线并非“所有文件不加区分”：现有 `buildsurface.ProductPath` 排除 `.git`、`.claude`、`.worktrees`、`docs/reports`、`e2e-workspace` 控制／验证目录；规范、配置和未归属的其它提交仍保留在完整审查面，`unattributed_paths` 标明缺少 S6 贡献归属。持续变化的仿真反馈应放在仓库外或已有报告目录，不应提交到普通产品路径后再静默排除。未归属不等于无影响，不新增任意路径排除开关来隐藏实际改动。

计划文件已按原不可变字节发布而 CAS 尚未发生时，同答可复用该文件继续原登记，不需要新 ID 或作者手工删除。原 Writer 在发布指针前确认或补回准确文件；不同内容继续报冲突，不能覆盖已有产物。失败清理沿原锁、pending、修订和引用检查。较晚的 CAS／持久化失败可以保留无引用的空验证目录：目录存在不授予派发或完成资格，也不以目录清理与其他准备争用。专业结构不成立的草稿仍在准备目录之前拒绝。

幂等重放以已接受的专业内容和回执为依据，不依赖可变采集缓冲继续存在。普通修正与真正的已接受结论变更必须分清，否则一次响应丢失就会变成第二次审查或覆盖审计事实。事务与修订的共同规则见[状态转换核心](../l4-mechanisms/L4-state-transition-core.md)及[修订机制](../l4-mechanisms/L4-revision-usage.md)。

### 12.3 轮次预算用于暴露不收敛

反复修复仍无法形成干净轮时，应分析是产品缺陷、发现收集不完整、契约含糊还是治理问题，不能靠改判 PASS 结束。达到完整轮预算后，由人类明确增加预算，或返回治理重新处理范围、设计与计划。

真正需要开启下一轮而预算已经耗尽时，原等待入口准备准确的预算决定申请。人只决定 `increase_budget` 或 `return_to_governance`，说明真实理由；选择增加时才给真正高于原上限的新值。Main 如实保存这三项专业内容，系统承接申请已固定的 Runtime、代际、轮次、旧上限、决定编号与授权来源，适配为原 `S7BudgetDecision` 并交原 `ApplyS7BudgetDecision`／Writer。增加预算仍走原 TR-012／TR-016 后继；退回治理沿原 GTR-006，原权威事实不另存一套。普通 Pre／Stop／状态面板只读已准备申请，不临时造表；空选择不登记批准。

计数达到上限本身不是催人追加预算的理由。当前 S7 仍可排空本轮，正常 S10 未决或 PASS 仍应按原验收继续；只有 S9 已到 `ready_for_full_review`，或当前原已接收 S10 `review_required` 确实要求新一轮时，才进入相应预算等待。S10 分支只读取准确现有接收封套，核对其原摘要、Runtime、代际与轮次，不为状态查询重跑全部门或 Git 链。原来源缺失／改变是 Main／系统恢复责任，不能由此推导预算批准。

申请固定当前决定对象。错误旧值、过期轮次、没有实际提高和错误分支值仍拒绝；已经接收的同答沿原证据与不可变对象只读重放，不能重授旧预算、重记人意或重复完成的出口。保留的显式 `runtime s7-budget-decision` 与完整内部 DTO 用于原兼容／恢复，不再作为正常作者交卷要求。此机制不自动扩大需求，也不允许复活旧审查者替新的产品基线签字。

## 13. 怎样观察进度和定位失效

观测应解释“卡在哪个事实环节”，不是用平台消息数或工具调用次数代替工作完成。

| 观察点 | 应看什么 | 能区分的问题 |
| --- | --- | --- |
| Main 计划准备与接收 | 准确路径、未消除占位、覆盖与登记反馈 | 尚未专业规划，还是已经登记但派发缺失 |
| 原 `s7 status` | 当前基线与轮次、命题处置缺口、待分派责任、队列、`blocker_ref`、结果与出口 | 未派、在等前提、实际阻塞和已完成未交接 |
| 原生上下文与自然事件接收 | 是否取得唯一原引用、原消费者接受或拒绝的具体原因 | 平台运行失败、引用交付缺失和领域答案错误 |
| 责任回执与不可变产物 | 原 owner、结果来源、专业内容、有效版本与接收事实 | 响应丢失、错误来源、同答重放和真正修订 |
| 轮次与事务记录 | 计划状态、发现批次或干净轮、随后实际转换及门失败 | 结果已接收但未收口、已收口但未进入下阶段 |
| 阶段指标 | 命题与责任数、计划修订、逐命题耗时、发现到封存时长、干净轮与接收阶段耗时 | 覆盖不足、过度拆分、重复修订、发现后停滞和接收链耗时 |

`loop-harness s7 status` 是读取已有事实的面板；不是另一套校验器或提交入口。发现缺少种子投射、责任题干或已接收事实不一致时，Main 先修复其权威来源，不要求 Worker 再交一个“完成报告”。指标记录失败也不应决定领域结果是否接受。

自动采集的命令输出只能证明实际执行过的内容；Hook 的审计记录只能证明发生过相应事件；Runtime 回执只能证明原领域消费者接受过该责任。它们合起来支持定位，但不能自动推导业务行为正确或真实平台完整验证已通过。

当前落地需特别区分以下能力与边界：

- **自动草稿不是适用性或可执行性证明。** `ui_impact=none` 会生成 E2E N/A 候选；浏览器 CASE 的文本匹配仅交付候选，不产生正式资产或自动状态。Main 必须完成影响分析、资产选择和非浏览器行为责任，不能把默认值当作产品无需验证或已有可用回归的结论。
- **结构校验不是语义审查。** 非空判据、来源和 N/A 清单 ID 不能自动证明内容正确；独立性检查也不能证明工程 ID 背后的实际平台作者互相独立。
- **历史排除有准确范围。** 只有原计划修订明确退下且当前不再使用的历史 Result 退出失效资格；其他失效与真实 Finding 继续阻断。现场丢失可以登记阻塞，但不保证自动完成恢复安排。Main 必须读取真实反馈，不能照状态名称推测已有完整恢复能力。
- **方法指引不再拥有派发协议。** 角色和质量技能承担实际审查方法，准确答卷、自然事件接收与原消费者承担工程衔接。专业输入不增加通用 PLAN／激活或手填资产摘要要求；已登记旧执行的恢复条件只约束其原记录。
- **验证资产不等于产品修改授权。** 冷启动资产写面与专业只读边界需要真实分工遵守，不能因工具调用未被拦截就认为允许修改产品。结果和退出门承担事实检查，不将每次工具调用变成执行批准。
- **题干升级不替换已发行责任。** 新发行使用当前题干；已发行答卷按受支持的原冻结模板、原 inputs／binding 和签发证明恢复。旧题干资产只服务其准确摘要对应的历史责任，不是新的提示入口。恢复不重签身份、不覆盖作者答案；未知模板或篡改题干仍拒绝。

本章给出阶段合同与实现索引；本轮新增合同不自动成为已落地能力，不以文档存在宣告测试、真实 Claude Code 派发、跨阶段转换和业务质量全部通过。它们分别需要对应范围的实际证据。

### 15.2 从准备到接收的最小完整交接

| 时点 | 当前执行者实际收到什么 | 专业工作与结束条件 | 系统接续 |
| --- | --- | --- | --- |
| Main 计划 | ReviewPlan 准确路径、规划来源及未决项 | 判断 Claim、oracle、覆盖与分工，保存原计划 | 原登记器接收；随后指出实际缺少的分工准备，不能提前声称 Reviewer 路径已就绪 |
| Main 派发 | 当前 Assignment、manifest 或准确准备命令，登记后真实 view／answer | 选择 Reviewer 和专业分工，按依赖原生派发 | 绑定系统已知身份、默认配置与准确路径，不让 Main 抄 Runtime |
| Reviewer 工作 | 唯一 view／answer、本人 Claim、冻结对象及本次已选择方法的准确路径和用途 | 实际检查、保留现场、填写并保存原 answer；正常汇报无需新增提交信号 | Start 衔接；Pre 有界定位本人，成功 Post／SubagentStop 兜底同一原消费者；专业拒错交本人，来源／提交／回执故障交 Main |

| 无法形成结论 | 原责任引用、真实来源／环境障碍及已尝试事项 | 原生返回给 Main；保留已有观察，不编造 verdict 或产品 Finding | 未接收明确留为未完成，Main 恢复来源或继续原责任；不以再触发一次 Stop 作为合法返回手续 |

| 阶段迁移 | 已封存批次、待交接状态 | Main 接续当前工作，不再派发已关闭轮次 | 下一次 Main `PreToolUse` 按原 guard 执行 TR-008，Stop 不拿旧 Assignment 阻止交接 |
| S8 接收 | intake 准确路径、Batch 和不可变 Findings | Main 填调查分组理由，不预判同根因 | 原 ingest 校验准确集合、摘要与基线，创建 Case 并准备后续调查材料 |

Main 的派发材料必须连成目的、准确输入、实际工作、准确输出与接收方式、异常处理和本人结束条件。较长说明放在原 view／题干，短交接仍保留完整路径；不能只写“按框架执行”。自然事件未匹配到唯一原责任不得猜测收卷，Main 按已有回执恢复原交接，不新增 actor 注册或启动握手。

本次专业方法来自原分工已选择的技能及其已解析来源，随原责任交付准确路径与用途；角色默认预加载不能代替追加专项方法的交付，也不因此恢复全量技能预加载。重新观察沿用原选择，不悄悄刷新已冻结 packet 的身份、题干或作者答案；旧发行按其原合同恢复。

接收 Result、封存 Batch、TR-008 和创建 Case 分别证明不同事实。反馈明确已经成功到哪里和谁接续，不要求作者为了下一个提示重复提交或执行无关工具。命令参考保留诊断和具名恢复用途，不能抢占正常保存／原生结束路径。

Hook 的运行成本由[机制分层](../l4-mechanisms/L4-hook-platform-wiring.md#101-机制减负的作者契约)承担。一次内部 deadline 不构成专业内容拒错；原接收器使用冻结答案、准确暂存归属和原 Writer pending 进行有限续跑，不让 Reviewer 改字段、重存、删证据或换 ID。显式取消不借恢复尾段继续提交。首次原结果已接收时接续本轮原出口；其后只恢复未完成部分，已收 Reviewer 普通观察不重跑 Gate，不能因为原工作 context 已过期就把已完成责任交回作者；同次后继共用有限收尾窗口。系统强制终止或材料真实缺失仍应如实报告当前已记录事实，不承诺不存在的后台执行者。

### 15.3 有限阻断与合法异常

Main Stop 只对当前确实可执行而未完成的工作要求继续。普通观察、会话开始和压缩后的首次观察，其派发判断均使用与真实派发相同的当前轮、计划状态、暂停、依赖和资源事实；等待静态波次、封存、已换阶段或暂停不能被解释为立即派发。不能为修正提示而放宽真正派发条件。恢复清单直接识别原 Assignment 的 blocked 状态，说明实际原因、原作者及恢复入口，不将它遗漏成“无阻塞”或改称缺少派发。

普通 Finding 已接收而本轮尚在继续检查时，没有封存 Batch 指针是正常状态。只有原封存事务成立才能宣称 Batch 已形成；不能由 cannot_clean／discovery_draining 推断批次已存在，更不能据此要求排查丢失指针。manifest 的完成条件、角色指引和答卷共同区分普通完整检查、真实 P0 中止和未形成结论的原生返回；后两种不得仍要求执行所有剩余检查。P0 能否封存由原消费者判断，普通 blocker 返回不构成 Claim 已处置或阶段已完成。

`blocked_claims` 的产品 Finding 关联、当前轮资格、失败前提和修复后重验须成立，证据则使用正常答卷的真实引用语义。`path:` 由原适配器从本人来源绑定，Runtime 引用按原索引解析，不能同时强迫同一个引用成为另一套裸 ID。接受路径不等于任意文件足以证明产品阻塞；前轮 Finding、凭空阻断与失效来源仍拒绝。

`site_lost` 的恢复仍沿原 blocker_resolved 事件及同一发现者的结果接收。显式恢复命令可从当前唯一原责任绑定消息身份与来源，Main 提供实际恢复说明，不手抄机器封套；真实现场修复、原事件校验与后续结果接收分别成立。只读提示不生成恢复证据，也不将一次返回或一句说明自动解释成审查完成。

阶段条件未满足不等于禁止普通工具。观察范围应覆盖支持的保存工具，接收器仍核对 Main 身份、成功事件、准确表单和内容变化；扩大监听不授权 Main 代填 Reviewer，也不授权 Reviewer 修改产品。旧冻结执行只按原合同恢复，不成为新责任开工前置。

### 15.4 变更与验收边界

领域提交、Hook／接线、静态指引可以按文件与消费者边界并行修复，主线持有本节及跨层契约。阶段字段变更须共同核对题干、适配器、原消费者、批次及下游；事件变更须共同核对平台配置、owner／成功过滤、实际接收与恢复。整合时扫描同一概念的旧叙述，不通过文末追加覆盖规则。

验收从发行的原材料开始，只填写专业字段，以真实分步编辑验证草稿不误收、同一缺项不反复刷屏且普通工具可用，再验证 Pre 有界定位及成功 Post／原生 Stop 兜底能到达原消费者。须分别覆盖不参与本人验证或实际漂移路径证明的 body 损坏不阻断本人，以及实际漂移路径所需的其他原卷来源损坏时具名反馈、恢复原来源和 revive 后接续同一原答；还须覆盖本人 body／source 缺失和索引／身份冲突准确交接、提交前失败不伪报成功、提交成功后 receipt 故障保留事实且不重复原事务，以及已收后 Gate／S10 准备分别失败时 Main 实际获得原因与原入口。新发行题面不再要求额外返回引用；旧 SHA 按完整原字节重建，原身份／路径／来源不变。公开事件在未就绪、首次接收、已收重放及故障窗口的读取与消费者次数、耗时和增长规模须分别计量，不能用套件总时长代替 Hook 成本。反例覆盖普通漏答、P0 同人部分观察、合法产品阻塞、错误证据、等待依赖、暂停、封存、换阶段、重放和来源漂移。首次交付与中断恢复使用同一实际状态比对；领域事务产生的未封存、blocked 和已接收状态不能由提示测试自行假定。已有 manifest 的恢复、追加方法送达及真实未完成返回均须验证，避免只断言某句提示出现。平台 matcher 测试不能由直接 CLI 调用替代；源码测试、进程接线与真实 Claude 会话分别报告。具体缺陷清单、分工与运行日志放在维护档案，不写成另一套 Blueprint 规范。
