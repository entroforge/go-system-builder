# L3-S7 完整验证轮

## 1. 为什么实现之后仍需独立验证

S6 回答“各项实现是否完成、自测并集成”，S7 回答“集成后的产品是否完整兑现承诺，工程质量是否可靠，实际使用是否成立”。实现者最熟悉自己的选择，也最容易沿着这些选择验证。单元测试通过、Builder 自测通过或 Main 合并成功，都不足以消除遗漏、共同误解和集成后的行为偏差。

因此，S7 对同一个产品基线组织三个互补视角：交付符合性、工程质量和端到端行为。它们分别检查“承诺与交付是否相符”“实现方式能否长期成立”“从实际入口使用会发生什么”。三个视角互相补充，不能用三份措辞相近的总评代替，也不意味着固定派三个子代理。

完整验证的单位是本轮应回答的全部具体问题。一个视角可以拆成多个责任；紧密相关的问题也可以由同一独立审查者承担。分工由专业问题、阅读上下文、方法、环境与独立性决定，不能为了控制人数而删除覆盖。平台容量只改变执行顺序。

S7 只确认观察到的偏差、保留现场并判断本轮是否完整。它不顺手修改产品，不将猜测直接登记为根因，也不把审查建议直接变成修复任务。原因调查交给 S8，修复和定向复验交给 S9；本轮完整通过后，验收与过程审计交给 S10。

本阶段承载[设计原则](../l1-principles/L1-design-principles.md)中统一来源、独立完整验证和按实际问题收敛的要求。它与 [S6 实现](L3-S6-build.md)、[S8 问题调查](L3-S8-finding-investigation.md)、[S9 修复](L3-S9-repair.md)共同构成质量闭环。

## 2. 一轮验证由哪些对象构成

一轮验证围绕 ReviewPlan 展开。计划明确验证对象、问题、适用性和分工；Reviewer 在原答卷报告实际观察与结论；系统接收一次后，根据原结论与适用责任完成情况接续 S8 或 S10，不另建手工角度登记簿。

| 对象 | 含义与责任 |
| --- | --- |
| ReviewPlan，验证计划 | Main 的原规划产物，记录基线、命题、适用性、责任、依赖和验证资产安排 |
| Claim，验证命题 | 有来源、对象、断言、判据和方法的具体专业问题 |
| ReviewAssignment，审查责任 | 一个工程 owner 承担的同视角、上下文相容的命题 |
| ReviewResult，审查结果 | Reviewer 原答卷中的逐项观察、结论、检查和发现 |
| Finding，发现项 | 已观察偏差及现场，不预设根因或修复授权 |
| 本次验证的接收与交接记录 | Writer 保存当前责任完成、原结论、发现引用和后继进度所需的最小内部事实 |

审查者完成专业工作、答卷被接收、适用责任完成和进入下一阶段分别反馈。阻塞可如实接收，不能投影为 PASS。系统沿本次 ReviewPlan、Assignment、Result 和 Finding 维护实际关联；`baseline_generation`、计划修订与 Runtime `revision` 各有原用途，作者不手抄机器编号。移除 `review_round` 的生产、消费和旧格式兼容接线。

Main 负责专业计划、覆盖判断、独立分工、原生派发、环境协调、剩余责任和阶段交接。`delivery-verifier`、`qa`、`e2e-tester` 承担各自观察面。系统信任原答卷的专业声明，不机器认证真实性、完整覆盖或实际独立性；接收成功只表示原责任的答案已记录。

四种原入口分别提供本次实际验证对象，并共用后面的计划、派发、接收和出口合同：

| 进入来源 | Main 获得的当前材料与规划起点 |
| --- | --- |
| S6 集成完成，经 TR-006 | 已接收的任务结果、Main 实际集成和检查事实、可用产品材料，以及本次原 ReviewPlan 与 guide |
| S8 判定无需变更任何相关产物并返回验证 | 原 Finding、调查判断及无需变更的实际决定，供 Main 判断重验范围 |
| S9 修复和定向复验完成，经 TR-012 | 原修复结论、实际变化和本次 ReviewPlan 种子；Main 细化完整验证，定向复验不代替 S7 |
| S10 验收要求重新验证，经 TR-016 | 验收发现和实际要求重验的范围，供 Main 确定本次验证对象 |

每种入口均由系统准备本次 Main 原计划及相邻 guide，并给出准确路径；Main 在同一原计划中表达专业规划。材料缺失由原准备入口恢复，不让上游作者重交，也不让 Main 猜路径或制造工具事件。上游事实无法确认时如实给出未知；不把未知当作无变化，也不让无关材料缺失阻断可理解的规划。S6→S7 的具体指引见 [指引分层](../l4-mechanisms/L4-agent-guidance.md#s6-s7-guidance)。

## 3. 先固定到底在验证什么

### 3.1 产品对象与完整变化面

S7 验证 S6 集成后的 Main 产品，而非某个 Builder 工作树或最后一个任务。Main 使用原 S5、S6 的需求、TASK、贡献、集成、自测与变化信息，明确产品版本及新增、修改、删除、残留实现和集成变化。已有需求、TASK、实际变更与覆盖说明可作为专业规划输入；Hook、原计划和消费者不计算、预填、登记或校验产品、证据、来源的 SHA／hash、摘要或 Git OID，也不让作者抄机器字段。历史对象可按原路径和责任读取，不重算或验证其遗留摘要。

这些输入帮助 Main 思考，不证明业务影响已经列齐。Main 判断权威依据、实际消费者和遗漏风险；需要改变需求、契约或产品时走原修订路径，不在审查中悄悄换判据。Hook 接收与阶段分流不重跑 Git 差异、产品指纹、证据文件或历史回执证明链，也不将 ignored／untracked／tracked／staged 状态作为答卷资格。真实产品变化由专业责任如实报告并处理。

原 guide 可按已有责任关系提供当前和先前已整合贡献、Main 自身工作与删除路径的实际可用材料；缺材料时说明未知，不自动推断“没有变化”，也不以历史扫描完整、ProductBaseline 或来源摘要作为计划接收资格。Main 可正常使用 Git 和原工作材料理解范围，机器不代替专业判断。

### 3.2 验证依据与覆盖判断

| 来源 | Main 与 Reviewer 需要追问的内容 |
| --- | --- |
| 需求与成功标准 | 用户目标、范围、非目标和成功条件是否兑现 |
| S2 设计与场景 | 正常、拒绝、边界与恢复路径，真实角色能否从声明入口走通 |
| S3 契约 | 接口、共享模型、错误、兼容性和跨组件接缝是否一致 |
| S4 TASK 与完成条件 | 交付和验证责任是否落实，有无遗漏消费者或集成步骤 |
| 产品变化面 | 实际变化有无解释与审查，删除是否破坏调用方，计划外变化是否增加风险 |
| 历史问题与本次修复 | 相同失效路径、邻接面和已承诺回归是否覆盖 |

系统提供已有明确来源和候选，不推导全部业务风险。Main 负责完整覆盖、非功能要求及不适用理由；机器不另扫描全仓或重建覆盖证明来批准答案。

### 3.3 从修复返回时仍是新的一轮

S9 定向复验回答已批准修复是否消除了所调查问题，不能替代完整验证。修复集成后，以原修复结论和产品说明准备新轮计划种子，Main 完成必要规划。种子不预填新的审查结论。原 Impact 的变化路径进入 QA 命题来源和覆盖线索，供 Main 和 Reviewer 判断实际验证范围；不计算、登记或核对文件 SHA／hash、旧冻结证明或 Git OID，缺少机器摘要不得阻断计划。S6、S8、S9 及 S10 要求重验的进入方式共用此原计划合同；种子、ReviewPlan 类型／schema、注册和 S10 上游消费者必须共同支持它。旧计划继续按原路径和实际关系读取，不重新计算或验证旧摘要，也不要求作者重交。

实际产品或权威输入已改变时，应明确新轮对象，不能复制旧 PASS 代表新产品。S8 排除发现而无须修复时，也按原无修复返回路径说明重验范围。本次验证的关联由系统承接原 ReviewPlan，作者无需追加来源证明。

## 4. 把覆盖写成可判定的命题

### 4.1 命题不是待办标题

“检查订单模块”无法确定读到哪里、什么现象算通过、需要保留什么证据。一个有效 Claim 至少交代：

- `source_refs`：为什么必须检查，来自哪项需求、条款、TASK、CASE 或实际变化。
- `target`：具体对象、入口或受影响面，避免含混的“全部代码”。
- `assertion`：要判断的承诺，既包括应发生的结果，也包括禁止的副作用。
- `oracle`：判断实际观察是否满足承诺的依据，不能与断言循环解释。
- `method`：如何取得足够观察，静态阅读、契约追踪、真实请求或浏览器操作各有适用范围。
- `required_evidence`：计划明确要求保留的证据引用；实际执行仍须报告真实观察。
- `applicability`：本轮必需，或有来源支持的不适用；未知不能写成不适用。

例如，下面是一项命题的结构示意；其中业务路径和 ID 必须来自目标项目的真实材料：

```json
{
  "claim_id": "claim-delivery-rejected-order",
  "lens": "delivery",
  "target": "POST /orders 的余额不足分支及其持久化消费者",
  "assertion": "余额不足时拒绝创建订单，且不产生订单、扣款或通知",
  "oracle": "契约规定返回 INSUFFICIENT_BALANCE；请求前后订单和余额不变，通知出口没有新增消息",
  "method": "追踪契约到处理器、事务及消息出口，并用实际拒绝请求核对行为",
  "applicability": "required",
  "source_refs": ["TASK-012", "CASE-order-insufficient", "docs/contracts/order-api.md"],
  "focus_key": "rejection-side-effects"
}
```

这里的拒绝响应和禁止副作用属于同一业务承诺。若持久化、异步通知分别需要不相容的执行环境或大量专门上下文，应进一步拆命题，并明确依赖；不能让一句“事务正确”掩盖几个从未检查的出口。

命题粒度应让审查者能够给出明确结论，也应让失败项保留清晰现场。同一命题包含数个彼此独立的失效问题时，可按实际专业判断拆开；系统不把每个失败 Claim 必须恰好对应一个 Finding 作为接收资格。

### 4.2 三个视角各自深入到哪里

**交付符合性**从承诺追到实现和实际消费者。它检查需求与 TASK 完成条件，核对设计、契约和代码是否一致，追踪接口是否真正被调用、状态是否真正落地，以及前后端、服务、存储与消息之间的接缝。只证明某个函数存在或测试通过，不足以证明完整交付。

**工程质量**检查实现方式及其长期影响。六个基础问题需要明确处置，而不是把所有 QA 工作缩成一次 lint：

| 基础关注点 | 应形成的判断 |
| --- | --- |
| 设计与边界 | 归属和依赖是否清楚，跨层调用、共享模型与契约有没有被绕过 |
| 模式与项目惯用法 | 所用抽象是否减少耦合与风险，是否符合项目已经成立的惯用法 |
| 逻辑、状态与错误 | 正常、边界、失败和重试是否自洽，状态转换和错误责任是否完整 |
| 可维护性 | 命名、阅读路径、抽象层级与认知复杂度是否支持后续维护 |
| 可测试性与判据 | 测试是否断言真实行为，拒绝和边界路径的预期是否有效 |
| 债务与可运维性 | 是否引入无主债务、不可观察失败或没有交接的后续工作 |

这些是不同的问题，不要求为了“使用模式”增加模式，也不允许以项目没有某种模式为由跳过适配性判断。安全、性能、可靠性、并发、迁移与兼容性等专项由实际风险触发，按相应技能执行。Main 必须说明哪些风险已由基础命题覆盖，哪些需要额外责任。

**端到端行为**从真实角色的声明入口执行旅程，观察可见结果、持久化、错误反馈、禁止副作用和恢复。浏览器流程应包含真实页面交互及关联请求；不能用数据库直写、未声明的直达链接或单独调 API 冒充用户走通。API、命令或状态型产品同样需要与真实入口相称的行为验证，不能把“没有 UI”误解为“没有可验证行为”。

三个视角允许引用同一证据，但仍要回答各自的问题。交付者确认某拒绝条款已落实，QA 判断错误传播与事务边界是否健全，行为审查者实际遇到拒绝并检查副作用，这三项判断并不重复。

### 4.3 不适用必须在计划中说明

不适用是有依据的计划处置。Claim 保留 `applicability=not_applicable`、`source_refs`、`na_rationale` 和 `na_checklist_id`，说明检查了什么影响、为什么不存在该验证对象。它不进入审查责任，不派一个空 Worker，也不通过提交一份 N/A ReviewResult 来补数。

无 UI、纯文档或没有跨服务调用，都只能作为适用性分析的事实，不能单独代替结论。缺环境、缺权限、没有时间和未知影响属于未完成或阻塞，不属于不适用。确无必需交付或 QA 命题时，也必须给出计划级覆盖解释，不能用空数组默默消去整个观察面。

## 5. 用专业上下文决定分工与顺序

### 5.1 从命题到审查责任

Main 先建立完整命题，再按相同视角、关注点、阅读集合、方法、环境、资源冲突和独立性组织责任。每项 required Claim 在当前计划中恰有一个责任承担，同一责任不能混用 `delivery`、`qa`、`e2e` 三种视角。

`focus_keys` 说明责任关注点，`non_overlap_boundary` 解释它与相邻责任如何分界。例如质量审查者可以共享订单模块阅读上下文，但“事务错误语义”和“安全鉴权”若需要不同专业方法、较大阅读量或互相独立的判断，应分别承担。不能把一组没有边界的“全面审查”同时派给多人，也不能让一个泛化 QA 会话吸收所有工作而失去深度。

当前草稿通常为交付追踪生成一项责任，为六个 QA 基础问题分别生成责任，并按可发现的浏览器 CASE 拆行为责任。这是便于 Main 开展规划的起点，既不是固定人数配额，也不是可直接登记的专业计划。合并必须限于同一视角且上下文确实相容，保留完整命题与真实边界；拆分则应说明减少了什么上下文负担或执行冲突。

例如小型无界面模块的几项 QA 命题若读取同一组材料、使用相容方法、没有相互结果依赖，可以由一个 QA 责任持有多个 `claim_ids`，逐项给出结论。Main 在首次专业计划中调整原 `assignments` 的命题归属，保留全部命题及其原身份、判据和证据要求，并使 `focus_keys`、阅读范围与边界准确反映工作；不用增加人数策略字段或另建分工表。交付视角仍独立，真正需要不同专长、环境或结果依赖的 QA 命题继续分开。减少重复上下文的依据是本次工作本身，不能由“只有一个模块”推出必然只派一名 QA。

冷启动行为验证同时包含准备资产和真实执行，尤其容易过载。应按角色、入口、流程簇、状态或拒绝路径组织相容工作；不能把多种独立上下文全塞给一个“全需求 E2E”责任。Main 应识别单一冷启动责任承接多个不相容关注面的过载风险，按实际专业上下文调整；系统不凭字段数量认证分工合理性。

### 5.2 两个执行波次

交付与 QA 属于 `static` 波次，行为执行属于 `behavior` 波次。静态工作先取得完整处置，再进入行为执行；这里要求的是每项静态必需命题有结论或合法的客观阻塞说明，不要求静态全部 PASS。

普通 Finding 已使本轮无法成为干净轮，但仍应完成其他安全可执行的检查，尽量一次保留完整问题面。若一发现失败就停止全部审查，后续修复会不断暴露本可在原轮发现的问题，后续验证会重复收集原本可以一起发现的问题。

环境探测、账号和数据前提确认、验证资产准备可以提前并行。Claim 的 `depends_on` 可表达具体结果依赖；Main 负责安排可执行顺序、避免自我等待，系统不为每份答卷重新计算完整依赖图作为接收条件。

共享可变账号、数据集或测试环境通过声明的 `resource_locks` 排序；互不冲突的责任并行。`dispatch_capacity_policy=coverage_complete` 表示覆盖完整优先于人数配额。平台暂时容纳不了的责任进入队列，不能改写为不适用或假装完成。

### 5.3 独立性属于工作分配

实现者不能审查自己在当前代际交付的产品。Main 应分配独立原生上下文，保留准确工程 owner，并在 manifest 中声明所需独立性。平台实际子代理身份是执行事实，不等于可以随意重命名的工程责任。

Main 根据真实实现参与和原生上下文安排独立审查，并对分工负责。系统只关联原 owner 与当前责任，不扫描 Builder 证据或比较身份字符串认证实际独立性。

## 6. 为真实行为准备环境与验证资产

### 6.1 场景先于脚本

有界面模块的 `cases.json`、`flows.md` 与 PATH 是场景输入。Reviewer 阅读本人责任所需场景，确认角色、入口、正常与拒绝分支、终态、持久化、禁止副作用和恢复。Main 从 REQ、TASK、实际 provider／consumer、契约、共享模型和旅程判断回归范围；已有明确模块引用可提供候选，不能以文本命中或 CASE 数量代替专业判断，也不要求新建模块图证明覆盖。

Main 提供真实服务地址、认证策略、数据前提及环境责任。行为审查者说明实际服务版本、真实依赖与 mock 边界，无法确认时如实交代限制；不能改产品绕过认证或把未执行写成通过。版本与证据的可信程度由专业责任判断，Hook 不另探测服务、复核 checkout 或验证构建来源。浏览器方法见 [e2e-browser-testing](../../skills/e2e-browser-testing/SKILL.md) 与 [playwright-e2e](../../skills/playwright-e2e/SKILL.md)。

### 6.2 验证资产安排

| `e2e_coverage_state` | 专业安排 |
| --- | --- |
| `cold_start` | 在原计划声明的验证资产目录准备缺失脚本与夹具，再执行真实行为 |
| `regression_available` | Main 选择与当前场景、入口及环境匹配的已有资产，Reviewer 阅读并运行 |
| `not_applicable` | Main 在原计划说明该维度不适用，不发行空责任 |

冷启动的 `verification_artifact_workspace` 是 `e2e-workspace/` 下的脚本与夹具写面；既有 `web/e2e/<module>/` 资产、产品代码和报告证据各有用途。S7 不授权 Reviewer 修改产品，也不要求为私人辅助产物增加引用、提交或登记。

Main 选用资产时说明实际场景、脚本、入口、定位方式和环境。场景使用完整引用以区分模块同名 CASE。候选发现不证明可执行或覆盖充分；尚未决定的安排留为规划未决，由 Main 处理，不以默认值伪造结论。

### 6.3 资产变化与原结论

Reviewer 报告实际执行的资产、结果和限制。执行后改动脚本或夹具，Main 按专业影响安排必要重验；无关资产变化不要求全轮重跑。新题面、结果、receipt、注册、出口和恢复均不生成、登记或校验资产 SHA／hash、`verification_artifact_digest`、其他散列或 Git OID。旧记录原字段可作为历史原样读取，但不重新计算、登记或以其作为继续条件。

## 7. 从计划到原生子代理的实际工作链

### 7.1 Main 保存原计划

系统交付当前 Main 原计划与相邻 guide 的准确路径；路径沿本次 ReviewPlan 身份生成，不嵌入审查序号。移除旧 `S7/r<round>/review-plan.json` 运行接线，不保留平行路径。ReviewPlan 是原规划 JSON，guide 是同源说明；Main 按实际进度填写命题、判据、方法、适用性、分工和依赖并自然保存，未决定部分保持未决。

Hook 根据当前 Main 原规划责任观察该文件，仅检查可解释结构、已有专业表达与当前责任关联，接收一次。计划接收不重读 TASK、Git、CASE、资产或历史证明来验证规划真假，也不认证覆盖完整。整份仍为空或占位的草稿不冒充计划；可理解计划中已声明但未分配或未完成的 required Claim 如实保留为未完成。E2E 可选分类缺失或局部占位本身不推导新的未完成责任，不成为出口门禁；已明确发行的必要责任按本人实际结论接续。可解析也不自动表示全部可执行。题面没有统一最终标记时，Main 正常保存既有规划表达即可，不另加完成声明或必填项；系统依据可见规划保存其实际已表达部分，不猜作者是否还想编辑。真实类型、必要字段或责任冲突给准确反馈，合法的未决表达不作为错误拒收。系统保留原稿，不为刷新提示重新生成答案。

S9 返回的原种子由 Main 在原计划入口细化；已开始执行的计划按真实责任变更处理。S7 活跃时 Main 普通 PreToolUse 自然观察当前原计划，成功 PostToolUse 对明确保存路径也调用同一消费者；已接收后仍可自然修改，系统比较当前原表达和必要已收内容，未变化则静默复用，真实变化沿原修订接收，保留旧判断和未受影响的责任／结果。在途原责任与晚到结果保持原关联，不冒充新责任；原内容无法比较时不猜测成功。本人正常保存计划不增加独立预检、计划登记／提交命令、来源证明、影响范围参数、重存或发行确认动作，也不限制修订次数；§7.2 的原 Main 工作组准备与登记仍承担派发职责，不是答卷额外交付。具名诊断与恢复入口只处理实际故障。具体事件、未知与接线见[工作流收敛 §3.3.5](../l4-mechanisms/L4-workflow-convergence.md#335-s6-交付至-s7-验证的进入接收和退出)。

相邻 guide 必须是安装后 Main 实际可读的指引，说明原路径、自然保存、可理解的部分规划和 §7.2 后继，并给出可复制且与现行 schema 一致的专业字段形状。需要引用 E2E 资产时，它解释 `e2e_assets` 数组每项的 `case_ref`（实际场景引用）和 `path`（所选资产路径），并说明可选项；不使用该资产或尚未决定时允许省略／保持未决，不以分类缺失或局部占位自动阻止可理解计划接收。实际安装的 guide／示例直接提供这些说明，不能指向安装包不存在的源码 schema，不能要求 Main 反查二进制、手抄机器身份、摘要或轮次。

预填出现 `e2e_coverage_state` 时，guide 同时解释 `cold_start`、`regression_available`、`not_applicable` 分别表示什么；尚未判断可保持空值或未决，继续保存已表达的规划。明确承担的行为验证责任仍按其实际安排和本人结论处理，分类本身不额外产生接收、派发或出口资格。

guide 中的形状示意可表达为 `"e2e_assets": [{"case_ref": "<实际场景引用>", "path": "<实际资产路径>"}]`：两个值由已有实际材料提供，示意占位符不是事实；需要时可说明已有 `asset_id`、`selector_ref`、`route_ref`、`environment` 为可选字符串。没有选用资产时无需编造这些值，旧机器摘要也不作为可选项提示作者填写。

### 7.2 Main 分工，平台执行

原计划接收后，系统为已声明且已解锁的原 Assignment 提供准确的 manifest 准备路径和原 `register-workgroup` 入口，Main 根据原计划确定实际工程 owner、专业分工和必要方法，并用该已有入口登记工作组。准备与登记复用本次原 Plan、Assignment、原 REQ／TASK 的实际路径和业务版本，不要求 `review.round`、轮次计数、SHA／hash、Git OID 或额外作者字段；历史摘要不计算、复制、登记或认证为新材料的资格。实际需要的源材料不可读、真实责任冲突和无法确定归属按准确事实反馈 Main／系统，不能因摘要不存在要求补填。原计划已接收而后继准备失败时保留已收事实，沿原准备入口续接，不要求作者重存计划。

manifest 路径由本次 Plan 身份和 Assignment 区分，同一代际两个计划即使使用同名 Assignment 也不能互用材料，不将无轮次写作固定 `r0`。同计划修订按实际表达接续，未受影响责任及结果保留原关联；移除旧数字路径和旧 manifest 兼容接线。归属未知的已有文件保留，不因其存在阻断当前计划，系统选安全可用路径。

对真实变更后需要重新履行、且原责任已登记或发行的 Assignment，系统以同一原 Plan、已有 Plan 内容修订版本及 Assignment 自动确定新派发的内部 owner／workgroup 和准备材料；这只是既有内容修订的工程关联，不是审查轮次、作者字段、证明或新阶段门。同一修订重放复用同一关联，连续真实修订各自不覆盖先前责任。未受影响的已登记、在途和已完成责任维持原 owner、题面及结论；受影响责任尚未登记时可沿实际未变的原准备材料继续，不能因为另一责任修订要求重新填写。原材料已发行后实际变化时，旧 owner、原答卷和在途结果仍沿原发行关系保存与接收；旧结果不冒充覆盖新责任，晚到 Finding 交 Main 按实际影响处理。旧材料身份不能确认时保留未知，不删除或阻断无关责任；同一 Claim 的判断文字真实变化也属于可能影响责任的变化，不能只比较 Claim ID。

原 `register-workgroup` 成功后，系统在后续自然事件通过原 issuer 为已登记且已解锁的责任准备其准确 view／answer 并将路径交 Main；Main 随后调用平台原生 Agent 执行。计划被接收不等于工作组已登记、题面已发行或 Reviewer 已完成；后继未就绪要显示准确进度。排队、依赖、资源冲突与暂停如实展示；平台容量不减少专业覆盖，也不使等待中的责任成为必须立即派发的工作。

Main 给原生 Agent 的任务包括目标、专业视角、必要输入和方法路径、写面、准确原答卷、异常交接和本人结束条件。Claude Code 负责创建、运行与恢复子代理；不增加 launcher、激活、通用 PLAN_REPORT 或平台身份登记手续。

新 Reviewer 原卷为 `.loop-submissions/s7/<packet-id>/<owner>/answer.json`，保留 `title/instruction/read/questions/answer` 五字段，只填写 `answer`。Main 不代填、不复制另一份稿，不要求结果证明、done、marker 或独立 Main 最终答卷。答卷路径用于关联责任，不因 Git 忽略、跟踪或暂存状态增设资格。产品修改边界仍由专业任务约束，不借文件状态门禁承担。

同一现行机制中已派发的责任、本人答卷、owner 和已接受事实沿原关联继续；当前消费者接收晚到结果。删除旧 frozen execution、独立旧来源根及其兼容入口，不依靠旧协议恢复，也不要求本人另补证明或重交。

### 7.3 Hook 定位、一次接收与同次分流

`SubagentStart` 提供简短指引；当前责任通过原派发中的准确引用或既有绑定解析，不能按角色、最近文件或唯一候选猜选。`PreToolUse`、成功 `PostToolUse`、`SubagentStop` 使用同一接收路径观察自然保存的原答卷；不要求制造第二次保存、返回引用或无关工具事件。

每次事件先读取必要的当前责任关联与最小接收状态。未接收时，仅一次读取本人原卷，完成必要结构、就绪／原结论与原责任关联检查；同一调用中的定位、适配、接收和分流共享结果，不反复打开同卷或遍历其他答卷。未表达可交接内容或 JSON 未写完整的草稿不误收，已有可理解结论即接收，不猜作者是否还想编辑；同一缺项不反复刷屏，普通工具照常可用。已接收的该次 Reviewer 交接直接复用原事实，不再次读取旧卷、提交或重跑检查；仍在 S7 活跃的 Main 原计划按 §7.1 继续观察当前表达，不因此遍历历史。责任仍 blocked 或未完成时，按 §12.2 保留其继续关系，原责任的新尝试不当作旧交接重放。

接收后在本次交接内根据原结论、已接收发现和适用必需责任完成情况分流，见 §11。Writer 只持久化当前责任、接收结果、结论引用及未完成后继所需的最小事实；事件幂等与并发控制是系统内部职责，不成为作者门禁。系统不核实证据、hash、Git、实际独立性或业务真实性，不从 `checks` 全部成功推算 PASS。

本人原卷缺失、不可读、身份／责任冲突或索引故障交 Main／系统修复准确来源，未确认不伪报成功。不相关答卷或证明材料损坏不影响本人。接收已成功而反馈、转换或下阶段材料准备失败时，保留事实，仅恢复未完成部分；不唤回已履职 Reviewer 重交。系统没有实际执行者时如实报告恢复入口，不承诺后台执行。

## 8. 审查者怎样形成专业结果

审查者根据本人实际责任和可用材料取得观察，说明已检查范围、结果和未执行事项；不为完成流转把未执行事项写成 PASS。如何逐项表达由专业题目和本人判断，不再因未逐条列完 Claim 而拒绝如实交接。真实 P0 中止遵循 §11.1：只交已观察项，保留未观察范围，不把中止伪装成产品前提阻塞。

Reviewer 只修改答卷的 `answer`，保留机器题干和绑定。答卷顶层仅保留 `title`、`instruction`、`read`、`questions`、`answer` 五个字段，不要把 view packet 的 `packet_id`、`template_id`、`binding`、`inputs`、`draft`、`view_path` 或 `answer_path` 抄入答卷。主要内容如下：

| 专业字段 | 内容与限制 |
| --- | --- |
| `claim_results` | 对已观察命题的实际结论、采用的方法和必要观察；未执行不能写为 `pass` |
| `blocked_claims` | 可选地描述具体未执行责任和实际前提，既可对应产品 Finding，也可说明环境或工具问题；没有发现时不要求编造 Finding |
| `checks` | 真正运行的命令及 `pass`／`fail`；未运行的计划不填成已完成检查 |
| `findings` | 本人实际发现及必要现场，粒度按专业判断，不要求每个失败命题恰好对应一项 |
| `deviations` | 实际执行偏差的字符串数组，没有则 `[]` |
| `site_lost` | 可选地说明发现现场无法恢复及其影响；保留实际发现和未知，不单凭该字段推定完成或禁止交接 |
| `verdict` | 结论可为 `pass`、`finding`、`blocked`、`req_change_required` 或 `release_blocked`；`blocked` 表达本人未完成并交 Main，不假装产品失败或通过 |

本人判断观察属于实际 Finding 时，在原 `findings` 表达并选 `verdict=finding`；环境、工具或权限受阻可选 `verdict=blocked`，在已有 `deviations` 或可选 `blocked_claims` 写清缺项与接手责任，无需另建报告、Finding 或证明。未设置结论的中间稿仍是草稿；现有题面和消费者须同步支持 `blocked`，不能将目标文案误称当前实现已支持。

证据引用服务 Reviewer 的专业说明和 S8 后续调查。作者按原题干引用真实路径、命令输出或 Runtime 引用，说明限制和缺口；不必为接收另存证明、抄摘要或组装机器封套。Hook 只检查必要字段形状，不读取证据文件验证内容、执行窗口、摘要或真实性。需要实际证据的专业工作仍由责任人完成，接收并不保证引用真实可用。

计划中的 `required_evidence` 提醒专业工作需要保留什么，不建立独立机器证明门。只有实际重复成立才写 `always`；一次明确观察可写 `once_with_deterministic_trace`，不为凑枚举重复危险操作。

## 9. Finding 应把真实现场交给调查者

### 9.1 先保留偏差发生的经过

Finding 要回答“原本要做什么，依照什么期望，从哪里开始，在哪里首次偏离，最后停在什么状态”。它是本次真实遇到问题的记录，不是留给下一位执行者的未来复现脚本。

作者说明真实失败的位置、应有与实际行为、依据和现场，并按实际需要关联本人 Claim；Finding 的粒度由专业判断决定，不强制每项失败恰好一条发现或为每条生成机器证明。既有 Schema 和编号可以作为兼容表达，系统不要求作者填写内部编号；同答按原接收事实幂等处理，不覆盖作者文件或已接受历史。

`expected` 和 `authority_refs` 固定应有行为及其来源，`observed` 描述实际偏差。`encounter` 将目标、运行上下文、操作过程、证据与失败边界连接起来：

- 最后正常点 `last_good_checkpoint`：什么事实仍符合预期。
- 暴露偏差的动作 `wall_action`：实际执行了什么请求、操作、命令或读取。
- 首次异常点 `first_bad_checkpoint`：最早可以确认的偏差，而不只是最后的错误提示。
- 结束状态 `terminal_state` 与被阻断后续：本次停在哪里，还有哪些步骤没有发生。
- 逐步证据、状态变化、尝试变体、副作用和清理状态：调查需要知道现场是否仍在、哪些观察能够复用。

`visible_impact` 位于 Finding 顶层，副作用位于 `encounter.side_effects` 字符串数组。`runtime_context`、`actor_context` 和 `symbol_trail` 使用字符串，不能随意改成自造对象。证据应脱敏，不记录凭据或不必要的个人信息；自动脱敏也不能替作者判断内容是否适合保存。

### 9.2 按观察模式记录，避免所有问题套浏览器步骤

| `observation_mode` | 模式需要保留的关键现场 |
| --- | --- |
| `user_flow` | 入口、真实操作时间线和终态，并关联页面、控制台及请求证据 |
| `api_flow` | 实际入口、请求与响应摘要和终态，必要时关联持久化与异步出口 |
| `command_flow` | 实际命令、整数退出码与终态，关联真实输出 |
| `state_transition` | 转换前后状态和终态，说明触发转换的实际动作 |
| `code_inspection` | 阅读入口 `inspection_entry` 与调用或数据流 `symbol_trail`，标出偏差边界 |

所有模式均保留 `journey_summary`、`wall_action` 和 `first_bad_checkpoint`。普通发现还需要最后正常点和终态；凡记录了时间线，每步均应有对应证据。静态阅读发现不必伪造 UI 操作，但必须让下一位调查者找得到具体入口和失效路径。

以下是 §4 订单命题失败时的专业 `answer` 示例，展示字段关系。引用和业务数据均为示意；实际提交必须使用本人的原 Claim、当前文件及真实证据，不能把示例当成已发生的事实：

```json
{
  "claim_results": [
    {
      "claim_id": "claim-delivery-rejected-order",
```

### 9.3 采集与补充服务真实调查

Finding 已接收后保留原事实。S8 的具体判别追问可由原发现者或明确安排的替代者沿原责任补充观察；复用已有 FindingSupplement 形状与原入口，不再新增补充登记表或证明链。新观察才形成新补充，同答重试复用原记录；系统不以当前文件摘要补造历史真实性。

## 10. 接收结果、阻塞与责任进度

### 10.1 接收边界

原消费者只检查答卷能否按已发行当前责任解释：必要字段、类型、结构、原结论与原责任关联，以及是否已接收。系统信任 Reviewer 的观察和判断，不重新审查答案真伪或用命令、证据、Git 与身份材料推翻结论。明显的结构冲突应明确反馈；专业完整性和结论依据由 Reviewer 与 Main 承担。

Writer 保存一次接收、原结论和责任进度，必要时原子登记 Findings；并发、pending 与重放沿原事务处理，不新增证明状态机。提交未确认如实显示未确认；已提交而反馈失败保留成功事实并恢复反馈与后继。本人原结论被接收后结束本人已完成部分，不必等待全轮；blocked 只记录阻塞与接手责任，不完成未执行的工作。

本人原答卷可以提到其他 Assignment 的 Claim、受影响范围或障碍。系统保留该原表达和实际 Finding 交 Main；`claim_results` 或 `blocked_claims` 中对其他责任的提及只作为本人的观察，不能据此改写对方的结论、阻塞状态、结果引用或完成情况，也不因提及而拒收本人答卷。同样规则适用于原题面接收和受支持的旧结果入口。能准确关联本人的结论才更新本人责任；归属不明的引用保留未知，不猜成本人或对方结论，也不妨碍其他可准确关联的责任。真实 Finding 按 §11 分流，不由跨责任投影代替对方的本人结果。

已接收、本人工作完成、真实 blocked 与完成情况未知分别反馈。已有接收事实后，若原结果或判断完成所需的事实暂不可读，保留已接收并交 Main／系统处理具体未知；不能仅凭读不到原文件把它称为 blocked 或 PASS，也不要求原作者重交。确有本人 blocked 表达时按原责任接续，不因其他人的跨责任观察推断本人 blocked。

### 10.2 如实区分失败与阻塞

| 情形 | 专业处理与下一责任 |
| --- | --- |
| 实际观察确认产品偏差 | 原结论报告 finding，保留发现与现场，交 S8；其他安全检查按 Main 安排继续。单条命令失败本身由作者判断含义，不自动构成产品 Finding |
| 产品问题破坏后续执行前提 | `blocked_claims` 说明受阻命题、相关 Finding、失败前提与修复后重验责任 |
| 环境、权限、工具或来源不可用 | 原责任说明实际障碍、已尝试事项、已有观察和接手人，交 Main 协调 |
| 时间、上下文或容量不足 | Main 调整顺序或分工，保留未完成责任，不写成 N/A 或 PASS |
| 产品或权威输入实际改变 | Main 明确新对象及需要重验的责任，不让旧 PASS 冒充新结论 |

原 `blocked_claims` 可继续使用 `claim_id`、`blocking_finding_ids`、`failed_precondition`、`evidence_refs`、`after_repair_required` 描述实际障碍。系统不读取证明来认证障碍，也不要求作者虚构产品 Finding 才能合法返回 blocked。未执行项与 PASS 区分；有真实发现时 S8 同时接收阻塞范围，没有发现且仍有必需工作受阻时由 Main 恢复，不进入 S10。

### 10.3 进度只表达已知事实

当前状态以原责任、接收结论和下一责任表达，不保留 `running`、`cannot_clean`、`discovery_draining`、`observation_sealed`、`clean`、`stale`、`paused` 的旧兼容展示接线，不要求走齐状态或快照才能分流。blocked 不表示通过，查询不遍历历史或重跑接收。

## 11. 轮次怎样交给 S8 或 S10

### 11.1 有真实 Finding 就交调查

原答卷明确报告实际 Finding 后，系统沿 TR-008 自动交 S8，复用原 Finding、观察、未执行范围、阻塞说明与原发现者路线。S8 需要的分组和原因调查继续由 Main 与 Investigator 完成；不能在 S7 按相似描述强行合根因或提前授权修复。

普通发现后，Main 依据实际产品、环境、依赖和安全风险，决定哪些原责任可继续，哪些需停止或重新安排；不能仅因阶段切换一律中止，也不能要求危险检查继续。“所有 Claim 已处置”不是已出现 Finding 进入 S8 的附加门禁。进入 S8 时把已派发和未完成责任交给 Main，TR-008 保留这些未收责任和原派发关联，不顺手关闭或删除；已派发 Reviewer 后续自然保存的原卷仍按其已有 S7 责任一次接收，不因当前阶段已变而丢弃或要求重交。若晚到结果含新 Finding，交 Main 纳入当前调查的实际材料；若当前调查已结束或批准意图已形成，Main 判断新发现的影响并沿真实修订／后续调查处理，不自动改写既有批准或重开整轮。无新发现的晚结果保留原接收事实即可。系统复用原责任关联和原接收入口，不建晚到结果账本、不全量扫描旧轮；已收后的重放只读原事实，不重复接收或再次迁移。

旧轮与新轮各自保留计划、作者、原路径、派发和接收关系；当前 stage 或新轮展示不是旧责任的唯一定位依据。Main 对旧轮在途项明确继续、真实取消或重新安排，取消保留原因与已有观察，不能把取消算完成。旧轮晚到结论只说明原对象上的工作，不能填作新轮 PASS；新 Finding 仍交 Main 判断当前调查、合同或新轮的实际影响。交接如实保留尚未完成的验证责任，不能暗示全轮已完整验证。P0 立即停止危险工作并交已有事实，不等其他责任，不虚构未执行项的结论。

S8 直接消费原已收发现与交接，不生产、封存或校验 ObservationBatch 作为 TR-008 前置；删除旧 Batch 兼容消费者和运行接线，不要求 Reviewer 补卷或 Main 新写最终总结。

### 11.2 无 Finding 且适用必需责任完成就交 S10

系统读取当前原计划的适用必需责任及各自已接收原结论。没有实际 Finding、没有未完成或 blocked 的必需责任，且原结论明确完成时，沿 TR-009 自动进入 [S10 验收与审计](L3-S10-acceptance-audit.md)。分流不将 `checks` 全部成功、逐命题统计或机器覆盖推算成 PASS，也不因个别 check 失败自动否决原总体结论；检查是否适用及其结论影响由作者与 Main 判断。不要求独立 Main 最终答卷批准。

Main 的专业计划、覆盖判断、独立分工、剩余工作处理和交接职责保留；进入 S10 表示这些责任报告完成，系统并未证明结论真实、覆盖完整或执行者实际独立。暂停、需求变化和发布阻断按原明确结论处理，不被无 Finding 自动掩盖。

当前链不生成或验证独立 CleanRound 快照，不调用产品 Git、E2E 资产、证据或摘要复核门重新认证原答案；删除旧 CleanRound 消费者和兼容接线。接收和后继共用必要读取与已记录事实，不增加结果证明。

### 11.3 同次交接与失败恢复

本次接收满足分支条件时，同次完成相应转换并准备下一阶段原材料，反馈实际接收、迁移及准备进度与准确路径。不能要求 Main 另用普通工具触发 TR-008／TR-009。某部分失败只恢复未完成部分，已接收不重收，已转换不重转；Main 按具名原入口接续。兼容命令可继续用于诊断，不是正常作者步骤。

`req_change_required`、`release_blocked` 沿原 TR-010／TR-011 保存必要暂停信息并交相应责任。人类用于真实需求取舍、发布阻断和实际要求由人决定的事项，不由默认轮数生成决定，也不反复批准常规检查或系统恢复。

## 12. 修订、重放与异常恢复

### 12.1 真实专业变化才修订

发现新的受影响面时，Main 在原计划说明来源、改变和影响，调整当前责任。不能通过删除失败命题、降低判据或复制旧 PASS 躲避已知问题。产品实际改变则明确新轮对象；未受影响结论可按专业判断保留，受影响责任安排重验。系统只维护当前关联和必要历史，不用路径 hash 或退出证明链代替 Main 判断。

### 12.2 系统故障不变成作者重交

| 异常 | 恢复责任与边界 |
| --- | --- |
| 原题干／答卷未准备或不可读 | Main／系统恢复准确原路径与责任，不覆盖仍在的专业答案 |
| 未接收答案类型错误、必要字段缺失或关联冲突 | 原作者依据具体反馈修改同一原卷，正常保存即可 |
| 并发、Writer pending 或持久化失败 | 系统沿原事务确认已成立事实，仅恢复未完成部分，不要求重存或改 ID |
| 已接收后回执、转换或材料准备失败 | 保留已收结果和实际后继进度，由 Main／系统沿原入口接续 |
| 已接受专业结论需要改变 | 原 Main 修订／返工路线保留原事实，不能覆盖后称同答重放 |
| 现场不可恢复或必需工作受阻 | 如实交接已有观察、未知与接手责任，不造 PASS |
| blocked 或未完成责任恢复 | Main 原安排或可准确归属原责任的本人自然继续后，系统使用已有责任关联观察新尝试；本人正常保存新观察即可，不要求恢复表、resume 或再提交 |

事件幂等、并发 revision、当前责任关联和最小后继记录属于内部持久化，不增加作者字段或门禁。不依赖可变采集缓冲重建接收，也不在重放时校验历史证据、Git 或原题干 SHA。真实缺失与身份冲突要明确交接，不能猜选别的卷。

某次 blocked 已收与该责任仍未完成分别保存。Main 的原恢复安排或可准确归属原责任的本人自然继续使当前尝试可接续，自然事件按该原责任接收新的实际表达，不要求先等 Main 登记；旧 blocked 与其他已收记录不覆盖，同答重放不伪装新观察。没有新的实际尝试时只反馈原阻塞，不猜其已经解除。

同一现行机制中已派发责任及已成立事实继续按原关联接收和接续；不保留旧格式兼容读取链。恢复不得覆盖作者内容、删除产品或私人产物，也不要求作者重交。共同事务与修订见[状态转换核心](../l4-mechanisms/L4-state-transition-core.md)、[修订机制](../l4-mechanisms/L4-revision-usage.md)与[L4 工作流收敛](../l4-mechanisms/L4-workflow-convergence.md)。

### 12.3 以实际验证责任关联，不统计审查次数

“本轮”“新轮”和“干净轮”描述本次实际完整验证及其结论，不表示第几次。新工作不生成、不累计、不展示审查轮数或剩余额度；重新进入 S7 使用新的原 ReviewPlan 身份，同次计划修订和故障恢复沿用该身份。即使产品基线相同，两次实际独立验证也不能借用彼此的结果。系统在首次生成题面前按真实进入事件确定本次身份，并保持计划、题面路径、派发和接收一致；使用已有非散列身份与原责任关联、Writer 并发版本处理重复事件，不以内容、Git OID 或摘要生成身份，也不增加作者字段、登记、证明或身份质量门。共同事务与旧格式边界见[工作流收敛 §3.3.3](../l4-mechanisms/L4-workflow-convergence.md#333-实际验证身份与不计数的接续)。

重复验证是否继续由 Main 依据实际未解决问题和用户实际要求判断；不以默认次数产生暂停、预算问题或额外审批。用户明确设定限制或要求人作决定时，保留真实约束和决定并沿实际去向接续；空选择不是批准。仅在会话中的约束不一定对自动消费者可见，系统不能据此宣称自动接续已独立核实所有用户意图，也不要求用户另填表。

真实专业历史、已收结果与决定保留为数据；删除旧数字路径、旧轮数和旧格式的运行接线。当前机制中同一责任晚到时仍沿原责任接收，不递增数字或要求作者重填。

## 13. 怎样观察进度和定位失效

| 观察点 | 展示必要事实 |
| --- | --- |
| 计划与派发 | 原路径、专业未决、当前责任、依赖、队列和真实可执行工作 |
| 原答卷接收 | 当前 owner、原结论、是否已接收、具体结构或关联问题 |
| 阻塞 | 实际原因、已有观察、未完成责任、接手人和原恢复入口 |
| 阶段交接 | 实际接收到哪一步、S8／S10 转换与材料准备是否完成 |
| 机制成本 | 本次必要读取、接收调用、持久化、后继调用与耗时，是否随无关历史增长 |

`loop-harness s7 status` 读取已有事实，不作为另一套校验或提交入口。指标故障不改变领域接收；Hook 审计、命令输出与回执都不证明业务正确、完整覆盖或实际独立性。

## 15. 指引分层、交接与验收

### 15.1 四层共同承载原责任

| 层次 | S7 责任 |
| --- | --- |
| 模板／原题干 | 定义需思考的问题、专业输入、判据、字段形状与异常出口；不预填结论或机器证明 |
| 角色／Skill | 提供覆盖、独立审查、工程质量、行为验证和现场保留方法；不重复提交协议或批准手续 |
| Hook／原消费者 | 关联当前责任，读取一次必要原卷，检查结构与就绪，接收一次并按原结论及责任进度分流 |
| 原答卷 | 作者自然保存实际观察、结论、发现、阻塞和剩余责任；是唯一专业交付源 |

全局入口、`docs/control/agent-protocol.md`、转换元数据、安装设置与生成指引是上述设计投影，不能增设另一套规则。Blueprint 面向框架实现者，不成为 Reviewer 新增必读输入。来源权威见[L4 指引分层](../l4-mechanisms/L4-agent-guidance.md)与[L4 工作流收敛](../l4-mechanisms/L4-workflow-convergence.md)。

### 15.2 最小完整交接

Main 取得原计划与 guide，自然保存专业规划；原消费者接收后反馈已解锁责任的准确材料准备与原工作组登记入口。Main 选定实际 Reviewer 并完成原派发协调，系统由后续自然事件给出该责任的 view／answer，Main 调用平台 Agent。Reviewer 读取必要输入和方法，实际检查并保存本人原卷；正常汇报无需提交信号。系统反馈本人接收事实，并同次按 §11 交 S8、S10 或明确未完成／blocked 的接手责任。

S8 使用原已接收 Findings、观察与未完成范围准备调查；S10 使用适用责任完成与原结论准备验收。Main 继续承担分组、协调、规划和异常交接，不另写最终答卷为旧答案背书。下游准备失败只恢复准备，不能要求原作者重交或额外制作 Batch、CleanRound、hash 与结果证明。

### 15.3 待落地验收

验收需要实际安装材料、平台事件、原消费者和下一阶段组合证明，至少覆盖：

- 尚无可交接内容或 JSON 未写完整的草稿不误收；已有可理解结论即接收，不猜作者是否还想编辑。必要结构或关联问题准确反馈且不反复刷屏，普通工具可用；仅自然保存即可接收，无 submit、done、重存或返回引用要求。
- S6、S8、S9 与 S10 要求重验的真实进入路径均从实际原题面、自然 Hook、原计划和本人结果走到对应出口；不预置 packet 代替入口。Hook 和其消费者不计算、登记或校验答卷、资产、计划、receipt、来源的任何散列或 Git OID，不能换名为 digest／fingerprint。当前责任准确定位，一次事件共享本人原卷及必要结果；同答复用、不重复写，S7 活跃计划仍自然观察当前表达，旧值不重算。
- 四类入口各自从自然保存原计划继续到正确的无轮次派发提示、无 SHA manifest、原工作组登记、自然事件发行准确本人题面、本人结果接收和 Finding／无 Finding 原出口；保留真实依赖、阻塞和责任冲突，不以手写 Runtime 或单独 helper 代替原链。验证已安装 guide 直接说明 `e2e_assets` 及预填 `e2e_coverage_state` 的语义和可保持未决的方式，无须访问缺失的源码路径或反查二进制，也不将可选分类变成资格。
- 同 generation 不同 Plan 即使复用 Assignment ID 也不串用 manifest；同计划修订保留原责任关联，删除旧数字路径接线。未知文件不覆盖、不猜选、不阻断无关责任。后继失败保留已收计划，重复事件复用事实，当前机制的在途及晚到结果归原责任。
- 原 finding 结论实际进入 S8，带走已有现场与未完成范围；P0 可安全中止，即使其他现场有缺口也不丢发现；原无 finding 且适用必需责任完成时进入 S10，不按 `checks` 计算 PASS、不要求 Main 最终答卷；blocked 如实交接且未执行项不变成完成。
- 本人原卷包含其他责任 Claim 的观察、blocked 提及或 Finding 时，原题面和受支持旧入口均保存表达和发现，不改写另一责任的状态、结果引用或本人结论；对方本人后来正常交卷、计划修订及晚到结果仍沿各自原责任接续。只看已接收原事实无法确认完成时反馈未知，不伪报 blocked 或 PASS，不要求作者重交。
- 必要内部状态、事件幂等与并发保护不表现为作者门禁；提交前失败不假报成功，提交后反馈／转换／材料失败保留已收事实，只恢复未完成后继。
- 受支持旧题干、路径和既存责任不重签、不覆盖、不重存；旧证明对象不成为新链门禁。原卷真实缺失或责任冲突交 Main，不凭角色或文件猜选。
- 对未就绪、首次接收、已收重放及失败窗口分别计量读取次数、消费者调用与耗时，验证无关历史增长不扩大普通 Hook 工作量。源码、进程接线与真实 Claude 会话分别报告，直接 CLI 测试不能代替平台事件验收。

具体实现与实际验证尚未完成的部分应逐项如实报告；本设计只保证可解释的答卷接收和责任交接，不承诺机器验证真实性、完整覆盖、实际独立性或全部业务质量。
