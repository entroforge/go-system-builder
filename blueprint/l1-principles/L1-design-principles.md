# L1 设计原则

本层回答为什么这样设计，不定义具体工具和命令。消费者是框架设计、实现与维护人员。

## 1. 使命与边界

本框架支持一名工程负责人和多个专业代理协作交付软件，让“完成”在代理、机器和人之间具有一致含义。负责人决定需求方向、必要的价值取舍和最终发布授权；代理连续开展专业工作，系统保存事实并提供明确交接。

框架以检查单式的辅助思考、真实检查和独立判断兜住质量下限，服务功能的连续、快速迭代。每项机制都应能说明它减少哪种实际遗漏或无效工作；流程完备、状态增多和测试数量本身不构成产品收益。

系统需要把控方向、真值、深度、状态、责任边界和收敛节奏。它不替人创造需求，不以结构检查裁决专业语义，不以代理自述代替真实执行，也不从门禁通过推导发布授权。

## 2. 设计约束

| 编号 | 约束 | 设计要求 |
| --- | --- | --- |
| C1 | 代理的会话记忆不可靠 | 状态、输入版本、决定与结果持久化，恢复依靠重读 |
| C2 | 额外手续容易导致绕行 | 观测贴近正常工作路径，减少重复报告和隐含协议 |
| C3 | 代理可能自信地给出错误结论 | 结论需要实际依据、独立审查和明确适用范围 |
| C4 | 人的注意力稀缺，计算与等待也有成本 | 人处理方向、出口和例外，额外验证有明确收益 |
| C5 | 未经实战检验的机制也会失效 | 设计随可复现问题修订，验证范围如实记录 |

## 3. 主干设计决策

### D1 权威外置

当前阶段、需求基线、责任、证据和授权由持久化事实表达。对话、摘要、文件存在或平台进程结束都不能单独成为完成依据。恢复从已有事实重建当前责任，不靠补造历史。

### D2 观测进入正常工作路径

输入与结果在正常交付路径上被读取、记录和消费。已有平台负责的执行能力直接使用平台机制；框架负责工程事实，不在其上维护重复的执行生命周期。

### D3 反馈指向下一步

常态反馈说明当前责任、具体缺项、实际位置和下一动作。阶段资格未满足时继续补齐工作；这不等于禁止普通工具。对执行的强制干预应当有明确、有限的理由。

### D4 产物引导思考

模板中的问题帮助作者说明目标、判据、实际观察、边界和风险。专业判断由作者完成，系统已知的身份、版本和机器字段由系统带出。没有消费者的字段不增加填写义务。

### D5 先引导，再增加必要约束

优先使用清晰任务和模板，再使用可判定的结构检查，最后才考虑强制限制。每次加码都要说明实际失效、收益和作者、运行、维护的总成本。先考虑删除、合并和复用，再修复必要缺口；不能用新证明、重试或授权层修补原本不必要的依赖。减少可见操作而显著扩大内部协议，不能直接称为减负。

### D6 完成需要独立背书

实现、自测、集成、独立验证和发布授权是不同责任。机器确认可公证事实，专业代理判断质量，人决定价值与发布。局部修复或定向重验不能代替完整验证轮；沉默不能当作不适用。

### D7 纠错必须可收敛

观察未满足要求、未解释发现、重复失败和返工范围是否减少。连续投入却没有进展时，重新调查或交人决定；不能依赖无限重试。历史失败保留，新的通过只证明其实际范围。

框架自身的整改也应固定支持路径与验收终点。新发现按回归、相关存量、无关问题、待验能力和能力扩展区分，不能全部变成下一轮必补分支。“不猜测”要求协议准确，专业判断仍需调查；未支持能力如实说明，不能事后缩小承诺来掩盖失败。

## 4. 机制准入公理

| 公理 | 审查问题 |
| --- | --- |
| 原型公理 | 是否对应真实工程协作中的角色、产物或动作？ |
| 分工公理 | 机器是否只公证事实，代理是否承担专业判断，人是否保留必要决定？ |
| 消费公理 | 每个概念、字段和检查由谁在何时消费？ |
| 成本公理 | 它防止什么实际失效，收益是否值得计算、等待和维护成本？ |
| 传达公理 | 执行者只看任务与反馈，能否理解理由并继续工作？ |

## 5. 需要防止的失效

| 失效 | 对应设计 |
| --- | --- |
| 只修表象，同类问题反复出现 | 先调查根因、范围与漏检原因，再形成修复约束 |
| 用模拟或自报替代真实验证 | 区分机制测试、实际执行和独立产品验证 |
| 标准随返工悄然降低 | 保留完整要求与不适用理由，禁止缩小分母冒充完成 |
| 格式正确但内容没有依据 | 结构检查与专业判断分离，保留独立背书 |
| 提示与门禁噪声过多 | 只给当前责任需要的资料和具体缺项 |
| 多套状态互相冲突 | 每类事实只有一个权威来源，视图从事实派生 |
| 持续忙碌但问题不减少 | 观察重复失败、轮次与未满足项，执行收敛预算 |

## 6. 四层分工

本节是文档层级的唯一概念定义。

| 层级 | 负责内容 | 不承担的内容 |
| --- | --- | --- |
| L1 原则 | 场景、约束、使命、设计决策与准入公理 | 具体流程和工具 |
| L2 生命周期 | 阶段目标、入口、出口、失败路由和全局交付要求 | 字段与接线细节 |
| L3 阶段 | 阶段工作流、角色、产物、机制消费和完成条件 | 另起跨阶段协议 |
| L4 机制 | 跨阶段对象、事实来源、事务、事件、恢复和验收边界 | 重复定义阶段目标或代替专业判断 |

下层设计应能说明承载的 L1 决策及实际消费者。具体字段、模板、命令和测试属于实现资产，由相关 L3、L4 链接；不在蓝图中复制完整规格。

## 7. 演化规则

发现实际失效后，先保留现场并定位到原则、阶段、机制、实现或指引。提出修订时说明问题、影响、取舍与验证方式，通过准入公理后同步所有消费者。

跨阶段机制的准入、范围与验收收口按[工作流边界与收敛设计](../l4-mechanisms/L4-workflow-convergence.md)执行。若同类缺口持续增加，应重新判断机制必要性，不能只靠逐项补全原实现延长整改。
