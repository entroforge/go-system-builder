# 原生工作区集成与恢复

S6、S9 的责任由 Main 使用原生 Agent 和工作区派发；按 brief 指定的本人路径保存专业答卷。S7、S8 的独立责任使用其原问卷。入口、角色和阶段职责见[原生工作区指南](workspace-integration.md)与[阶段协议](control/agent-protocol.md)。本人答卷接收、实际 Git 集成、Main 检查和阶段推进是分别成立的事实。

## Main 集成与继续流程

Main 根据原返回和待办处理实际贡献：

```sh
loop-harness runtime workspace pending --root <Main>
loop-harness runtime task-integrate --root <Main> --assignment-id <assignment-id>
```

第二条是 S6 集成入口；S9 沿其本人结果、Main 实际集成、Impact 和独立 Targeted 的原责任继续。Main 执行实际合并和必要检查，不能把 Worker 自检当成 Main 检查。检查失败或合并冲突按真实结果处理；检查失败的 preserved checkpoint 按待办提示解决原因后使用 `--retry-preserved`，已成功集成后只续未完成的后继。合并结果无法确认时保留未知，不自动重复合并或要求本人重交答卷。

已接收的答卷、已记录的检查和 ACK 不因后续清理失败而撤销。无法安全清理的私人、未跟踪或未知文件保留，由 Main 根据实际待办继续处理；清理不是不依赖它的阶段后继的前置条件。

## 本人结果与检查

Builder 按原 brief 和责任完成专业工作，保存本人 Plan 和 Result，如实记录检查、风险及未完成事项。S9 的自然事件监听原答案，接收无需先运行 Git、提交额外表单或登记摘要；Main 需要实际集成时再使用 Git。Targeted 由独立责任人填写原答案，最后适用的通过结论沿原出口准备新 S7。真实批准仍由原授权人作出。

实际检查按其责任、命令和结果记录，失败、不可运行或未知不能写成通过。原检查配置允许静态复用时，使用当前责任及已接受的真实结果判断；Main 集成检查和独立验证各自承担责任。检查或答卷接收不要求作者计算、登记或校验散列，也不因历史机器字段缺失而要求补证明。

## 运行中断

沿原 Runtime、责任和当前待办恢复实际未完成的步骤。接收成功但后继准备失败时保留已接收事实，只继续后继；事务损坏或原材料缺失如实交由 Main／系统处理，不猜测历史内容，也不覆盖用户文件。诊断与恢复不要求重新派发已完成责任或额外保存同一答案。
